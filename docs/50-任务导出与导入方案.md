# 50-任务导出与导入方案

> 日期：2026-10-27
> 状态：已实施（2026-10-27），后端/前端/测试均已落地，blob 下载已实机验证。
> 背景：需要把一台电脑上某个项目的任务（含顺序、优先级、置顶、依赖关系）搬到另一台电脑，
> 当前只能手工重录。本文给出文件格式、服务端契约与前端交互的完整实现方案。
> 范围：`apps/control-server/internal/app`、`apps/web/src/features/tasks`、`apps/web/src/lib`；
> 不改数据库 schema，不改移动端远程控制协议。

## 1. 目标

1. 任务页（`/projects/:id/tasks/board`）工具条提供「导出」「导入」两个入口。
2. 导出得到一份**自包含、可读、可手工编辑**的 JSON；导入到另一台电脑（同项目或另一项目）后，
   任务内容、优先级、置顶、队列顺序、**未完成前置的阻塞关系**与源项目等价。
3. 导入是**一个事务**：要么全部落地，要么一条都不落。重复导入不产生重复任务，也不丢依赖。

## 3. 为什么不能前端逐条调 `createTask`

1. **标题会被改写**：`validateTaskInput` 强制用 description 重新生成 title。
2. **AI 精炼被触发 N 次**：导入 30 条起 30 次只读 Agent 调用，每条最长 20 秒，结果覆盖标题。
3. **没有原子性**：依赖要第二遍 POST，中途失败留下半套任务。
4. **依赖是 uuid 外键**：跨机器 id 全失效，必须重建映射——只有服务端掌握新 id 时最自然。

## 4. 文件格式

```json
{
  "format": "milevia.tasks",
  "version": 1,
  "exportedAt": "2026-10-27T09:30:00Z",
  "source": { "project": "milevia" },
  "droppedDependencies": 2,
  "tasks": [
    { "key": "t1", "title": "修复登录态失效", "description": "……", "priority": "high",
      "pinned": false, "status": "todo", "createdAt": "2026-10-20T02:11:00Z", "dependsOn": [] },
    { "key": "t2", "title": "补充回归用例", "description": "……", "priority": "normal",
      "pinned": true, "status": "todo", "createdAt": "2026-10-21T06:40:00Z", "dependsOn": ["t1"] }
  ]
}
```

| 字段 | 说明 |
| --- | --- |
| `key` | 文件内唯一引用，`t1…tN`，长度 ≤64；**不导出本机 uuid** |
| `title` | 原样保留；导入折叠单行 + 截断 120，空则按 description 生成 |
| `priority` | `urgent/high/normal/low`，非法值回退 `normal` |
| `pinned` | 保留（显示位置见 §8） |
| `status` | 只取 `todo/done/cancelled`；源 running / awaiting_review / action_required 一律写 `todo`。**导入端不用它决定新任务状态，只用来判断依赖是否已满足**（见 §7） |
| `createdAt` | 可选；晚于当前时间按当前时间处理 |
| `dependsOn` | 文件内 `key` 数组，顺序即依赖展示顺序 |
| `droppedDependencies` | 导出时被裁掉的依赖条数，仅供提示，导入端忽略 |

**必须保留 `status`**：没有它就无法区分「前置已完成（不该阻塞）」和「前置未完成（该阻塞）」。
导入后所有新任务仍然是 `todo`——`status` 只服务于依赖判定，不会让已完成任务复活。
数组顺序即队列顺序，不导出 `position`。

## 5. 服务端

新增 `internal/app/task_transfer.go`，在 `app.go` 任务路由段注册：

```go
r.Get("/api/projects/{projectID}/tasks/export", s.exportTasks)
r.Post("/api/projects/{projectID}/tasks/import", s.importTasks)
```

### 5.1 导出

`GET /api/projects/{projectID}/tasks/export?scope=active|all`

- 先 `projectExists`（否则 404）；`scope` 只接受这两个值，其它 400。
- 缺省 `active`：排除 `done`、`cancelled`（与前端 `filterQueueTasks` 的 active 一致）；`all` 全量。
- 排序按 `position, created_at`，**不要带 `pinned desc`**：导入端按数组顺序重新编号 position，
  而看板列内排序只看 position。带置顶优先会让置顶任务在文件里提前，导入后看板手工顺序与源项目
  不一致。`pinned` 是独立字段，队列视图自己会按它排。
- 依赖用**一条 join 查询**取 `task_id → predecessor_id`，不要为了依赖跑整个 `hydrateTasks`
  （它还会查 lastRun 与编排）。查询**必须带 `order by dependency.created_at, dependency.rowid`**：
  同一任务的依赖共用同一个 created_at，少了 rowid 文件里的依赖顺序就不稳定，导入后展示顺序会变
  （`task.go:1083` 的注释专门记录过这个坑）。
- key 按导出顺序编号 `t1…tN`。
- **依赖裁剪**：指向未导出任务的依赖不写入，累加 `droppedDependencies`。
- 返回 `200` + JSON；**不用附件响应头**（下载由前端完成，见 §6.2）。

### 5.2 导入

`POST /api/projects/{projectID}/tasks/import?dedupe=false`

请求体是导出文件本身，但服务端只解码 `format` / `version` / `tasks`；前端也只发送这三项——
`exportedAt` 在服务端是 `time.Time`、`droppedDependencies` 是 `int`，原样回传时被手工改坏会让整份
请求 400。`dedupe` 缺省 `true`。

**上限：2000 条 / 64MB，两个独立生效。**
- 全局 `maxJSONBodyBytes` 是 16MB，而单条描述上限 12000 字（中文约 36KB），400 条满描述就超 16MB。
  导入端点自己用 `http.MaxBytesReader(w, r.Body, 64<<20)` 解码，捕获 `*http.MaxBytesError` 后
  返回 413 + 固定文案。
- 2000 条的依据是 `SetMaxOpenConns(1)`：导入是同步长事务，期间所有 DB 请求排队。
  正常描述（几百字）2000 条约 1–2MB、事务在秒级；极端满描述会先撞 64MB。

**前置校验（任一失败整体 400，不落库）**

| 校验 | 错误文案（固定短句，进翻译表） |
| --- | --- |
| `format != "milevia.tasks"` / 版本不是 1 | `unsupported task export file` / `task export file version is not supported` |
| `tasks` 为空 | `task export contains no tasks` |
| 超过 2000 条 | `task export contains too many tasks` |
| 实际字节超过 64MB | `task export file is too large`（413） |
| `key` 不匹配 `^[A-Za-z0-9_-]{1,64}$`、为空或重复 | `duplicate task key in export file` |
| `dependsOn` 引用不存在的 key，或引用自身 | `task export references an unknown dependency` |
| 依赖图成环 | `task export dependencies form a cycle` |

- 文案必须是固定短句：`localizedErrorText` 的翻译表是精确匹配，带参数的句子会退化成
  「请求参数无效…：英文原文」。所有新文案同时补进 `app.go` 的 `translations`。
- 成环检测在**内存里做 Kahn 拓扑排序**：任务此刻还没入库。
- `dependsOn` 里的重复 key 直接去重，不报错。

**事务内逐条创建**（顺序即数组顺序）

1. 先建 `key → 目标 id` 映射（新任务用 `uuid.NewString()`，去重命中用已存在任务的 id）。
2. `position`：事务内取一次 `max(position)`，按文件顺序 +1 递增（追加队尾、保留相对顺序）。
3. `title`：文件值折叠空白 + 截断 120；为空用 `generatedTaskTitle(description)`。
4. `description`：trim 后必须非空且 ≤12000，否则计入 `invalid` 跳过。
5. `status`：**一律 `todo`**，`completed_at`/`cancelled_at` 留空，`updated_at = now`。
6. `pinned`、`priority`、`created_at` 保留。
7. **去重键只取 `description`**：title 是 AI 精炼产物，两台电脑可能不同，带 title 会漏判；
   编辑器也没有 title 输入，description 是唯一真相来源（`task.go:374` 注释）。
   比对范围 = 项目内已有任务 **+ 本次已插入的任务**（同一文件里两条同说明，第二条也会跳过）。
   去重命中不改动已存在任务的任何字段，只记 `key → existingID` 供依赖使用。
   已存在任务有多条同说明时，取 `position, created_at` 最靠前那条，保证结果确定。
8. 依赖在所有任务插入后统一写 `task_dependencies`（`created_at = now`，按文件顺序），
   规则见 §7。只处理本次**新建**的任务：去重命中的任务连同它自己的依赖一起跳过——往已有任务上
   追加阻塞关系会悄悄改掉目标项目里那条任务的状态。因此新建任务的依赖归入三类之一
   （建立 / `satisfiedDependencies` / `droppedDependencies`），重复任务的依赖不计数。
9. 每条记 `task.created` 事件，payload 带 `{"status":"todo","source":"import"}`。
   注意：配置了云端 relay 时，每条事件都会推进 `remote_instance` 序列并唤醒一次长轮询
   （`remote_control.go:808`），2000 条会产生 2000 次唤醒——这是可接受的，而且正是它让手机端
   快照在导入后自动刷新；没有 relay 时不产生任何额外开销。
10. **不调用** `refineTaskTitleAsync`。

**响应**（`200`，不是 201：返回的是本次导入的统计而不是单个资源）

```json
{ "imported": 12, "duplicates": 2, "invalid": [{ "key": "t7", "reason": "任务说明为空" }],
  "satisfiedDependencies": 3, "droppedDependencies": 1, "dependencies": 5,
  "created": [{ "key": "t1", "id": "…" }, { "key": "t3", "id": "…" }] }
```

- `created` 只回 `key → 新 id` 的映射，**不回完整 Task**：2000 条 Task 会把响应撑到 MB 级，
  而前端刷新列表即可拿到全部字段。
- `invalid[].reason` 由服务端直接给中文（它不是 `writeError` 的文案，不进翻译表）。

任一步 DB 错误整体回滚并返回 500，不留下半套数据。

5. 结果提示注明保存位置（WebView2 默认「下载」文件夹），并提示
   `droppedDependencies > 0` 时的「另有 N 条依赖指向未导出的任务，已忽略」。

### 6.3 导入

1. 隐藏 `<input type="file" accept=".json,application/json">`；选中后 `file.text()`。
2. 预解析（纯函数）：`file.size ≤ 64MB`、格式/版本、非空且 ≤2000、key 合法唯一、依赖存在、无自依赖、
   依赖成环（Kahn，20 行）。**前端这套校验与服务端清单必须完全一致**，前端拦得住，服务端 400 就只是兜底。
   **先剥 UTF-8 BOM**（`text.replace(/^\uFEFF/, "")`）：用记事本另存的文件会带 BOM，
   `JSON.parse` 直接抛错；若解码后含 NUL（`\u0000`，典型的 UTF-16 另存），提示「请以 UTF-8 保存后再导入」。
   **不要用 `\uFFFD` 判断编码**：任务说明里真的含替换字符时，整个文件会被误判成编码错误，
   用户怎么另存都导不进去（端到端实测踩到过）。
3. 预览确认：「共 N 条任务 · M 条依赖 · 其中 K 条与现有任务重复（将跳过）」。
   K 用 Set 按 trim 后 description 比对，仅供提示，以服务端为准。
   预览态提供「跳过与现有任务说明相同的条目」开关（默认开）：勾选时请求不带参数（服务端
   默认 dedupe=true）；取消勾选时请求 `?dedupe=false`，同说明的条目各建一条，K 恒为 0。
   重复任务自身的依赖不会重建（见 §5.2 第 8 条）。
4. 确认 → `POST /api/projects/{id}/tasks/import`，body 为文件原文；busy 期间提示
   「导入中，请不要关闭窗口」。
5. 结果：「已导入 N 条任务，跳过 M 条重复」；列出前 5 条 `invalid` 原因；
   `satisfiedDependencies` 说明「N 条依赖因前置已完成而不再阻塞」；
   `droppedDependencies` 说明「N 条依赖因目标不存在被忽略」。
6. 关闭后：**清空搜索词**（否则新任务被过滤挡住，用户以为没导入）→ `loadTasks()` → 清空选中。

## 7. 依赖语义（本方案最容易做错的地方）

`blockedBy` 只排除 `done`（`task.go:1103`），所以导入时必须按**文件里的源 status**决定是否重建依赖：

| 源前置状态 | 源项目里是否阻塞 | 导入处理 | 结果 |
| --- | --- | --- | --- |
| `todo` | 阻塞 | 建依赖 | 阻塞 ✓ |
| `cancelled` | **阻塞**（只排除 done） | 建依赖 | 阻塞 ✓ |
| `done` | 不阻塞 | **不建依赖**，计入 `satisfiedDependencies` | 不阻塞 ✓ |
| 被去重跳过 | 取决于 B 端真实状态 | 建依赖，指向已存在任务 | 由 B 端状态决定 ✓ |
| `invalid` / 未导出 | — | 不建，计入 `droppedDependencies` | 不阻塞（已知偏差） |

**为什么 `done` 前置必须特殊处理**：导入后所有任务都是 `todo`，如果把指向 done 前置的依赖原样建上，
这些任务在新电脑上会立刻变成「等待前置完成」且**永远无法下发**（前置任务本身也被改成了待办，
没有人会去「完成」它）。这是第一版方案里最严重的漏洞。

**环检测与去重的关系**：是否去重要到事务里查库才知道，所以环检测按文件全图保守判定
（只排除无效条目与 done 前置）。手工合并过的文件如果只在「会被去重的任务」上成环，会被拒绝——
这是可接受的保守行为，导出的原文件本身不可能有环（源项目的依赖写入带环检测）。

**已知偏差**：`scope=active` 不导出 `cancelled` 任务，因此被 cancelled 前置阻塞的任务在导入后会解锁。
原因是 active 的语义是「搬未完成的活」，而被取消的前置本来就不该参与新电脑的队列；
导入结果里会通过 `droppedDependencies` 说明。若要求严格等价，请用 `scope=all`。

## 8. 边界与防护

- **置顶的显示位置**：position 追加队尾，但**会话页侧栏的队列**先按 `pinned desc` 排（看板只看 position），
  所以导入的置顶任务在队列里排在「已有置顶之后、普通任务之前」，不是绝对队首。对话框说明一句。
- **单连接**：导入事务期间所有 DB 请求排队；2000 条上限就是为此设的。
- **敏感信息**：任务说明可能含路径、密钥片段，导出对话框提示「导出文件包含任务全文，请妥善保管」。
- **并发**：导入期间按钮 busy；去重查询必须在同一事务内完成。
- **版本兼容**：旧控制服务 + 新前端会 404，按普通错误提示（404 也可能来自项目刚被删除，
  不额外猜测「版本不支持」）。桌面端前后端同包，随安装包升级（`docs/35-发布操作手册.md`）。
- **不导出**：`task_runs`、`task_events`、`verification_runs`、编排状态、`source_insight_fingerprint`。
- **跨项目导入**：允许；依赖只在文件内部建立。
- **移动端**：不加入口，导入结果在远程任务列表可见。

## 10. 验收

1. A 导出（默认仅未完成）→ B 导入同项目：数量、顺序、置顶、优先级一致；需要前置的任务仍等前置。
2. 源项目里「A 已完成 → B 待办（B 依赖 A）」全量导出到空项目：B 可直接下发（A 变成待办但不阻塞 B）。
3. 再导入一次同一文件：全部重复，数量与依赖数不变。
4. B 先手工建一条与文件同说明、标题不同的任务，再导入：该条跳过，其它任务对它的依赖仍成立。
5. 导出「全部」→ 空项目：已完成/已取消任务也在，且都显示待处理。
6. 记事本另存带 BOM 后再导入：成功。
7. 搜索框有词时导入：成功后搜索清空，新任务可见。
8. 导入中断网/杀进程：数据库没有半套任务。
9. 现有轮询、拖拽排序、批量管理、下发流程不受影响。
