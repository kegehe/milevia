# 任务编排与人工下发

> 日期：2026-07-20<br>
> 阶段目标：为每个已加载项目提供独立任务看板、人工下发和人工验收闭环；为后续自动编排保留稳定的数据与事件边界。
> 已确认决策：任务由用户手工创建；任务由用户手工下发；存在未完成前置任务时禁止下发；AI 执行成功后必须人工验收才算任务完成。

## 1. 背景与问题

当前平台已经具备“在项目中向 Claude 发送消息、观察一次 Run、停止运行、查看过程与结果”的闭环。但当前的 `Run` 是一次执行过程，不是可长期管理的开发计划：它没有任务优先级、验收标准、依赖关系，也不能回答“接下来应该做什么、为什么现在不能做、这次结果是否已经确认”。

这会造成三个问题：

- 多个开发事项只能混在同一段对话中，无法按项目和优先级维护待办；
- AI 的一次正常结束容易被误认为业务任务已完成，代码质量与验收责任却没有明确归属；
- 后续若直接在 Run 上叠加队列和自动执行，会把计划、执行、审阅和调度混为一个模型，重试、依赖和审计都会变得脆弱。

本功能将“项目计划”与“AI 执行”分离：任务看板管理人要做什么，Run 管理某次 AI 实际做了什么。用户始终控制创建、下发与完成确认。

## 2. 调研结论与设计取舍

### 2.1 外部实践

- GitHub Projects 将同一项目项以表格、看板和路线图等不同视图呈现，并以字段和工作流组织状态。这说明“任务记录”应是唯一数据源，视图只是投影，不能各自维护状态。
- Temporal 的工作流文档将每次执行与其状态转换、事件历史分开记录，并将完成、失败、取消等作为可追溯事实。这说明自动化之前应先确保每次执行具有稳定身份、终态和历史。
- Jira 等问题跟踪工具普遍把依赖作为显式关系而不是仅凭排序推断。对开发任务而言，依赖图必须由服务端校验，并禁止环形依赖。

参考资料：

- GitHub Docs: [About Projects](https://docs.github.com/en/issues/planning-and-tracking-with-projects/learning-about-projects/about-projects)
- Temporal Docs: [Workflow Execution](https://docs.temporal.io/workflow-execution)
- Atlassian Support: [Link work items](https://support.atlassian.com/jira-software-cloud/docs/link-issues/)

### 2.2 方案比较

| 方案 | 内容 | 优点 | 问题 | 结论 |
| --- | --- | --- | --- | --- |
| 轻量待办 | 标题、状态、直接绑定一个 Run。 | 实现快。 | 无法可靠支持重试、验收、依赖和自动调度。 | 不采用。 |
| 独立任务模型 | `Project -> Task -> TaskRun`，依赖和验收属于 Task。 | 计划与执行清晰分离，未来可接入调度器。 | 首期需增加数据迁移和状态规则。 | 采用。 |
| 首期即工作流引擎 | DAG、队列、重试、并发与自动触发全部实现。 | 形式上功能完整。 | 未验证任务粒度和失败处理，误执行风险与复杂度过高。 | 延后。 |

### 2.3 核心原则

1. **计划与执行分离。** Task 不等于 Claude Run；一个 Task 可以有多次 TaskRun。
2. **人工控制优先。** 首期任何 Run 都必须由用户在任务详情中明确下发。
3. **验收不是执行成功。** AI 成功结束只进入待验收，用户确认后才完成任务并解锁后继任务。
4. **依赖是硬规则。** 未完成前置任务阻塞下发；浏览器不能绕过服务端校验。
5. **历史可解释。** 下发时固化任务内容，之后编辑任务不会改写历史 TaskRun。
6. **状态以服务端为准。** 页面只展示业务状态与过程事件，不自行推断完成或失败。

## 3. 范围与非目标

### 3.1 首期范围

- 每个 Project 创建、编辑、排序、删除和重新打开已完成任务；
- 任务看板和列表两种同源视图；
- 标题、任务说明、验收条件、优先级、前置任务和执行历史；
- 点击任务手动下发到项目选择的 Conversation，并复用既有 Message、Run、WebSocket、权限、停止与用量链路；
- 服务端硬性校验依赖、环形依赖、任务状态与同任务并发执行；
- 任务 Run 的过程、终态、验收决定与关键操作审计；
- AI 成功后人工确认完成或要求修改；
- 在项目页、工作区总览显示可下发、受阻、执行中和待验收任务的计数。

### 3.2 首期不包含

- AI 自动拆分需求或自动创建任务；
- 根据依赖自动启动后继任务、定时任务、事件触发器和跨项目批量执行；
- 自动重试、自动验收、自动合并、部署或发布；
- 跨项目依赖、子任务层级、任务模板、标签体系、工时估算和团队分派；
- 直接由浏览器或控制服务执行 Shell 命令；
- 团队角色、通知中心和外部项目管理工具同步。

## 4. 领域模型

### 4.1 实体关系

```text
Project
  -> Task
       -> TaskDependency（当前任务依赖的前置任务）
       -> TaskRun（一次下发形成的不可变执行快照）
            -> Conversation
            -> Message / Run / Event / Artifact（既有执行链路）
       -> TaskEvent（任务操作与状态历史）
```

| 实体 | 作用 | 关键约束 |
| --- | --- | --- |
| `Task` | 用户维护的开发计划和验收对象。 | 只属于一个 Project；不保存某次 AI 过程。 |
| `TaskDependency` | 表示“当前任务依赖前置任务”。 | 两端必须属于同一项目；禁止自依赖和环。 |
| `TaskRun` | 一次人工下发的执行事实。 | 绑定一个 Task、Conversation 和既有 Run；保存下发快照。 |
| `TaskEvent` | 任务创建、编辑、下发、状态变化和验收等审计记录。 | 追加写入，不用 UI 状态覆盖历史。 |

### 4.2 Task 字段

| 字段 | 说明 |
| --- | --- |
| `id`、`project_id` | 稳定身份与所属项目。 |
| `title` | 简洁、可扫描的任务名称。 |
| `description` | 下发给 AI 的任务背景、范围、限制和实现要求。 |
| `acceptance_criteria` | 用户可判断完成与否的验收条件；下发提示词中必须包含。 |
| `priority` | `urgent`、`high`、`normal`、`low`，用于人工排序和后续调度权重。 |
| `position` | 同一视图中的稳定排序值；不用于推断依赖。 |
| `status` | 持久化任务状态，见第 5 节。 |
| `last_task_run_id` | 最近一次下发记录，便于显示结果入口。 |
| `pinned` | 是否置顶（布尔）。后续增量添加的列，用于看板置顶展示。 |
| `created_at`、`updated_at`、`completed_at` | 生命周期与审计时间。 |

首期不建立 `assignee`、`due_date`、标签或父子任务字段。它们不影响人工下发闭环，并且会在没有身份和团队模型时制造伪能力。

### 4.3 TaskRun 快照

TaskRun 至少保存 `task_id`、`conversation_id`、`run_id`、`sequence`、`status`、`prompt_snapshot`、`acceptance_snapshot`、`created_at`、`started_at`、`finished_at`、`failure_reason`。`prompt_snapshot` 由标题、任务说明和验收条件在服务端构造；它保存实际发给 Claude 的文本，保证后续查看历史时不会受到 Task 编辑影响。

## 5. 状态机与依赖规则

### 5.1 任务状态

| 持久化状态 | 看板名称 | 含义 |
| --- | --- | --- |
| `todo` | 待处理 | 尚未下发，或已被重新打开。 |
| `running` | 执行中 | 已创建 TaskRun，正在运行或在 Conversation 队列等待。 |
| `awaiting_review` | 待验收 | 最近 TaskRun 成功结束，等待人工判断。 |
| `action_required` | 需处理 | Run 失败、被停止、服务重启中断，或验收要求修改。 |
| `done` | 已完成 | 用户确认验收，通过依赖门禁。 |

“受阻”不是数据库状态。它是 `todo` 或 `action_required` 的视图投影：只要存在一项前置任务不是 `done`，页面即显示受阻、列出阻塞任务，并禁用下发。

### 5.2 状态转换

```text
todo / action_required
  -> 手动下发 -> running

running
  -> Run 成功 -> awaiting_review
  -> Run 失败、停止或中断 -> action_required

awaiting_review
  -> 确认验收 -> done
  -> 要求修改 -> action_required

done
  -> 重新打开 -> todo
```

- `done` 是唯一能满足前置依赖的状态。
- 同一 Task 同时只能有一条 `queued` 或 `running` 的 TaskRun。
- `awaiting_review` 不能再次下发；用户需先要求修改使其回到 `action_required`。
- 重新打开完成任务后，依赖它的任务会重新受阻；该副作用必须在确认弹窗中说明。

### 5.3 依赖校验

创建或修改依赖时，服务端在同一事务内检查：任务存在且属于当前项目、两端不相同、关系未重复、添加边后不存在从前置任务回到当前任务的路径。若发现环，拒绝保存并返回包含任务标题的环路说明。

下发前再次读取所有直接前置任务并要求状态均为 `done`。这是最终约束，不能仅在前端按钮禁用时检查，以应对多窗口、刷新和并发请求。

## 6. 首期用户体验

### 6.1 项目页与任务视图

项目详情增加“任务”入口，默认显示看板，可切换列表：

- 看板列：待处理、受阻、执行中、待验收、需处理、已完成；
- 卡片显示标题、优先级、前置任务数量、受阻原因、最近 Run 状态与更新时间；
- 列表展示相同数据并支持按优先级、最近更新、状态和受阻原因筛选；
- 拖动或菜单调整只改变人工展示顺序，不自动创建依赖，也不改变状态；
- 项目总览显示任务总数、待验收数、受阻数和执行中数，避免用户遗漏人工操作。

### 6.2 新建与编辑

表单要求用户填写标题、任务说明和至少一条验收条件。任务说明推荐包含背景、允许修改的范围、限制和需要运行的检查；验收条件应是可验证的结果，例如“新增接口覆盖未授权与成功场景，测试通过”。

前置任务选择器仅显示同一项目中的其他任务。保存依赖后立即显示“被哪些任务阻塞/阻塞了哪些任务”，不把依赖藏在编辑表单中。

### 6.3 下发与验收

下发前，详情页展示实际提示词预览、目标 Conversation、依赖检查结果和当前权限模式。用户点击“下发”后，TaskRun 和既有 Message/Run 由服务端一次创建；页面跳转或链接到现有运行过程。

Run 成功时，任务进入待验收。验收区聚合 Claude 最终说明、代码 diff、命令输出和测试结果，并只提供三个明确动作：

- **确认完成**：记录验收决定，任务变为已完成，符合条件的下游任务解除阻塞；
- **要求修改**：填写简短原因，任务变为需处理；用户编辑后重新下发；
- **重新打开**：用于已完成任务，回到待处理并重新施加依赖门禁。

删除、重新打开和确认完成都必须二次确认；删除不可恢复，后两者会影响下游任务的可执行性。

## 7. 服务编排、接口与一致性

### 7.1 服务端职责

Task Service 是 Control Server 内的独立业务模块，负责 Task、依赖、状态转换、TaskRun 和 TaskEvent；它调用既有发送消息服务来创建实际 Run。浏览器只调用 Task API，不传入最终任务状态、Run ID 或渲染后的提示词作为可信数据。

```text
Browser
  -> Task API
  -> Task Service: 校验依赖与状态、固化 TaskRun 快照
  -> Existing Conversation Service: 创建 Message 与 Run
  -> Claude Runner
  -> Existing Event/Run terminal callback
  -> Task Service: 更新 TaskRun，推进 Task 状态，写入 TaskEvent
```

### 7.2 浏览器 API

```text
GET    /api/projects/{projectID}/tasks
POST   /api/projects/{projectID}/tasks
GET    /api/tasks/{taskID}
PATCH  /api/tasks/{taskID}
POST   /api/tasks/{taskID}/dependencies
PUT    /api/tasks/{taskID}/dependencies        # 替换整组依赖（replaceTaskDependencies）
DELETE /api/tasks/{taskID}/dependencies/{predecessorTaskID}
POST   /api/tasks/{taskID}/dispatch
POST   /api/tasks/{taskID}/stop
POST   /api/tasks/{taskID}/review
POST   /api/projects/{projectID}/tasks/review-all   # 批量验收
POST   /api/tasks/{taskID}/reopen
GET    /api/tasks/{taskID}/runs
GET    /api/tasks/{taskID}/events

# 编排队列（orchestration，已落地，见 §10 与 docs/14）
POST   /api/projects/{projectID}/orchestration/enqueue
POST   /api/projects/{projectID}/orchestration/pause
POST   /api/projects/{projectID}/orchestration/resume
POST   /api/projects/{projectID}/orchestration/dequeue
```

`dispatch` 不接受浏览器提交的最终提示词或依赖结论。它在事务中重新计算可执行性，创建 `TaskRun` 和 `TaskEvent`，再调用复用的 Message/Run 创建服务。若既有 Conversation 是持久流式会话，TaskRun 可先为 `queued`；若该会话不支持队列，则返回冲突而不是伪造等待状态。

`review` 请求只能针对 `awaiting_review`，动作是 `accept` 或 `request_changes`，并可附带纯文本说明。接受与解锁下游任务以数据库事务提交；浏览器刷新后重新读取任务即可得到正确状态。

### 7.3 运行终态回写

既有 Run 终态是 TaskRun 的唯一执行事实来源：

| Run 终态 | TaskRun 终态 | Task 转换 |
| --- | --- | --- |
| 正常完成 | `succeeded` | `running -> awaiting_review` |
| 执行错误 | `failed` | `running -> action_required` |
| 用户停止 | `stopped` | `running -> action_required` |
| 服务重启或进程丢失 | `interrupted` | `running -> action_required` |

终态处理必须具备幂等性：同一 Run 事件重复到达不创建多条 TaskEvent、不覆盖已记录的验收决定。控制服务启动时会扫描仍为活动状态却没有活跃 Runner 的 TaskRun，统一标记 `interrupted`，防止任务永久显示执行中。

## 8. SQLite 数据与迁移

首期沿用本地 SQLite 和当前项目、会话、消息、运行表。新表使用外键和索引保证查询及完整性。

```text
tasks
  id text primary key
  project_id text not null references projects(id) on delete cascade
  title text not null
  description text not null default ''
  acceptance_criteria text not null default ''
  priority text not null default 'normal'
  position real not null
  status text not null default 'todo'
  last_task_run_id text
  created_at datetime not null
  updated_at datetime not null
  completed_at datetime
  cancelled_at datetime

task_dependencies
  task_id text not null references tasks(id) on delete cascade
  predecessor_task_id text not null references tasks(id) on delete restrict
  created_at datetime not null
  primary key (task_id, predecessor_task_id)

task_runs
  id text primary key
  task_id text not null references tasks(id) on delete cascade
  conversation_id text not null references conversations(id) on delete restrict
  run_id text unique references runs(id) on delete set null
  sequence integer not null
  status text not null
  prompt_snapshot text not null
  acceptance_snapshot text not null
  failure_reason text not null default ''
  created_at datetime not null
  started_at datetime
  finished_at datetime

task_events
  id text primary key
  task_id text not null references tasks(id) on delete cascade
  task_run_id text references task_runs(id) on delete set null
  event_type text not null
  payload text not null default '{}'
  created_at datetime not null
```

索引包括 `tasks(project_id, status, priority, position)`、`task_dependencies(predecessor_task_id)`、`task_runs(task_id, created_at desc)`、`task_runs(run_id)` 与 `task_events(task_id, created_at)`。任务状态值、优先级值和 TaskRun 状态值均由服务端枚举校验。

## 9. 安全、失败与边界条件

- 任务说明与验收条件作为普通提示词发送给 Claude；它们不能提升 Conversation 的权限模式，也不能绕过现有 Bash 审批 Hook；
- 同一任务的重复下发请求应由数据库事务和活动 TaskRun 查询拒绝，避免双击或网络重试导致重复执行；
- 对任务标题、说明、验收条件、依赖数与单项目任务数设置服务端长度和数量上限，避免 SQLite 与页面被异常数据拖垮；
- 删除 Project 时任务可随项目级联删除；在首期单机产品中这是可接受的。任务也支持硬删除，但已编排的任务因审计要求不能删除；
- TaskRun 只引用当前项目可访问的 Conversation；禁止把任务下发到其他项目的会话；
- 用户编辑 Task 时不影响已创建 TaskRun 的快照；验收依据默认展示该次 Run 的快照与产物；
- 页面断线后先查询任务和历史 TaskRun，再订阅已有 Conversation WebSocket，避免依靠临时前端状态。

## 10. 第二阶段：自动编排与队列执行

> **更新**：本节原描述为"第二阶段未实现的自动 Scheduler"。实际 `orchestration.go` 已落地一套**人工入队的编排队列**（非全自动 Scheduler），包含 `project_orchestration_configs`、`task_orchestration_jobs`、`project_orchestration_leases`、`orchestration_outbox`、`release_snapshots` 五张表，以及 enqueue/pause/resume/dequeue/reorder 等 API（`app.go` orchestration 路由块）。它实现的是用户手动把任务入队、按序执行、lease 互斥、outbox 可靠投递，而非本节§10.1 描述的完全自动候选调度。严格串行 dev 集成的完整方案见 `docs/14-严格串行Dev集成任务编排方案.md`。下文为原始的自动 Scheduler 设计，保留作演进参考。

自动编排不是"把所有待办依次发送"。它是在明确策略下，由 Scheduler 创建与人工下发完全相同的 TaskRun。首期数据模型已经提供了所需的任务图、优先级、执行记录和人工验收门禁。

### 10.1 Scheduler 的职责

1. 在事务内找出前置任务均为 `done`、任务状态为 `todo` 或策略允许的 `action_required` 的候选任务；
2. 应用项目级策略：自动化开关、最大并发数、优先级、允许的 Runner/Conversation、执行窗口；
3. 以 TaskRun 创建时的条件再次校验，避免多个调度循环或人工下发产生竞争；
4. 将 TaskRun 放入持久队列并派发给 Runner；
5. 在失败、超时、人工暂停、策略改变和服务恢复时留下明确事件，而不是静默跳过任务；
6. 成功 Run 仍停在 `awaiting_review`，除非未来经过单独设计引入受控的自动验收策略。

### 10.2 自动化前置条件

进入第二阶段前，必须补齐以下产品决策：

- 每项目与每 Runner 的并发上限，及同一 Git 工作目录的隔离方式；
- 重试次数、退避、失败后是否暂停整条编排、是否允许跳过；
- Queue 持久化、去重键、租约和服务恢复语义；
- 自动下发范围、时间窗口、预算/用量上限和紧急停止开关；
- 多 Conversation、分支或工作树的选择策略；
- 通知与人工接管入口；
- 团队身份、权限、审计保留与项目级策略管理。

当这些策略稳定后，可使用 SQLite 队列表作为单机过渡；多 Runner 或跨机器调度再采用专用队列/工作流基础设施。无论采用何种基础设施，Task、TaskRun、验收与 TaskEvent 的业务语义保持不变。

## 11. 验收标准

1. 用户可在任意已加载项目中创建、编辑、排序、删除和重新打开已完成任务；每个任务都能保存标题、说明、验收条件和优先级。
2. 看板与列表展示同一批任务；受阻状态能显示未完成的具体前置任务。
3. 用户可以添加同项目依赖；自依赖、跨项目依赖和环形依赖被服务端拒绝。
4. 有任一前置任务不是 `done` 时，`dispatch` 返回业务错误且不创建 Message、Run 或 TaskRun。
5. 用户下发可执行任务后，系统恰好创建一条 TaskRun、一条用户 Message 和一条既有 Run；重复请求不产生并发重复执行。
6. TaskRun 保存下发提示词与验收条件的快照；后续编辑任务不改变历史记录。
7. Run 成功只使任务进入待验收；用户确认后才进入已完成并解除下游任务阻塞。
8. Run 失败、停止或恢复中断均使任务进入需处理，且可通过编辑和重新下发产生新的 TaskRun。
9. 任务、依赖、TaskRun 和任务事件在页面刷新与控制服务重启后仍可正确恢复和追溯。
10. 既有权限模式、审批、停止、WebSocket 实时过程、会话排队和使用统计在任务下发场景下保持一致。

## 12. 建议实施顺序

1. 建立 Task、TaskDependency、TaskRun、TaskEvent 的领域模型、SQLite 迁移和服务端状态机测试；
2. 提供任务 CRUD、依赖校验、列表查询和项目页任务入口；
3. 提取既有消息/Run 创建服务，接入原子 `dispatch` 与 Run 终态回写；
4. 实现任务详情、下发预览、运行历史和验收操作；
5. 实现看板、列表筛选、受阻原因与项目总览计数；
6. 覆盖并发下发、环检测、停止竞争、Run 重复事件、重启恢复和依赖重新阻塞的自动化测试；
7. 基于真实使用记录确定自动编排的策略，再另立第二阶段设计与实现计划。

## 13. 最终决策记录

| 决策 | 结论 | 原因 |
| --- | --- | --- |
| 创建方式 | 首期全部手工创建。 | 先验证任务粒度与用户工作方式。 |
| 下发方式 | 首期全部人工点击下发。 | 避免 AI 在不明确时自动改动项目。 |
| 依赖策略 | 未完成前置任务禁止下发。 | 防止无效或顺序错误的开发。 |
| 完成定义 | AI Run 成功后进入待验收，人工确认后完成。 | 保留用户的质量判断与控制权。 |
| 核心模型 | 独立 `Task -> TaskRun`。 | 计划、执行与调度能够各自演进。 |
| 自动编排 | 第二阶段由 Scheduler 创建同一种 TaskRun。 | 不重做首期模型，先补齐安全与调度策略。 |
