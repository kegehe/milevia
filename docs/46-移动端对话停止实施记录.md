## 0. 一句话结论

手机端此前**没有任何停止对话的入口** —— 任务队列里的任务能停（`task.stop`），对话却只能等它自己跑完。
本次补上：会话页输入条上，这条会话跑起来时**发送键的位置换成停止键**；停止要等电脑端把进程收干净，
期间按钮显示「停止中」并禁掉。

这不是"按钮藏起来了"，是前后端都没有这条能力。见 §1。

## 1. 动手前先核实的现状

| 层 | 现状 |
| --- | --- |
| 手机端 UI | `MobileRemotePage` 里「停止」二字只出现在任务队列面板（`task.stop`）。会话页输入条只有 [+][输入][发送] 三样，运行中只显示一条**只读**状态条（徽标 / 阶段词 / 已耗时） |
| 桌面端 | 停止走 `POST /api/runs/{runID}/stop?force=true`（`ConversationPage.tsx` 的 `stopRunInternal`），按 **run** 停 |
| 中继（RPC） | op 表只有 `fs.*` / `git.*`，且落点路径固定成 `/api/projects/{projectID}` + Path —— `/api/runs/{...}` 不在其下，所以这条通道当时够不着 |
| 命令通道 | `executeRemoteCommand` 只实现 `conversation.create` / `conversation.message` / `conversation.shortcut` + `task.*`，没有会话级的停止 |

## 2. 已定决策

| # | 问题 | 决定 | 理由 |
| --- | --- | --- | --- |
| 1 | 走哪条通道 | **中继**（新 op `conversation.stop`），不走命令通道 | docs/40 §0 决策 3 定的判据：除非真的需要命令通道那三样（幂等键 / 持久化审计 / 终态机），新操作一律走请求-响应。见 §3 |
| 2 | 按 run 停还是按会话停 | **按会话** | 桌面端手里有 run id（它跟着事件维护），手机端没有、也不该有。见 §4 |
| 3 | 落点 | 新增 `POST /api/conversations/{conversationID}/stop`，与 `clear` / `activate` / `messages` 同族 | 会话级的控制就该挂在会话下；`/api/runs/{runID}/stop` 保持不动（桌面端继续用） |
| 4 | `conversationID` 从哪来 | **只来自信封**，`Path` 里不出现 `{conversationID}` 占位符、`PathParams` 里也不声明它 | 它决定请求落到**哪条会话**，与 `projectId` 决定落到哪个项目同理。声明成路径参数就等于让 `params` 顺手改掉落点 |
| 5 | 没有活跃的那一轮 | `200 + {"status":"idle"}` | 幂等空操作。"按下停止"与"那一轮恰好自己跑完"是常态竞态，报错等于把"其实已经停了"说成失败。**但会话本身不存在仍是 404**（见下） |
| 5b | 有一轮、但不由本实例控制 | `200` + 那一轮自己的状态（如 `queued`），手机端按"没停成"处理并提示稍后重试 | `stopRunByID` 的原样返回。它与 `idle` **必须分开**：一句"没有在运行的任务"会把还在排队的那一轮说丢 |
| 6 | 还有排队中的请求 | `409` + 码 `active_runs_present` → 手机端弹确认框 → 带 `force` 重发 | 与桌面端逐字同一条分支（`requiresForceStop`）；不这样，一次点击会把用户排队等着跑的请求一起取消掉 |
| 7 | 停止键放哪 | 发送键**左边加一颗**，不取代它 | 跑着的时候再发一条是既有能力（桌面端运行中同样能发，还有「立即发送 / 预约发送」）；换掉发送键等于在最需要它的时刻把入口藏起来。代价是输入框在运行期间窄约 48px |
| 8 | 停止的目标会话由谁定 | 手机端把 id（`stopConfirmTarget`）一路传到请求里；请求发出前用它和**当前渲染的那条会话**比对一次 | 确认框可能挂在 A 上、而用户此刻已切到 B（点通知就能切）。没了这一道，「强制停止」会落在 B 上 —— 它还会连排队中的一起取消。判据用"当前渲染的那条"而不是 `selectedConversationRef`：后者可能指向一条已从快照消失的会话（`conversation` 会回落到 isCurrent 那条），拿它当判据会让停止键**点了没反应** |
| 9 | 超时预算 | 客户端**提议** `45s`（`conversationStopTimeoutMs`） | 服务端这条路径要拿一把**全局**流式锁（`streamMu`），与"某条会话正在冷启动 AI 进程"争锁；默认 20s 会被真实地跑爆，症状是"假失败" |

## 3. 为什么是中继而不是命令通道

停止这条操作**一样都不需要**命令通道那三样：

- 入参不含内容（命令通道的 payload 会落进云端 PostgreSQL，这条顾虑在停止上不存在）；
- 天然幂等（重复停无害），所以不需要幂等键；
- run 自己的状态与事件就是审计。

而走命令通道要多付三笔代价：

1. **两份白名单要同步**。命令类型在 `enqueueRemoteCommand`（control-server）与云端 `createCommand`
   （`cloud-control/internal/cloud/server.go`）各有一份允许清单 —— 这正是中继的设计一直在避开的结构性风险
   （见 `remote_relay.go` 顶部那段）。中继的 op 名单**只有执行点这一份**，云端与 Agent 都不认识 op。
2. **云端要先部署**。命令类型的新增要改一个**已部署的**服务，于是多出一个"新桌面 + 旧云端 = 400"的偏斜窗口。
3. **失败会被压成一句话**。`executeRemoteHTTPCommand` 只留 `{"error": "<本地化文案>"}`，
   `active_runs_present` 这样的稳定机器码到不了手机 —— 而决策 6 那条分支必须按**码**判，不能按文案判
   （文案会被本地化，按原文匹配的分支会静默失效）。中继的 `rpcResponse` 逐字保留 `status` 与 `code`。

代价与取舍：中继**不重放**（手机断网时那次停止会丢，用户重按一次即可；重复停无害）。
命令通道的持久化在停止这件事上收益约等于零，所以这笔取舍是划算的。

## 4. 为什么按会话停（而不是把 run id 传到手机）

桌面端能按 run 停，是因为它维护着 `run` 状态（由事件与 `activeRunId` 喂出来）。手机端没有这套东西，
它只有"这条会话在跑"这一个读数（`conversation.status` + 实时事件）。补一套 run 生命周期是最容易做错的一段：
错了不会报错，只会"点了没反应"或者"显示停止中但什么也没停"。

而"哪一轮是活跃的"在服务端就是一次查询（`activeRunIDForConversation`：`runs` 里 `queued`/`running`
按创建时间取最新）。取最新而不是最旧，是因为一个会话的 AI 进程会把后来的消息接成**排队回合**
（见 `forceStopConversationRuns` 的说明），于是"用户刚发的那条"才是他按停止时想停的东西。

顺带一个结论：它与桌面端的 `/api/runs/{runID}/stop` **不是重复端点**，粒度不同 ——
桌面端停的是"这一轮"，手机端停的是"这条会话现在在跑的"。

## 7. 已知边界

- **必须桌面端一起更新。** op 名单只有电脑端那一份（`remoteOperations`），所以"新手机 + 旧电脑端"
  的停止键会拿到一句"不支持的远程操作"（400）；反向（新电脑端 + 旧手机）没有影响。
  云端**不需要**改动 —— 它不认识 op（这正是选这条通道而不是命令通道的收益之一）。
- **不撤回用户消息、不回填草稿。** 桌面端在"助手还没有输出"时会把用户那条消息撤回并把正文放回输入框；
  手机端**没做**：手机端的消息来自服务端快照（权威），撤回要靠本地过滤并记住 runId，成本高、收益低。
  停止后那条消息留在列表里，没有回复。
- **编排对话的停不在这里。** 服务端拒绝并提示去编排面板（这条文案同时服务桌面端与手机端；
  原文是英文，此前不翻译，手机上会看到"当前操作与进行中的操作冲突，请稍后重试。：stop automatic
  orchestration from the orchestration controls"）。
- **「停止中」有 60 秒兜底放开。** 正常路径靠"这条会话不再在跑"这个读数摘掉它，但它有可能清不掉
  （`processingConversations` 里那条乐观记录在"还有待确认的消息"时会被对账跳过）。到点无条件放开：
  再点一次是幂等的，卡死比多一次无害的请求糟得多。
- **超时到点是"未知"，不是"失败"。** 客户端提议 45s（见决策 9），超了云端回一句
  "电脑端没有在 N 秒内回应这次请求" —— 那次停止**可能已经生效**。用户能做的只有再点一次
  （幂等，无害），或者看会话自己转闲。真要让这条路径更快，得改服务端那把全局流式锁的持有范围，
  不属于本次改动。
- **信封里的 `projectId` 不与 `conversationID` 绑定。** 会话域这条 op 不用 projectId（落点只有会话），
  所以一个"项目 A + 项目 B 的会话"的错配请求不会被拒 —— 项目域那些 op 会 404，这里不会。
  不是权限问题（中继本就以 Agent 令牌鉴权、调用方能触达全部项目），是**有意不加固**：
  绑定就要让中继层认识业务。理由与"真要加固该怎么做"写在 `remote_conversation.go` 顶部。
