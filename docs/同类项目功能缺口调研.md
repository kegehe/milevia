# 同类项目功能缺口调研

> 调研日期：2026-07-28  
> 目的：记录当前平台与同类 AI 编码 Agent 编排产品相比仍缺少的能力，并区分已实现、已有方案和后续候选项。

## 项目基线

当前平台已经具备以下核心能力：

- 管理本地 Windows、WSL 与 SSH 项目，支持 Claude Code 与 Codex CLI 会话；
- 记录 Project、Task、TaskRun、Run、Event，展示实时过程并保留审计；
- 任务优先级、依赖校验、人工下发、人工验收和重开；
- 命令审批、停止运行、Git 工作台、项目进程、文件浏览编辑和通知；
- 严格串行编排的任务分支/worktree、预设检查、独立审查、修复循环和自动集成到 `dev` 的实现基础。

因此，本调研不将“有任务看板”“有 Claude/Codex 会话”“有人工验收”作为缺口；也不将已经存在于严格串行编排中的 worktree、固定验证和独立审查重复列为未实现能力。

## 功能缺口

### 并行任务实施与合并治理

当前编排的安全前提是单项目严格串行。它避免了基线漂移和合并冲突，但尚未支持多个彼此独立的任务并行实施、分别验证，再由调度器治理合并顺序。

- 按依赖图和文件/模块范围判断可并行性；
- 多个 worktree、分支、端口和开发服务器的资源隔离；
- 并行任务的基线漂移检测、重基、冲突升级和可解释的合并策略；
- 并发、队列、模型和 Runner 的项目级配额。

参考：Agent Orchestrator、Superset、Paseo、Bernstein。

在没有可靠文件所有权、冲突处理和测试证据前，不应直接开启“所有可下发任务并行”。

### Git 托管平台与 PR/CI 闭环

当前已有本地 Git 操作和 `dev` 集成线，但没有将 GitHub/GitLab 等托管平台作为一等集成对象。

- 创建、更新和关联 Pull Request / Merge Request；
- 查询 CI 状态、日志、失败步骤和代码扫描结果；
- 将 Review 评论、请求修改和合并冲突路由到对应 TaskRun；
- 由人工确认后的受控 push、PR 合并与回滚；
- 将 Issue、PR、提交和发布版本关联到任务、运行与审计事件。

参考：Agent Orchestrator、1Code、Bernstein、GitHub Copilot coding agent。

自动 push、自动合并 `main` 不属于首期目标；平台应先提供受策略限制的候选操作和证据，再由用户确认。

### 外部事件与定时触发

当前任务主要由用户在界面中创建和下发，缺少统一触发器模型。

- Cron/日历定时任务，例如依赖更新、夜间检查和日报；
- GitHub、GitLab、Linear、Slack、Webhook、Git 事件触发；
- 触发规则的过滤条件、幂等键、去重、暂停、重放与失败告警；
- 触发事件到 Task、TaskRun、Run 的完整可追溯关联。

参考：1Code、Superset、amux。

任何自动触发均应复用既有 Task 和审批策略，不能绕开人工验收或直接执行任意浏览器传入的命令。

### 更广的 Agent 适配与能力协商

当前以 Claude Code 与 Codex CLI 为核心。新增 CLI 时仍需明确其是否支持会话恢复、流式事件、停止、审批、只读审查、使用量、远程运行和更新检查。

- 对 Cursor、Copilot CLI、Gemini CLI、OpenCode、Aider 等建立适配器；
- 使用统一的能力声明，而不是在页面或任务代码中硬编码某个 CLI 的权限与会话语义；
- 支持 Agent 角色选择，例如实施、审查、测试、规划和安全检查；
- 按任务阶段选择 Agent/模型，并保留实际选择的快照、版本和费用证据。

参考：Agent Orchestrator、Superset、Omnigent、Paseo。

### 细粒度策略、沙箱与资源控制

现有审批和完全控制模式能覆盖基本交互，但不等同于任务级隔离与组织级策略。

- 每个 TaskRun 的容器或云沙箱，以及项目目录、网络、凭据和进程树隔离；
- 命令、工具、MCP、网络域名、文件路径的允许/拒绝策略；
- 运行时长、CPU、内存、并发数、Token 与费用预算上限；
- 策略命中、例外批准和安全事件的审计记录；
- 对不可信项目、远程 Runner 和外部 MCP 的差异化默认策略。

参考：Omnigent、OpenHands、1Code。

这是自动触发、并行执行和团队共享之前的安全前置条件。

### 多 Runner 注册、调度与恢复

当前可在本地（Windows/WSL）或 SSH 项目中执行，Runner 注册与持久化已实现（`runner_registry.go` 的 `register`/`unregister`/`list`/`get`/`getMeta`，`runner_persistence.go` 的 `runners` 表 + 迁移回填 + `projects.runner_id`），但尚未形成多个长期注册 Runner 的完整调度面。

- ~~Runner 注册~~、心跳、版本、能力和健康检查（注册已实现；心跳/健康检查/能力上报仍缺）；
- 按项目位置、Agent 可用性、资源与策略自动选择 Runner；
- 断线重连、失联运行识别、租约、fencing token 和可恢复队列；
- 容器、Windows、Linux、远程服务器和云沙箱的统一运行时；
- Runner 升级、凭据轮换和失效隔离。

参考：Paseo、Superset、Omnigent。

### Agent 间协作与共享知识

当前编排由服务端和用户驱动，没有让多个 Agent 在受控范围内主动协作。

- Agent 间消息、委派、任务认领、结果回传和共享上下文；
- 只读顾问、独立审查、实现 Worker 等角色的权限边界；
- 项目级知识库、任务结论、失败经验和可复用 Skill；
- 从成功任务提炼 Skill 的提案、Diff 审阅、人工批准和版本回滚；
- 防止多个 Agent 重复工作、互相覆盖和无限委派的配额与深度限制。

参考：amux、Paseo、oh-my-claudecode、Tiger CoWork。

自动生成的知识或 Skill 必须经过人工审阅，不能直接改变全局执行规则。

### 团队、权限与协同操作

当前平台面向单用户本地控制，尚未具备可安全共享的组织模型。

- 用户、组织、工作区、项目成员和角色权限；
- 共享会话、观察者、协同操控、任务指派和操作人审计；
- 项目、Runner、凭据、MCP 和工件的访问控制；
- 通知偏好、值班人、审批人和跨时区协作；
- 审计导出、保留策略和敏感信息脱敏。

参考：Omnigent、Superset。

### 多端控制与远程观察

当前入口为 Web 控制台与 Tauri 桌面端。桌面端已提供系统托盘与品牌面板（`docs/27`）、在线升级（`docs/23`）、sidecar 生命周期管理，但缺少适合移动端的客户端能力。

- ~~PWA 或原生桌面端，提供系统通知、托盘~~、离线动作队列（原生桌面端与托盘已实现；离线动作队列仍缺）；
- 手机上查看运行、停止任务、确认低风险审批和处理告警；
- 远程主机发现、连接、唤醒和安全隧道；
- 多端状态同步、设备撤销和会话接管。

参考：Paseo、Superset、amux、1Code。

### 工件、可观测性与成本分析增强

平台已保存事件和部分运行结果，但尚缺统一的工件与跨项目分析面。

- 测试报告、构建产物、截图、覆盖率、部署日志和 Diff 的统一工件模型；
- 对象存储、校验和、保留策略、下载授权和运行间对比；
- Agent、模型、项目、任务阶段和 Runner 维度的成本、时延、失败率与成功率；
- 失败分类、重试效果、人工介入次数和质量门禁通过率；
- 可查询、可告警的运行指标与审计检索。

参考：Bernstein、Agent Orchestrator、amux。

### 任务管理扩展

当前任务模型刻意保持轻量，尚不支持组织级项目管理能力。

- 父子任务、里程碑、模板、标签、负责人、截止时间和工时；
- 跨项目依赖、批量操作和跨项目工作流；
- 从 Issue/需求导入任务，但不把外部系统状态当作本地任务状态的唯一来源；
- 任务优先级以外的排队策略，例如截止时间、成本预算和服务等级。

参考：Codex Mate、1Code、amux。

## 已有基础但需要继续完善

| 能力 | 当前基础 | 后续完善方向 |
| --- | --- | --- |
| 严格串行编排 | 任务分支、worktree、验证、独立审查、修复和 `dev` 集成。 | 提供运行可视化、恢复演练、配置界面和真实项目的端到端验证。 |
| 人工验收 | Task 与 Run 分离，验收决定影响任务完成。 | 将测试、审查和 Diff 等证据聚合为结构化验收包。 |
| 多 Agent | Claude Code 与 Codex CLI 已进入统一会话/运行模型。 | 完成能力协商、适配器注册和更多 CLI 的一致性测试。 |
| 本地/SSH 执行 | 项目可通过本地与 SSH 运行时执行。 | 演进为可注册、可监控、可调度的多 Runner 控制面。 |
| Git 工作台 | 已有仓库状态、Diff 和 Git 操作。 | 接入远程托管平台，并与 TaskRun、CI、PR 证据关联。 |

## 建议优先级

| 优先级 | 建议范围 | 原因 |
| --- | --- | --- |
| P0 | 完成严格串行编排的端到端验证、工件化验收包、Runner 恢复与租约测试。 | 直接决定当前自动化链路是否可信。 |
| P1 | GitHub/GitLab PR/CI/Review 集成；适配器能力协商；任务级策略与预算。 | 让现有任务结果进入真实协作与交付流程，同时控制风险。 |
| P2 | 多 Runner 注册调度、定时/事件触发、受控并行任务。 | 需要 P0/P1 提供可靠状态、隔离和策略前提。 |
| P3 | 团队协作、移动端、Agent 间自主协作、自动 Skill 沉淀。 | 产品价值高，但会显著扩大权限、数据与运维边界。 |
