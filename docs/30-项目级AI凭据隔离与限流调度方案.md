# 项目级 AI 凭据隔离与限流调度方案

> 日期：2026-08-20
>
> 状态：默认方案（本机 Runner 的项目隔离、凭据池与运行级限流）已实施并经回归验证；远端 Agent 与请求级网关为可选扩展
>
> 关联：[AI CLI 配置档案管理调研与实施方案](./18-AI%20CLI配置档案管理调研与实施方案.md)、[会话页项目级AI配置重塑方案](./21-会话页项目级AI配置重塑方案.md)、[Codex CLI集成调研与实施方案](./13-Codex%20CLI集成调研与实施方案.md)

## 1. 结论

可以实现项目间的 Claude Code / Codex API 凭据隔离，并通过不同 API Key 分担 RPM、TPM 与并发限制。

单纯让每个项目保存一套 `base_url`、API Key 和模型虽然可用，但不是长期最优方案：会重复保存凭据，无法统一轮换，也会造成某些 Key 满载、其他 Key 闲置。推荐采用“项目路由、Provider 档案、凭据、额度组与调度”五层模型。

```text
项目 + Agent
  -> 路由策略（固定档案 / 凭据池）
  -> Provider revision（协议、端点、模型）
  -> Credential revision（API Key）
  -> Quota groups（Key / 组织 / 工作区 / IP 共享额度）
  -> 对应 CLI 子进程
```

该设计同时满足两类需求：

- **严格隔离**：项目 A 固定使用 Key A，项目 B 固定使用 Key B；
- **提升吞吐**：普通项目进入凭据池，在多个可替换 Key 间按余量分配。

### 默认部署范围

默认方案不新增网关或守护进程，适用于 Claude Code、Codex 都在 Milevia 本机 Runner
执行的项目。它在 CLI 启动前实施并发、RPM、TPM 保守准入，在运行结束后根据 CLI 回传的
usage 结算 TPM，并在上游返回 `429`/`Retry-After` 时冷却对应凭据。对于“多个项目共用
API Key 导致限流”这一目标，这是部署成本和收益最平衡的方案。

SSH/远端 WSL 的受管密钥与逐 HTTP 请求的硬性 RPM/TPM 整形不属于默认范围：前者需要
目标机 Runner Agent，后者必须在 Provider 请求路径的网关或代理实现。两者均为可选扩展，
不会影响本机项目隔离、固定 Key 或凭据池分流。

## 2. 现有基础与差距

### 2.1 已具备的能力

当前 `agent_profiles` / `agent_profile_revisions` 已保存 Agent、Base URL、模型和认证模式；`profile_secrets` 使用 AES-GCM 加密保存 API Key。运行时根据 revision 构建独立子进程环境：

- Claude Code：`ANTHROPIC_API_KEY`、`ANTHROPIC_BASE_URL`、`--model`；
- Codex：`OPENAI_API_KEY`、`OPENAI_BASE_URL`、`-c model=...`；
- 未选择档案时继续使用原 CLI 配置；显式选择的档案会清除继承的 API Key 和 Base URL。

会话和运行记录已保存 `agent_profile_revision_id`，因此运行可以固定到创建时的配置快照。定时任务也已保存 `profile_revision_snapshot`。

### 2.2 当前限制

1. `projects.default_profile_id` 是单列。一个项目最后只能自动应用一个档案，无法让 Claude 与 Codex 分别拥有默认配置。
2. 档案按 Runner 管理，不是显式的“项目 + Agent”绑定；另一 Agent 的配置需要在创建会话时手选。
3. 当前没有以 Key 为单位的并发、RPM、TPM 和 `429` 冷却调度。多个项目若复用同一档案，仍会互相限流。
4. Codex 不能把任意网关都视为仅替换 `OPENAI_BASE_URL` 即可兼容。其自定义 Provider 需要 `model_provider`、`model_providers.<name>.base_url`、`wire_api`、`env_key` 等结构化配置，并应逐 Provider 验证。
5. SSH 与跨边界 WSL Runner 当前不接收本机 API Key 注入，仍使用目标机器的 CLI 配置。

## 3. 推荐数据模型

### 3.1 不可变 revision 原则

Provider、凭据和项目路由都分为“可命名的身份”和“不可变 revision”。运行、会话和定时任务不能只保存可变 ID：否则编辑端点、模型或轮换 Key 后，已排队任务会在不知情的情况下改变真实执行配置。

```text
provider_profiles                 # 身份、名称、当前 revision
provider_profile_revisions        # 端点、协议、默认模型、受控 Provider 配置
credentials                       # 身份、名称、当前 revision、启用状态
credential_revisions              # provider revision、secret_ref、模型能力约束
project_agent_routes              # project_id + agent_id 的身份与当前 revision
project_agent_route_revisions     # pinned / pool / cli_managed、模型覆盖
credential_pools                  # 身份、名称、当前 revision
credential_pool_revisions         # 成员、选择策略、兼容性与公平策略
```

- API Key 的 `secret_ref` 只属于 `credential_revisions`，不允许在 revision 间就地覆盖。
- 普通编辑创建新 revision；会话和已准入运行保存 provider、credential、route revision ID。
- 凭据池任务在排队时只固定 route revision；真正获得准入时再选择一个可用 credential revision，并立即写入会话和运行记录。
- 额度和冷却属于实时调度状态，不作为历史配置快照。更新额度应立即影响尚未开始的运行。
- 所有会解析密钥或拼接 CLI Provider 参数的资源必须绑定 `runner_id`。Provider、credential、pool、quota group 不跨 Runner 共享；跨 Runner 复用配置只能通过导出不含密钥的模板再在目标 Runner 创建资源。

### 3.2 Provider 档案

Provider 档案描述“如何访问某一类服务”，不含项目选择关系，也不含明文 Key：

```text
provider_profiles
  id
  runner_id
  agent_id                 # claude-code | codex
  name
  current_revision_id
  enabled

provider_profile_revisions
  id
  provider_profile_id
  revision
  transport                # anthropic | openai_responses | codex_provider
  base_url
  provider_config_json     # Codex model_provider / wire_api 等非敏感字段
  default_model
  state                    # active | deprecated | revoked
```

`transport` 必须是受控枚举。不要开放任意环境变量或任意 CLI 参数，以免用户配置意外覆盖认证、代理或安全相关变量。生产端点必须为 `https`；仅 loopback mock Provider 可使用 `http`，且验证请求不得跟随 HTTPS 降级或跨主机重定向。

### 3.3 凭据

凭据独立于 Provider 与项目，API Key 继续采用现有的加密存储机制：

```text
credentials
  id
  runner_id
  name
  current_revision_id
  enabled

credential_revisions
  id
  credential_id
  provider_profile_revision_id
  secret_ref
  model_capabilities_json  # 可使用的模型 / 部署约束
  state                    # active | deprecated | revoked
```

同一 Key 可被多个项目引用；Key 轮换创建新的 credential revision，不需要逐项目重新填写。一个 Key 只能绑定一个兼容的 Provider revision；若端点、协议或认证方式变化，必须创建新的凭据 revision。

### 3.4 项目与 Agent 路由

用独立表替代 `projects.default_profile_id`：

```text
project_agent_routes
  project_id
  agent_id                 # claude-code | codex
  current_revision_id
  enabled

project_agent_route_revisions
  id
  project_id
  agent_id
  mode                     # pinned | pool | cli_managed
  credential_id            # mode=pinned 时指定身份
  pool_revision_id         # mode=pool 时固定选择范围与策略
  model_override
  state                    # active | deprecated | revoked
  updated_at

primary key (project_id, agent_id)
```

一个项目因此可以同时配置 Claude Code 和 Codex，且不会发生“后保存者覆盖前者”的问题。`model_override` 属于项目路由，Provider revision 的 `default_model` 用于共享默认值。

`pinned` 路由在**创建会话、定时任务或编排任务时**解析当前 active credential revision，并将其与 provider revision 写入该对象；之后轮换 Key 不影响该对象。`pool` 路由允许在首次真正准入前保持“未分配 credential”的状态，但一旦启动会话或运行，选中的 credential/provider revision 必须写入并保持不变。长驻 Claude 会话不能在后续用户回合无提示地切换 Key。

### 3.5 凭据池

```text
credential_pools
  id
  runner_id
  name
  current_revision_id
  enabled

credential_pool_revisions
  id
  pool_id
  revision
  provider_compatibility_key
  strategy                 # fair_queue | least_loaded | round_robin
  project_max_concurrency
  state                    # active | deprecated | revoked

credential_pool_revision_members
  pool_revision_id
  profile_revision_id        # 创建 pool revision 时冻结，不随档案轮换漂移
  weight
  enabled
```

路由 revision 必须引用 `pool_revision_id`，而不是可变 `pool_id`。调整成员、策略、并发上限或兼容性时创建新的 pool revision；已排队任务继续依据其快照的 pool revision 选择，但停用或撤销成员仍可使其失去资格并触发重新排队说明。

`provider_compatibility_key` 由 Agent、传输协议、规范化端点、`wire_api`、部署区域和可用模型集合生成。仅允许兼容键相同的凭据加入同一池；不同 Provider、不同 API 协议或模型能力不一致的凭据不得混池。跨模型降级只能作为项目路由明确声明的 fallback，不能由调度器静默替换。

### 3.6 额度组

供应商的限额不一定按 API Key 独立计算，可能按组织、工作区、模型、出口 IP 或中转服务账户聚合。因此不能把 `credential_id` 当作唯一限流键。

```text
quota_groups
  id
  runner_id
  provider_profile_id
  scope                    # credential | organization | workspace | model | ip
  scope_key                # 例如组织 ID、模型部署 ID；不含明文 Key
  name
  rpm_limit                # 可为未知
  tpm_limit                # 可为未知
  max_concurrency
  enabled

credential_quota_groups
  credential_id
  quota_group_id

quota_group_state
  quota_group_id
  runner_id
  rpm_tokens
  tpm_tokens
  cooldown_until
  last_refilled_at
  updated_at

quota_reservations
  id
  quota_group_id
  run_id                   # 与 quota_group_id 共同唯一，保证幂等
  runner_id
  state                    # reserved | running | released | expired
  concurrent_lease_until
  reserved_rpm
  reserved_tpm
  created_at
  updated_at
```

每个 credential 至少属于一个 `credential` 额度组；同一组织或中转账户下的 Key 额外加入共同额度组。`scope_key` 是 quota group 的唯一语义键，不能只用显示名称区分模型、组织或中转账户。

一次准入必须在 Runner 自己的持久化存储中按稳定顺序原子取得该 Key 所属的所有额度组配额，并以 `run_id` 生成幂等 reservation。任一组不足即回滚本次尚未消费的预留并排队。运行期间以心跳续期并发租约；Runner 重启后扫描过期 reservation，核对本机进程仍存活时续租，否则释放并发租约。RPM/TPM token 的消耗和 refill 保留在状态表中，不能只存在内存。这样既能限制单 Key，也不会错误地把组织级额度累加为多 Key 的总和。

## 4. 运行时选择与限流

### 4.1 解析顺序

创建会话或任务时固定 route revision；`pinned` 同时固定 credential/provider revision，`pool` 在首次执行前由执行地点的调度器完成分配与准入：

```text
项目 + Agent
  -> project_agent_route_revision
  -> 固定 credential revision，或候选 pool revision members
  -> 对全部 quota groups 原子准入
  -> 固定 provider / credential / model revision 到 conversation 和 run
```

任务一旦准入，就将选择的 revision 写入会话和运行记录。后续编辑项目路由或轮换 Key 只影响新对象，不追溯改变已经固定的会话或运行。尚未选择 credential 的池任务会在开始时从其 pool revision 的有效成员中选择，避免排队期间因已停用成员永久阻塞。

### 4.2 准入策略

调度器不以项目 ID 计量，而是对 credential 关联的全部 `quota_groups` 共同准入。每个额度组独立维护：

- 活跃运行数，不超过 `max_concurrency`；
- 请求 token bucket，用于 RPM；
- 估算 token bucket，用于 TPM；
- `cooldown_until`，收到 `429` 或服务端 `Retry-After` 后暂停；
- 最近失败原因与最近使用时间，用于可观测性和均衡选择。

CLI 的一个会话回合可能触发多次模型请求、工具回合和子 Agent；长驻 Claude 会话还会在启动后的任意时刻继续请求。因此 Milevia 在 CLI 外部**不能承诺硬性的请求级 RPM/TPM 限制**。首期只承诺：

- 对新会话、新运行和新用户回合执行并发与保守预算准入；
- 使用完成后的 usage 回填估算 TPM，并在 429 后按 `Retry-After` 冷却；
- 无法获得 usage 时，将 TPM 状态明确标记为估算或未知，不虚报精确值。

若需要硬性控制每个 API 请求的 RPM/TPM，必须由 Provider 网关或受控代理在请求路径上完成整形；不能仅靠 CLI 进程启动前的 token bucket。

候选凭据选择顺序：过滤停用、撤销、冷却中、并发已满、额度组不足和不兼容成员后，选择预计最早可执行的 Key。当前定时任务会保留在队列等待重试；普通交互请求会返回带 retry-after 的准入错误，不会启动 CLI 后再等待 429。收到 429 后，优先遵守 `Retry-After`；缺失时使用有上限的指数退避。

### 4.3 固定与池的边界

- `pinned`：适合有严格预算、业务隔离或某项目必须使用指定模型/供应商的场景。
- `pool`：适合批量任务、定时任务与普通开发项目，能最大化已购额度的利用率。
- `cli_managed`：保留原有 CLI 登录态，不参与 API Key 调度；用于 OAuth、订阅账号或不希望 Milevia 管理 Key 的用户。

同一供应商组织下的多个 API Key 是否真的拥有独立限额，取决于供应商或中转服务的限流维度。产品必须要求用户将共享额度的 Key 归入同一个 quota group；若无法获知限流维度，默认按保守共享额度处理，而不是假设可叠加。

### 4.4 多项目公平性

当前实现只提供每个路由 revision 的项目并发上限，以及凭据成员的 `round_robin` / `least_loaded` 选择。历史兼容的 `fair_queue` 名称当前等价于成员轮询，**不表示项目间公平队列**。额度不足时，交互请求返回可重试错误；定时任务保留其现有队列状态。

完整的项目公平队列仍需要每项目 FIFO 子队列、权重、等待老化、交互/后台服务份额，以及可持久化的排队位置和阻塞原因。它不属于当前本机无网关方案的已交付承诺，不能据此宣称不会发生跨项目饥饿。

### 4.5 调度器归属与跨 Runner

调度器必须与“解析密钥并实际启动 CLI”的 Runner 位于同一执行地点。只有这样，额度预留、进程启动、429 冷却和配额释放才能在一个故障域内保持一致。

- 本机 Runner：Control Server 内的调度器负责原子 `reserve -> start`。启动失败回滚本次预留；成功后运行结束仅释放并发租约，RPM/TPM 令牌按时间或实际 usage 回填，不在结束时无条件归还。
- SSH / WSL Runner Agent：目标 Agent 本地保存 Provider、credential、pool、quota group 和额度状态，并提供原子 `reserve -> start / rollback -> finish` RPC。Control Server 在配置变更时将不含密钥的 route revision 镜像为目标 Agent 的 `remote_route_revision_id`；执行请求携带该目标本地 ID 与幂等运行 ID，Agent 据此解析自己的资源。
- 未部署目标 Runner Agent 的远端 Runner：继续拒绝受管 API Key 与凭据池，不允许由本机预留后远端自行执行。

多实例或未来集中调度时，quota group 的预留状态必须进入单一协调存储或由唯一 Runner Agent 所有；禁止多个 Control Server 各自维护一份内存 token bucket。

### 4.6 轮换、停用与撤销

- **轮换**：创建新的 credential revision。已准入运行保留旧 revision 直到结束；尚未准入的池任务使用新 revision。
- **停用**：拒绝新的准入，不主动中断已运行任务；用于计划维护或额度耗尽。
- **撤销**：视为安全事件，采用持久化状态机，不能把数据库事务与 OS 进程停止伪装成一个原子动作。

撤销流程固定为：

1. 短事务将 credential revision 标记为 `revocation_requested`，同步拒绝新准入，并创建 `revocation_jobs`；
2. worker 取消排队 reservation，向使用该 revision 的本机或目标 Runner 发送停止请求；
3. Runner 返回已停止确认后，job 标记为 `completed`，再销毁或隔离 `secret_ref`；
4. 超时、Runner 离线或停止失败时，job 标记为 `failed` 并持续告警，credential revision 保持不可准入；
5. 若供应商支持 API Key 吊销，单独触发并记录其结果；本地删除 `secret_ref` 不能撤回已泄露或已注入进程的 Key。

已启动 CLI 的环境中仍有 API Key，因此撤销必须停止相应进程。服务端崩溃恢复后，worker 从未完成 `revocation_jobs` 继续处理，不能遗漏半途撤销。

## 5. CLI 与 Provider 适配

### 5.1 Claude Code

Claude Code 使用每个子进程独立的 `ANTHROPIC_API_KEY`、可选 `ANTHROPIC_BASE_URL` 和 `--model`。适配层应为每次运行重新构建环境，清除继承的 Anthropic / OpenAI 认证变量，不修改用户全局 Shell 配置。

自定义端点必须与目标 Claude Code 版本及对应 API 协议完成连通性、流式输出、工具调用、模型名和 429 行为验证后才能标记为可用。生产验证仅允许 HTTPS 端点；测试环境的 HTTP loopback mock 必须与生产配置隔离。

### 5.2 Codex

Codex 官方 API 可使用 `OPENAI_API_KEY`。对于自定义端点，适配层应显式生成受控的 Codex Provider 配置，而不是承诺所有网关都支持单一 `OPENAI_BASE_URL`：

```text
model_provider
model_providers.<name>.base_url
model_providers.<name>.wire_api
model_providers.<name>.env_key
model
```

配置优先通过本次执行的 `-c` 参数提供，避免写入或污染用户的 `$CODEX_HOME/config.toml`。需要为每一种 `wire_api` 和目标 Provider 保存验证结果，并拒绝不受支持的重定向、明文端点或模型组合。

本机 Codex `0.148.0` 的 mock Provider POC 已验证：显式 `model_provider` 与 `OPENAI_API_KEY` 能向本地 Responses mock 端点发送带目标模型和 Bearer Key 的请求。该 POC 不能证明当前仅设置 `OPENAI_BASE_URL` 的路径适配全部兼容网关。

## 6. 安全边界

当前可行的实现是把解密后的 Key 放入启动 CLI 的子进程环境，且不写入命令行、数据库响应、事件流和日志。这可以实现运行配置隔离，但不是针对不可信代码的强密钥隔离：Agent 能执行命令时，可能读取自身环境或通过同权限进程获得等价访问能力。现有“数据库旁的主密钥文件 + AES-GCM”只能降低单独导出数据库的风险，不能防御同一 OS 账户被攻破。

因此：

- 受管 Key 应可轮换，并限制在受信任项目与 Runner 上使用；
- 生产或高风险凭据使用独立 OS 用户、容器或远程 Runner；
- 强隔离必须配合网络出口白名单与 Provider 代理策略，不能仅依赖“环境变量隐藏”；
- 代理若可被 Agent 随意调用，本身就是等价凭据，不能被误认为安全边界。
- `HTTP_PROXY`、`HTTPS_PROXY`、`ALL_PROXY`、`NO_PROXY`、自定义 CA 与证书覆盖变量不能盲目继承。它们必须由 Provider revision 的受控 schema 显式声明，并进入端点验证与日志脱敏范围。

## 7. 实施顺序

### P0：正确的项目绑定与 revision 迁移

1. 增加 `project_agent_routes` 与 route revision，迁移现有 `default_profile_id` 到其对应 Agent。
2. 迁移必须幂等：缺失、停用、撤销、Agent 无法识别或 Runner 不匹配的旧默认值不自动猜测，改为清空并记录可审计迁移结果。
3. API 改为按 `project_id + agent_id` 读取和更新路由；项目 AI 配置页分别保存 Claude 与 Codex，不再互相覆盖。
4. 会话、新建任务、定时任务与编排任务均保存 route / provider / credential revision；固定路由在创建时保存，池任务在首次实际准入时补写 credential revision。
5. 保留原 `default_profile_id` 的读取兼容，完成迁移验证后停止写入。

实施记录（2026-08-20）：已建立 `project_agent_routes` 与
`project_agent_route_revisions`，启动迁移会将可用的旧默认档案迁入对应
Agent 路由；无法验证的旧值会清空并写入迁移结果。新会话、运行、定时任务
与编排会话均保存 route revision 快照；项目配置页按 Agent 分别保存和清除，
Claude Code 与 Codex 不再覆盖彼此。`default_profile_id` 仅保留为旧数据库的
读取兼容和迁移来源，新的项目配置不再写入该列。

### P1：Provider 适配正确性

1. 将 Provider 配置从任意 `env` 升级为受控 schema。
2. 为 Claude 和 Codex 的每种 Provider 适配执行 loopback mock 连通性 POC，并对生产 HTTPS 端点执行单独的 TLS、重定向和证书校验。
3. 对不支持的端点明确报错，不静默回退到用户全局 CLI 配置。

实施记录：Claude 继续使用受控环境注入；Codex 受管 API Key 运行时生成独立
`CODEX_HOME/config.toml`，固定 `model_provider`、`wire_api=responses` 和
`env_key=OPENAI_API_KEY`。生产端点要求 HTTPS，HTTP 仅允许 loopback mock。

### P2：本机凭据池与限流调度

1. 增加 pool revision、credential revision、quota group、持久化额度状态和幂等 reservation。
2. 在本机 Runner 的运行真正启动前增加原子 `reserve -> start / rollback -> finish` 准入；一个准入同时占用全部关联 quota groups，完成时只释放并发租约，重启时将中断运行并释放其租约。
3. 从 CLI 输出或 Provider 响应提取 429、`Retry-After` 与 usage，并更新运行状态；CLI 侧 TPM 必须标记为估算值。
4. 实现轮换、停用和基于 `revocation_jobs` 的撤销状态机，撤销会取消使用旧 revision 的排队与运行任务，并等待 Runner 停止确认。
5. 在项目与凭据管理页展示已配置的额度组；不展示明文 Key。项目公平队列、预计可执行时间、冷却状态和近期限流事件仍是后续规划项。

实施记录：已增加 `credential_pools` 的不可变 member revision、`quota_groups`、
`credential_quota_groups`、持久化 token 状态、并发租约、幂等 `quota_reservations`
和 429 冷却；每个档案默认拥有独立额度组，可通过 API 将多个档案加入共享组。
池成员会冻结到创建时的 profile revision。池只允许相同 Agent、协议、规范化端点和模型的成员，选择时会跳过冷却、额度不足
或并发已满的成员，并按轮询/最小负载策略推进。运行记录落库后、CLI 启动前原子预留；
重复准入不重复扣减 RPM/TPM，运行期间续期租约，结束时释放并发租约。429 会解析
`Retry-After`（缺失时保守冷却 30 秒）。撤销任务仅在关联运行实际进入终态后完成。
项目 AI 配置读取接口会显式返回 pool 路由，前端不会将池误判为空配置并覆盖。

已补充 CLI usage 回填：Claude/Codex 在输出中提供 token usage 时，运行结束会将准入时
预留的 TPM 调整为实际 input、output 和 cache token 总和；缺少 usage 时才保留一 token
的保守预留。配置管理页已支持受管 API Key 档案、额度组、凭据池，并可直接从项目 AI
配置中绑定既有池；额度组可在界面中创建、关联到其他档案、编辑额度和启停。额度余额
不会在服务重启时按零余额推断为“未初始化”并重置。认证方式变更会生成新 revision，旧
revision 的密钥只会在显式撤销该 revision 后销毁。未部署 Runner Agent 的 SSH / WSL
Runner 会在所有受管凭据、额度组和凭据池写入口被拒绝，避免出现“已配置但远端未生效”。

仍未实施：请求级 TPM/RPM 整形、完整的项目公平队列（权重、老化、交互/后台份额），
以及所有 Provider 的流式和工具调用 loopback mock 验收。CLI 进程外的调度只能在“运行

Provider 网关或受控代理在每个请求经过的位置实现。

3. 对高风险档案提供独立账户/容器执行与网络出口策略。

实施记录：已加入 `RunnerAgent` 协议、能力查询接口和本机实现；SSH/跨边界 WSL

## 8. 验收标准

1. 同一项目的 Claude Code 和 Codex 可各自保存独立 route revision、端点、模型和凭据，不发生覆盖。
2. 两个项目使用不同固定 credential revision 并发运行时，子进程环境和模型参数互不串用。
3. 编辑 Provider、路由、pool 成员或轮换 Key 后，已固定对象保持原 revision；未准入池任务只从其 pool revision 的有效成员中选择。
4. 多个本机项目共用同一 credential 或同一组织 quota group 时，超过配置的并发、保守预算或冷却时间将拒绝本次准入并给出 retry-after；定时任务保留排队状态。Runner 重启时会将中断运行标记为 interrupted、释放租约，并避免重复扣减 reservation。
5. 凭据池在一个成员冷却、额度组不足或模型不兼容时选择其他兼容成员；轮询和最小负载策略仅保证候选成员的均衡，不承诺尚未实现的项目权重、老化或交互/后台公平份额。
6. 停用仅阻止新准入；撤销创建可恢复的 `revocation_job`，取消使用该 revision 的队列和运行，等待长驻 CLI 停止确认，且不泄漏明文 Key。
7. 后续验收要求：每个 Provider 适配均通过 loopback mock 的认证、模型、流式、工具调用和 429 POC；生产端点拒绝 HTTP 与不允许的重定向，并通过独立 TLS、代理与证书验收。
8. SSH 与跨 Runner 路径在未部署具备原子调度能力、持久化额度状态的目标 Runner Agent 前明确拒绝受管 Key，不静默降级；这不影响默认本机方案。
