> 本文扩展文件工作台的预览能力，并替换第 16 篇文档中“Prism 负责只读源码查看、CodeMirror 仅负责编辑”的决策。目录树、文件读写、workspace lease 和 SFTP 抽象维持不变。

## 1. 目标与边界

### 1.1 目标

在文件页面为下列文件提供与类型匹配的查看体验：

| 类型 | 目标体验 |
| --- | --- |
| Markdown | 渲染文档、表格、任务列表和项目内图片 |
| JSON / JSONC / JSON5 | 源码与可折叠结构树切换，显示解析错误 |
| SQL、Python、Java、Go 及其他源码 | 语法高亮、行号、搜索、折叠和只读浏览；进入编辑时保持同一语言能力 |
| SQLite（`.db`、`.sqlite`、`.sqlite3`） | 表/视图列表、表结构、分页数据，仅只读 |
| 图片 | 原尺寸约束内的图片预览 |
| 其他二进制文件 | 元信息和可用的下载能力 |

### 1.2 非目标

- 不构建完整 IDE，不引入 Monaco、code-server 或 LSP/IntelliSense。
- 不在文件页执行 SQL、脚本或数据库写入操作。
- 本方案不支持 SSH/SFTP 项目的 SQLite 数据预览。
- 不预览压缩包、Office、PDF、音视频等复杂二进制格式。

## 2. 当前实现与问题

### 2.1 已具备的能力

- `file-model.ts` 已能从扩展名识别 JSON、SQL、Python、Go、Java、Rust、YAML、XML 等语言。
- `FileViewer.tsx` 已将 Markdown、图片、二进制和普通文本分流；普通文本交给 `prism-react-renderer` 显示行号和语法高亮。
- `FileEditor.tsx` 会懒加载 CodeMirror，因此编辑器不影响初始页面加载。
- Go 控制服务已使用 `mattn/go-sqlite3` 管理应用自身的 SQLite 数据。

### 2.2 语言支持发生漂移

当前文件名识别、只读高亮和编辑器加载是三套独立映射。结果如下：

| 文件 | 查看态 | 编辑态 | 问题 |
| --- | --- | --- | --- |
| `.json`、`.py`、`.go` | Prism 已内置语法 | 已有 CodeMirror 语言包 | 基本可用，但没有结构化 JSON 预览 |
| `.sql` | Prism 已内置语法 | 没有 SQL 语言包 | 编辑退化为纯文本 |
| `.java` | 扩展名被识别，但 Prism 未内置 Java 语法 | 没有 Java 语言包 | 查看和编辑都退化为纯文本 |
| YAML、XML、Rust、C/C++ 等 | 部分 Prism 语法可用 | 没有对应语言包 | 查看和编辑体验不一致 |
| `.db`、`.sqlite` | 被判为二进制 | 不可编辑 | 只能显示元信息，无法浏览数据 |

继续为 Prism 逐个注册语言，会长期维护两套语法注册和两套测试矩阵；任何新增扩展名都可能再次出现“能识别、不能高亮”的问题。

### 2.3 二进制下载与大文件缺口

- 前端二进制信息页的“下载”链接使用 `/fs/raw`，但该端点只允许图片类型，数据库等二进制文件会收到 HTTP 415。
- 当前打开文件一律先请求 `/fs/read`。因此大于 10MB 的图片和数据库会在进入预览器前失败，不能依赖后续 `ImagePreview` 或 `SqliteViewer` 再解决该限制。
- 文件读取上限为 10MB；当前 Prism 逐行创建 DOM，接近上限的源码文件可能显著卡顿。
- 现有 1MB/10MB 大文件策略只记录在历史方案中，尚未成为预览路由的明确行为。

## 3. 方案决策

### 3.1 预览路由

文件页面按文件元信息和名称选择预览器，而不是将全部文件视为 Markdown 或普通代码：

```text
图片                         -> ImagePreview
Markdown（不含 MDX）          -> MarkdownPreview
SQLite 文件头 + 数据库扩展名   -> SqliteViewer
JSON / JSONC / JSON5          -> JsonViewer
其他文本文件                  -> CodeMirrorSourceViewer
其他二进制                    -> BinaryFileInfo
```

`CodeMirrorSourceViewer` 和编辑模式共享语言注册表、语言扩展加载器与基础配置；两者只在 `readOnly`、`editable` 和保存工具栏上不同。

文件打开流程必须先按文件名得出临时预览类别，再取得元信息，不能无条件读取完整内容：

```text
点击文件
  -> GET /fs/stat?path=
  -> 图片：直接使用 /fs/raw，不请求 /fs/read
  -> SQLite：请求 /fs/sqlite/tables，由服务端验证文件头，不请求 /fs/read
  -> 普通二进制：显示元信息和下载入口，不请求 /fs/read
  -> 源码 / JSON / Markdown：大小允许时请求 /fs/read，再进入对应预览器
```

因此 `OpenFile` 不能再假设所有标签都拥有 `content: string`。应改为按预览类别区分的联合状态；源码标签保存内容和版本，SQLite、图片、二进制标签只保存 `FileInfo` 与路径。这样数据库预览的独立大小上限和大图片预览才真正生效。

### 3.2 统一使用 CodeMirror 查看与编辑源码

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| Prism 查看 + CodeMirror 编辑 | 首屏最轻 | 两套语言能力，现已发生漂移 | 不再作为扩展方向 |
| **CodeMirror 只读 + 编辑共用** | 单一语言注册、搜索/折叠/行号一致、可按语言懒加载 | 首次打开源码需加载编辑器核心 | **推荐** |
| Shiki | 静态着色质量高、语言多 | 仍要与编辑器维护两套语言体系 | 不采用 |
| Monaco | IDE 能力完整 | 体积和复杂度过高 | 不采用 |

文件页本身就是主动查看源码的工作区。将 CodeMirror 核心在首次打开源码文件时懒加载，换取查看与编辑的一致性，优于继续保留轻量但不完整的 Prism 查看器。

### 3.3 语言注册表

前端新增唯一的语言定义模块，例如 `source-language.ts`：

```typescript
type SourceLanguage = {
  id: string;
  extensions: readonly string[];
  fileNames?: readonly string[];
  load: () => Promise<Extension>;
};
```

该模块负责扩展名/特殊文件名识别和 CodeMirror 语言包懒加载；`FileViewer`、`FileEditor`、文件图标和测试都从此处读取定义。后端仍保留独立的文本/二进制判断，不将前端语言名作为安全依据。

首批新增的官方 CodeMirror 语言包：

| 包 | 覆盖文件 |
| --- | --- |
| `@codemirror/lang-sql` | SQL |
| `@codemirror/lang-java` | Java |
| `@codemirror/lang-cpp` | C、C++、头文件 |
| `@codemirror/lang-rust` | Rust |
| `@codemirror/lang-yaml` | YAML |
| `@codemirror/lang-xml` | XML、SVG |
| `@codemirror/lang-markdown` | Markdown 源码编辑 |

Kotlin、Scala、Ruby、Shell 等没有合适官方语言包时，才通过 `@codemirror/legacy-modes` 补充；使用前应逐个验证折叠、缩进和高亮质量。没有语言扩展的文本仍可在 CodeMirror 中安全查看和编辑。

### 3.4 JSON 专用预览

`JsonViewer` 提供“结构”和“源码”两种模式：

- 默认保持源码模式，避免打开大 JSON 时立即解析和创建大量节点。
- 用户切到结构模式时才解析；对象/数组节点默认折叠，允许复制 JSON Path。
- `.json` 用 `JSON.parse`；`.jsonc` 使用 `jsonc-parser`；`.json5` 使用 `json5`，避免把注释和尾逗号误报为损坏文件。
- 解析失败显示行列错误并保留源码模式，绝不丢失或改写原始内容。
- 结构模式仅处理不超过 2MB 的文件；超过阈值保留源码模式，避免阻塞主线程和递归渲染大量节点。
- “格式化”仅改变预览字符串，不修改编辑缓冲区；文件写入仍须由用户进入编辑模式并保存。

所有键和值必须按 React 文本节点输出，禁止 `dangerouslySetInnerHTML`。

### 3.5 SQLite 专用预览

SQLite 不是文本文件，不能用语法高亮代替数据库浏览。本方案仅支持本地和 WSL 项目；SSH/SFTP 项目明确显示“暂不支持远程数据库预览”。

后端新增只读接口：

```text
GET /api/projects/{id}/fs/sqlite/tables?path=
GET /api/projects/{id}/fs/sqlite/schema?path=&table=
GET /api/projects/{id}/fs/sqlite/rows?path=&table=&limit=100&offset=0
```

建议响应：

```json
{
  "columns": ["id", "name"],
  "rows": [[{"kind": "number", "value": 1}, {"kind": "text", "value": "Ada"}]],
  "limit": 100,
  "offset": 0,
  "hasMore": true
}
```

单元格使用显式类型避免 SQLite 的 `NULL`、文本、数值和 BLOB 在 JSON 中混淆。BLOB 只返回固定长度的 Base64 摘要及原始长度，不返回完整内容。

实现约束：

- 同时校验扩展名和 `SQLite format 3\u0000` 文件头，不能只信任扩展名。
- 前端仅凭 `.db`、`.sqlite`、`.sqlite3` 选择 SQLite 请求路径；服务端校验失败时返回可区分的“不是 SQLite 文件”状态，前端退回二进制信息页。
- 必须先通过既有 `Filesystem` 路径校验，再解析本地绝对路径；接口不得接受操作系统原始路径。
- 使用 SQLite 只读连接（`mode=ro`），连接后设置 `PRAGMA query_only=ON`；不使用 `immutable=1`，以免忽略仍在使用的 WAL 数据。
- 每次请求使用独立短生命周期连接，`SetMaxOpenConns(1)`，并通过 `context.WithTimeout` 限制查询时间。
- 表名和视图名只能从已枚举的 schema 对象中选择；标识符由服务端安全引用。不提供任意 SQL 查询接口，也不允许 `ATTACH`、写入或 DDL。
- 行数固定上限 100，限制响应体和单元格文本长度；默认不执行全表 `COUNT(*)`，避免大表打开即产生重查询。
- 数据库文件预览上限独立配置，建议默认 64MB；此上限不复用文本读取的 10MB 限制，因为服务端按页读取数据而非将整个数据库传到浏览器。

远程数据库支持需要同时获取主文件、`-wal` 和 `-shm` 的一致快照，或在远程机器运行受控查询服务；否则可能读取到不一致数据。因此不能简单把远程 `.db` 下载到临时目录后打开。

### 3.6 二进制下载

保留 `/fs/raw` 作为图片内联预览端点，并新增：

```text
GET /api/projects/{id}/fs/download?path=
```

下载端点应通过受路径沙箱保护的流式读取实现，设置安全的 `Content-Disposition: attachment` 文件名。它不能复用将完整文件读入内存的 `/fs/read`，否则大于 10MB 的二进制文件仍无法下载。现有 `/fs/raw` 图片端点也必须改为同一流式读取能力；仅在前端避开 `/fs/read` 仍不足以解决大图片预览。

`Filesystem` 需要新增面向下载的流式读取能力，例如 `OpenRead(ctx, path) (io.ReadCloser, FileInfo, error)`；本地实现以 `os.Open` 返回受校验路径的文件，SFTP 实现返回远程文件流。handler 使用 `io.Copy` 写入响应并始终关闭流，不将文件编码为 Base64 或累计在内存中。

## 4. 性能与容量策略

| 文件类别 | 大小 | 行为 |
| --- | --- | --- |
| 源码、配置、SQL | ≤ 1MB | 正常 CodeMirror 源码查看/编辑 |
| 源码、配置、SQL | 1MB - 10MB | 只读 CodeMirror 查看；禁用 JSON 结构模式和自动格式化 |
| 文本 | > 10MB | 显示元信息和下载，不读取内容 |
| JSON 结构模式 | ≤ 2MB | 按需解析、默认折叠节点 |
| SQLite（本地/WSL） | ≤ 配置上限 | 后端按页查询，不将整个文件传到浏览器 |
| 图片 | 不经 `/fs/read` | 通过流式 `/fs/raw` 在原尺寸约束下预览 |
| 其他二进制 | 任意 | 元信息与流式下载 |

`JsonViewer`、`SqliteViewer` 和各语言扩展均使用动态导入。查看器切换文件时必须取消未完成请求，避免 SFTP 延迟或快速切换标签导致旧响应覆盖当前标签。

## 5. 安全要求

| 风险 | 处理方式 |
| --- | --- |
| 路径穿越 | 所有新增接口复用本地 `resolvePath` 或远程根路径校验 |
| SQLite 写入/注入 | 只读连接、白名单表名、分页固定查询，不开放通用 SQL |
| Markdown / JSON XSS | Markdown 继续 `skipHtml`；JSON 仅渲染文本节点 |
| 大文件、深层 JSON | 服务端大小限制、结构模式 2MB 阈值、默认折叠 |
| 响应过大 | SQLite 行数、字段长度和查询超时限制 |
| 下载响应注入 | 清理 `Content-Disposition` 文件名，不信任路径中的换行或引号 |
| SQLite WAL 一致性 | 本地只读连接可读取当前状态；远程预览延后，不能复制单一主文件 |

## 6. 一期完整实施范围

以下内容作为一个完整版本交付，不拆分为多期上线；开发中可以按依赖顺序编写，但只有全部验收项通过后才视为本方案完成。

| 工作项 | 一期完成标准 |
| --- | --- |
| 预览路由与标签状态 | 先获取 `stat`，再按类型加载；图片、SQLite 和二进制不触发 `/fs/read`；标签状态支持无文本内容的预览类型 |
| 通用源码查看与编辑 | 提取唯一语言注册表；只读 CodeMirror 替换普通文本 Prism 查看；SQL、Java、C/C++、Rust、YAML、XML、Markdown 等语言包按需加载 |
| JSON 预览 | 支持 JSON、JSONC、JSON5 的源码/结构切换、错误回退、2MB 阈值和安全文本渲染 |
| SQLite 预览 | 本地/WSL 支持列出表/视图、查看 schema 和分页数据；完成文件头、只读、超时、行数、字段与 BLOB 限制 |
| 下载与大文件 | 新增本地/SFTP 通用流式下载；图片原始预览不受文本读取上限阻塞；落实 1MB、2MB、10MB 策略 |
| 测试与浏览器验证 | 本节全部单元、后端和桌面/移动浏览器验收项通过 |

SSH/SFTP 的 SQLite 预览、CSV/TSV、TOML、PDF 等格式不属于本方案的承诺范围；它们不会阻塞一期完成，也不会以半成品入口暴露给用户。

## 7. 验收与测试

### 7.1 前端单元测试

- 语言注册表覆盖 `.sql`、`.java`、`.py`、`.go`、`.json`、`.yaml` 和特殊文件名。
- 只读和编辑模式针对同一文件得到同一语言扩展。
- JSON、JSONC、JSON5 的合法、非法、超限和深层嵌套输入均有预期回退。
- 二进制文件显示下载入口；图片仍走 `/fs/raw`。

### 7.2 后端测试

- `/fs/download` 对文本、二进制、超大文件和非法路径的响应正确。
- 打开超大图片或 SQLite 文件时，不发生 `/fs/read` 请求；SQLite 元信息接口仍可成功响应。
- 临时 SQLite 文件可列出表、读取 schema、分页读取数据。
- 损坏文件头、伪造 `.db` 扩展名、未知表名、超限 `limit`、BLOB 超限和路径穿越均被拒绝。
- SQLite 预览不改变数据库内容，接口不接受写入或任意 SQL。
- SSH 项目访问 SQLite 接口返回明确的不支持状态，而不是静默下载或 500。

### 7.3 浏览器验证

- 桌面和移动视口分别打开 Markdown、JSON、SQL、Java、Go 和 SQLite 文件。
- 验证 JSON 结构折叠、源码切换、无效 JSON 回退、源码搜索和编辑保存。
- 验证 SQLite 表切换、分页、空值/二进制单元格显示及错误状态。
- 验证 1MB、2MB、10MB 边界文件不会使页面失去响应。

## 9. 最终决策

文件预览采用“一个通用源码引擎，三个专用预览器”的结构：

```text
Markdown -> ReactMarkdown
JSON     -> JsonViewer
源码     -> CodeMirror（只读 / 编辑共用）
SQLite   -> SqliteViewer + Go 只读接口
图片     -> ImagePreview
二进制   -> 元信息 + 下载
```

该结构消除源码查看与编辑的语言支持漂移，同时将结构化数据和数据库作为各自独立的安全边界处理，适合当前以 AI 辅助开发为核心、但不追求完整 IDE 的产品定位。

本文第 6 节列出的所有能力均为一期一次性交付范围；不再采用按功能拆分多期上线的安排。
