# 49-运行状态卡死与状态广播修复

> 日期：2026-10-27
> 背景：桌面端出现两类状态错误 ——「对话实际已经结束，界面仍显示运行中」与「已经开始运行，总览页仍显示已就绪」，
> 对话页与项目总览页会同时出错。本文记录真机证据、根因与修复后的契约。

## 1. 现象与真机证据

在用户本机的 `milevia.db`（只读查询）里，201 条 run 中有 170 条带 `turn.completed`，其中 **3 条在回合结束后继续「运行」**：

| run | 回合完成 `turn.completed` | `runs.status` 转终态 | 多显示运行 | 收尾方式 |
| --- | --- | --- | --- | --- |
| `b96892e2` | 10-12 06:51:50 | 10:29:32 | ~3 小时 38 分 | 控制服务重启（interrupted） |
| `b47c9801` | 10-26 10:40:16 | 13:35:19 | **2 小时 55 分** | 用户点「停止」（stopped） |
| `bb815c21` | 10-26 09:09:42 | 10:00:40 | ~51 分钟 | 控制服务重启（interrupted） |

三条都是 Codex（`agent_id=codex`）。卡住期间 `conversations.status` 一直是 `running`，于是总览页的「正在执行」、
对话页的运行指示与停止按钮同时亮着；`b47c9801` 那一轮的工具调用还起了 `API 23012 / Frontend 23032 / Collector 23200` 三个长驻服务。

反方向的证据：`run.completed` 事件在事务提交之后才广播，而生成回退快照排在两者之间。实测「提交 → 广播」的间隔为
**75.4 / 39.1 / 23.4 / 7.6 秒**（快照是磁盘活），这段时间总览页已经是空闲、对话页还在运行中。

## 2. 根因

### 2.1 运行的终态被绑在「输出管道 EOF」上

一次性 CLI 运行的收尾是 `wg.Wait()`（等 stdout/stderr 的 reader 结束）→ `cmd.Wait()` → `finishRun`。
只要有一个**后裔进程**还握着 stdout/stderr 的写端（`npm run dev`、playwright、后台 shell、setsid 的子进程都会这样），
reader 就永远等不到 EOF：`Run` 不返回，`finishRun` 不被调用，`runs.status` 与 `conversations.status` 一起停在 `running`。

主进程被杀掉也没用 —— 管道写端在别人手里。探针那条路径早就踩过同一个坑并写下了结论（见 `probe_job_windows.go` 的注释），
但 agent 运行路径还在用「按 PID 快照遍历父子关系」的 `terminateProcessGroup`：中间进程被回收后，它下面的孤儿进程再也挂不回根 PID。

### 2.2 一次性运行没有运行级超时

流式 Claude 会话有初始响应 / 回合空闲 / 工具结果三档超时，而 Codex / Cursor / OpenCode / WSL / SSH 这些一次性运行
**一条都没有**：CLI 卡住（既不输出、也不退出、也不报错）就是永久 `running`，只能重启控制服务。

### 2.3 运行起止不广播状态失效事件

`/api/projects/statuses` 按 `conversations.status` 聚合「正在执行」，是总览页与项目页的唯一来源。
但运行开始与结束从来不发 `stEvProjects`，页面只能靠 30 秒兜底轮询（对话页的 tab 运行点靠 8 秒轮询）。
于是「刚开始跑」「刚跑完」都要错最多半分钟，短任务甚至整个生命周期都不会被显示成「正在执行」。

### 2.4 前端在 WS 放弃重连时清空运行态

`ConversationPage` 的 WS 重连达到上限后直接 `setRun("")`，后端可能还在跑 —— 停止按钮消失、页面显示成空闲，
用户除了刷新没有别的办法。

## 3. 修复后的契约

| 关注点 | 契约 | 实现 |
| --- | --- | --- |
| 终态判据 | 终结事件（`result` / `turn.completed`）或进程退出，先到者为准；终结事件只是一轮答完，**不等于进程已退出** | `watchAgentProcess`（`agent_process.go`） |
| 收尾上界 | 终结事件到达后**先等进程自然退出**（最多 `agentProcessTeardownGrace`，5s）；仍不退出才结束进程树，再等一个宽限仍未收敛就强杀并**关闭输出读端**。自然退出路径仍补一次进程组回收（POSIX 裸 exec 路径；容器托管命令已由 cgroup 收尾处理，Windows 由 Job Object 兜底） | 同上 + `reapProcessGroupAfterExit` |
| 成功结果优先 | CLI 已给出成功终结 `result`（`is_error:false`）时，之后进程以非零码退出、容器收尾告警与 SSH 通道收尾错误都不再判失败——与 Codex「turn.completed 即结果」同口径；取消仍如实报错，夹带租约/工作区治理类错误（`ErrAuthority` / `ErrConflict` / `ErrProtocol`）仍判失败 | `claudeResultErrorSink.resultSucceeded` + `claudeRunExitSucceeded` + `claudeGovernanceFailure` |
| SSH 一次性 Claude | 与本地/WSL 同口径：`result` 到达后先等远端自然退出（宽限内），仍不收敛就 SIGKILL 并关闭通道；成功结果已到则按成功收尾 | `ssh_runner.go` 的 `terminal` 分支 |
| 孤儿回收 | 本地**一次性**运行把进程树放进 `KILL_ON_JOB_CLOSE` 的 Job Object，句柄关闭整组结束（流式 Claude 会话走自己的退出宽限期，未改） | `containAgentProcess`（复用 `probeProcessJob`） |
| 卡死兜底 | 一次性运行连续 30 分钟没有任何事件 → 取消并按失败收尾，错误文案「Agent 长时间没有输出，已自动停止，请重试」 | `agentRunIdleWatchdog` + `AUTO_AGENT_RUN_IDLE_TIMEOUT` |
| 广播顺序 | 事务提交后立刻广播 `stEvProjects`；回退快照仍排在 `run.<status>` 之前（对话页收到终态会重拉节点列表） | `finishRun` / `startMessage` |
| 前端 | 断连不再清空 `run`，一律以 `activeRunId` 为准 | `ConversationPage` WS `onclose` |

要点：**业务状态不许由管道关闭的时机决定**。管道只是传输；终结事件与进程退出才是事实。
收尾上界是兜底，不是主路径 —— 正常运行时 reader 先结束，一毫秒都不多等。

附带后果（有意为之）：Job 句柄随控制服务进程一起销毁，所以控制服务崩溃/被重启时，本机正在跑的 CLI 会
一起结束，而不是变成"界面已经不在跑、机器上还在改文件"的孤儿。重启后的 `recoverInterruptedRuns` 照旧把这些
运行标成 interrupted。

## 4. 为什么不在终结事件到达时立即 finishRun

`usage.updated` 常常在 `turn.completed` 之后几毫秒到一秒才到（`b47c9801`：`.386` 收 turn.completed，`.391` 收 usage.updated）。
立即结束会丢掉这一轮最后的 token 统计。正确做法是「终态事件 + 有界等待」：正常路径照常收尾，异常路径有上界。

## 5. 为什么不把状态改成「快照之后才广播」的另一套顺序

对话页收到 `run.<status>` 会立刻重拉回退节点列表。快照若排在事件之后，刚跑完的那一轮就会从回退入口里消失（新会话甚至会让入口变灰）。
所以「先广播终态、再生成快照」是错的；正确的分工是：**事务提交后立刻广播 `stEvProjects`（卡片用），快照之后再发 `run.<status>`（对话页用）**。

代价要说清楚：`run.<status>` 仍会被快照推迟几秒到几十秒。这段窗口由对话页自己的两条兜底轮询封顶 —— 运行态 15 秒
（`ConversationPage` 的 `poll`，不依赖 `run` 是否为空）、tab 运行点 8 秒（会话目录轮询）。总览页则在同一提交后立刻收敛。

## 6. 测试

### 6.1 2026-11-04 回归：终结事件上立即杀进程

v0.1.14 的 `watchAgentProcessWithin` 在收到终结事件时**立刻** `terminateProcessGroup`。但 claude 打出
`result` 之后还要约 0.55 秒才真正退出（实测 2.1.266 / 2.1.316 一致；这 0.55s 用于刷转录、发遥测）。
在 Windows 上 CLI 是 `.cmd` shim，杀掉 cmd.exe 后 `cmd.Wait()` 返回 `exit status 1`，于是每一次
**已经成功产出结果**的本地一次性运行（优化建议扫描/复核、编排独立审查）都被报成
`Claude 运行失败：exit status 1`，结构化结果被丢弃。

2026-11-09 在 v0.1.14 源码上用假 CLI 做了不依赖模型的确定性复现：脚本先输出成功的 `result`，
再延迟收尾并 `exit 0`；旧代码仍在 `result` 之后立刻杀进程，`Run` 返回与线上逐字一致的
`Claude 运行失败：exit status 1`，收尾标记文件不存在；同一脚本在当前实现上通过且标记文件写出。

修复分三层，缺一不可：

1. `watchAgentProcessWithin`：终结事件后先给一个自然退出窗口，窗口内 `done` 关闭就补一次进程组回收后返回；
   超时才进入原来的"强杀 → 等宽限 → 关读端"流程。用户取消仍立即回收。POSIX 没有 Job Object，
   裸 exec 路径的自然退出必须补 `reapProcessGroupAfterExit`，否则 setsid 后不再握着管道的后裔会活过
   本次运行；容器托管命令由收尾 goroutine 的 cgroup terminate 负责，reap 不再重复停一次。
2. `claudeResultErrorSink` 记录成功的终结 `result`；本地 Run / WSL `runClaudeOnce` / SSH 一次性
   Claude 在成功 `result` 已完整到达、且未取消时按成功收尾（共用 `claudeRunExitSucceeded`）。该判定
   必须排在失败详情/流错误之前——成功收尾时 stderr 仍可能有告警行，结果之后 SSH 通道重置也不代表
   这次运行没跑完。成功帧会清掉先前记录的失败原因，避免旧失败原因被拼进后续错误。
   收尾错误里 join 的工作区治理类失败（`ErrAuthority` / `ErrConflict` / `ErrProtocol`）**不豁免**：
   租约失效、身份冲突、协议错误说明这次运行的授权事实已不可信，结果不能按成功采信
   （见 `claudeGovernanceFailure`，`errors.Is` 穿透容器收尾与 fmt 包装）。
3. SSH 一次性 Claude 补上终结信号：`result` 后先等远端自然退出（宽限内），仍不收敛才 SIGKILL
   并关闭通道。此前远端后裔握着 stdout 时只能等用户取消（本地/WSL 早有上界）。
4. `terminalSignalSink` 同步转发 `assistantMessageIDSetter` / `assistantDeltaSink`：`readOutput` /
   `readClaudeJSONLines` 会对 sink 做可选接口断言，不转发会让增量输出与 assistant message id 被静默吞掉
   （SSH 新增这层包装，本地/WSL 早已在链路上）。

## 7. 与 docs/39 的关系

docs/39 §4 写的是「Codex 走一次性 `Run`，进程退出即回合结束，不存在这个问题」。
这句话对**回合语义**成立，对**运行收敛**不成立：进程退出不等于 reader 收敛，而运行状态是等 reader 的。详见本文 §2.1。
