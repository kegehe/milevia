## 一、已核实成立

### 1. 发版脚本不写 Android 版本号（高）

- `scripts/release.mjs` 只同步三处桌面版本（`tauri.conf.json` / `Cargo.toml` / `desktop/package.json`，第 48–89 行）；第 52 行的 `androidDir` 仅用于 `cwd` 和取产物路径，脚本内**没有任何** `versionCode` / `versionName` 写入。
- 直接读已发布包的实证（`aapt2 dump badging release/Milevia_0.1.5_android.apk`）：

  ```
  package: name='info.keyanjia.milevia' versionCode='2' versionName='0.1.4'
  ```

- 真实影响（修正）：`versionCode` 相同且签名相同时**仍可覆盖安装**，所以"装不上"不成立。问题是：
  1. 包内版本（0.1.4）与对外文件名（0.1.5）不一致，任何读包内版本做判断的逻辑都会错；
  2. `versionCode` 不递增 → Google Play 不会接受为更新；
  3. 版本号只能靠手工改 `app/build.gradle` 维护，极易漏。
- 修法：与桌面三处一起递增 `versionCode`、写入 `versionName`。

### 2. 分发的是 debug 包（高）

- `release.mjs` 第 139 行执行 `gradlew.bat assembleDebug`，第 145 行取 `app/build/outputs/apk/debug/app-debug.apk`；`app/build/outputs` 下**只有** `apk/debug`，无 release 产物；`build.gradle` 无 `signingConfigs`，仓库内也没有任何 `.jks`/`.keystore`。
- APK 最终 Manifest 实证：`android:debuggable(0x0101000f)=true`。
- `release-notes.md` 第 49 行亦自述使用本机 debug 签名。
- 影响：不可上架；debuggable=true 有性能与安全代价；将来换正式 keystore 后，已装的 debug 版**无法覆盖升级**，必须卸载重装。

### 3. 通知能力在 APK 内不可用（高）

- APK 最终 Manifest 里的权限只有：`INTERNET`、`CAMERA`、`ACCESS_NETWORK_STATE`、`DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION`——**没有 `POST_NOTIFICATIONS`**。
- `capacitor.plugins.json` 只注册 `@capacitor-mlkit/barcode-scanning` 与 `@capacitor/app`，没有任何推送/本地通知插件。
- MDN 兼容表明确标注：`Notification.permission` 在 **WebView Android = 不支持**（即 `window.Notification` 为 `undefined`）。
- 代码后果：`MobileRemotePage.tsx` 第 336 行 `typeof Notification === "undefined" → "unsupported"`；第 1483 行 `notificationPermission === "default" && <开启通知>` 永不渲染；第 760 行 `notifyHiddenMobileEvent()` 永远 return。
- 与设计文档《32-移动端App与云端远程控制终极方案》phase 4「推送通知」未落地一致，但 UI 预留了入口，容易误以为可用。

### 4. 物理返回键失效（高，症状已更正）

- 全项目无 `App.addListener("backButton")`；`CapacitorApp` 只用于 `minimizeApp()`（第 1474 行）。
- 原生包在 `App.tsx` 第 60/67 行整体替换为 `MobileRemotePage`，单路由、`canGoBack()` 恒为 false。
- Capacitor `AppPlugin.java` 第 46–62 行的默认实现：

  ```java
  this.onBackPressedCallback = new OnBackPressedCallback(!disableBackButtonHandler) {  // 默认 true
      public void handleOnBackPressed() {
          if (!hasListeners(EVENT_BACK_BUTTON)) {
              if (bridge.getWebView().canGoBack()) bridge.getWebView().goBack();
          } else { /* 派发给 JS */ }
      }
  };
  ```

- 结论（更正）：无监听 + 无法回退时，该回调**什么也不做但会吞掉事件**，因此返回键变成**「无操作」**——既不回项目列表，也不退出应用。（初版写成"会直接退出 App"是错的。）
- 修法：注册 `backButton`，按 `mobileView` / `tasksOpen` / 弹窗状态分层返回，最外层再 `minimizeApp()`。

### 5. 云端令牌存 localStorage，且随系统备份（中）

- `MobileRemotePage.tsx` 第 229 / 246 / 313 / 882 行读写 `localStorage.milevia.cloud.token`。
- APK 最终 Manifest 实证：`android:allowBackup(0x01010280)=true`。
- 影响：长时令牌未进系统安全存储，且会进入 adb / 云备份。设计文档 6.2 要求 Refresh Token 存系统安全存储（对应 OWASP MASVS），实现与该要求不符。

### 6. `custom_url_scheme` 只声明未接线（低，配置冗余）

- `res/values/strings.xml` 第 6 行声明了 `custom_url_scheme`。
- APK 最终 Manifest 中 `MainActivity` 的 intent-filter 只有 `MAIN` + `LAUNCHER`，**没有 `<data android:scheme=...>`**。
- 且 `@capacitor/android` 的 Java 源码里完全不引用 `custom_url_scheme`（Capacitor 不会自动接线，需手写 intent-filter）。
- 影响：仅「预留未启用」，当前没有依赖深链的功能，属清理项。

### 7. 页面头部没有顶部安全区处理（中，带前置条件）

- Capacitor 8 `SystemBars.java` 第 200 行：

  ```java
  boolean shouldPassthroughInsets = getWebViewMajorVersion() >= WEBVIEW_VERSION_WITH_SAFE_AREA_FIX /* 140 */ && hasViewportCover;
  ```

  第 206–223 行在该分支下**只给 WebView 加 IME 的底部 padding**，顶部完全铺开，仅注入 `--safe-area-inset-*` 并依赖 WebView 自己暴露 `env(safe-area-inset-*)`；默认 `insetsHandling = "css"`（第 37/58/99 行）。
- `index.html` 含 `viewport-fit=cover` → `hasViewportCover = true`。故 **WebView ≥ 140 时页面真正全屏铺开**。
- 而全项目 `env(safe-area-inset-top)` **只出现在一处**：`mobile-remote.css` 第 79 行 `.mobile-task-drawer`。页面 header 只有 `.mobile-remote { padding: 24px ... }`，≤620px 时降为 `18px 12px`（第 43 行）。
- 结论：在 WebView ≥ 140 的设备上，状态栏/挖孔会压住标题与品牌标识。WebView < 140 时 Capacitor 改走原生 padding 分支，不会重叠。
- 修法：header 加 `padding-top: max(18px, env(safe-area-inset-top))`。

### 8. 消息列表不自动滚动（中）

- 全文件 grep `scroll|scrollTop|scrollIntoView` 只命中第 1077 行的 `input.scrollHeight`（输入框自增高），**没有任何列表滚动控制**。
- `.mobile-message-list` 也没有做成独立的内部滚动容器，靠整页滚动。
- 影响：发出消息或 Agent 回复到达后，视口不跟随，用户必须手动下滑才能看到新内容。

### 9. 后台轮询不随页面可见性暂停（中，范围已收窄）

- 常驻不暂停的三项：第 796 行 `setInterval(loadInstances, 5000)`、第 811 行 `setInterval(loadSnapshot, 15_000)`、以及第 826 行起的 SSE 长连接（断线按 1s→30s 退避重连）。
- 全文件无 `visibilitychange` / `useDocumentVisible`（`lib/useDocumentVisible.ts` 存在但此处未用）。
- 更正：命令状态轮询（5s）、手机等待确认（1.5s）、桌面确认轮询（2s）都是**有条件的**，随操作结束而清理，不计入本条。

## 二、核查更正（初版误判，已撤回）

### ❌ 更正：扫码链路并非「无问题」（2026-09-14 实测推翻，已修）

初版把「扫码链路」列进"已核实不是问题"，依据是 **meta-data / CAMERA 权限 / 权限拒绝文案都在** ——
这三条本身没错，但它们只覆盖了"相机能不能启动"，**完全没覆盖"画面能不能被看见"**，而后者才是
用户报的「摄像头起不来」：

- `@capacitor-mlkit/barcode-scanning` 的 `startScan()` 把 CameraX 的 `PreviewView` 插到
  **WebView 之下**（`BarcodeScanner.java`：`((ViewGroup) webView.getParent()).addView(previewView, 0)`），
  并自己把 WebView 底色改成透明。也就是说**相机一直在正常运行**，能不能看见只取决于
  WebView 之上每一层 DOM 的背景透明度。
- `style.css` 的 `:root { background: #f3f8f4 }` 给根元素铺了一层不透明画布底色，
  而旧 CSS 只清了 `body` / `#root` / `.mobile-remote`，**从没清 `<html>`** → 整块画面被盖住。
- 取证：`.tmp/probe-scan-overlay.mjs` 的计算样式 A/B（把清底规则换回旧写法，`documentElement`
  背景恒为 `rgb(243,248,244)`，同一时刻 body/#root 已是 `rgba(0,0,0,0)`）；
  以及像素 A/B（页面放进透明 iframe、底下铺"摄像头"）：旧 CSS 取景窗中心 `[243,248,244]`，
  新 CSS `[59,120,100]`。修前/修后图 `.tmp/scan-overlay-native-before-390.png` /
  `.tmp/scan-overlay-native-after-390.png`。
- 同一轮还查出三个真缺陷：① 遮罩原来是**铺满屏的深色块**，它本身也盖画面；② 报错提示挂在
  配对面板里，而扫码期间那块整块 `visibility: hidden` —— 报错从来没被看见过；③ 侧滑返回
  （`leaveConversationView`）不收取景层，会带着 `position: fixed` 的浮层退回项目列表、摄像头一直开着。

**方法论教训**（比结论更重要）：这一条初版是**静态审查**的产物 —— 把"依赖/权限/文案都在"当成了
"功能可用"。凡涉及"用户能不能看见/点得到"的结论，都必须有**运行时证据**（计算样式、像素、DOM 状态），
不能只来自"代码里都写了"。

### ❌ 撤回：`colors.xml` 缺失导致构建失败

**实际不存在此问题。** 跑 `:app:processDebugResources --rerun-tasks`（强制重新 merge 资源）结果为 **BUILD SUCCESSFUL in 57s**。

那三个颜色的真实来源是 Capacitor 自身的库：

```
node_modules/.pnpm/@capacitor+android@8.5.1_@capacitor+core@8.5.1/
  node_modules/@capacitor/android/capacitor/src/main/res/values/colors.xml
    <color tools:ignore="UnusedResources" name="colorPrimary">#3F51B5</color>
    <color tools:ignore="UnusedResources" name="colorPrimaryDark">#303F9F</color>
    <color tools:ignore="UnusedResources" name="colorAccent">#FF4081</color>
```

我判错的原因：`node_modules/@capacitor/...` 是 pnpm 创建的**符号链接**，前两次 grep 没有跟进 `.pnpm` 实体目录，于是误以为「仓库和依赖里都没有」。

附带更正：那三个色确实是模板默认靛蓝，但使用它的 `AppTheme`（parent `Theme.AppCompat.Light.DarkActionBar`）并不在 Activity 实际主题链上（Activity 用 `AppTheme.NoActionBarLaunch` → `Theme.SplashScreen`），所以**没有可见影响**，只是主题配置里的一段冗余。

### ❌ 撤回：http 二维码与 Android 明文策略冲突

**实际不影响配对。** 手机从不加载二维码里的 URL：`acceptScannedPairing()` → `pairingFromScan()` 只用 `new URL(value)` 取 `pairingId` / `code` 两个查询参数；随后 `claimPairing()` 调的是 `cloud()` → `${cloudURL}/v1/pairings/...`（`cloudURL` 固定为 `https://keyanjia.info:8443`）。所以 QR 用 http 还是 https 与手机能否连上无关。`pairingURLWithCode()` 放行 `http:` 只是一段用不到的宽松判断，属代码整洁性问题。

## 三、待真机确认（无法从代码定论）

1. **第 7 条顶部安全区**需在 WebView ≥ 140 的真机上确认重叠程度（取决于状态栏高度与是否挖孔）。
2. **PWA 图标**：`public/manifest.webmanifest` 只声明了 1 个 `sizes:"any"` 的 SVG。web.dev 官方说明要求 Chromium 至少提供 192×192 与 512×512 的图标，并建议「为不支持 SVG 的浏览器提供光栅兜底」。当前声明不满足该建议，**是否影响「添加到主屏幕」横幅需在目标浏览器实测**，不宜直接判定为缺陷。
3. **键盘弹出**：Manifest 已有 `adjustResize`，且 `SystemBars.java` 第 208 行在键盘弹出时会补底部 padding，基础可用；无 `visualViewport` 兜底在个别机型上可能跳动，需实测。
4. **横屏**：`MainActivity` 未锁定方向，横屏下会落到 820px 档位布局，未验证。

## 七、启动页素材修复（2026-09-12）

### 症状

点开 App 先看到一个蓝底白色"扳手"图标，与 Milevia 没有任何关系。

### 根因

`AppTheme.NoActionBarLaunch` 的写法（`parent="Theme.SplashScreen"` + `android:background`）
本身没错 —— §13 当初正是据此把它判为"不是问题"的。漏掉的是 `@drawable/splash` 指向的
**素材**：

- `drawable/splash.png`、`drawable-land-*/splash.png` ×5、`drawable-port-*/splash.png` ×5
  —— 11 个文件全是 Capacitor 脚手架默认的蓝白图，从未替换。
- 桌面图标 `mipmap-*/ic_launcher.png` 反而是品牌图，所以表现为「图标对、启动页错」。

另有一处叠加问题：Android 12+ 走的是系统 SplashScreen API，它**不读 `android:background`**，
而 `windowSplashScreenBackground` / `windowSplashScreenAnimatedIcon` 都没配，系统于是退回
「白底 + 应用图标」。结果是低版本看到蓝白图、高版本看到白底图标，同一台手机上两套表现。

### 改法

| 文件 | 变化 |
|---|---|
| `res/values/colors.xml` | 新增，`launch_background = #f3f8f4`（刻意与首屏 `.mobile-remote` 的 background 同色） |
| `res/drawable/launch_mark.xml` | 新增，品牌 M 矢量，固有尺寸 128dp，内容占 64/96 以适配圆形遮罩 |
| `res/drawable/launch_screen.xml` | 新增，layer-list：品牌底色 + `gravity="center"` 的标记（不用位图，避免按屏幕比例拉伸） |
| `res/values/styles.xml` | `android:background` 改指 `launch_screen`；补 `windowSplashScreenBackground`、`windowSplashScreenAnimatedIcon`、`postSplashScreenTheme` |
| `res/drawable*/splash.png` ×11 | 删除 |
| `res/mipmap-anydpi-v26/` | 新增 `ic_launcher.xml` / `ic_launcher_round.xml`，真正启用自适应图标 |
| `res/drawable-v24/ic_launcher_foreground.xml` | 坐标按安全区收缩 |
| `res/drawable/ic_launcher_background.xml` | 删除（青色网格图，无任何引用） |
| `res/mipmap-*/ic_launcher_foreground.png` ×5 | 删除（无引用，尺寸也不符合安全区） |
| `MainActivity.java` | 覆写 `onCreate`：用 `androidx.core.splashscreen` 给启动页加 220ms 淡出，并把 WebView 底色设成 `launch_background` |

**关于 WebView 底色**：WebView 在解析到 `body` 的背景之前用的是系统默认白，而启动页与
首屏都是 `#f3f8f4`，两者相差可见 —— 不设这一项，启动页淡出的瞬间会露出白底。Capacitor
本身支持用 `capacitor.config.ts` 的 `android.backgroundColor` 配（`Bridge.java` 里读取并
调用 `setBackgroundColor`），但那条路径要等 `cap sync` 才进包；改在 `MainActivity` 里能立刻
生效，也和启动页其它处理放在同一处。

**关于图标坐标收缩**：108×108 画布上系统只在中间 72×72 展示内容，圆形遮罩机型更严格 ——
可见区就是直径 72 的内切圆。原来 M 的含描边范围是 72×60、圆角点在 x16..88 / y24..84，
超出半径 36 的安全圆；实测 x=22 处可见 y 仅 37.5..70.5，而笔画本身要到 30..78，**两端被削平**。
现改为 54×45，四角到中心约 35.1，稳定落在圆内。`logs/splash-launch-and-icon-compare.png` 有前后对照。

### 为什么没有使用 `@capacitor/splash-screen`

它的 `showOnLaunch()` 在 `installSplashScreen()` 之后挂了一个持续返回 `false` 的
`OnPreDrawListener`，**阻止首屏绘制直到 `launchShowDuration` 走完**（默认 500ms）——
等于强制启动页多停一段固定时间，启动反而更慢。我们要的只是淡出，而
`androidx.core:core-splashscreen` 本来就在 `app/build.gradle` 的依赖里，直接调它的
`setOnExitAnimationListener` 即可，不必引入额外插件。另外注意：`installSplashScreen()`
必须在 `super.onCreate()` **之前**调用，否则在 Android 12+ 上不生效。

### 第三轮复检（2026-09-13）

**① 高低版本的标记大小差 2.3 倍（本次修复）**

| 版本 | 渲染路径 | 标记占屏宽（Pixel 5 / 393dp） |
|---|---|---|
| Android 12+ | 系统把 `launch_mark` **缩放填满 288dp 容器** | 47.1%（≈193dp） |

## 八、项目列表卡片重做（2026-09-13）

**由来**：用户反馈手机端「选择项目」的卡片不好看。逐项量过之后，"不好看"其实是四个可指认的问题：

| # | 症状（改造前实测） | 根因 |
|---|---|---|
| 1 | 「运行中」胶囊比「未运行」高 8px（26.3 vs 20.3） | 胶囊带裸类名 `running`，被 `style.css` 里全局的 `.ready, .running { padding: 6px 9px }` 命中 |
| 2 | 同一张卡在不同卡片间量到 72 / 77.3 两个高度 | `.mobile-project-choice small` 继承了全局行高，没显式写 `line-height` |
| 3 | 右侧 `N 个会话` 占着"操作位"，还跟着一个 `b::after` 拼出来的箭头 | 会话数与"前进"这个动作没有任何关系，读数被带偏 |
| 4 | `min-height: 88px` + 垂直居中，1 行名字的卡片下方多出一条空白带 | 内容实际只有 64px，钉死 88px 必然多出 16px |

**改法**（`MobileRemotePage.tsx` 第 2134 行 + `mobile-remote.css`）：

- 卡片改成三列 grid `auto minmax(0, 1fr) auto` = [环境图标块] [内容] [`›` 真元素]。
  内容列写 `minmax(0, 1fr)` 是承重的：`auto` 轨道会按最长那条内容的 min-content 撑开，
  把箭头挤出卡片，再被 `.mobile-remote` 的 `overflow-x: hidden` 静默裁掉（320px + 长项目名必然触发）。
- 新增 `.mobile-project-mark`：带环境色底的圆角图标块（Windows 蓝 / WSL 紫 / SSH 绿），
  承担"这是哪台机器上的项目"。元信息因此可以按"越靠前越重要"排序
  （`环境 · 分支 · 任务数 · 会话数`）并允许省略号截断——窄屏先被牺牲的只会是尾巴上的计数。
- 运行状态仍是**文字**胶囊（不只给圆点：它是"现在能不能连上去"的唯一先验），改成不加边框的
  实底色，去掉"卡里套卡"的描边噪音。
- 卡片高度交给内容算：1 行名字 74px、2 行 95px（≤380px 屏 72 / 86.9）。圆角取 12px，
  与同屏的任务队列卡片一致（7px 留给信息面板）。
- 悬停反馈只在 `@media (hover: hover) and (pointer: fine)` 下给：触屏上 `:hover` 会粘在刚点过的卡片上。

**根因记录（本次最有价值的一条）**：第 1 条是**改造前就存在**的老问题，且是"裸类名串味"的第二次现身
（第一次见 §六：裸 `error` 曾把卡片钉到屏幕右上角）。`style.css` 里 `.ready` / `.running` / `.error` /
`.empty` / `.task*` 都是不带前缀的全局类名，新组件一旦也起这些名字就会被一起命中；同权重时**样式表顺序**
决定胜负，而 `mobile-remote.css` 排在 `style.css` 之后那一侧的规则反而会输。
**结论：新组件一律加前缀，状态类一律用 `data-*` 属性选择器**（不参与类名碰撞，也不受样式表顺序影响）。

## 九、键盘弹起后会话不贴底（2026-09-17）

### 症状

真机反馈：会话已经滚到最底部，点一下输入框调起键盘 —— 输入条被顶到键盘上方（这部分正常），
但最后几条消息一起被输入条 + 键盘压住，画面停在原地不动，还得手动再划一下才看得见。
没滚到底时不提这个要求（用户要的就是那个阅读位置）。

### 根因

`AndroidManifest.xml` 是 `windowSoftInputMode="adjustResize"`：键盘弹起时 WebView 整体被压矮
（一个键盘的高度；验收夹具里按 324px 模拟），**页面 `scrollY` 一动不动**。于是文档底部连同最后
几条消息一起落进被压掉的那一截里，而"距底距离"凭空多出大半个键盘的高度。

`MobileRemotePage` 原来的 `resize` 监听直接挂的就是重算「贴底」的那个函数：

```ts
window.addEventListener("resize", onScroll);   // onScroll 重算 stickToBottomRef（100px 容差）
```

视口一矮，重算必然把「贴底」判成 `false`（324 > 100），之后新消息到达、回复流式输出都不再跟随。
§六第三轮给的那条"发送时无条件 `stickToBottomRef = true`"只兜住了**发送**那条路径，
点输入框调键盘这条路径没兜住 —— 用户这次报的正是后者。

### 改法

`MobileRemotePage.tsx` 的 window 滚动监听：scroll 仍走 `measure()`，resize 改走一个先判方向的
`onResize`，**视口在变矮的整段过程里只补底、不重算**：

- `height < settledViewportHeight`（视口正在变矮）→ 累计矮了 **80px 以上**（= 键盘弹起；地址栏收放
  只有五六十像素，整段都碰不到这条线）**且**弹起前就贴着底 → 补一次
  `window.scrollTo({ top: scrollHeight })`；然后一律 **return**，不重算；
- 视口长回来（键盘收起 / 地址栏收回）或只是横向变化 → `settledViewportHeight = height` 后再
  `measure()`。

两处要点：

1. **变矮的过程中不能重算**：此刻"距底距离"凭空多了被压掉的那一截，重算必然把贴底判成 `false`
   —— 那正是要修的症状，刚补完就被 `measure()` 顶掉等于没修。
2. **判据是"累计矮了多少"，不是"这一帧矮了多少"**：有些机型把键盘弹出拆成几帧下发（单帧可能
   只有几十像素），逐帧比大小时每一帧都判成"不是键盘"，而中间那几帧的 `measure()` 已经把贴底
   顶掉了。`settledViewportHeight` 只在视口长回来时才往前走，所以它始终是"这一轮收缩的起点"。

### 验证

- 新增夹具 `apps/web/.tmp/probe-keyboard-pin.mjs`（复用 `build-refresh-preview.mjs` 的产物，
  真组件 + 真样式 + playwright；用 `setViewportSize` 矮掉 324px 模拟键盘 —— 同样的"布局视口变矮、
  `scrollY` 不动、输入条重新贴住新视口底部"）。12 条断言，含两条反面用例（上翻着历史时不许把用户
  拽回底部；分帧下发时同样不许）。跑法：
  `cd apps/web && node .tmp/build-refresh-preview.mjs && node .tmp/probe-keyboard-pin.mjs`
  - 本次实现 **12/12 PASS**：键盘弹起后距底 0px，最后一条消息底边 408 < 输入条顶边 460。
  - 反向对照 ①（把 resize 改回 `measure`，即真机上的现状）**7/12**：距底 324px、消息底边 732 >
    输入条顶边 460 —— 与用户描述的画面完全一致。
  - 反向对照 ②（"逐帧比较"那一版实现，即本次修复的中间稿）**10/12**：一次性矮掉时通过，**分帧
    下发时距底仍是 324px** —— 这条用例是专门为它写的，也顺带证明 Chromium 真的会把中间那几帧的
    resize 事件派发出来。
  - 两条反面用例在三个版本里都 PASS，说明"不在底部就不打扰"没有被破坏。
- 源码文本用例（`mobile-remote-agent.test.mjs` 的 "mobile keyboard opening keeps a bottom-pinned
  conversation pinned"）：五条变异（resize 改回 `measure` / 收缩分支里先 `measure()` /
  去掉 `stickToBottomRef` 条件 / 把基准线更新写进收缩分支 / 去掉收缩分支的 `return`）均判红。
- `pnpm --filter @milevia/web test` → **412/412**；`tsc --noEmit` → exit 0。

## 十、任务队列的增删改在手机上没反应 / 报失败（2026-09-17）

### 症状

真机反馈：任务队列里创建、编辑、删除都没法立即响应，最后还失败，"无法创建、编辑和删除"。

### 根因（五段，每段都有真机证据）

**① 命令往返被拖到 19~75 秒，越过手机端 30 秒的等待上限。**

把云端 `cloud_commands` 的 `created_at → updated_at`（云端收到 → 桌面端回执）对齐手机提交时刻，
2026-09-16 当天：

| 时间 | 命令 | 端到端 | 手机轮询次数 |
| --- | --- | --- | --- |
| 16:27:19 | task.delete | 3 s | 8 |
| 16:58:16 | conversation.shortcut | 6 s | 13 |
| 19:19:29 | task.dispatch | **75 s** | 76 |
| 19:24:33 | conversation.message | 22 s | 45 |
| 19:29:56 | conversation.create | 19 s | 39 |

手机端 `waitForCommand` 的上限是 30 秒，晚上这批全部接近或越过 —— 界面报失败，
而桌面端其实晚几十秒才执行完。nginx 日志里手机的请求状态码只有 200/202/204，
没有任何 4xx/5xx：所谓"失败"全是**超时**，不是报错。

**② 拖慢的源头：agent 在 WebSocket 读循环里一条 ack 发一次 HTTP。**

`readCommands` 每收到一个 `event.ack` 就同步 POST 一次本地 `/api/remote/outbox/ack`。
事件洪峰下云端按每秒几百条的节奏回执，读循环全耗在这些请求上，下行的命令挤不进来。
同一天 agent 的一条 WebSocket 连接在 4.5 小时里被灌了 **792 MB** 下行
（nginx `$body_bytes_sent`，用 snapshot 那个已知 47 字节的响应体校验过日志格式）——
绝大部分是对同一批老事件的重复确认。

**③ 那批老事件为什么确认不掉：jsonb 存不下 NUL，而云端对此"永久沉默"。**

本地 `remote_outbox` 队头 23 条事件的 payload 各带 84 个 ` ` 转义
（WSL 那边 UTF-16LE 解码的残留）。`cloud_events.payload` 是 jsonb，而 PostgreSQL 的
jsonb 拒收 NUL 转义（本地真 PG 16 实测：`ERROR: unsupported Unicode escape sequence`）。
云端 `storeEvent` 把这类错误归成"临时数据库故障"：**既不回 ack 也不回 reject**。
于是本地那几行永远删不掉，每一轮读取都占住批次名额；`attempts < maxRemoteOutboxAttempts`
那道闸门对它完全无效（attempts 只在云端 reject 时才涨，实测全表 attempts 全是 0），
队头被钉死了 12 天（最早一条是 09-05）。

**④ 云端一把全局写锁把影响放大。**

`agentWrite` 用一把**全局** `s.writeMu` 包住"检查连接 + 写一帧"，且没有写截止时间。
任意一条连接写阻塞，所有实例的中继写全部排在它后面 —— 包括手机刚下发、等着送到
电脑端的命令。

**⑤ 收尾：agent 卡死，重连循环再也没跑过。**

2026-09-17 07:35:23，agent 的 WebSocket 关闭（nginx 101 记录，5.8 MB）。之后进程活着、
**零个 TCP 连接**、CPU 30 秒内 0.00s、日志停在断线那一刻。`runConnection` 的关闭路径
`<-writeDone / <-readErr / <-snapshotDone / <-outboxDone` 都没有超时，卡在里面就永远
不会再重连一次 —— 这是"手机发什么都不可能成功"的最后一段。

### 改法

| 层 | 改动 | 位置 |
| --- | --- | --- |
| agent | 回执改成"读循环只入队、后台成批提交"（一次 HTTP 最多带 500 条） | `outbox_ack.go`（新） |
| agent | 同一批原样退回来**超过 1 秒**才按指数退避（200ms → 6.4s），不再每秒重推 5 次 | `agent.go` `syncOutbox` |
| agent | 关闭路径全部加超时，且五个等待**共用一个期限**；心跳与命令回执的写队列拥塞超过 20 秒就断开重连 | `agent.go` `runConnection` / `readCommands` |
| control-server | outbox 增加投递窗口（1 小时）与容量上限（5000 行），清理**分块提交**（每块 2 万行）以免占死那条唯一的 SQLite 连接；**读取端刻意不加时间条件**（见第三轮复检第 1 条） | `remote_outbox_retention.go`（新） |
| cloud | 入库前把 payload 里的 NUL 转义换成 U+FFFD（事件 / 快照 / 命令三处） | `event_payload.go`（新） |
| cloud | 数据异常（SQLSTATE 22/23）升级成永久冲突 → 回 `event.reject`，不再永久沉默 | `server.go` `permanentEventStoreError` |
| cloud | 写锁改成**每条连接**一把，加 15 秒写截止时间，写失败即关连接（半帧连接不能继续用） | `server.go` `agentConnection` |
| cloud | 电脑端没有活连接、命令又过了宽限期（8 秒）时落 `failed` 并写明原因，不再让手机干等 30 秒 | `server.go` `pushCommand` / `failStaleQueuedCommand` |
| web | 任务增删改改成本地立刻生效 + 卡片标「同步中」，命令在后台跑；新建拿到电脑端回执里的**真 id** 后按 id 精确对账 | `MobileRemotePage.tsx`、`lib/task-mutations.ts`（新） |

手机端那部分的规则：本地改动会**在每一次快照落地时重新叠加**（快照有上传节流，命令
成功那一刻拿到的往往还是命令之前那一版）；只有快照真的反映了结果才把「同步中」摘掉。
三种收尾分得很清楚：

- **明确失败**（云端拒绝 / 命令过期 / 请求没发出去）→ 回滚并说明原因；创建失败还会把
  用户刚打的字放回输入框。
- **成功** → 重拉一次快照对账。新建优先用回执里的真 id 比对（`withResolvedCreateID`），
  拿不到真 id 才退回「标题 + 描述」比对，并且要求快照里同内容的条数不少于还没落地的
  同内容创建数 —— 否则用户连建两条同名任务时，第二条会被第一条误判成已落地。
- **只是还没回执**（30 秒窗口内没等到终态）→ **什么都不撤**。30 秒没等到终态不等于
  电脑端没做，撤掉卡片就是把一张可能已经建好的任务从用户眼前删掉；留着它最坏只是多
  显示一会儿「同步中」。

### 复检发现并修掉的问题（第二轮）

第一轮改完之后又逐文件复检了一遍，其中四条是**第一轮自己引入的**：

1. **退避在正常路径上误伤**：按「重复了几轮」升级退避，而回执是攒 250ms 成批提交的，
   泵读第二遍时那批行必然还在 → 一次普通收发就白等几百毫秒。改成按「这批原样退回来
   多久了」升级，头一秒不升级。
2. **写超时把连接留在「半帧」状态**：加了 15 秒写截止时间之后，超时的连接可能已发出
   半帧，而回执路径的调用方是 `_ = s.agentWrite(...)` 不看返回值。改成写失败即关连接，
   读循环随即报错、注销、重连。
3. **首次清理会占死那条唯一的 SQLite 连接**：真机上要删 112 万行，一条 DELETE 删完，
   期间桌面端所有请求都在排队。改成分块提交（每块 2 万行、各一个事务）。
4. **换真 id 时漏搬「同步中」与收尾目标**：待确认表和 pendingTaskBusy 都按 id 索引，
   只换表里的键值不搬 busy 标记，卡片会在同步途中丢掉「同步中」，成功对账也被跳过。
5. **收尾等待是串行的**：五个 goroutine 各给 15 秒，最坏 75 秒才重连。改成共用一个期限。
6. **连接结束时冲刷可能连发多个注定超时的请求**：`queue.take()` 不限量，本地服务卡住时
   每个请求吃满整段超时。改成每片前看一次 ctx，并把冲刷超时收到 10 秒（小于 15 秒的
   收尾宽限，避免留下孤儿 goroutine）。
7. **清理间隔 15 分钟偏长**：容量上限只在清理那一刻成立，两次之间表还在长。收到 5 分钟
   （清理本身很便宜）。
8. **新建的卡片可能落在当前分类之外**：新任务状态是待处理，用户若停在别的分类页就看不
   到那张乐观卡片 —— 和「没生效」在用户眼里没有区别。改成建完把面板切到「待处理」。
9. **未改动的项目保持对象引用**：原来每次都给所有项目造新对象，会让 `project` 的依赖链
   整体失效、白白重渲染。

### 复检发现并修掉的问题（第三轮：在真机库上实测查询）

前两轮都是读代码，这一轮改成**在真机库和合成库上实测**，抓到一个前两轮完全没看出来的问题：

1. **读取端的时间过滤把一次读取从 0.8ms 变成 2659ms。** 我给 `readRemoteOutbox` 加了
   `created_at >= 窗口`，本意是"别投递过期事件"。真机库（138 万行积压）实测：无过滤
   0.8ms、加过滤 **2659ms** —— 符合条件的行都在 `agent_sequence` 的**末尾**，扫描必须走完
   整张表才能凑够 `limit` 的条数；而每次读取都持着那条唯一的 SQLite 连接，每秒好几次，
   等于把整个服务按在地上。合成库上对照了多种写法（加 `(created_at, agent_sequence)`
   索引、用子查询先定下界），只要存在大量过期行，就都会退化成全表扫描。

   **改法**：把过滤条件撤掉，"不投递过期事件"交给**删除**保证 —— 删除是批量的、可以让出
   连接，而过滤是每一次读取都要付的代价。另外把首次清理从启动后 2 分钟提前到 **5 秒**
   （分块之后它和启动交互并不冲突），并加了一条**查询形状**用例，防止有人出于好意再把
   过滤条件加回来。

   **验证**：分块清理在合成库（140 万行）上实测 —— 70 块、总耗时 11.4 秒、**单块最慢
   254ms**，即连接每次最多被占用 254 毫秒，而不是十几秒。

### 仍需人工决定的两件事

1. **本机积压**：`remote_outbox` 里有 112 万行、约 1 GB，其中 23 条是永远投不出去的
   NUL 行。清理会动真机 SQLite，需要单独确认后再执行。
2. **发版**：agent 与 control-server 的改动要随桌面端安装包发布，手机端要重发 APK，
   改动才在真机生效 —— 只改源码是不会影响已安装版本的。

## 十一、扫码配对「手机端没有任何反应」（2026-09-17）

### 症状

用户报：手机上点「扫描二维码」，扫了电脑端刚生成的二维码，**手机端没有任何反应**，
最后还是必须把电脑屏幕上的 6 位校验码手打一遍才能绑定。

### 根因

二维码 URL 里被删掉了校验码（`apps/web/src/pages/MobileRemotePage.tsx`）：

```ts
pairingURLWithCode()  →  parsed.searchParams.delete("code");
```

而手机端的唯一接收点 `acceptScannedPairing()` 是**按"二维码里有没有 6 位数字"分岔**的：

```ts
if (/^\d{6}$/.test(scanned.code)) { void claimPairing(scanned.pairingID, scanned.code); }
else { setPairingStatus("…请手动输入…"); }
```

两边一合，扫码的全部产出就只剩"预填一个 pairingId + 把焦点移到输入框" ——
相对手输校验码不再是一条并列的通路，而是一段装饰。这与文档 32 §6.1 写的
"电脑生成一次性二维码**或** 6 位配对码"也对不上：二维码本应自成一条路。
当初删掉它的理由是"校验码不该进 URL"，但那个顾虑在本项目里不成立（见改法）。

### 改法

1. `pairingURLWithCode(value, pairingID, pairingCode)` 增加第三个参数：**校验码是 6 位数字就写进二维码**，
   否则仍走"删除 code"的分支（兼容旧版电脑端生成的码、被截断的码）。
2. `createDesktopPairing()` 把 `value.code` 一起传进去（少传一个实参就等于扫码失效）。
3. 文案同步：配对面板与取景层的说明从"再输入 6 位校验码"改成"在电脑上点击「确认绑定」"；
   手机端提交成功的状态改成「已扫码并提交，请在电脑上点击「确认绑定」」。
4. 兜底那条路保留，并把原因点明：「已识别配对会话，但二维码里没有校验码，请手动输入…」。

**为什么把校验码放进二维码是安全的**：令牌必须被"激活"才可用，而激活只由电脑端的
`POST /api/remote/pairing/confirm` 写入（`cloud_access_tokens.activated_at`，鉴权 SQL 里带
`activated_at is not null`）。二维码被拍照/截屏最多只能发起一次 claim，仍要等**电脑端那一次点击**；
校验码本身 5 分钟失效、单次有效。手机扫码只解析这个 URL、从不加载它（`pairingFromScan`）。

### 验证

- `node --test src/mobile-remote-agent.test.mjs` 51/51；`pnpm test` 488/488；`pnpm build`（tsc -b + vite build）0 报错。
- 浏览器探针 `.tmp/probe-scan-overlay.mjs` 27/27，其中新增两条：
  - 喂一张**带 code** 的二维码 → 取景层退出 + 云端**真的收到** `{pairingId, code:"123456"}` + 提示改成"去电脑上点确认绑定"；
  - 喂一张**不带 code** 的二维码 → 仍是"退回手输"（兜底没被破坏）。
- 变异检验 `.tmp/mutation-scan.py` 33 处全部挡下（新增 ㉛ 二维码里不写校验码 / ㉜ 生成二维码时丢掉校验码），
  还原后源码 sha1 与改动前逐字节一致。

### 遗留

- 该修复落在**电脑端**（二维码由电脑端生成），**电脑端要出新包才生效**。手机端不改代码也能配对成功
  （旧版手机端的 `pairingFromScan` 早已会读 `code`），但文案仍是旧说法，建议一起发版。
- 原生扫码依赖插件的 `voteForBarcodes`：同一 rawValue 要连续命中 **10 帧**才会回调
  （`@capacitor-mlkit/barcode-scanning` 8.1.1 的 `BarcodeScanner.java`）。所以扫的时候要端稳一秒左右，
  一晃就走不会回调 —— 这属于插件行为，应用侧调不了，写在这里避免下次误判成"扫码又坏了"。

## 十二、配对流程的界面重做（2026-09-17，用户提"还能不能优化优化"）

前面第十一条修的是**扫码能不能绑定**（二维码里补上校验码）。这一条修的是**整条链路的显示**：
两个端一共九个问题，全部配了运行期证据。

### 症状（用户视角）

1. 扫码提交后只有一行 12px 绿字，等待 / 成功 / 失败长得一模一样 —— 上一轮"手机端没有任何反应"
   的体感有一半来自这里。
2. **绑定成功的确认根本看不见**：确认后 `setPairingExpanded(false)` + 落令牌 → `showMobilePairing`
   立刻变 false → 整块 `.mobile-pairing`（含那行状态）被卸载，"电脑已确认，绑定完成"跟着一起消失。
3. 电脑端二维码**到期后画面不变**：提示换成了"配对已失效"，但那张已经扫不动的码还挂在屏上，
   用户拿着它反复扫，手机端只会回"配对已失效"。
4. 电脑端「生成二维码」按钮文案不变，再点一次会**静默作废**上一张（手机正在扫的那张）。
5. 电脑端「确认绑定」在手机提交前是一颗灰按钮，只有一行小字解释为什么不能点。
6. 校验码离二维码很远（在卡片外面单独一行），也无法复制。
7. 手机端「解除绑定」是一颗裸文本按钮，**误触即吊销令牌**。
8. 实例状态直接把云端枚举渲染出来：一颗写着 `online` 的绿胶囊。
9. 手机端重开配对面板时，上一轮的状态行会残留（把上次的"配对已失效"读成这次的结果）。

### 改法

- 状态行抽成 `{ text, state }`（`idle | waiting | success | error`）并渲染在**配对面板之外**，
  `data-state` 落到 DOM 由 CSS 上色；等待态带 spinner，成功态 8 秒后自己走掉。
- 电脑端按云端 `expiresAt` 走倒计时；到点用 `data-expired` 把二维码判死（灰度 + 遮罩 + 就地重新生成），
  用过的码标 `data-spent`（"已使用"）。确认按钮改成三态文案：等待手机扫码… / 确认绑定 / 已绑定。
- 校验码与二维码并排，加「复制」（走 `lib/clipboard.ts`）；去掉卡片外那行重复的校验码。
- 手机端解绑加二次确认（复用任务弹层那一套），并进返回键链 + `leaveConversationView`。
- 实例状态中文化（`online → 在线`），类名仍用原始值供 CSS 上色。

### 一个可复用的教训

**"成功提示"这类只在终局出现一次的 UI，不能挂在会被自己关闭的容器里。** 这一条如果只做静态审查
（"代码里明明写了 setPairingStatus"）永远看不出来 —— 必须有"跑完整链路 + 断言那一刻 DOM 里还有没有它"
的运行期证据。位置类规则同理：光断言"那一行在文件里"，把它挪进面板内部照样绿，
所以既要断言嵌套位置（锚点写 `"mobile-pairing" `，带尾随空格），也要配一个"挪一行"的变异。
