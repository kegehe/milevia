## 2026-09-10 修复：配对链路可用性与可靠性

### 阻断级：桌面端无法生成配对二维码
- `/api/remote/*` 由 `remoteAgentOnly` 保护，desktop-api 模式下只认 `X-Milevia-Agent-Token`；而桌面页面只持有 `X-Milevia-Session`，因此"生成二维码"和"确认绑定"必然返回 401。
- 现在 `remoteAgentOnly` 对 `desktopPairingPaths` 白名单（`/api/remote/pairing`、`/pairing/confirm`、`/pairing/status`）额外接受 **desktop-api 模式下的有效会话令牌**；其余 relay 端点（outbox、commands、credentials 等）仍只认 Agent 令牌。已用 httptest 覆盖边界。
- 新增 `GET /api/remote/pairing/status` 转发云端配对会话状态，桌面端据此在手机提交后启用"确认绑定"，不再盲点。

### 安全：配对必须由电脑确认
- 原先 claim 即签发可用令牌，`userAuth` 不校验配对是否已确认，"电脑端确认"形同虚设。
- `cloud_access_tokens` 新增 `pairing_id` 与 `activated_at`；claim 写入时 `activated_at` 为空，`userAuth` 只接受已激活令牌；`agentConfirmPairing` 在**同一事务**中确认会话并激活令牌。升级时旧记录（`pairing_id=''`）自动标记为已激活，避免破坏既有配对。

### 安全：撤销语义与限流
- `POST /v1/instances/{id}/revoke` 现按 `scope` 区分：默认 `mobile` 只吊销手机令牌，**不再连带吊销 Agent 凭据**（原行为会把整台电脑踢下线且发布版无法自愈）；`scope=agent` 保留原语义。
- 为未认证端点增加按客户端 IP 的令牌桶限流：注册 30/min、配对 claim 30/min、配对状态 300/min（手机每 1.5s 轮询）。

### 可靠性
- 事件序号/ID 冲突不再断开 relay 连接：云端回 `event.reject`，Agent 通过 `/api/remote/outbox/fail`（`permanent=true`）丢弃该死信事件；数据库瞬时故障既不 ack 也不断连。
- 本地 outbox 增加投递预算上限（`maxRemoteOutboxAttempts`），耗尽的事件退出投递窗口，避免队首阻塞。
- Agent `publishCredentials` 改为每次连接建立后重试（原仅启动时执行一次）；HTTP 401（快照上传）也会触发限流重注册，不再只有 WebSocket 握手能发现凭据被吊销。
- Agent 凭据读写加锁（`credMu`），消除重注册与快照/心跳 goroutine 之间的数据竞争。
- 远程命令执行加 60s 超时，避免单条慢命令卡住串行 worker。

### 体验
- 二维码地址改为仅在绝对 http(s) 时生成，云端未配置 `MILEVIA_CLOUD_APP_URL` 时明确提示改用校验码，不再回退到 tauri 协议生成无效二维码。
- 云端 401 时前端清除失效令牌并回到配对流程；移动端新增"解除绑定"入口；扫码文案修正为"扫码 + 输入 6 位校验码 + 电脑确认"。

### 已知限制（未在本次处理）
- 移动端令牌无设备标识，撤销粒度为实例级，无法单独下线某一台手机。
- 二维码仍不携带校验码（避免经浏览器历史/代理日志泄漏），因此扫码后必须手输 6 位码；Android 未配置 App Links，系统相机扫码只会打开浏览器。
- 云端下行仍为 200ms 轮询数据库（未接入 Redis/LISTEN-NOTIFY）；权限位（`read:projects` 等）仍未实现。

### 操作要点（踩过的坑）

- **`docker cp` 会保留源文件权限**。容器以非 root（uid 10001）运行，若先 cp 再 `chmod` 会得到 `Operation not permitted`，二进制不可执行、容器起不来（`exec: permission denied`）。**必须先 `chmod 0755` 源文件，再 `docker cp`**。这一点在历史部署命令里本来就有，容易漏。
- 构建：本机交叉编译 `CGO_ENABLED=0 GOOS=linux GOARCH=amd64`（cloud-control 全为纯 Go 依赖，无 CGO），目标 Alpine 可直接运行。依赖需走 `GOPROXY=https://goproxy.cn`，`proxy.golang.org` 不可达。
- `docker commit` 会把容器 Env（含注册令牌、DB 密码、user token）一并烘焙进镜像。虽然 `--env-file` 在运行时优先级更高、轮换令牌仍生效，但旧值会残留在本地镜像层里，该镜像不可外推。
- 回滚资产：旧容器 `milevia-cloud-control.old`（已停止）、`/tmp/cloud-control-prev`、`.env.server.bak-20260911`。
- 排查手法：用 chi v5.2.3 写最小复现程序验证「`/v1` 子路由是否遮蔽父级注册的 `/v1/agent/register`」——结论是**不遮蔽**，`r.Route("/v1")` + 父级 `r.Group` 注册公开路由的现有写法是正确的，路由问题纯属部署版本落后。

### 部署提速：改为服务器侧编译（2026-09-11 晚）

**问题**：整条流水线约 15 分钟，其中 **14 分 04 秒**只花在「上传 10.2 MiB 二进制」这一步。runner 在 Azure eastus（境外），该步骤日志从 06:23:48 静默到 06:37:52，期间无任何输出——10,719,394 字节 ÷ 844 秒 ≈ **12.7 KB/s**。服务器侧实测：GitHub release 资产 ~44 KB/s、raw.githubusercontent ~11 KB/s，而 Cloudflare 中立测速 ~694 KB/s、腾讯云镜像 ~63 MB/s。即：不是带宽不够，也不是服务器不能编译，而是「到 GitHub/Azure 这条跨境路径」被严重劣化。

**改法**：把编译搬到服务器。

- CI 只打包源码（`tar czf`，排除 `.tmp` 里的历史二进制），上传 **30.4 KB** 的源码包；
- 服务器侧 `deploy-cloud-control.sh` 解包后编译，用 `GOPROXY=https://goproxy.cn,direct` + `GOTOOLCHAIN=auto`——服务器已有 go1.22.2，编译时会自动拉取 go.mod 要求的 **Go 1.26.2** 工具链（首次约 28 秒，含依赖），之后工具链与模块缓存复用；
- `-trimpath -ldflags "-s -w"` 保证产物可复现：服务器编译出的二进制为 `010f8967…ecc8e`、10,719,394 字节，与 CI 交叉编译产物**完全一致**。

**实测结果**：

| 环节 | 改造前 | 改造后 |
|---|---|---|
| 跨境传输 | 10.2 MB / 844 秒 | 30.4 KB / **2 秒** |
| 服务器编译 | 不适用 | **1 秒**（缓存命中；首次 28 秒） |
| 端到端部署 | 约 14 分钟 | **5 秒** |

**触发路径同时收窄**：`paths` 从 `apps/cloud-control/**` 收窄为 `**/*.go` + `go.mod` + `go.sum` + 部署脚本 + 工作流本身，改 README 不再触发一次生产部署。

## 2026-09-11 手机端事件流停滞（延迟根因）与延迟优化

### 根因：`mobileEventStream` 的排空查询永远看不到最新事件

原实现每次排空都用同一条查询：

```sql
select ... from cloud_events
where instance_id=$1 and agent_sequence>$2   -- $2 = max(0, lastSequence - 5000)
order by agent_sequence limit 100             -- 升序取「窗口里最早的 100 条」
```

`sentSequences` 只对 `<= lastSequence-5000` 做裁剪，而查询窗口同样从该处开始、升序、限 100 条。于是**一旦实例事件数超过 100**，返回结果会被已发送的行占满，游标不再前进，最新事件永远不可达——除非客户端断线重连（`Last-Event-ID` 会让 `lastSequence` 跳到更大值）。

生产库实测（2026-09-11，唯一有事件的实例，也正是手机已配对的实例
`cmd-8026a38fd96dc9f642b517524758f0a2`）：

| 实例总事件数 | 最新事件是否可达 |
|---|---|
| 100 | 是 |
| 101 | 否（可达 99 条） |
| 150 | 否（可达 50 条） |
| 1000 | 否（可达 0 条） |

该实例当时 **1375 条事件（1733–3127）**，即事件流早已完全停滞。**这才是手机端「延迟高」的主因**：SSE 一条新事件都送不到，界面只能靠客户端自己的 15 秒兜底轮询与整份快照刷新推进。此前实测到的 194–200ms 是在一个孤儿实例（事件数很少）上做的，因此没能暴露该问题；换言之，批次 1 的 `LISTEN/NOTIFY` 改造虽然本身正确，但在该状态下**不会带来任何可见收益**。

### 修复

把单条查询拆成两趟（`drainInstanceEvents`）：

1. **前向追赶**：`agent_sequence > lastSequence` 升序、按批读取，循环直到不足一批，游标严格单调前进，因此必然收敛；单次最多投递 `cloudEventCatchUpPerDrain`(=500) 条，达到上限时返回 `more=true`，调用方立刻再排空一次（`catchUp` 通道），不必等下一次通知。
2. **乱序补扫**：只回扫游标前 `cloudEventBackfillWindow` 条（=1 批 =100）用于兜住乱序到达的上传。**窗口宽度不得大于批大小**，否则升序+limit 又会被已发送的行占满，把迟到事件挡在后面。

另外两处配套改动：

- **无游标的流从实时位置开始**：`lastSequence==0` 时先用 `instanceEventCursor()` 跳到当前最大序号。客户端加载时会自行拉取整份快照，回放上千条历史事件对手机没有价值，只会把实时事件挡在后面；断线重连仍走 `Last-Event-ID` 续传，不丢数据。
- **折叠通知的时机从「读取之后」移到「读取之前」**。原先在排空后折叠，会把「在本次 SELECT 之后、折叠之前」到达的通知一并丢弃，而那条通知对应的事件并未被本次读取看到，最坏要等 2 秒兜底。改到读取之前折叠则没有该窗口：读取期间到达的通知会存活并触发下一趟。

### 同批次其他修复（延迟优化）

- **电脑端 outbox 长轮询引入了热循环（本次自查发现）**：本地 `remote_outbox` 的行只有云端回 `event.ack` 后才删除，所以「已读但未确认」的这批行会被长轮询**立即**返回；而 Agent 侧循环在拿到非空批次后立刻 `continue`，于是变成对本地 SQLite 的紧密空转。实测 **400ms 内 4349 次读取**（约 1.1 万次/秒），每次还把同一批事件重复推给云端。修复：`syncOutbox` 记录上一批的签名，批次未变（说明等 ack）时按 `outboxAckGrace`(=200ms) 节流；仍保留重发，因为它是「ack 丢包」的恢复路径。
- **`assistant.delta` 不落本地事件表、不广播给本地订阅者**，只走远端中继。桌面端 `ConversationPage` 会把每个事件无条件追加进 `events` 并随会话整包加载，增量落库会让事件时间线被几百条不渲染的条目污染。
- **`slowRequestLogger` 豁免长轮询**，否则 20 秒挂起的 outbox 请求会被反复记成慢请求，淹没真正需要它的信号。

## 2026-09-11 手机端应用内更新 + 更新清单的双源分发

### 手机端更新机制（v0.1.6 / versionCode 4）

Android 包无法自己完成"下载并安装"（需要 `REQUEST_INSTALL_PACKAGES` 加原生代码），因此先做最小可靠闭环：**比对版本号 → 把下载地址交给系统浏览器**。用的是页面里已有的外链机制（Capacitor 会把非应用域名的导航交给系统浏览器，本项目 `allowNavigation` 未配置），所以**不需要新依赖、不需要新权限、不需要原生插件**。

- `apps/web/src/features/updater/android-release.ts`：清单解析 + 版本比较 + 多源回退（不 import Capacitor，可直接单测）
- `apps/web/src/features/updater/mobile-update.ts`：`App.getInfo()` 取 versionCode + 拉清单
- `MobileRemotePage.tsx` / `mobile-remote.css`：顶部可关闭横幅「发现新版本 vX · 立即更新」
- 比较依据是 **versionCode**（Android 认它）；字符串比较会把 `0.10.0` 判成比 `0.9.9` 旧
- `scripts/release-mobile.mjs`：升版本号 → 构建 Web + APK → 写清单 → `--deploy` 上传

**首次安装**：手机浏览器打开 `https://keyanjia.info:8443/updates/Milevia_0.1.6_android.apk` 装一次；此后每次发版都会在 App 内提示。已核实新包签名与在装 0.1.5 完全一致（同一 debug keystore，SHA-256 `0e19b1e1…85eb`），可直接覆盖安装、**不用卸载、不会丢配对令牌**。

### 更新清单的两份分发（修掉"备用源说谎"）

**问题**：`release.mjs` 生成的两份 `latest.json` 内容完全相同、下载 `url` 都硬编码指向 `keyanjia.info`。GitHub Pages 存在的唯一目的是兜"自建源整个挂了"，但那时 App 会先弹"发现新版本"、再在下载那一步必然失败。

**修法**：抽出 `scripts/lib/update-manifest.mjs`，两份清单的下载地址各自指向"拿到它的客户端真能下到的地方"：

| 清单 | 位置 | 下载地址指向 |
|---|---|---|
| 自建源 | `release/updates/latest.json` → 服务器 `/updates/` | 自建服务器（国内快，主用） |
| 备用源 | 仓库根 `latest.json` → GitHub Pages | GitHub Release 资产 |

关键规则：**某个平台若在 GitHub 上没有已发布资产，备用源那张就不写它的下载信息**（`platforms` 里整段去掉），表现为"没有更新"。宁可少提示一次，也不要给出一个注定失败的下载 —— 因此备用源是"诚实降级"而不是"半吊子状态"。`gh` 未安装/未登录时自动降级并告警。

同时把 GitHub Release 资产上传自动化（原先只是 `release.mjs` 打印的一条手工命令）：`--deploy` 会建/更新 `v<版本>` 的 Release 并上传安装包（桌面端）或 APK（手机端）。实测 24MB 上传 **18 秒**。

### 版本号约定：两端从 0.1.6 起各自递增

- Android 的 versionCode/versionName、APK 构建、清单里的 `platforms.android` 段，**全部由 `release-mobile.mjs` 独占管理**；`release.mjs`（桌面端）不再碰 `apps/web/android`，也不再覆盖 android 段。
- 原因：Android 升级只看 versionCode；而清单**顶层的 `version` 属于桌面端**（桌面更新器只读它），手机端单独发版若去改它，桌面端会立刻提示有新版本、而下载地址仍指向旧 exe。所以 mobile-only 发版天然不能同步升共享版本号。
- 顺带修掉原桌面脚本的两处副作用：它会在本地偷升一次 Android 版本号、并白建一个既不上传也不进清单的 APK，让 `build.gradle` 的数字跑到线上包前面。
- 两个脚本现在都**只写自己那段**，另一段原样保留（桌面脚本会保留 `platforms.android`，反之亦然）。

### 备用源的实测可用性（重要，别高估它）

从不同网络位置拉 GitHub Release 资产（`.../releases/download/v0.1.6/Milevia_0.1.6_android.apk`，Range 取 1KB）：

| 位置 | 结果 |
|---|---|
| 开发机（本机，国内） | **3 次全部失败**（HTTP 000 / connect timeout / ECONNRESET） |
| 服务器 `111.229.52.158` | **206 成功**（2.3s） |
| 自建源（同一台开发机） | 206，稳定 |

→ 典型的国内到 `objects.githubusercontent.com` 被重置：`github.com` 页面能开、资产下载不定。所以**备用源是"尽力而为"**，它的价值在于"自建源整个挂了时还有一条可能走通的路"，而不是"一定能下到"。要一条**可靠**的备用源，需要换 Cloudflare R2 之类的对象存储（服务器实测到 Cloudflare 有 ~694 KB/s），这需要新建存储与凭据，未做。
