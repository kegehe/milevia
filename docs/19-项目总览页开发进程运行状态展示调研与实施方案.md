# 19-项目总览页开发进程运行状态展示调研与实施方案

> 日期：2026-08-07
> 状态：调研完成，方案已定稿。一次完成，含秒级实时推送。

## 1. 背景与需求

用户可以在项目页面配置并启动项目的开发服务器（如 `npm run dev`、`go run .`），启动后即使跳到其他页面，进程仍在后台运行。但当前的**项目总览页（Dashboard）卡片**只显示**会话（Claude 对话任务）状态**，看不到**开发进程是否在运行**及其运行状态。

需求：在总览页的项目卡片上，同时展示两类状态：
1. **会话运行状态**（现状已有）— 该项目的 AI 对话/任务是否正在执行。
2. **开发进程运行状态**（本次新增）— 该项目启动的开发服务器进程是 运行中 / 启动中 / 停止中 / 异常退出 / 已停止。

## 2. 现状分析

### 2.1 两类状态分属完全不同的后端子模块

| 维度 | 会话运行状态（现状） | 开发进程运行状态（目标） |
| --- | --- | --- |
| 后端模块 | `listProjectStatuses`（`app.go:2146`） | `projectRunner`（`project_runner.go`） |
| 数据来源 | SQLite 查询（`conversations` 表） | **进程内存**（`runManagers` map） |
| 含义 | 是否有 `is_current=1` 的会话在跑 AI 任务 | 开发服务器进程（`npm run dev` 等）是否活着 |
| 状态取值 | `running(int，0/1)` | `stopped / starting / running / stopping / failed` |
| 前端展示 | 卡片"正在执行 / 已就绪 / 工具不可用" | 卡片运行状态点徽标（待实现） |

结论：总览卡片当前**完全不知道**开发进程状态，因为卡片数据来自"会话状态"接口，从未查询进程状态。

### 2.2 后端进程状态基础设施已经完备

`projectRunner`（`project_runner.go`）已经具备完整的运行状态能力：

- **状态机完整**（`project_runner.go:30-34` 状态常量，`wait()` 在 `:616`）：`stopped / starting / running / stopping / failed`，进程退出时 `wait()` 自动置 `stopped` 或 `failed`。
- **线程安全**：所有状态读写都通过 `pr.mu`（RWMutex）保护。
- **现成快照方法**：`StatusSnapshot()`（`project_runner.go:747`）返回 `RunStatusResponse`。
- **空闲 runner 已在内存中**：`projectRunManagerForExistingProject`（`app.go:5022`）在启动时把 runner 存入 `runManagers` map；即使未启动，`newProjectRunner`（`project_runner.go:134`）也已创建，状态默认 `stopped`。因此**批量查询任意项目的进程状态不需要额外建 runner，也不依赖 DB**。
- **本地与 SSH 统一抽象**：`projectRunnerInterface`（`ssh_project_runner.go:18`）已抽象 `StatusSnapshot()`，本地与 SSH runner 均可查询。

### 2.3 前端已有可复用的状态文案与颜色

`features/run/run-model.ts` 已定义：
- `RunStatus` 类型（"stopped" | "starting" | "running" | "stopping" | "failed"）
- `statusLabels`（`run-model.ts:47`）：已停止 / 启动中 / 运行中 / 停止中 / 异常退出
- `statusColors`（`run-model.ts:55`）：灰 / 橙 / 绿 / 橙 / 红

`ProjectRunPanel`（单个项目页）已在用这套徽标渲染。**总览卡片可直接复用**。

## 3. 调研中发现的问题与关键决策

### 3.1 ⚠️ 问题一：不能把整个 `StatusSnapshot()` 塞进批量接口

`RunStatusResponse.recentLogs`（`app.go:137`）携带 **200 条环形缓冲日志**（`projectRunLogHistory = 200`）。项目数 N，每 10s 轮询总览，会传输 `200 × N` 条日志只为拿一个状态字——违背总览接口轻量原则，也浪费带宽与 JSON 序列化 CPU。

**决策**：进程状态来源**只取精简字段**（`runStatus` + 可选 `runPid` / `runStartedAt`），不背日志。为遵循"单一 owner"架构（见 5.2.2），进程状态走**独立的新端点** `/api/projects/processes/statuses`（调 `LightStatusSnapshot()`，见 5.1.2），而不是改现有会话状态接口 `/api/projects/statuses`。完整日志仍由单项目 `/api/projects/{id}/run/status` 提供。

### 3.2 ⚠️ 问题二：进程状态是纯内存数据，server 重启即失（这是设计如此，非缺陷）

`runManagers` 存于进程内存（`app.go:180`），control-server 重启会清空，且 `Close()`（`app.go:599`）会停掉所有运行进程（`runner.Stop()`）。所以**重启后进程被停，总览显示"已停止"是正确语义**，不需要持久化运行状态。

**决策**：不引入持久化；重启后状态归"已停止"符合产品预期。

### 3.3 ⚠️ 问题三：通知系统不适合承载瞬时进程状态（关键设计判断）

表面看可复用通知 WS（`/ws/notifications`）做状态推送，但深入核对其实现后**不能复用**：

- `broadcastNotification`（`notification.go:182`）**先写 DB、再广播**，通知是持久化数据，用户需在通知中心手动 dismiss。
- 进程启动/停止是高频瞬时态，若写入会**污染任务通知中心**，产生一堆无意义且需手动忽略的"进程启动"通知。
- `NotificationEvent`（`notification.go:20`）是面向任务/会话通知的消息结构，语义不符进程状态。

**决策**：为进程状态广播**新增独立的轻量 WS 通道**，不落库、不污染通知中心，也不与单项目的 run 日志 WS（`/ws/projects/{id}/run`）共用（那个是按项目分频道推日志的；总览需要一个全量状态广播）。

### 3.4 轮询 vs 推送

- 总览页已有 10s 轮询（`DashboardPage.tsx:36`），用于会话状态。把它作为**基线兜底**（保证断线/首帧也能收敛）。
- 需求要求"一次完成 + 实时"。进程状态变化（启动成功要能看到绿点、异常退出要能看到红点）是用户最关心的，10s 延迟体验差。
- 因此**推送作为实时通道**，轮询作为兜底，两者互补。

## 4. 总体方案

```
┌────────────────────────────────────────────────────────────┐
│ 前端 Provider 树 (App.tsx: TooltipProvider→Notification→Project)│
│  ProjectProvider（现有）                                    │
│    会话状态:  /api/projects/statuses 10s 轮询（不变）          │
│  ProcessStatusProvider（新增，仿 NotificationProvider 单例）  │
│    进程状态:  REST /api/projects/processes/statuses 10s 兜底  │
│               WS   /ws/processes（首帧快照 + 实时变更）        │
│              自动重连(指数退避) + BroadcastChannel 跨 Tab      │
│  卡片: 会话状态徽标（现有） + 开发进程状态点徽标（新增）并列      │
└───────────────┬────────────────────────────────────────────┘
                │ REST: /api/projects/processes/statuses (仅进程状态)
                │ WS:   /ws/processes (进程状态广播)
                ▼
┌────────────────────────────────────────────────────────────┐
│ 后端 (app.go / project_runner.go / 仿通知通道但不落库)         │
│   1. 新增批量进程状态端点 (仅 runStatus/runPid/runStartedAt)  │
│      循环查 runManagers → LightStatusSnapshot()，不带日志     │
│   2. 新增 processStatusSubs (map[*conn]) + 广播                 │
│      复用 notificationSubs 单 writer goroutine 模式，不落库   │
│   3. projectRunnerInterface 增加 LightStatusSnapshot()       │
│      + setStatusListener 回调（状态变更点触发）                │
│   4. runner 状态回调 → broadcastProcessStatus → WS 订阅者     │
└────────────────────────────────────────────────────────────┘
```

三个协同层：
1. **REST 兜底**：新增批量进程状态端点 `/api/projects/processes/statuses`，ProcessStatusProvider 每 10s 拉一次保证首帧与断线收敛。**与会话状态轮询分离，各归各的 Provider，object 单一 owner，无冲突。**
2. **WS 实时**：`/ws/processes` 全局广播，连接即逐项目推送全量快照（同帧形状），之后状态变更实时推唯一一份状态字。
3. **前端渲染**：Dashboard 卡片同时消费 `ProjectProvider`（会话状态）与 `ProcessStatusProvider`（进程状态），两个徽标并列。

## 5. 详细设计

### 5.1 数据模型（后端）

#### 5.1.1 状态变更事件（WS 负载）

新增类型（`project_runner.go` 或独立 `run_status.go`）：

```go
// RunStatusEvent WS 推送的进程状态变更事件（轻量、不落库、无日志）。
// 与批量接口的 RunStatus/RunPID/RunStartedAt 字段一一对应，前端从此单一来源收敛，
// 不再派生冗余布尔（status=="running" 即 running，避免两字段不一致）。
type RunStatusEvent struct {
    ProjectID   string     `json:"projectId"`
    Status      RunStatus  `json:"status"`
    StartedAt   *time.Time `json:"startedAt,omitempty"`
    PID         *int       `json:"pid,omitempty"`
}
```

**设计要点**：
- **不携带 recentLogs**，避免 3.1 的问题。
- 用 `ProjectID` 广播，前端据此更新总览对应卡片，无须查询项目名（卡片已有 project 信息）。
- `StartedAt` / `PID` 为可选字段，仅供卡片展示更多细节；value 仅在有意义时填充（参照 `RunStatusResponse` 的指针字段约定，`app.go:133-137`）。
- **不要**额外带 `running` 布尔字段——前端用 `status` 即可判定（`statusLabels`/`statusColors` 以 `status` 为键），多余布尔会造成两字段漂移的隐患。WS 与 REST 推送的是同一份 `RunStatus`，语义一致、幂等。

#### 5.1.2 进程状态批量端点（新增；`/api/projects/statuses` **保持不变**）

**一个关键职责划分（实施前审计修正）**：进程状态交给**独立的 `ProcessStatusProvider`** 统一拥有（见 5.2.2）。因此**不**往会话状态接口 `/api/projects/statuses`（`app.go:716`）塞 runStatus——否则 `runStatus` 会被 `ProjectProvider` 的轮询和 `ProcessStatusProvider` 的 WS 两个 owner 写同一个对象，产生轮询/WS 字段覆盖竞态（`projectStatuses` 由 `ProjectProvider` 持有，`useProjectStore.tsx:40`）。**改为新增独立的批量进程状态端点** `/api/projects/processes/statuses`，与会话状态彻底解耦、单一 owner：

```go
// 新增路由：r.Get("/api/projects/processes/statuses", s.listProjectProcessStatuses)
type projectProcessStatusItem struct {
    ID           string     `json:"id"`
    RunStatus    RunStatus  `json:"runStatus,omitempty"`     // 缺省默认填 stopped
    RunPID       *int       `json:"runPid,omitempty"`        // 仅 running/stopping 有值，与单项目端点 pid 命名对齐
    RunStartedAt *time.Time `json:"runStartedAt,omitempty"`
}
```

handler 遍历**现存项目的 runner**（`listProjects` 得到项目 id 集合，逐 id 查 `runManagers`），未创建 runner 的项目 `RunStatus` 置 `stopped`。返回 `[]projectProcessStatusItem`。

**新增轻量快照方法（最佳实现关键，避免 N×200 日志拷贝）**：现有 `StatusSnapshot()`（`project_runner.go:747`）每次内部调用 `pr.logBuf.Recent(200)`（持锁深拷贝 200 条），即使调用方只要 status。批量每 10s 对 N 个项目各调一次等于 `N×200` 槽位拷贝——与 3.1"不背日志"相悖。故为 runner 追加**不碰 logBuf 的轻量快照**：

```go
// projectRunner —— 本地版（含 PID）
func (pr *projectRunner) LightStatusSnapshot() RunStatusResponse {
    pr.mu.RLock()
    defer pr.mu.RUnlock()
    snap := RunStatusResponse{Status: pr.status, ExecutionTarget: pr.executionTarget} // 不调 logBuf
    if !pr.startedAt.IsZero() { startedAt := pr.startedAt; snap.StartedAt = &startedAt }
    if pr.pid > 0 && (pr.status == RunStatusRunning || pr.status == RunStatusStopping) {
        pid := pr.pid; snap.PID = &pid
    }
    if pr.hasExitCode { exitCode := pr.exitCode; snap.ExitCode = &exitCode }
    return snap
}
```

> ⚠️ **SSH 版省略 PID**：`sshProjectRunner` **没有本地 PID 概念**（`ssh_project_runner.go:345` 注释"SSH 远端进程 PID 不可靠获取，统一不返回"），其 `LightStatusSnapshot()` 不设 `PID`。因此 **SSH 项目的 `runPid` 恒为空**，前端渲染勿依赖 PID。（SSH 版同样不需要 `ExecutionTarget` 填充。）

`projectProcessStatuses handler` 内取 `s.runManagersMu.RLock()` 是安全的——与 DB 迭代锁不同资源，`projectRunManagerForExistingProject`/`deleteProjectLocked` 都在该锁下改 map，读锁无死锁：

```go
// 伪代码：
ids := listAllProjectIDs()                    // projects 表
s.runManagersMu.RLock()
for _, id := range ids {
    item := projectProcessStatusItem{ID: id, RunStatus: RunStatusStopped}
    if runner, ok := s.runManagers[id]; ok {
        snap := runner.LightStatusSnapshot()
        item.RunStatus, item.RunPID, item.RunStartedAt = snap.Status, snap.PID, snap.StartedAt
    }
}
s.runManagersMu.RUnlock()
```

> `PID` 语义：`StatusSnapshot()` 只在 `running/stopping` 时填充 PID（`project_runner.go:759`），`failed`（崩了）或 `stopped` 时 PID nil、但有 `ExitCode`。卡片若要显示退出码，再带 `runExitCode`（本方案未要求）。

#### 5.1.3 WS 广播通道（新增，仿 notificationSubs 但不落库）

在 `Server` 结构（`app.go:502`）新增字段：

```go
processStatusSubs    map[*websocket.Conn]*processStatusSubscriber
processStatusSubMu   sync.Mutex
```

新增订阅者结构（仿 `runLogSubscriber` / `notificationSubscriber`，`notification.go:35`、`app.go:222`）：

```go
type processStatusSubscriber struct {
    conn           *websocket.Conn
    send           chan RunStatusEvent
    closeOnce      sync.Once
    closeFrameOnce sync.Once
}
func (sub *processStatusSubscriber) close() { sub.closeOnce.Do(func() { close(sub.send) }) }
func (sub *processStatusSubscriber) closeWithStatus(code int, reason string) {
    sub.close()
    sub.closeFrameOnce.Do(func() { initiateWebSocketClose(sub.conn, code, reason) })
}
```

**关键：无写入锁，靠单 writer goroutine。** 现有订阅者（`runLogSubscriber`/`notificationSubscriber`）都没有 write mutex，而是每个连接一个 `send` 队列，由**独立的 writer goroutine**消费（仿 `notification.go:114-124`）：

- 广播方只向 `sub.send` 投递（`select ... default:` 满则断连），**永不做并发 `WriteMessage`**；
- writer goroutine 串行 `WriteMessage`，天然避免并发写同一连接的竞态；
- `close()` 关闭队列使 writer goroutine 退出。

新增 WS 端点与广播函数：

```go
// WS 端点：连接后推送全量进程状态快照，之后实时推变更。
func (s *Server) subscribeProcessStatuses(w http.ResponseWriter, r *http.Request) { ... }

// 广播：不落库，直接推给所有订阅者；慢客户端断连。
func (s *Server) broadcastProcessStatus(event RunStatusEvent) { ... }

// 停机时关闭所有进程状态订阅者，须并入 Server.Close 关闭清单。
func (s *Server) closeAllProcessStatusSubscribers() { ... }
```

**端点生命周期必须完全对齐现有 WS 约定**（`websocket_lifecycle.go`），`subscribeProcessStatuses` 内部需依次：
1. `beginWebSocketSubscription(w)`（计入 `websocketWG`，`websocket_lifecycle.go:83`）+ `defer s.websocketWG.Done()`；
2. upgrade 后 `s.isClosing()` 检查 + `initiateWebSocketClose` 停机关帧；
3. `startWebSocketHeartbeat(conn, "/ws/processes")`（心跳/读超时）；
4. 先启动 writer goroutine，再 `addProcessStatusSubscriber`（`mu` 锁内检查 `closing`，仿 `addNotificationSubscriber`，`notification.go:168`）；
5. 注册后推送全量快照；
6. 读循环检测断开，defer 内 `sub.close()` + `conn.Close()` + `stopHeartbeat` + `<-writerDone`。

> ⚠️ **必须在 `Server.Close()` 停机清单挂接**：`app.go:571` 附近已有明确的关闭序列
> `closeAllConversationSubscribers()` / `closeAllRunLogSubscribers()` / `closeAllNotificationSubscribers()`
> + `waitForWebSocketSubscriptions()`（`app.go:572`，其实现见 `websocket_lifecycle.go:100`）。
> 本方案须在此序列前补一行 `s.closeAllProcessStatusSubscribers()`（仿 `closeAllRunLogSubscribers`，
> `app.go:5492`：锁内收集全部订阅者并清空 map，逐个 `closeWithStatus(CloseGoingAway)`，WG 等待），
> 否则新连接不会被停机流程发现，`Close()` 将挂起（websocketWG 计入了本订阅也不会被释放）。

> 🧭 **路由选择 `/ws/processes` 而非 `/ws/projects/...`**：现有项目前缀已被
> `/ws/projects/{projectID}/run`（`app.go:796`）占用——该段是命名参数树节点。若再加静态段
> `/ws/projects/processes`，会落入"命名参数与静态段同位置"的 chi 路由脆弱区（chi v5.2.3
> 虽静态优先，但歧义易在后续加路由时踩坑）。本次广播是**全量进程状态广播**（全局语义，
> 与 `/ws/notifications` 同级，`app.go:797`），不是按项目订阅，放根级 `/ws/processes` 最干净，
> 可挂载于 `r.Get("/ws/processes", s.subscribeProcessStatuses)`，与现有 `/ws` 组并列。
>
> 🆚 **REST 端点是安全挂载，勿被上面的 WS 顾虑误导**：批量端点 `/api/projects/processes/statuses` 落在 `/api/projects/` 树，该树**已有静态段先例**——`/api/projects/validate`（`app.go:714`）、`/api/projects/statuses`（`app.go:716`）与 `/api/projects/{projectID}`（`app.go:718`）并存且正常工作，说明 chi 静态段优先解析已在生产验证。新增 `processes/statuses` 两段静态路径沿用同一 proven 模式即可，**无冲突**。只有 WS 的 `/ws/projects/` 树之前是纯 `{projectID}/run` 命名参数、无静态先例，才需规避到根级 `/ws/processes`。

**订阅时全量快照**：连接建立后，遍历 `runManagers`，对每个 runner 取 `LightStatusSnapshot()`（复用 5.1.2 轻量取值，不碰日志），组装 `RunStatusEvent`。**按"每项目一帧"逐帧发送**——首帧快照与后续实时变更用的是**完全相同的帧形状**（`projectId + status + pid + startedAt`），前端对"快照帧"和"实时帧"走同一条处理逻辑，无需分支。这保证 WS 首帧即收敛，且前端代码零特判。

**广播触发点**：进程状态发生用户可见变化时触发：
- `start()` 成功置 `running`（`project_runner.go:273`）后；
- `wait()` 置 `stopped/failed`（`project_runner.go:629/634`）后；
- `start()` 失败置 `failed`（`project_runner.go:209/242/252/262` 多分支）后；
- `stop()` 置 `stopping`（`project_runner.go:662`）后。

实现方式：考虑到 `projectRunner` 当前仅注入 `logBroadcaster`，需**为接口增加状态回调**(同时补上 5.1.2 的轻量快照)：

```go
type projectRunnerInterface interface {
    // ...现有方法...
    StatusSnapshot() RunStatusResponse
    LightStatusSnapshot() RunStatusResponse      // 新增：批量接口用，不含 logBuf 拷贝
    setStatusListener(func(RunStatusEvent))      // 新增：状态变更回调
}
```

`projectRunner` 内部在每次状态切分归位后，若已设置 listener 则回调组装好的 `RunStatusEvent`。Server 侧注入 `func(e) { s.broadcastProcessStatus(e) }`。SSH runner 同样实现（远端 `Wait` 状态回传，`ssh_project_runner.go` 与本地状态机相同构，可直接套用）。

**回调触发位置（已核实，锁外触发、无死锁；需覆盖不对称的启动失败路径）**：四个状态变更点（`project_runner.go`）在 happy-path 都是**先 `pr.mu.Unlock()`、再 `emitLog`**——`running` 在 `:273-274`、`failed/stopped`（wait）在 `:634-637`、`stopping` 在 `:662-663`。**因此 happy-path 状态回调与 `emitLog` 并列放在 Unlock 之后**，与现有 `logBroadcaster` 同一触发位、同一锁状态。

⚠️ **启动失败路径没有 `emitLog` 插槽**：`start()` 内 `newProjectRunCommand` 失败（`:204-215`）与 `cmd.Start()` 失败（`:260-268`）只置 `failed` → close(exitChan) → Unlock → return，**不写日志**。故状态回调**不能只挂在 emitLog 边**，应为这三条失败分支各补一个独立的 `emitStatus()`（Unlock 后调用），否则"启动即崩"状态不会推到总览。（可封装 `emitStatus()` 供 emitLog 并列处与失败分支共用。）

> 备选简化：也可在状态变更点直接调用 Server 的广播，但通过接口回调保持 runner 与 Server 解耦，与现有 `logBroadcaster` 注入模式一致（`project_runner.go:98`），推荐回调。

### 5.2 前端模型与状态管理

#### 5.2.1 类型扩展

进程状态**不改现有 `ProjectStatus`**（那是会话状态，由 `ProjectProvider` 拥有），新增独立类型：

```ts
export type RunStatus = 'stopped' | 'starting' | 'running' | 'stopping' | 'failed';
export type ProjectProcessStatus = {
  runStatus: RunStatus;
  runPid?: number;
  runStartedAt?: string | null;
};
export type ProjectProcessStatusMap = Record<string, ProjectProcessStatus>;
```

#### 5.2.2 全局状态（新增 `ProcessStatusProvider`，仿 `NotificationProvider` 单例）

**关键架构决策（实施前审计修正）**：进程状态**不放**进 `useProjectStore`/`ProjectProvider`。原因：
- `ProjectProvider` 的职责是"项目数据拉取 + 会话草稿持久化"，不含长连接生命周期；把 WS（重连/去重/closing）塞进去会职责混乱。
- `projectStatuses` 若被两个 owner（ProjectProvider 轮询写 runStatus + WS 写 runStatus）同时写同一对象，会字段覆盖竞态。
- 代码库已有成熟先例：**`NotificationProvider`**（`NotificationProvider.tsx`）就是一个位于根部的独立单例 Provider，持有 `wsRef` + 指数退避重连 + `BroadcastChannel` 跨 Tab + 内存事件集防重复。

因此新增 `ProcessStatusProvider`，**逐行对照 `NotificationProvider` 的形态**：

- **挂载位置**：根部，与 `NotificationProvider` 同层（`App.tsx`，`NotificationProvider` 与 `ProjectProvider` 之间）。
- **REST 兜底**：挂载时 + 每 10s 拉 `/api/projects/processes/statuses`，得到 `ProjectProcessStatusMap` 写入 state。
- **WS 实时**：`createWebSocket('/ws/processes')`，`onmessage` 解析 `RunStatusEvent`，按 `projectId` 原地更新对应条目（`{runStatus: e.status, runPid: e.pid ?? prev.runPid, runStartedAt: e.startedAt}`）。
- **自动重连**：`onclose` → 指数退避 `setTimeout`（仿 `NotificationProvider.tsx:229-234`），`wsRef` 管理。
- **跨 Tab**：可选 `BroadcastChannel("app-process-status")` 转发（仿 `NotificationProvider.tsx:253-270`），多个标签页实时一致。
- **暴露 hook**：`useProcessStatusMap()`（`Record<string, ProjectProcessStatus>`）。

现有 `useProjectStore` **零改动**（`refreshStatuses` 不再需要碰进程字段）。`DashboardPage` 同时用 `useProjectContext()`（会话状态）+ `useProcessStatusMap()`（进程状态）。

### 5.3 前端卡片渲染

`DashboardPage.tsx` 的 `ProjectCard`（`DashboardPage.tsx:158`）新增**独立的开发进程状态点徽标**，与会话状态徽标（现有 "正在执行 / 已就绪 / 工具不可用"）并列：

- `ProjectCard` 增加 `runStatus` prop（由 `useProcessStatusMap()` 传入），复用 `statusLabels` / `statusColors`（`run-model.ts:47/55`）。
- 渲染逻辑：

```tsx
const runStatus = (runStatusProp ?? 'stopped') as RunStatus;
{/* 已停止可灰点或不显示；关键把 running/starting/stopping/failed 可视化 */}
{runStatus !== 'stopped' ? (
  <span className={`run-state run-state-${runStatus}`} title={`开发进程: ${statusLabels[runStatus]}`}>
    <i style={{ background: statusColors[runStatus] }} />
    {statusLabels[runStatus]}
  </span>
) : null}
```

> 从 WS/REST 取不到进程状态时默认 `stopped`；为减少噪声，"已停止"可省略徽标（进程未启动是常态），仅 running/starting/stopping/failed 显示。

卡片视觉示意：

```
┌──────────────────────────────────────────────┐
│  [M]  ● 正在执行  [Windows]            [×] │  ← 会话状态(现有)
│        ● 运行中                             │  ← 开发进程状态(新增)
│  项目 · my-app                             │
│  正在构建首页                               │
└──────────────────────────────────────────────┘
```

**筛选维度**：`ProjectFilter`（`types.ts:5`，all/running/ready/offline）当前按会话状态筛选。本次**不扩展运行筛选**（会话"进行中"与进程"运行中"是两维，混入会混乱）；卡片内并置展示即可。如需后续给进程状态加筛选，另立维度，不在本次范围。

### 5.4 状态合并优先级（WebSocket 与 REST 幂等）

进程状态来源只在一个 owner（`ProcessStatusProvider`）内，以下两者**写同一字段、值语义相同**，幂等：
- 初始态：REST 批量，未启动为 `stopped`。
- WS 实时事件覆盖：优先级最高（秒级）。
- 10s 轮询兜底：次高，断线重连后首次 REST 拉取也会覆盖收敛。
- WS 可能短暂投递与轮询重叠的事件，但都是同一份 `RunStatus`，最终值一致。

## 7. 边界与竞态处理

1. **并发删除项目**：WS / REST 事件到达时若该项目已不在进程状态 map 中（或已被删除列表移除），`ProcessStatusProvider` 保留最新值即可，卡片按 `project.id` 取不到时回退空/`stopped`；不因一个项目的缺失影响其他条目（`Record` 天然隔离）。
2. **重建 runner 与广播先后**：`statusListener` 仅在 runner 创建后注入；若项目从未创建 runner，REST 批量返回 `stopped`，WS 也不会收到该项目的 push（因为根本没进程），语义一致。
3. **慢客户端**：`broadcastProcessStatus` 满队列直接断连（同 `broadcastRunLog`，`app.go:5456`）。
4. **全局订阅者无需按项目清理**：run 日志通道是**按项目**订阅（删除时需 `closeProjectRunLogSubscribers(projectID)`，`app.go:1860`/`5476`），而 `processStatusSubs` 是**全局**的，删除项目时**不需要逐项目清理**——删项目即删 runner（见下行），此后自然不再为该 ID 广播。实现者勿为此过度设计按项目订阅表。

> ✅ **已核实：删除即清理，无残留**。`deleteProjectLocked`（删除项目）显式 `delete(s.runManagers, projectID)`（`app.go:1855-1858`）并 `Retire()` 停进程。因此 `runManagers` **不残留已删项目**，WS 全量快照遍历它是安全的，不会推已删项目；REST 批量端点同样基于现存项目 id，天然只覆盖现存项目。

## 8. 与现有功能的关系

- **不完全替换**：现有"会话运行状态"徽标保留，开发进程状态徽标**新增并置**，两者语义独立、互补。
- **复用而非复制**：状态机、文案、颜色、WS 订阅生命周期模式全部复用现有实现；新增的是**独立的进程状态批量端点 + 全局 WS 广播通道 + 独立 Provider**，不侵入会话状态链路。
- **通知中心不受影响**：不写 `notifications` 表，不产生需手动忽略的进程通知。
