# 架构设计

> 日期：2026-07-17（初版）/ 2026-08-12（按实际实现重写）
> 架构方向：多客户端控制台 + 控制平面 + 多环境 Runner。
> 当前形态：Windows 桌面端（Tauri 壳 + Go sidecar）+ Web 控制台，本地一体化部署。

## 0. 阅读说明

本文档分两部分：

- **§1–§7 描述当前实际已落地的架构**。这部分与代码一一对应，是理解系统的可靠入口。
- **§8 描述目标架构的演进方向**。这些是规划中的能力，**当前代码尚未实现**，保留作为扩展边界参考。早期版本（2026-07-17）将目标架构当作已实现来描述，会误导读者，本次重写把两者明确分开。

一个核心事实：当前系统是**模块化单体**，控制平面和"执行平面"都在同一个 Go 进程（control-server）内，通过接口调用协作，没有独立的 Runner 服务。目标架构里的独立 Runner、gRPC、PostgreSQL/Redis/S3 目前都未落地。

## 1. 当前实际架构

```text
桌面端 (Tauri/Rust)              Web 浏览器
  ├─ 系统托盘 + 品牌面板            │
  ├─ 在线升级 (updater)            │
  └─ 内嵌 Go sidecar ──────────────┴──► Control Server (Go 单进程)
                                        ├─ HTTP API (chi)
                                        ├─ WebSocket 实时推送 (gorilla/websocket)
                                        ├─ 业务逻辑 (internal/app, 36 个文件)
                                        ├─ Agent Runner (Claude / Codex, 本地接口实现)
                                        │   ├─ wsl-local   (Windows 宿主跨 WSL 执行)
                                        │   ├─ windows-local (Windows 原生执行)
                                        │   └─ ssh-{id}    (SSH 远程执行)
                                        ├─ Filesystem (本地 UNC / SFTP)
                                        ├─ Git 操作 (本地 CLI / SSH 远端)
                                        └─ SQLite (data/milevia.db, 34 张表)
```

系统的关键分界仍是：**控制平面决定"做什么、由谁做、结果是什么"；执行平面负责"在何处、如何执行"**。只是当前两者同进程，通过 Go 接口而非网络协议通信。

### 1.1 技术栈

| 层 | 当前选型 |
| --- | --- |
| 前端 | React + TypeScript + Vite |
| 桌面端 | Tauri (Rust) + 内嵌 Go sidecar |
| 后端 | Go + `net/http` + `chi` 路由 |
| 实时通信 | `gorilla/websocket`（6 个 WS 端点） |
| 数据存储 | SQLite（`go-sqlite3`，需 CGO） |
| AI 工具 | Claude Code CLI、Codex CLI（经 `wsl.exe` / 原生 / SSH 调用） |
| API 契约 | 手写 HTTP 路由（无 OpenAPI 生成） |

### 1.2 当前没有的（目标架构里有，但代码未实现）

- 独立 Runner 服务（`apps/runner` 全是 `.gitkeep`）
- gRPC + Protocol Buffers（Control ↔ Runner 通信）
- OpenAPI 契约生成（`packages/contracts/openapi` 为空）
- PostgreSQL / Redis / S3 对象存储
- 身份、工作区、成员、角色系统（单机单用户）
- 独立的 Artifact、Policy & Audit、Integration 模块
- `apps/worker` 异步任务服务（为空）
- `packages/` 下的共享包（contracts/domain/ui/sdk/plugin-kit 均为占位）

## 2. 客户端架构

所有客户端共用同一个 Control Server 的 HTTP API 和业务模型。

| 客户端 | 当前状态 | 主要能力 |
| --- | --- | --- |
| Web 控制台 | 已实现 | 管理项目、任务、运行过程、审阅结果、Git、文件、AI 配置、优化建议。 |
| 桌面应用 | 已实现 | Tauri 原生壳，内嵌 Go sidecar，增加系统托盘、品牌面板、在线升级、本机进程管理。Web 前端复用为 WebView 内容。 |
| 外部集成 | 未实现 | 规划中。 |

### 2.1 Web 前端

前端采用 **React + TypeScript + Vite** 的单页控制台架构，10 个页面、6 个功能模块（files/git/insights/run/tasks/updater）。

```text
页面层 (pages/)
  -> 功能模块层 (features/)
    -> 通用组件与状态层 (components/, stores/)
      -> 前端服务层 (lib/)
        -> Control Server HTTP API + WebSocket
```

页面包括：DashboardPage、ImportProjectPage、ConversationPage、TaskBoardPage、GitWorkbenchPage、FilesPage、ProjectRunPage、SSHManagerPage、AgentProfilesPage、InsightsPage。

前端通过项目 ID、任务 ID、运行 ID 获取信息。前端不持有项目文件权限，不直接执行 Git 或 AI CLI，也不解析某个 CLI 的原始输出。

### 2.2 桌面端

桌面端是 **Tauri (Rust)** 工程（`apps/desktop/src-tauri`），不是简单"复用 Web"。它是一个原生壳：

- **Go sidecar**：打包 `milevia-control.exe` 作为 sidecar，启动时绑定随机本地端口，主窗口 WebView 指向该端口。
- **approval helper**：打包 `milevia-approval.exe`，用于 AI 工具（Claude/Codex）的权限审批弹窗。
- **系统托盘**：自绘无边框品牌面板（替代原生菜单），支持 DPI clamp、预建窗口消除首点延迟。
- **在线升级**：`tauri-plugin-updater`，从 GitHub Pages 上的 `latest.json` 检查并安装更新。
- **安全连接**：稳定 Origin（`https://tauri.localhost`）+ session token 认证，WebSocket 子协议校验。

详见 `docs/17-Windows桌面端最终架构与实施方案.md`、`docs/23-Windows打包与在线升级方案.md`、`docs/27-系统托盘品牌面板实现.md`。

### 2.3 客户端契约

当前客户端通过**手写的 HTTP REST API**（116 个路由）访问 Control Server，实时过程订阅使用 **WebSocket**。没有 OpenAPI 定义文件，前端类型手写。

目标架构希望以 OpenAPI 固定跨语言契约，但尚未落地。

## 3. 后端架构（Control Server）

后端使用 **Go + `net/http` + `chi`**，是**模块化单体**。所有业务逻辑集中在 `apps/control-server/internal/app/` 下（36 个非测试 Go 文件）。

> 注：早期架构文档规划的 `internal/modules/`、`runner-gateway/`、`realtime/`、`integrations/`、`shared/` 目录目前都是 `.gitkeep` 空目录，实际代码全部在 `internal/app/`。

```text
Web / Desktop Client
  -> Control Server (单进程)
    -> internal/app/
      -> HTTP 路由 + WebSocket (app.go)
      -> Agent Runner 接口实现 (claude_runner / codex_runner / wsl_agent_runner / win_agent_runner / ssh_runner)
      -> 业务域 (task / orchestration / git / filesystem / insights / skills / notification / project_runner ...)
      -> SQLite 持久化
```

### 3.1 控制平面（实际实现）

Control Server 管理业务决策、记录和协调。它**直接**修改项目文件、调用 AI CLI、执行 Git——因为这些"执行平面"能力当前就内嵌在同一个进程里，通过接口调用。

| 实际模块 | 职责 | 代码位置 |
| --- | --- | --- |
| Project | 项目登记、项目规则、Runner 归属。 | `app.go`、`project_runner.go` |
| Task | 任务描述、验收、状态机、依赖。 | `task.go` |
| Run Orchestrator | 运行创建、排队、分发、停止；编排队列。 | `claude_runner.go`、`orchestration.go` |
| Agent Runner | Claude/Codex 的本地/WSL/Windows/SSH 执行适配。 | `claude_runner.go`、`codex_runner.go`、`wsl_agent_runner.go`、`win_agent_runner.go`、`ssh_runner.go` |
| Filesystem | 项目文件浏览/编辑（本地 UNC + SFTP）。 | `filesystem.go`、`fs_handler.go` |
| Git | 快照、暂存、提交、分支、push（本地 CLI + SSH 远端）。 | `git.go`、`git_operations.go`、`git_ssh.go` |
| Insights | AI 驱动的项目优化建议扫描。 | `insights.go` |
| Skills | Claude/Codex 的 SKILL.md 发现与展示。 | `skills.go` |
| Notification | 跨项目通知与 WebSocket 推送。 | `notification.go` |
| Agent Profiles | AI CLI 配置档案（密钥、端点、环境变量）。 | `agent_profiles.go`、`profile_secrets.go`、`agent_target_env.go` |
| Runner Registry | Runner 注册、持久化、环境分发。 | `runner_registry.go`、`runner_persistence.go` |

未实现的模块（目标架构里有）：Identity & Workspace、Review（独立模块）、Artifact、Policy & Audit、Integration。

### 3.2 执行平面（实际实现）

"Runner" 当前不是一个独立服务，而是 Control Server 进程内的 `AgentRunner` 接口实现。按项目环境分发到不同实现：

| Runner | 执行环境 | 代码 |
| --- | --- | --- |
| `wsl-local` | Windows 宿主服务端，跨 `wsl.exe` 到 WSL 执行 AI CLI；文件走 UNC | `wsl_agent_runner.go`、`wsl_agent_run.go` |
| `windows-local` | WSL 服务端，跨到 Windows 侧执行；或 Windows 原生执行 | `win_agent_runner.go` |
| `ssh-{id}` | SSH 远程机器上执行 AI CLI 和 Git；文件走 SFTP | `ssh_runner.go`、`ssh_project_runner.go`、`ssh_connection.go` |

环境分发逻辑在 `agent_target_env.go`，根据服务端 OS 和项目 runner 字段决定用哪个 AgentRunner 实现。

### 3.3 AI 工具适配层

```text
任务
  -> Run Orchestrator
  -> AgentRunner 接口 (按环境分发到具体实现)
  -> Claude Code / Codex CLI
```

接口定义（`claude_runner.go`）：

- `AgentRunner`：`Version` / `CheckUpdate` / `Update` / `Run`
- `StreamingAgentRunner`：`StartSession`（流式对话）
- `CodexCapableRunner`：`CodexReady` / `CodexVersion` / `CodexCheckUpdate` / `CodexUpdate`（Codex 支持）

新增 AI 工具只增加 Adapter 实现，不需要改动前端或任务模块。

## 4. 数据与事件架构

当前所有数据都存在 **单个 SQLite 文件**（桌面端 `data/milevia.db`，开发态 `data/auto.db`），共 34 张表。没有 Redis，没有对象存储。

| 数据类别 | 内容 | 当前存储 |
| --- | --- | --- |
| 业务数据 | 项目、任务、运行、对话、消息、配置档案、SSH 连接、快捷任务。 | SQLite |
| 过程事件 | AI 消息、工具动作、命令输出、状态变化。 | SQLite `events` 表 |
| 工件数据 | diff、日志。 | SQLite + 文件系统（无独立对象存储） |
| 审计数据 | Git 操作、快捷任务审计、编排任务事件。 | SQLite `git_operations` / `shortcut_audit_events` / `task_events` |

核心关系：

```text
Project
  -> Task
    -> TaskRun
      -> Run
        -> Event / Artifact / Review Decision
  -> Conversation
    -> Message
      -> Run
        -> Event
```

一个任务可以运行多次。每次 Run 都独立保存过程和结果。

实时页面由过程事件驱动：AgentRunner 上报事件，Control Server 记录后通过 WebSocket 推送给当前页面；页面重新打开时先读取历史过程，再继续接收新事件。6 个 WebSocket 端点：`/ws/conversations/{id}`、`/ws/projects/{id}/run`、`/ws/processes`、`/ws/notifications` 等。

## 5. 通信与扩展边界

| 通信双方 | 当前实现 |
| --- | --- |
| 客户端 ↔ Control Server | 手写 HTTP REST + WebSocket。客户端不接触项目文件。 |
| Control Server ↔ AgentRunner | 同进程 Go 接口调用（非网络）。 |
| AgentRunner ↔ AI 工具 | 由各 Runner 实现管理（`wsl.exe` / 原生 / SSH），工具差异不扩散到业务模块。 |
| Control Server ↔ 外部系统 | 无统一 Integration 模块；Git 凭据、SSH 连接各自管理。 |

## 6. 部署形态

当前只支持**本地一体化**部署：Tauri 桌面端内嵌 sidecar，所有组件在同一台机器。

## 8. 目标架构（演进方向，尚未实现）

以下是架构演进的**规划方向**，当前代码未实现，保留作为扩展边界参考。新增功能应朝这个方向靠拢，但不应假设已经具备这些能力。

### 8.1 目标总体架构

```text
客户端层
  Web 控制台 / 桌面应用 / 外部集成
                    |
访问层
  身份与权限 / 统一 API (OpenAPI) / 实时过程推送
                    |
控制平面
  工作区 / 项目 / 任务 / 运行编排 / 审阅 / 通知 / 集成
                    |
执行平面
  Runner 管理 / WSL Runner / Windows Runner / 远程 Runner / AI 适配器
```

### 8.2 目标存储边界

| 存储 | 承载内容 | 原因 |
| --- | --- | --- |
| PostgreSQL | 业务数据、事件索引、审阅与审计记录。 | 支持多工作区、事务、关联查询。 |

| S3 兼容对象存储 | 完整日志、diff、测试报告、截图。 | 工件体积和保留周期独立于业务数据。 |

当前 SQLite 阶段在引入远程 Runner 或多人协作前可继续使用。

### 8.3 目标通信契约

| 通信双方 | 目标契约 |
| --- | --- |
| 客户端 ↔ Control Server | OpenAPI 定义的 HTTP API + WebSocket。 |
| Control Server ↔ Runner | gRPC + Protocol Buffers 双向通信。 |
| Runner ↔ AI 工具 | Adapter 管理。 |

### 8.4 目标控制平面模块

| 模块 | 职责 | 后续扩展方向 |
| --- | --- | --- |
| Identity & Workspace | 用户、工作区、成员与角色边界。 | 多团队、组织级权限、单点登录。 |

| Run Orchestrator | 运行创建、排队、分发、停止、重试。 | 多 Runner 调度、并发策略、自动路由。 |

| 新能力 | 在现有架构中的位置 |

| 效率统计 | 基于 Run、Event 和 Artifact 数据增加分析模块。 |

## 9. 架构结论

当前平台采用 **React + TypeScript Web 控制台 + Tauri 桌面端 + Go 单进程 Control Server + SQLite** 的架构。Control Server 通过手写 HTTP API + WebSocket 对外，通过 Go 接口在进程内调用 Agent Runner 执行 Claude/Codex。桌面端内嵌 sidecar，提供系统托盘和在线升级。

这是**本地一体化的模块化单体**，已能完成"加载项目 → 下发任务 → 查看过程 → 查看结果"的完整闭环，并支持 Windows/WSL/SSH 三种执行环境。

目标架构已区分客户端、控制平面、执行平面、数据与工件层，并固定 Workspace→Project→Task→Run→Event 的核心关系。当后续需要团队协作、远程 Runner、云端控制时，按目标架构演进——把进程内接口拆为 gRPC 服务、把 SQLite 迁移到 PostgreSQL/Redis/S3、引入身份与 Integration 模块——而不需要重新设计核心模型。
