# 架构设计

> 日期：2026-07-17  
> 架构方向：多客户端控制台 + 控制平面 + 多环境 Runner。  
> 首期形态：Web 控制台和 WSL Runner 运行在同一台机器；目标形态：可支持 Web、桌面端和多个 Runner。

## 1. 架构目标

这是一个管理多个项目、下发 AI 开发任务并观察全过程的平台。架构既要支持当前的本地 WSL 项目，也要支持后续的团队协作、桌面端、远程机器、分支、部署和统计能力。

架构设计的目标不是预先实现所有功能，而是先固定不会轻易变化的边界：

- 项目由工作区管理，任务属于项目；
- 一项任务可以有多次 AI 运行；
- Runner 是唯一接触项目目录和执行 AI 工具的角色；
- 页面只通过控制核心管理项目、任务和运行；
- AI 工具、项目环境和客户端界面都可以替换或新增；
- 任务过程、结果和人工决定可以完整追溯。

这些边界稳定后，后续增加功能只是在对应模块中扩展，不需要推翻核心架构。

## 2. 目标总体架构

```text
客户端层
  Web 控制台 / 桌面应用 / 后续外部集成
                    |
访问层
  身份与权限 / 统一 API / 实时过程推送
                    |
控制平面
  工作区 / 项目 / 任务 / 运行编排 / 审阅 / 通知 / 集成
                    |
执行平面
  Runner 管理 / WSL Runner / Windows Runner / 远程 Runner / AI 适配器
                    |
数据与工件层
  业务数据 / 过程事件 / 审计记录 / diff、日志和部署等工件
                    |
项目环境
  本机项目 / WSL / 容器 / 远程 Linux 服务器 / 后续云环境
```

系统的关键分界是：**控制平面决定“做什么、由谁做、结果是什么”；执行平面负责“在何处、如何执行”**。这使项目位置和 AI 工具变化时，页面和任务模型都不需要重做。

## 3. 客户端架构

所有客户端共用同一个控制核心和业务模型，只在交互方式上不同。

| 客户端 | 定位 | 主要能力 |
| --- | --- | --- |
| Web 控制台 | 首期主入口 | 管理项目、任务、运行过程、审阅结果和后续协作。 |
| 桌面应用 | 后续本机高频入口 | 复用 Web 业务页面，并增加本机目录、终端、编辑器和 Runner 管理能力。 |
| 外部集成 | 后续扩展入口 | 供 Git、部署、消息和其他系统读取状态或触发工作流。 |

### 3.1 Web 前端

前端采用 **React + TypeScript + Vite** 的单页控制台架构。

```text
页面层
  -> 功能模块层
    -> 通用界面与状态层
      -> 前端服务层
        -> 控制核心
```

| 前端层级 | 职责 |
| --- | --- |
| 页面层 | 组织项目、任务、运行过程、审阅、设置等页面。 |
| 功能模块层 | 按工作区、项目、任务、运行、审阅等业务组织界面和状态。 |
| 通用界面与状态层 | 提供导航、表格、表单、状态、日志、diff 等可复用能力。 |
| 前端服务层 | 与控制核心通信、订阅实时状态、维护页面数据缓存。 |

前端通过工作区 ID、项目 ID、任务 ID 和运行 ID 获取信息。前端不持有项目文件权限，不直接执行 Git 或 AI CLI，也不解析某个 CLI 的原始输出。

### 3.2 页面架构

| 页面 | 主要职责 |
| --- | --- |
| 工作区总览 | 查看项目、任务队列、运行状态和需要处理的事项。 |
| 项目列表 | 加载和进入已管理项目。 |
| 项目详情 | 聚合一个项目的基本状态、任务、运行、代码变更和后续能力入口。 |
| 任务页面 | 创建、编辑、查看、筛选和管理任务。 |
| 运行过程页面 | 实时展示 AI 对话、操作、命令输出、文件变更和错误。 |
| 结果审阅页面 | 查看任务结果、变更和检查证据，作出继续、接受或驳回决定。 |
| 设置页面 | 管理工作区、项目规则、Runner、AI 工具与集成配置。 |

### 3.3 客户端契约

Web、桌面端和外部集成通过 **OpenAPI** 定义的 HTTP API 访问控制平面。OpenAPI 是跨语言契约，因此前端可以生成 TypeScript 客户端与类型，后端也不需要为了共享类型而绑定到 TypeScript。

浏览器的实时过程订阅使用 WebSocket。实时事件的身份和顺序仍由项目、任务和运行模型定义，而不是由某个前端框架定义。

## 4. 后端架构

后端使用 **Go + 标准 `net/http` + `chi`**。首期采用模块化单体，而不是直接拆分微服务。模块化单体能快速完成产品闭环，同时模块边界、事件和 Runner 协议保证后续可独立扩展。

```text
Web / Desktop Client
  -> Control Server
    -> 业务模块
      -> 运行编排与 Runner Gateway
        -> Runner
```

### 4.1 控制平面

Control Server 是控制平面的核心。它不直接修改项目文件或调用 AI CLI，而是管理业务决策、记录和协调。

| 模块 | 职责 | 后续扩展方向 |
| --- | --- | --- |
| Identity & Workspace | 用户、工作区、成员与角色边界。 | 多团队、组织级权限、单点登录。 |
| Project | 项目登记、项目规则、项目与 Runner 的归属。 | Git 托管、项目模板、项目健康度。 |
| Task | 任务描述、验收要求、优先级、状态和依赖关系。 | 任务模板、计划拆分、跨项目任务。 |
| Run Orchestrator | 创建运行、排队、分发、停止、重试和恢复。 | 多 Runner 调度、并发策略、自动路由。 |
| Review | 用户对结果的继续、接受、驳回和确认记录。 | 合并请求、审批流、变更单。 |
| Event & Realtime | 保存过程事件并向客户端实时推送。 | 通知、订阅、搜索和统计。 |
| Artifact | 管理 diff、日志、测试报告、截图和部署结果等工件。 | 工件保留、下载、跨运行对比。 |
| Integration | 管理 Git、部署、消息等外部系统连接。 | 第三方插件和自动化工作流。 |
| Policy & Audit | 管理运行规则、权限边界和关键操作记录。 | 组织策略、合规与审计导出。 |

模块之间通过统一的领域对象和事件协作。即使以后其中一部分独立为服务，前端和 Runner 也不会因此改变通信模型。

### 4.2 执行平面与 Runner

Runner 是独立的 **Go** 执行服务。它运行在项目所在环境中，负责执行任务但不负责用户界面、任务规则或审阅流程。

| Runner 模块 | 职责 |
| --- | --- |
| Runner Registry | 让控制平面了解每个 Runner 的位置、能力和可用状态。 |
| Project Workspace | 定位与管理 Runner 所属环境中的项目目录和工作空间。 |
| Process Manager | 管理 AI 工具与项目命令的运行生命周期。 |
| AI Adapter | 屏蔽 Claude Code、Codex CLI 等工具的差异。 |
| Event Collector | 将工具输出、文件变更和结果转换为统一过程事件。 |
| Artifact Collector | 收集 diff、日志、检查报告和其他运行工件。 |
| Runner Client | 接收控制平面任务、上报状态、事件与结果。 |

首期项目在 WSL 中，因此使用 WSL Runner。后续项目位于 Windows、本机 Linux、容器或远程服务器时，只增加对应环境的 Runner，不改变项目、任务和页面结构。

Control Server 与 Runner 使用 **gRPC + Protocol Buffers** 进行双向通信。Runner 可以持续上报过程事件，也可以持续接收停止、继续或补充任务等控制指令。该协议与浏览器 API 分离，保证 Runner 可以独立部署、升级和扩容。

### 4.3 AI 工具适配层

```text
任务
  -> Run Orchestrator
  -> Runner
  -> AI Adapter
  -> Claude Code / Codex CLI / 后续工具
```

AI Adapter 将不同工具的对话、操作、文件变更、检查、完成和失败，转换为平台统一能理解的过程事件和结果。新增工具只增加 Adapter，不需要改动前端、任务模块或 Runner 调度逻辑。

## 5. 数据与事件架构

平台需要同时保存业务状态和大量过程信息，两者职责不同。

| 数据类别 | 内容 | 架构要求 |
| --- | --- | --- |
| 业务数据 | 工作区、用户、项目、任务、运行、审阅和配置。 | 支持关联、权限和状态查询。 |
| 过程事件 | AI 消息、工具动作、命令输出、状态变化和错误。 | 按运行顺序保存，可恢复实时页面。 |
| 工件数据 | diff、完整日志、测试报告、截图、构建和部署结果。 | 与运行关联，可长期保留和独立读取。 |
| 审计数据 | 关键任务操作、审批、策略变更和外部集成操作。 | 不可随普通业务记录一起丢失。 |

目标形态使用以下存储边界：

| 存储 | 承载内容 | 原因 |
| --- | --- | --- |
| PostgreSQL | 业务数据、事件索引、审阅与审计记录。 | 支持多工作区、事务、关联查询和长期演进。 |
| Redis | 任务队列、短期状态和实时分发协调。 | 将长时间运行任务与请求处理解耦。 |
| S3 兼容对象存储 | 完整日志、diff、测试报告、截图、构建和部署工件。 | 工件体积和保留周期独立于业务数据。 |

首期可以将这些组件以本地方式运行，但业务模块从第一天就按这三类存储职责设计，不以单机文件或单一数据库承担全部内容。

核心关系保持稳定：

```text
Workspace
  -> Project
    -> Task
      -> Run
        -> Event / Artifact / Review Decision
```

一个任务可以运行多次。每次 Run 都独立保存过程和结果，因此用户可以在任务层面看整体进展，在运行层面追溯某一次 AI 做了什么。

实时页面由过程事件驱动：Runner 上报事件，控制平面记录后推送给当前页面；页面重新打开时先读取历史过程，再继续接收新事件。这保证刷新页面、短暂断连或稍后审阅时都不会丢失过程。

## 6. 通信与扩展边界

| 通信双方 | 边界原则 |
| --- | --- |
| 客户端 <-> Control Server | 客户端只访问控制平面，不接触项目文件和 Runner。 |
| Control Server <-> Runner | 以任务、状态、事件和工件为统一通信语言，不暴露具体 CLI。 |
| Runner <-> AI 工具 | 由 Adapter 管理，工具差异不能扩散到其他模块。 |
| Control Server <-> 外部系统 | 通过 Integration 模块接入，Git、部署和消息系统彼此隔离。 |

系统需要长期保持以下契约：项目、任务、运行、事件、工件和审阅决定的身份与关联关系不因客户端、Runner 或 AI 工具变化而改变。这是未来不推翻架构的关键。

## 7. 部署形态

架构支持三种形态，业务模型和客户端使用方式保持一致。

| 形态 | 使用场景 | 架构关系 |
| --- | --- | --- |
| 本地一体化 | 当前单人 WSL 使用。 | Web 控制台、控制平面和 WSL Runner 在同一台机器。 |
| 团队自托管 | 多项目、多成员或多机器。 | 一个共享控制平面，多个环境中的 Runner 接入。 |
| 云端控制 | 后续跨设备和组织使用。 | 云端控制平面，用户机器或服务器保留 Runner。 |

首期采用本地一体化部署，但内部仍按控制平面和 Runner 分层。以后从同机 Runner 变成远程 Runner 时，不需要重写页面或任务管理。

## 8. 项目目录结构

项目使用单仓库结构。目录先按目标架构建立，未实现的应用和包可保留为空或在需要时创建；重点是边界和依赖方向不变。

```text
milevia/
├── docs/                         # 产品、架构、数据和交互文档
├── apps/
│   ├── web/                      # React Web 控制台
│   ├── desktop/                  # 后续桌面客户端，复用 Web 业务界面
│   ├── control-server/           # Go 控制平面
│   │   ├── cmd/                  # 控制服务启动入口
│   │   └── internal/
│   │       ├── modules/          # 工作区、项目、任务、运行、审阅等业务模块
│   │       ├── realtime/         # 实时过程与通知边界
│   │       ├── runner-gateway/   # Runner 管理与 gRPC 通信边界
│   │       ├── integrations/     # Git、部署、消息等外部集成
│   │       └── shared/           # 控制平面通用能力
│   ├── runner/                   # 可部署到不同环境的 Go 执行服务
│   │   ├── cmd/                  # Runner 启动入口
│   │   └── internal/
│   │       ├── registry/         # Runner 身份、能力和状态
│   │       ├── workspace/        # 项目工作空间
│   │       ├── process/          # 进程与运行生命周期
│   │       ├── adapters/         # AI 工具适配器
│   │       ├── events/           # 过程事件收集与转换
│   │       ├── artifacts/        # 运行工件收集
│   │       └── client/           # 与控制平面通信
│   └── worker/                   # 后续异步任务：通知、集成和工件处理
├── packages/
│   ├── contracts/                # OpenAPI、Protobuf 与各端生成的通信定义
│   ├── domain/                   # 与框架无关的核心业务规则
│   ├── ui/                       # Web 与桌面端复用的界面基础能力
│   ├── sdk/                      # 后续外部集成或客户端使用的 SDK
│   └── plugin-kit/               # 后续 AI 工具和集成扩展的插件边界
├── infrastructure/               # PostgreSQL、Redis、对象存储和部署定义
├── scripts/                      # 项目级开发、维护和迁移脚本
└── data/                         # 本地运行数据，不与源代码或项目目录混放
```

### 8.1 目录依赖规则

- `apps/web` 和 `apps/desktop` 只能访问 `packages/ui`、`packages/contracts` 和控制平面，不直接依赖 Runner。
- `apps/control-server` 负责业务协调，可依赖 `packages/domain` 与 `packages/contracts`，但不依赖某个具体 AI Adapter。
- `apps/runner` 负责环境与工具执行，可依赖 `packages/contracts` 和 `packages/plugin-kit`，不依赖页面。
- `packages/domain` 不依赖 React、Go Web 框架、Runner 或具体数据库，保证核心规则可长期复用。
- `packages/contracts` 是跨边界的稳定语言，修改必须兼顾前端、控制平面、Runner 和后续客户端。
- `infrastructure` 与 `data` 不承载业务逻辑，也不与被管理项目目录混合。

## 9. 后续扩展如何不改核心架构

| 新能力 | 在现有架构中的位置 |
| --- | --- |
| 桌面应用 | 新增 `apps/desktop`，复用控制核心、领域对象和 Web 界面能力。 |
| 多人协作 | 扩展 Identity & Workspace 模块，不影响项目、任务与 Runner 模型。 |
| 分支与合并请求 | 扩展 Project、Review 和 Integration 模块。 |
| 部署与回滚 | 扩展 Integration、Artifact 和 Review 模块。 |
| 多 AI 协作 | 扩展 Task 依赖与 Run Orchestrator，不改变单次 Run 的定义。 |
| 新 AI CLI | 新增 AI Adapter，不改变前端和任务管理。 |
| 远程执行环境 | 新增或注册 Runner，不改变控制平面与客户端。 |
| 效率统计 | 基于 Run、Event 和 Artifact 数据增加分析模块。 |

## 10. 架构结论

平台采用 **React + TypeScript Web 控制台 + Go 控制平面 + Go 多环境 Runner** 的架构。浏览器 API 以 OpenAPI 固定契约，Control Server 与 Runner 以 gRPC + Protocol Buffers 固定契约。

首期将 Web 控制台、Control Server 和 WSL Runner 一体运行，以最小成本完成真实任务闭环；目标架构已经区分客户端、控制平面、执行平面、数据与工件层，并固定工作区、项目、任务、运行、事件和工件的核心关系。

后续功能应围绕既有模块、契约和 Runner 机制增加，而不是让页面直接操作项目或让某个 AI CLI 进入业务核心。这样扩展桌面端、团队协作、远程 Runner、分支、部署和统计时，不需要重新设计平台骨架。
