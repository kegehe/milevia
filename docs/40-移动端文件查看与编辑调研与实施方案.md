## 0. 已定决策（2026-09-21）

| # | 问题 | 决定 |
| --- | --- | --- |
| 1 | 手机端是否允许编辑 | **一期就默认允许编辑**（不加二次授权开关） |
| 2 | 云端是否为文件内容破例落库 | **不落库**。读写内容全程不经云端数据库 |
| 3 | 延迟方案 | **走 WSS 上的请求-响应帧**，不排队轮询命令通道 |

决策 3 带来一个**比原方案更好的结果**，因此实际实现与原方案 §4.2 有一处**有意的偏差**：

> **写入也走新的请求-响应通道，不再经命令通道。**
>
> 原方案把写入留在命令通道是为了拿它的幂等键、审计与终态机。但那条通道会把 payload
> 落进云端的 `cloud_commands.payload`（jsonb），于是为满足决策 2 就得再加一层
> 「DB 存摘要占位 + 内容放内存 hold + 投递时还原」的机制 —— 而 hold 一旦被逐出，
> 重投就会发出空 payload。改走请求-响应通道之后，**文件内容从头到尾不碰数据库**，
> 决策 2 由结构本身保证，不需要任何补救机制。
>
> 连带消掉三个问题：
>
> - **256 KiB 的 payload 上限不再卡住写入**（那是命令通道的限制）；
> - **双白名单的结构性风险没有被扩大**：不再新增 `fs.*` 命令类型，
>   `enqueueRemoteCommand` 与云端 `createCommand` 两份名单都不动；
> - **写入从"提交 + 轮询"变成同步结果**，手机端不必等 500ms 一轮的终态确认。
>
> 代价是写入失去了命令通道那份持久化的审计记录。这是**有意的取舍**：审计记录的收益
> 远小于"把项目源码写进云端数据库"的风险。若将来确需审计，正确做法是让云端只记
> 元数据（路径、字节数、内容 sha256、结果）而不记内容。


## 1. 结论

技术可行，且改动面比预期小。核心原因有三个：

1. **桌面端的文件工作台本来就是"取数可注入"的**。`FilesPanel` 只通过一个
   `request: <T>(path, init) => Promise<T>` 拿数据（`FilesPanel.tsx:17`），
   所有 `/api/projects/{id}/fs/*` 调用都走这一个入口。手机端只要提供一个把这套 REST
   翻译成远程命令的适配器，树、查看器、编辑器、JSON/SQLite 预览可以**整块复用**。
2. **电脑端已经有完整的文件 API 且被远程命令层复用**。`executeRemoteHTTPCommand`
   会用 `httptest` 合成请求直接调既有 handler（`remote_control.go:1869`），
   `conversation.shortcut` 走的正是这条路。文件命令照抄这个模式即可，不必写第二套文件逻辑。
3. **`/fs/read` 已经同时返回 stat、content、version**（`filesystem.go` 的 `FileContent`），
   桌面端却拆成 stat → read 两跳。手机端把它合成一跳，正好抵消远程往返的延迟。

真正的瓶颈是**通道容量与延迟**，不是编辑器：

- 命令 payload 与 result 各 ≤ **256 KiB**（`remote_control.go:683`、`:1628`；云侧 `server.go:1544`）；
- Agent WebSocket 读上限 **512 KiB**（`server.go:1689`）；
- 远端命令 worker **串行、500ms/tick**（`remote_control.go:1658`），一次读取实际约
  0.5–1.5 秒；
- 云端**没有对象存储**（`cloud-control` 里没有 MinIO/S3/presign 任何代码），
  所以大文件没有"绕过通道"的现成退路；
- 快照上限 32 MiB 且**每次有事件推进（3 秒节流）就整份重传**，
  因此文件树**不能塞进快照**。

结论：一期把 `≤ 256 KiB` 的文本体验做完整（查看 + 编辑），超限一律**如实降级**，
不做"看起来能打开其实只有一半"的假完整。

## 2. 现状与缺口

### 2.1 手机端现有能力

| 项 | 现状 |
| --- | --- |
| 视图 | 只有 `"projects" \| "conversation"` 两个 view（`MobileRemotePage.tsx:898`），非路由 |
| 读通道 | 全部来自云端快照 `GET /v1/instances/{id}/snapshot`（`:1540`） |
| 写通道 | `POST /v1/instances/{id}/commands` + 轮询 `GET /v1/commands/{id}`（`waitForCommand`，`:4297`） |
| 文件相关 | **零**。没有 README、diff、文件树、任何文件入口 |
| 桌面端文件能力 | 完整：树 / 查看 / 编辑 / JSON 结构 / SQLite / 流式下载（`fs_handler.go:23-43`） |
| 远程命令白名单 | 10 种 `task.*` / `conversation.*`，**无任何 fs 类型**（`remote_control.go:678`、`server.go:1539`） |

### 2.2 缺口清单

1. 远端命令白名单缺 `fs.*`（两处，必须同步）。
2. 没有面向手机的文件取数命令，也没有"一次拿完一个文件"的契约。
3. `fsReadDir` 忽略 `depth` 参数（`fs_handler.go:160`），目录树只能一层一层要，
   在 0.5s/次的通道上是硬伤。
4. 手机端没有文件视图与入口，也没有把"AI 改了哪个文件"变成可点链接。
5. 云端没有任何二进制/大文件传输能力。

## 3. 硬约束（实现时必须当成前提）

| 约束 | 数值 | 来源 | 影响 |
| --- | --- | --- | --- |
| 命令 payload | ≤ 256 KiB | `remote_control.go:683` | 写入文件内容上限 |
| 命令 result | ≤ 256 KiB | `remote_control.go:1628` | 读取文件内容上限 |
| Agent WS 读上限 | 512 KiB | `server.go:1689` | 给 result 留的余量很薄 |
| 命令 worker | 串行 + 500ms tick | `remote_control.go:1652-1670` | 并发读会排队 |
| 命令 TTL | 15 分钟内 | `remote_control.go:693` | 长任务不可行 |
| 快照 | 32 MiB，事件驱动重传 | `server.go:1836` | 文件树不能进快照 |
| 对象存储 | 无 | — | 大文件没有旁路 |
| 内容落库 | 命令 payload 进 PG `jsonb` | `server.go:1564` | 文件内容会被云端持久化，隐私问题 |

## 4. 方案决策

### 4.1 读走"命令"，但按"一个动作一条命令"设计

新增读命令，全部复用既有 handler：

| 命令 | 复用的 handler | 说明 |
| --- | --- | --- |
| `fs.tree` | `fsReadDir`（扩展 depth 与忽略规则） | 一次返回一棵子树，手机端本地缓存 |
| `fs.read` | `fsStat` + `fsReadFile` 合成 | **一次拿到 stat + content + version**，服务端按上限决定给不给内容 |
| `fs.search` | `fsSearch` | 文件名模糊搜索 |
| `fs.sqlite.tables` / `schema` / `rows` | `fsSQLite*` | 数据库预览，分页 |

关键设计三点：

- **树一次多拿**。`fs.tree` 增加 `depth`（默认 3、上限 5）与 `maxEntries`，
  服务端在 Go 侧用一份常量忽略名单裁剪（`node_modules`、`.git`、`dist`、`build`、
  `target`、`.next`、`vendor`、`__pycache__`、`.venv`、`coverage` 等），
  返回 `truncated` 标记。手机端拿到后缓存，展开子目录**零往返**。
  一次命令换整棵树，把"每个目录一次往返"变成"每棵树一次"。
- **`fs.read` 带服务端闸门**。手机端不做 stat → read 两跳；服务端拿到路径后先 `Stat`，
  按下面的上限表决定：给内容、给截断内容（带 `truncated`）、还是只给元信息（`contentOmitted`）。
  这样**无论多大文件都只花一条命令**，也不会出现"手机端已经请求了 200MB 才被拒"。
- **不做 `fs.read` 的 offset 分片**。一期不做续传式分片阅读：它会让"完整性"变成
  一个需要用户理解的状态机，而手机上看 1MB 以上源码不是真实场景。
  若后续确有需求，再按 `offset/length` 扩展同一条命令（契约上预留 `offset` 字段）。

### 4.2 写走既有命令通道，沿用乐观锁

| 命令 | 复用的 handler | 冲突语义 |
| --- | --- | --- |
| `fs.write` | `fsWriteFile` | `expectedVersion` 不匹配 → 409 |
| `fs.mkdir` | `fsMkdir` | 已存在 → 409 |
| `fs.rename` | `fsRename` | 目标存在 → 409；跨目录 → 400 |
| `fs.remove` | `fsRemove` | — |

两点必须讲清楚：

- **workspace lease 语义天然一致**。写 handler 内部会 `acquireWorkspace`
  （`fs_handler.go:384`），AI 正在跑时返回 409。手机端必须把这个 409 翻译成人话
  （"电脑上 AI 正在运行，文件编辑已锁定"），而不是笼统的"保存失败"。
- **`expectedVersion` 是手机端唯一防覆盖手段**。手机上打开文件时记下
  `version`（sha256，`contentVersion`），保存时带上；不一致就说明电脑端已经改过这个文件。
  这是既有机制，手机端照用即可。

### 4.3 入口：两条路，会话深链才是主场景

| 入口 | 位置 | 说明 |
| --- | --- | --- |
| 项目文件 | 会话视图「⋯」菜单新增一项（与「历史会话 / 任务队列 / 新会话 / 刷新」同列） | 最小改动，符合"顶栏一行标题 + ⋯ 菜单"的既有约规 |
| **会话文件深链** | 会话时间线里的文件路径、AI 的 Edit/Write 工具卡片 | **手机端要文件查看，九成是为了看 AI 刚改了什么**。这条比从根目录浏览整个项目重要得多 |

明确**不采用**"长按项目卡弹菜单"：手机端「选择项目」的拖动排序已经占用长按 / 指针手势
（见 `lib/use-card-drag.ts`），再挂长按菜单会互相抢事件。若要从项目列表直接进文件，
必须在卡片上加一颗显式的「⋯」按钮，而不是长按。

### 4.4 文件视图必须绑定工作区

`resolveRequestWorkspaceFromRequest` 用 `projectID` + **可选** `conversationId`
查 query 决定工作区（`conversation_workspaces.go:64`）。多会话 Tab 存在工作区隔离，
同一项目不同会话可能落在不同的 worktree / 分支上。

因此：

- 从会话进入文件视图时必须带上 `conversationId`；
- 从项目列表进入则不带，落到项目共享工作区；
- 文件视图头部必须显示**当前工作区标识**（分支名或 worktree 名），
  否则用户会在"以为是项目根"的地方编辑到另一个 worktree 的文件。

## 5. 后端改动

### 5.1 白名单与命令分发

- `remote_control.go:678` 增补 8 个 `fs.*` 类型；
- `cloud-control/internal/cloud/server.go:1539` **逐字同步**同一份名单
  （两处注释都写明了必须一致，漏一处手机端只会拿到语焉不详的 400）；
- `executeRemoteCommand`（`remote_control.go:1767`）新增分支，全部经
  `executeRemoteHTTPCommand` 调用既有 handler；`path` 查询参数通过
  `extraParams`（`"名,值"` 成对）补 `conversationId`；
- 错误沿用既有约定：只把 `{"error": "..."}` 那一句回给手机。

> ⚠️ 白名单分两处是既有结构性风险。建议本次同时补一个 **Go 测试**：
> 用同一份期望名单分别校验 control-server 与 cloud-control 的映射，
> 任一处漏加就红。这属于"改一处必须同时登记"那条纪律的自动化兜底。

### 5.2 `fsReadDir` 增加 depth 与忽略规则

```go
// depth: 0/1 = 只有本层；默认 3；上限 5
// 返回 { entries, truncated }，truncated 表示命中忽略名单或条目上限而裁剪
```

忽略名单必须是 **Go 侧常量**（前端不可作为安全或性能依据），并配单测。
条目上限建议：单目录 500、总计 3000。

### 5.3 `fs.read` 合成契约

```json
{
  "stat": { "name": "...", "path": "...", "isDir": false, "size": 12345,
            "modTime": "...", "mode": "0644", "isText": true, "mimeType": "text/plain" },
  "content": "……",
  "encoding": "base64",
  "version": "sha256:…",
  "truncated": false,
  "contentOmitted": false,
  "omittedReason": "too_large"
}
```

服务端闸门顺序：`Stat` → 目录则报错 → 按 §6 上限表决定 `content` 是否存在。
二进制与图片走 `encoding: "base64"`（与既有 `FileContent.Encoding` 一致）。
`content` 为 null 时**不能省略键**，避免前端按 `string` 解析到 `undefined`
（这条是本项目已经踩过的坑：切片字段留 nil 会整页空白）。

### 5.4 隐私：内容全程不落库（已由结构保证）

命令通道会把 payload 存进云端 PostgreSQL 的 `jsonb` 列。文件内容一旦走那条路，
就等于把项目源码持久化到云端，直接违背第 32 篇 §9.2「项目源码不上传云端」。

**实现选择的是"根本不走那条路"**，而不是"走了再擦掉"：

```
手机 ──POST /v1/instances/{id}/fs──▶ 云端（只在内存里组装一帧，不写任何表）
                                        │ Agent WSS
                                        ▼
                                    milevia-agent（转发，不留存）
                                        │ loopback HTTP
                                        ▼
                     control-server /api/remote/fs（复用既有 fs handler）
```

因此云端的数据库里不存在任何文件内容、路径片段或内容摘要。这比"存摘要占位 + 内容放
内存 hold + 投递时还原"更彻底，也顺带避免了后者"hold 被逐出后重投空 payload"的坑。

回归方式：`enqueueRemoteCommand`（control-server）与 `createCommand`（云端）两份命令白名单
里**一个 `fs.*` 类型都没有**，`cloud_commands` 表不可能出现文件内容。

## 6. 分层上限表（已实施，数值由通道能力反推）

| 文件类别 | 大小 | 手机端行为 | 服务端字段 |
| --- | --- | --- | --- |
| 文本（源码/配置/MD/JSON） | ≤ 256 KiB | 完整内容，**可查看 + 可编辑** | `editable: true` |
| 文本 | 256 KiB – 320 KiB | 完整内容，**只读**，界面明示原因 | `editable: false` + `readOnlyReason: file_too_large` |
| 文本 | > 320 KiB | **不给内容**，只给元信息卡 | `content: null` + `omittedReason: too_large` |
| 图片（png/jpg/gif/webp/ico） | ≤ 128 KiB | base64 内联预览 | `encoding: "base64"` |
| 图片 | > 128 KiB | 只给元信息卡 + "请在电脑上查看" | `omittedReason: binary` |
| SQLite（本地/WSL） | ≤ 64 MiB | 分页浏览表 / 结构 / 数据 | 走 `fs.sqlite.*` |
| 其他二进制（含 PDF/压缩包） | 任意 | 只给元信息卡，**不提供下载** | `omittedReason: binary` |

**三个数字是夹出来的，不是拍的**（实现在 `apps/control-server/internal/app/fs_open.go`）：

```
云端 Agent WebSocket 读上限 512 KiB（会掐断整条中继连接，不只是这次请求失败）
   ↓ 必须远小于它
帧上限 384 KiB
   ↓ 减去 JSON 转义与信封余量
查看上限 320 KiB  ← 文本给内容的硬边界
   ↓ 写入要原样发回去，双向都要余量
可编辑上限 256 KiB
图片内联 128 KiB   ← 还要 base64 膨胀约 1/3（100 KiB 的 PNG 编码后是 137 KiB）
```

「图片按编码后长度判断」这一条踩过一次：先用文件原始大小去比 128 KiB，一张 100 KiB 的
PNG 会被判成"没超限"，实际发出去 137 KiB。所以闸门是**两道**：读之前按元信息决定要不要读
（省一次全量读取），读之后必须按**传输长度**再判一次。两道不能合并 —— 前者用原始大小，
后者必须用编码后长度，差值正好在这一档上翻车。

**同一个错在文本上又存在过一轮**（2026-09-21 复查抓到）：第二道闸门当时量的是
`len(content)`，那是文本的**原始**长度，而发出去的是 **JSON 转义之后**的文本 ——
`"` 与 `\` 翻一倍、控制字符变六字节、`<`/`>`/`&` 变 `\u003c` 这种六字节形式。
一个 200 KiB 但引号密集的 JSON 转义后是 400 KiB，原始长度看着远在安全区内，
发出去却超过帧上限（384 KiB），于是手机拿到一句"超过中继通道容量"—— 而那时服务端
已经把它标成可读、甚至可编辑了。现在第二道闸门统一量转义后的长度
（`fsRemoteOpenTransmitLimit` = 380 KiB，给信封与 stat 留 4 KiB）。
判据：**凡是"发出去的东西"与"盘上的东西"形状不同，闸门就必须量前者。**

**刻意不做截断阅读**：返回半个文件又允许用户编辑它，等于让用户在不知情的情况下用半截
内容覆盖整个文件。要么完整给、要么明确说"太大，去电脑上看"。

**不做手机端大文件下载**是刻意的：一条能下载任意文件的通道，等于给被盗手机一个
"把整个项目拖走"的能力。这条要写进界面文案，而不是静默不给按钮。

## 7. 前端改动

### 7.1 核心：`mobileFsRequest` 适配器

```ts
// apps/web/src/features/files/mobile-fs-request.ts
export function createMobileFsRequest(
  projectId: string,
  conversationId: string | null,
  send: (type: string, payload: unknown) => Promise<unknown>,
): <T>(path: string, init?: RequestInit) => Promise<T>;
```

职责：把 `FilesPanel` 会发出的 REST 调用映射成命令。

| 输入 | 映射 |
| --- | --- |
| `GET /fs/tree?path=` | `fs.tree`（手机端带 `depth=3`） |
| `GET /fs/stat?path=` | `fs.open`（只用它的 `stat` 字段；命中缓存则本地答） |
| `GET /fs/read?path=` | `fs.open`（一次拿到 `stat` + `content` + `version`，不再是两跳） |
| `GET /fs/search?query=&path=` | `fs.search` |
| `GET /fs/sqlite/*` | 同名操作 |
| `PUT /fs/write` | `fs.write`（必须透传 `expectedVersion`） |
| `POST /fs/mkdir` / `rename`、`DELETE /fs/remove` | 同名操作 |
| `GET /fs/raw?path=` | 一期不支持 → 抛结构化错误，由查看器降级为元信息卡 |

适配器还要把三个**服务端判定**如实转成界面状态，不要在客户端另立判据：

- `editable: false` + `readOnlyReason` → 编辑按钮禁用并说明原因（`file_too_large` / `binary_file`）；
- `omittedReason` 非空 → 走元信息卡，不渲染空内容区；
- 传输失败的 HTTP 码要分开：`409 instance_offline`（电脑掉线，去看看）、
  `504`（电脑没回话）、`200 + ok:false`（操作本身失败，显示服务端那句中文）。

必须做两层本地缓存，否则每次打开都往返：

- **内容缓存**：`Map<path, { content, version, stat }>`，以 `fs` 视图生命周期为界；
- **树缓存**：`fs.tree` 的结果按 `path` 缓存；写操作成功后只失效受影响的目录，
  复用桌面端 `files-tree-refresh.test.mjs` 已经固化的"只刷变化目录"语义。

  与 `leaveConversationView()`（`:4323`）。漏一处就会出现"点错也能执行"；

### 7.5 会话深链（一期纳入）

会话消息里的文件路径需要变成可点链接，点击后直接打开该文件的查看器。
这是手机端文件能力的**实际使用入口**，比目录树更重要。

实现要点：

- 路径识别必须与桌面端共用一份实现，不要在手机端另写一套正则；
- 只能识别**项目内相对路径**，且必须经过服务端路径校验，不能凭字符串直接请求；
- 打开失败的降级要把三种真相分开说（文件不存在 / 路径在项目外 / 电脑端读不到），
  遵循本项目"空态必须说清是哪一种"的纪律。

### 7.6 缓存失效：AI 改了文件之后

一期沿用桌面端策略：手动刷新 + 保存后刷新受影响的目录 + 切回视图时刷新。
**手机端必须能手动刷新**（头部已有刷新胶囊，文件视图内再加一颗局部刷新）。

一期不新增 `fs.changed` 事件。二期可以复用既有事件通道发一种轻量事件
（只带路径与 revision，不带内容），让文件视图自动失效缓存 ——
这比轮询省电得多。

## 8. 安全

### 8.1 中继命名空间的边界变了，注释必须跟着改

`/api/remote/*` 原本的定位是「只暴露控制类元数据，不提供任意文件系统或 Shell 访问」，
那句话写在 `app.go` 的路由组上。加入 `/api/remote/fs` 之后它**不再成立**，因此那句注释
已同步改写成新边界：

> 除 `/api/remote/fs` 之外都只暴露控制类元数据；那个端点提供**项目沙箱内**的文件读写
> （路径一律经 `Filesystem` 的 `resolvePath` / `resolveMutationPath` / `remotePathWithinRoot`
> 校验，出不了项目根），且不提供任何 Shell、命令执行或任意 URL 转发能力。

一句已经失实的「这里没有文件访问」比没有注释更危险 —— 后来的人会据此放松审查。

**鉴权边界保持不变**：该端点只认 Agent 令牌，桌面页的会话令牌**不能**用它。
桌面页本来就能通过 `X-Milevia-Session` 调本机全部 `/api/projects/*`，再给它一条
"以 Agent 身份操作项目文件"的路，等于给一个被 XSS 拿到的页面加一条绕过 session 边界的出口。
这条已登记进 `TestRemoteRelayAcceptsDesktopSessionForPairingOnly` 的用例表。

### 8.2 风险与处理

| 风险 | 处理 |
| --- | --- |
| 路径穿越 | 全部复用 `resolvePath` / `resolveMutationPath`（本地）与 `remotePathWithinRoot`（SFTP）。中继层额外拒绝 `projectId` 里的 `/ \ ? # %` —— 它会被拼进合成请求的 URL 路径，一个 `../` 就能把请求指到别的路由上 |
| 越权读写 | 手机侧走 `userAuth` + `authorizedInstance`；本机侧走 `remoteAgentOnly`。文件通道不新增旁路 |
| 源码泄漏到云端 | 见 §5.4，结构上不落库 |
| 超大帧掐断中继连接 | 双端各一道帧上限（384 KiB，见 §6）。这是**最容易被忽略的一条**：响应超限不会只让这次请求失败，而是让这台电脑与手机之间的命令、事件、快照一起断掉 |
| 手机丢失后被用来拖走项目 | 不提供任意文件下载；二进制只给元信息 |
| 误改 / 误删 | 保存前 diff 确认；删除必须二次确认且文案写明不可恢复；`rename` 限同目录（既有约束） |
| 与 AI 抢写 | 沿用 workspace lease，AI 运行时写入返回 409 并明确告知 |
| 客户端伪造文件操作 | 操作名单**只有一份**，在执行点（`remoteFSOperations`）。云端不认识 op，Agent 不映射 op —— 因此不存在"某处漏加一个 op 导致半路 400"或"两份名单不同步"的问题 |

关于「允许手机修改项目文件」的授权开关：**决策 1 定为不设**（一期就默认允许编辑）。
能写电脑源码的风险由「手机本身已要求配对 + 电脑端点击确认绑定」这条既有链路承担；
若将来要收紧，开关的正确位置是**电脑端**（在 `remoteFSOperations` 之外加一道
"是否允许写入类 op"的实例级配置），而不是手机端 —— 手机端是待验证的一方，让它自己决定
自己的权限没有意义。

### 适配器落地时确认的三件事

1. **图片不能再用 `<img src="/fs/raw">`**。`FileViewer` 现在有两处把 raw/download 拼成
   URL 直接交给 `<img>` / `<a>`（那是一次浏览器导航，带不了 `Authorization` 头，
   手机也到不了电脑的本机端口）。手机端要改成用 `fs.open` 已经取回来的 **base64 载荷**
   转成 `data:`/Blob URL。这是 `fs.open` 对小图片内联 base64 的全部理由。
2. **`/fs/stat` 与 `/fs/read` 在适配器里合成一次 `fs.open`**。桌面端拆两跳是为了先看
   `isText`/`mimeType` 再决定读不读；`fs.open` 已经把这两件事合在一次答复里。
   没有这层合并，打开一个文件就是两次往返（手机到电脑每次几百毫秒到一秒），白等一半。
3. **内容被省略时必须抛 `MobileFsError("content_omitted")`，绝不能返回 `""`**。
   `FilesPanel` 现有写法是 `content: res?.content ?? ""` —— 直接交出空串会渲染出一个
   空文件，用户以为文件是空的。错误里带上完整载荷，供查看器渲染元信息卡。
   这是"宁可说看不了，也不能假装能看"那条纪律在适配器这一层的落点。

**子树缓存是怎么做到"展开零往返"的**：适配器发一次带 `depth: 3` 的 `fs.tree`，
把嵌套响应**摊平**成「目录 → 该目录的直接子项」存起来。于是
`ProjectFileTree` 那套逐目录懒加载的 provider **一行都不用改**，它下一次
`fetchDir("src/lib")` 就直接命中。摊平还有个好处：失效范围能说清楚 ——
某个目录的列表变了，只丢它自己那一条。

失效规则按"这次改动会让**哪个目录的列表**变化"来定，不是一律清空
（一律清空会让上一次展开的子树全丢，用户每删一个文件都要重新点回原位置）：
`write` 丢该文件内容 + 父目录树；`mkdir` 丢父目录树；`rename` 丢两个父目录 + 旧路径子树；
`remove` 丢父目录 + 被删路径及其子树。**点「刷新」必须调 `invalidateAll()`**，
否则 AI 在电脑上改完文件、用户点刷新，适配器会把缓存里的旧内容还回去。

## 13. 最终形态

```text
读：fs.tree（一次拿整棵，depth=3）→ fs.open（一次拿完 stat+content+version，服务端闸门）
写：fs.write + expectedVersion（乐观锁天然提供重放安全）
通道：cloud_commands 一行都不写 —— 文件内容全程不进云端数据库
边界：≤256 KiB 完整可编辑 ／ ≤320 KiB 完整只读 ／ 更大与二进制只给元信息
```

不引入第二套文件逻辑、不新增基础设施、不改变既有鉴权与并发语义，
也不扩大"两份白名单必须同步"那类结构性风险。代价是"大文件看不了"，
而这个代价被如实呈现在界面上，而不是靠静默截断掩盖。

| # | 问题 | 说明 |

| 6 | **文本的传输长度判据用错了对象**（见 §6 新增那段） | 第二道闸门拿原始长度去比，而发出去的是 JSON 转义后的文本。引号密集的 200 KiB JSON、`<`/`>` 密集的 HTML 都能突破帧上限，结果是手机收到一句"超过中继通道容量"，而那之前服务端已经把它标成可看可编辑了。**与"图片按编码后长度判断"是同一个错的第二次出现** |

**这一轮确认没问题的几处**（查过、别再怀疑）：

- 前端发出的三个改动类请求字段名与适配器的失效逻辑**逐字一致**：
  `fs/mkdir` 的 `path`、`fs/rename` 的 `oldPath`/`newPath`、`fs/remove` 的查询 `path`。
  （这类不对上不会报错，只会"改完树的缓存没失效"，表现为"重命名了但树里还是旧名字"。）
- `/fs/open` 里 `stat` 的两个来源（读之前的 `Stat` 与 `ReadFile` 带回的 `Stat`）
  都出自同一个 `makeFileInfo`，本地与 SFTP 两套实现都一样 —— 不会有"省略时字段全、
  给内容时字段缺"的分裂。
- 云端的帧上限检查虽然在 `decode` 之后，但 `decode` 本身有
  `http.MaxBytesReader(…, 512 KiB)`，所以"用一条请求把云端内存写爆"确实被挡住了。
- 手机端 `409` 分支依赖的状态码是对的：版本冲突与 lease 占用都是显式 `StatusConflict`，
  不是经 `writeFSError`（那会把它们压成 400）。

**还没动、但值得知道的一处**（不在本期范围，桌面端同样如此）：
SSH runner 离线时服务端返回 `{"error":"runner_offline","runnerId":…}`，
而界面直接把 `error` 当文案显示 —— 用户在手机上会看到一个英文枚举 `runner_offline`。
前端没有任何地方按这个字段分支，所以改法是给响应体补一句人话（如 `message`），
但那属于共享错误契约，要连桌面端一起评估，没在本期单方面改。
