> 日期：2026-08-20
>
> 状态：核心实现已完成，待三环境人工验收
>
> 关联：[项目启动停止功能](./12-项目启动停止功能.md)、[SSH远程项目支持](./11-SSH远程项目支持.md)、[Windows桌面端最终架构与实施方案](./17-Windows桌面端最终架构与实施方案.md)

## 1. 结论

项目终端采用真实交互终端架构：前端使用 `@xterm/xterm` 渲染，控制服务通过 WebSocket 双向转发字节流，后端按项目 Runner 创建并管理 PTY 会话。

```text
项目工作区“终端”页面
  -> xterm.js（ANSI、光标、快捷键、尺寸）
  -> WebSocket（输入、输出、resize、控制事件）
  -> terminalManager（会话上限、生命周期、重放与清理）
  -> Windows ConPTY / WSL PTY / SSH PTY
  -> 项目根目录中的交互 Shell
```

本方案是“终端”需求的最佳实现，而不是把“项目启动”页面增加命令输入框：`projectRunner` 只能管理固定命令和按行日志，不能正确处理交互输入、终端控制序列、全屏程序、窗口大小、`Ctrl+C` 或 Shell 内部工作目录变化。

一期一次性交付 Windows、WSL、SSH 三类环境；不允许将任一环境以“暂不支持”或“单次命令执行器”降级上线。

## 2. 目标与范围

### 2.1 一期目标

对每个已加载项目提供一个“终端”一级工作区页签，初始目录为该项目根目录，用户可在其中启动 Shell 并执行任意该环境本身允许的命令。

一期完成后，下列环境全部通过验收：

| 项目 Runner / 目标环境 | Shell 与 PTY 实现 | 初始工作目录 |
| --- | --- | --- |
| `windows-local` | Windows ConPTY + `cmd.exe /d /q` | Windows 项目根目录 |
| `wsl-local` | Windows ConPTY + `wsl.exe -d <distro> --cd <linux-path> --exec <shell>` | WSL 项目根目录 |
| WSL 服务端上的本地项目 | POSIX PTY + `$SHELL -l` | WSL / Linux 项目根目录 |
| WSL 服务端上的 `/mnt/<盘符>` Windows 项目 | 原生 Windows terminal bridge 中的 ConPTY + Windows Shell | 映射后的 Windows 项目根目录 |
| `ssh-*` | SSH `RequestPty` + 受控 Shell `Start` | 远程项目根目录 |

一期界面能力：

- 首次进入“终端”页时自动建立一个默认会话；打开项目或停留在其他工作区时不启动 Shell；
- 命令输入、实时 ANSI 输出、颜色、光标控制、`Ctrl+C`、退格、方向键和粘贴正常工作；
- 窗口尺寸变化同步到后端 PTY；
- Shell 退出后清楚展示退出状态，可重新打开；
- 支持新建、关闭、重连和清屏；一期最多同时保留 3 个会话，默认只显示一个；
- 当前项目目录是初始目录，Shell 内执行 `cd` 后保持该会话自身的目录；
- 浏览器/WebView 短暂断线后可重连到同一会话；项目删除、应用退出、SSH 失联时会话及其子进程均被结束。

### 2.2 非目标

- 不构建完整 IDE，不实现 LSP、调试器、端口转发或终端分屏。
- 不把 Shell 历史、输出或输入持久化到 SQLite；终端中可能包含 token、密码、私钥路径和敏感业务数据。
- 不承诺终端会话跨 control-server 重启恢复；服务退出会主动终止会话。
- 不提供“只允许项目目录内文件操作”的伪沙箱。交互 Shell 以当前用户权限执行，真正隔离需要容器、Windows Sandbox 或 OS 级策略，超出本方案范围。

## 3. 现状与决策依据

### 3.1 可复用基础

当前项目已经具备实现终端所需的大部分外围能力：

- 前端项目工作区路由和页签位于 `apps/web/src/App.tsx`、`components/ProjectLayout.tsx`；可以新增 `/projects/:projectId/terminal`。
- `packages/sdk/src/index.ts` 的 `createWebSocket()` 已同时处理 Web 模式和桌面模式的地址、`Sec-WebSocket-Protocol` 会话令牌，终端必须复用它。
- 服务端已具备 WebSocket 心跳、关闭握手、慢客户端队列与控制服务关闭等待逻辑。
- SSH `sshClient.newSession()` 可复用已验证和已认证的 SSH 连接；`golang.org/x/crypto/ssh` 原生支持 `RequestPty`、`Shell`、`WindowChange`。
- `golang.org/x/sys/windows` 已包含 `CreatePseudoConsole`、`ResizePseudoConsole`、`ClosePseudoConsole` 及扩展进程属性 API，可作为 Windows ConPTY 的底层实现。
- 项目 Runner 与 `resolveAgentTargetEnv()` 已能区分 Windows、WSL、远程 Linux；终端按同一分发语义选择环境。

### 3.2 不复用项目启动功能

`projectRunner` 与 `sshProjectRunner` 的语义是“固定命令的生命周期管理”：配置命令、启动、停止、重启、退出码和按行日志缓冲。终端的语义不同：持续输入输出、二进制控制序列、尺寸变化、用户主动关闭和重连。

因此不得在 `projectRunner` 内追加 stdin 或复用 `/ws/projects/{id}/run`。应新增独立的 `terminalManager` 与 `TerminalSession` 接口；两类进程可以同时存在，互不互相停止或抢占。

### 3.3 方案比较

| 方案 | 优点 | 致命问题 | 结论 |
| --- | --- | --- | --- |
| 单命令 HTTP 执行 | 快速、实现少 | 没有交互、`Ctrl+C`、全屏程序、Shell 状态与持续日志 | 不采用 |
| 运行页日志 + stdin | 可复用部分 UI | 不是 PTY，`vim`、颜色、窗口变化和命令行编辑错误 | 不采用 |
| 前端 xterm.js + 后端普通管道 | UI 完整 | 子进程仍检测不到终端，交互 CLI 行为不可靠 | 不采用 |
| **xterm.js + WebSocket + 平台 PTY** | 真实终端语义，可统一三类 Runner | Windows ConPTY 需要专门实现与 POC | **采用** |

## 4. 架构设计

### 4.1 页面与路由

新增 `TerminalPage.tsx`、`features/terminal/TerminalPanel.tsx` 和 `terminal.css`。

- `App.tsx` 增加 `terminal` 子路由；
- `WorkspaceTab` 增加 `terminal`；
- `ProjectLayout` 增加带终端图标的页签与键盘导航；
- 终端区域占满项目工作区，不嵌套装饰卡片；工具栏仅放会话选择、当前环境/目录、创建、重连、清屏、关闭等操作；
- 使用 xterm 的 `FitAddon` 结合 `ResizeObserver` 计算列数和行数，容器可见后才执行 `fit()`；
- 页面失焦、标签切换和 Resize 都不得丢失 xterm 的输入焦点管理。

前端新增依赖：

```json
{
  "@xterm/xterm": "^6.0.0",
  "@xterm/addon-fit": "^0.11.0"
}
```

不使用已废弃的 `xterm` 包名。xterm 输出直接写入实例，不经 React 逐行渲染，避免 ANSI 控制序列失真和大输出造成大量 DOM 节点。

### 4.2 后端对象模型

新增 `apps/control-server/internal/app/terminal.go`，定义平台无关接口：

```go
type TerminalSession interface {
    ID() string
    ProjectID() string
    Environment() string
    Ready() <-chan error
    Read(p []byte) (int, error)
    Write(p []byte) (int, error)
    Resize(cols, rows uint16) error
    Close() error
    Wait() error
}

type TerminalSpec struct {
    ProjectID string
    RunnerID  string
    Target    string
    WorkDir   string
    Shell     string
    Cols      uint16
    Rows      uint16
}

type TerminalFactory interface {
    Open(ctx context.Context, spec TerminalSpec) (TerminalSession, error)
}
```

`terminalManager` 是 `Server` 的成员，至少维护：

```go
type managedTerminal struct {
    session       TerminalSession
    projectID     string
    runnerID      string
    target        string
    ownerID       string
    createdAt     time.Time
    detachedAt    time.Time
    output        *byteRingBuffer
    subscribers   map[*websocket.Conn]*terminalSubscriber
    cancel        context.CancelFunc
    closeOnce     sync.Once
}
```

`TerminalSpec` 由服务端根据项目记录和 Runner 元数据生成，前端不得提交原始操作系统路径、Runner ID 或 Shell 路径。`TerminalFactory` 负责按 `RunnerID` 和目标环境选择 Windows ConPTY、WSL、POSIX、Windows bridge 或 SSH 实现；每个实现必须在 `Open` 返回前完成工作目录、Shell、尺寸和权限校验，并启动资源初始化。`Open` 返回的 session 可能仍处于 `starting`，管理器必须等待 `Ready()`：成功后广播 `ready` 并将状态改为 `running`，失败则关闭并移除会话。`Ready()` 只能完成一次，`Close()` 必须解除其等待者。PTY/bridge 在 `Open` 到管理器登记期间产生的输出必须留在可读管道或内部缓冲中；实现不得把输出写入无人消费的临时 channel 后丢弃。会话登记后立即启动唯一 reader。

接口并发契约：`Read` 由单一输出 goroutine 调用；`Write` 与 `Resize` 可由 WebSocket 读取循环触发，但必须由会话级 mutex 串行化；`Close` 必须解除阻塞中的 `Read`、`Write`、`Wait`，并可被重复调用；管理器只允许一个 goroutine 负责最终 `Wait` 和状态广播。实现不得在 `Close` 内等待自己持有的读写锁或等待会再次调用 `Close` 的 goroutine。

管理器职责：

- 以 UUID 创建不可猜测的 `sessionId`；
- 校验项目存在、Runner 在线、会话配额和 Shell 可启动性；
- 启动单一读取 goroutine，把 PTY 原始字节广播给订阅者并写入限额重放缓冲；
- 串行化 PTY 写入和 resize，避免并发写入破坏输入；
- 在进程结束、显式关闭、项目删除、服务关闭和 SSH 断开时幂等清理；
- 只在短暂断线窗口内保留无人订阅会话，超时关闭；
- 不将终端数据写入项目运行日志、通知、数据库或普通服务日志。

终端创建、项目删除、SSH 连接切换/断开必须经过同一个项目生命周期 admission gate。该 gate 不得覆盖 PTY 启动的 10 秒等待：现有全局 `projectLifecycleMu` 只用于短暂的 admission 操作，不能被终端管理器持有到 `Open` 完成。

采用项目级 terminal lease（租约）避免竞态：

1. 创建请求在全局 gate 内确认项目存在、Runner 在线，生成带 `runnerID` 的 `TerminalSpec`，并登记项目级 lease（包含递增 generation）；随后立即释放全局 gate。
2. `TerminalFactory.Open` 在 lease 有效期间启动 PTY。启动完成后，在登记会话前再次校验 lease 的 generation、项目存在性和 RunnerID 未变化；失效则立即关闭新会话并返回冲突错误。
3. 会话登记成功后 lease 转为 active session 关联；启动失败、超时或校验失败都必须回收 lease 和已创建资源。
4. 项目删除或 SSH Runner 替换先在全局 gate 内使对应 lease 失效并阻止新的 admission，再释放 gate，调用 `CloseProject` / `CloseRunner`，最后删除项目或替换 Runner。

这样既避免“校验项目存在后项目被删除，Shell 才开始启动”的竞态，也不会阻塞 Agent 运行、SSH 操作或项目删除。所有关闭操作必须幂等，且不能在持有全局管理器锁时等待 PTY、SSH 或 bridge 退出。

会话策略：每项目最多 3 个、全局最多 12 个；输出重放缓冲上限 1 MiB；每个 WebSocket 出站队列 1 MiB。管理器必须将 PTY 输出分块为最多 256 KiB 的原始 payload，且队列按二进制协议头后的实际帧字节数计量，不能把 1 MiB 原始数据作为单帧入队。客户端无法及时消费时，以 `1013 Try Again Later` 关闭该客户端而不阻塞 PTY 读取。无人订阅会话保留 60 秒，重连后取消清理计时；到期后停止整个终端进程树。

会话状态固定为 `starting -> running -> exited|failed|closed`；`starting` 只允许 `attach`、`resize` 和查询，不转发输入；`running` 才允许输入；终态只允许重放和读取最终状态，不接受写入。状态转换由管理器串行执行，重复的退出、关闭和失败回调不得重复广播或扣减配额。

终端创建使用独立超时，建议默认 10 秒：SSH 连接/PTY 申请、WSL 启动、bridge 启动和本地 Shell 创建分别受同一 context 约束。超时或启动失败必须关闭已创建的进程、SSH session、管道和会话登记，不得留下占用配额的半开会话。

### 4.3 WebSocket 协议

使用单一双向 WebSocket：

```text
POST /api/projects/{projectID}/terminal/sessions
GET  /api/projects/{projectID}/terminal/sessions
DELETE /api/projects/{projectID}/terminal/sessions/{sessionID}
GET  /ws/projects/{projectID}/terminal/{sessionID}
```

`POST` 请求可带可选的初始尺寸：

```json
{ "cols": 120, "rows": 36 }
```

创建响应不含任何敏感命令或环境变量。PTY 启动是异步阶段，初始状态必须为 `starting`；只有 WebSocket 收到服务端 `ready` 后才允许输入：

```json
{
  "id": "uuid",
  "projectId": "uuid",
  "environment": "windows",
  "cwdDisplay": "D:\\projects\\demo",
  "status": "starting",
  "createdAt": "2026-08-20T00:00:00Z"
}
```

WebSocket 的文本帧只承载 JSON 控制消息，终端字节流使用二进制帧，避免 Base64 约 33% 的膨胀突破 1 MiB 队列上限。二进制帧格式为 little-endian `u64 seq` 加原始终端字节；服务端输出帧和客户端输入帧均使用该格式，输入帧的 `seq` 固定为 0（输入不参与重放）。每个输出 payload 最多 256 KiB，数据不按行切分，也不做 ANSI 解析。

```json
{ "type": "attach", "afterSeq": "40", "cols": 120, "rows": 36 }
{ "type": "ready", "environment": "windows" }
{ "type": "resize", "cols": 120, "rows": 36 }
{ "type": "replay-complete", "seq": 41 }
{ "type": "exit", "code": 0 }
{ "type": "error", "code": "runner_offline", "message": "SSH 连接已断开" }
```

WebSocket 建立后，客户端第一帧必须是 `attach`；服务端在会话锁内完成“校验 sessionID、重放 `afterSeq` 之后的历史、登记实时订阅、发送 `replay-complete`”这一原子步骤。实时输出在 `replay-complete` 之后发送，避免重放与实时数据交叉或丢失。每个会话一期只允许一个可写 WebSocket；新连接 attach 时，旧连接收到 `replaced` 后关闭，避免两个终端同时向同一个 Shell 写入。关闭连接只解除订阅，不会自动关闭会话。

客户端在 xterm 的 `onData` 中用 `TextEncoder` 发送二进制 `input` 帧；服务端在 `ready` 之前拒绝输入并返回 `not_ready`。前端收到二进制输出后，以 `ArrayBuffer` 取出 little-endian `seq`，将剩余 `Uint8Array` 直接传给 xterm 的 `write`，由 xterm 的流式 UTF-8 解码器处理分段字符。在 `ResizeObserver` 完成 `fit()` 后发送 `resize`。服务端只接受预定义消息类型，限制单个输入帧原始 payload 为 64 KiB，并验证 `cols` 为 1-500、`rows` 为 1-200。`Ctrl+C` 必须按普通字节 `0x03` 转发给 PTY，不应另设“取消命令”HTTP 接口。`afterSeq` 在 JSON 中必须使用十进制字符串，避免 JavaScript `number` 对 `u64` 的精度丢失；服务端暂时兼容安全整数的旧数值形式。该序号不是权限凭证，服务端不将其持久化，也不依赖它做安全判断，只按输出缓冲范围执行重放。

重连时携带最后成功消费的 `seq`：

```json
{ "type": "attach", "afterSeq": "41", "cols": 120, "rows": 36 }
```

若缓冲已覆盖该序列，服务端发送当前可用重放并明确告知 `truncated: true`；客户端继续显示，不伪造完整历史。`replay-complete` 必须带本次重放的最后序号；实时输出从其后的序号继续单调递增。

桌面端必须通过既有 `createWebSocket()` 创建连接，以 `Sec-WebSocket-Protocol` 传递会话令牌；禁止在查询参数、URL 片段、日志或错误信息中携带令牌。

### 4.4 Windows ConPTY

Windows 本地终端使用 ConPTY，不使用 `cmd.StdoutPipe()` / `StdinPipe()` 伪造。

- 调用 `windows.CreatePseudoConsole` 创建输入/输出管道与初始 `windows.Coord`；
- 使用 `ProcThreadAttributeList` 为 `CreateProcess` 注入 `PROC_THREAD_ATTRIBUTE_PSEUDOCONSOLE`；
- Shell 默认 `cmd.exe /d /q`，工作目录在进程创建时设置为已验证的 Windows 项目根目录；
- `Resize` 调用 `windows.ResizePseudoConsole`；
- `Close` 先关闭伪控制台和输入端，随后使用 job object 或既有 `taskkill /T /F` 兜底终止完整子进程树；
- Shell 应以 `cmd.exe /d /q /k "chcp 65001 >nul & echo <随机内部标记>"` 启动。ConPTY 读取输出直至收到完整的随机内部标记，将该标记从转发流中剔除后才发送服务端 `ready`；超时未收到标记即启动失败并回收进程。在 `ready` 之前前端禁用输入，避免用户字节早于 UTF-8 初始化到达。仍需在 ConPTY POC 中验证中文输入、中文输出和 ANSI 控制序列；PTY 输出保持原始字节流，禁止复用现有运行日志的 GBK 按行转码模型。

实现放在带 `//go:build windows` 的 `terminal_windows.go`；非 Windows 目标提供无该实现的编译安全文件。需要在 Windows 10 1809+、Windows 11 上验证 ConPTY 可用性；不可用时创建请求返回明确的环境不支持错误，不能退回普通管道。

当 control-server 运行在 WSL 而项目目标是 Windows 时，WSL 进程不能直接调用 Windows ConPTY API。此路径必须随一期提供一个原生 `milevia-terminal-bridge.exe`：它以受控的 stdio 协议接收已解析的 Windows 工作目录、初始尺寸、输入和 resize，且只在本机由 control-server 启动；bridge 内部拥有 ConPTY 与 Windows 进程树。控制服务只转发终端字节流，不通过 TCP 暴露 bridge，也不把浏览器输入拼进 PowerShell 脚本。

bridge 使用版本化、长度前缀的二进制帧，避免 stdout 文本分隔与终端输出互相污染。`open` JSON 必须包含固定 `protocolVersion: 1`；bridge 只接受兼容版本，`ready` 返回实际协商版本，不兼容时返回 `error` 并退出。所有多字节整数均为 little-endian：长度为 `u32`，尺寸为 `u16`，退出码为 `i32`。

```text
请求帧：little-endian u32 length + u8 type + payload
  1 open：JSON（`protocolVersion`、绝对 Windows 工作目录、shell、cols、rows）
  2 input：原始终端字节
  3 resize：u16 cols + u16 rows
  4 close：空 payload
响应帧：little-endian u32 length + u8 type + payload
  16 output：原始 ConPTY 字节
  17 ready：JSON（协商后的 `protocolVersion` 和 PID）
  18 exit：i32 exitCode
  19 error：UTF-8 错误文本（不得包含 token）
```

bridge 的 stdin/stdout 只能承载上述协议，诊断信息全部写 stderr；`length` 包含 type 和 payload，最大 1 MiB，超过上限或读取到未知 type 立即关闭 bridge。单帧大小、启动超时和关闭顺序与 `terminalManager` 相同。Windows 桌面发布包需在 `tauri.conf.json` resources 中加入 bridge，并由 `build-sidecar.mjs` 构建和指纹跟踪；WSL 开发部署通过 `MILEVIA_TERMINAL_BRIDGE` 指定可执行文件路径，未配置时明确报告 Windows bridge 不可用。这样 Windows 目标在 WSL 开发部署和原生 Windows 桌面部署中都保持真实 PTY 语义。

### 4.5 WSL 终端

WSL 项目在 Windows control-server 下也必须具备真实 PTY：ConPTY 运行的是 `wsl.exe`，而不是让 Windows 侧以管道模拟 Linux 终端。

启动参数的语义如下：

```text
wsl.exe -d <distro> --cd <linuxProjectPath> --exec <shell> -l
```

- 项目持久化的 UNC 路径通过既有 `uncToWslPath()` 转为 Linux 路径；仅接受当前 `wsl-local` 所属发行版；
- 先验证 `wsl.exe`、发行版、目录与默认 Shell 可用，再创建 PTY；
- 不通过字符串拼接把用户输入注入 WSL 启动脚本；命令输入永远仅通过 PTY stdin 传递；
- WSL 进程终止由 ConPTY 外层进程树处理，关闭时确保 `wsl.exe` 及其 Linux 子进程不残留。

若 control-server 本身运行在 WSL/Linux，使用 POSIX PTY 启动 `$SHELL -l`；工作目录指向项目路径，关闭时终止独立进程组。该实现放入 `terminal_unix.go`（`linux` / `darwin` build tag）。依赖库必须明确支持目标平台并锁定版本；若使用 `creack/pty` 等 Linux/macOS 库，只能用于 POSIX 文件，Windows 仍必须走 ConPTY 或上述 bridge，不能以跨编译通过代替运行时支持。

### 4.6 SSH 终端

SSH 项目复用 `sshClient.newSession()`，每个本地终端会话创建一个独立 SSH session，不与 Agent 会话或项目运行 session 复用。

启动顺序：

1. 确认 `ssh-*` Runner 仍在注册表中且连接有效。
2. 通过 `canonicalProjectPath()` 获取远程真实项目根目录。
3. `session.RequestPty("xterm-256color", rows, cols, ssh.TerminalModes{})`。
4. 连接 stdin 与唯一输出管道：`session.Stdout` 和 `session.Stderr` 都写入同一个带 mutex 的 `io.Writer`，该 writer 再写入 `io.PipeWriter`；`TerminalSession.Read` 只从对应的 `io.PipeReader` 读取。不得让两条 goroutine 无同步写同一缓冲，否则 ANSI 或 UTF-8 字节会交错。
5. 以 `session.Start()` 启动受控的 `cd <shell-quoted-path> && exec "${SHELL:-/bin/sh}" -l`。`session.Shell()` 无法携带初始目录，不能单独使用；`cd --` 不作为远程 `/bin/sh` 的必需语法。
6. resize 调用 `session.WindowChange(rows, cols)`；关闭优先 `session.Close()`，失效时关闭底层连接使 session 收敛。

`Close` 还必须关闭 SSH session、`io.PipeWriter` 和 `io.PipeReader`，以解除阻塞中的 `Read`；关闭顺序和错误处理必须支持重复调用。唯一输出 writer 仅保证单次 `Write` 原子，不承诺远端 stdout/stderr 的全局时间顺序，这是 SSH PTY 场景可接受的字节流语义。

远程 `cd` 路径只能来自数据库记录并经 `canonicalProjectPath()` 解析，必须使用已有 `shellQuote` 引用。`SHELL` 只接受远程环境中存在且为可执行文件的绝对路径，异常时回退 `/bin/sh`。用户在终端输入的任意命令则只经 PTY stdin 转发，绝不拼入服务端 SSH 命令字符串。

SSH 网络中断时，控制服务向订阅者发 `runner_offline` / `exit`，关闭本地托管会话并释放配额。不会使用 `tmux` 或 `screen` 保活，因为一期语义是“连接断开则终端结束”，这比无界的远程孤儿进程更安全、可预测。

## 5. 生命周期与安全

### 5.1 统一清理路径

| 事件 | 行为 |
| --- | --- |
| 用户关闭一个终端 | 关闭 WebSocket、PTY、进程树，移除内存会话 |
| 页面/网络断开 | 断开订阅，保留会话 60 秒等待重连，超时后关闭 |
| Shell 自行退出 | 推送 `exit`，保留只读输出至最后订阅者关闭或短暂重连窗口结束 |
| 项目删除 | 删除前关闭该项目所有终端，再完成项目删除流程 |
| control-server 关闭 | 关闭终端 WebSocket，停止全部会话及进程树，再关闭 HTTP/SQLite |
| SSH Runner 断开或删除 | 关闭与该 Runner 关联的所有终端会话 |

`Server.Close()` 和 `deleteProjectLocked()` 必须调用 `terminalManager.CloseAll()` / `CloseProject(projectID)`；SSH 连接的断开、删除和重新配置路径必须在关闭旧 `sshClient` 之前调用 `CloseRunner(runnerID)`。这些操作必须幂等、无锁等待 PTY I/O；`terminalManager` 使用创建与已登记会话两组 `WaitGroup`，保证进程真正回收后服务才退出。项目删除和 SSH Runner 替换必须先阻止新的 terminal admission，再执行关闭，避免关闭过程中又创建新会话。

### 5.2 安全边界

| 风险 | 处理 |
| --- | --- |
| 任意本机网页访问终端 | 复用 `requireSession`、精确 Origin、桌面 WebSocket 子协议认证 |
| 令牌泄露 | 令牌仅位于 HTTP Header 或 WebSocket 子协议，不进入 URL/日志/响应体 |
| 越权访问其他项目 | 每个 REST/WS 请求校验 projectID、sessionID 归属、项目存在与 Runner 状态 |
| 路径穿越 | 初始目录仅由项目记录与既有路径解析函数导出；前端不提交原始路径 |
| 输出洪泛/内存耗尽 | 输入、队列、重放缓冲、会话数全有限额；慢订阅者断开 |
| 子进程残留 | Windows 进程树、Unix 进程组、SSH session 三种实现均有关闭和兜底策略 |
| 敏感内容落盘 | 不持久化命令、输出、环境变量；错误日志只含会话 ID 与非敏感状态 |

终端能力本身等价于向当前操作系统用户授予 Shell。因此“项目根目录”只代表初始目录，不能当作权限沙箱。产品 UI 应在首次使用时明确标识执行环境与该安全事实，但不以不可执行的命令黑名单制造虚假安全感。

## 7. 测试与验收

### 7.1 后端单元与集成测试

- 会话创建拒绝不存在项目、离线 Runner、非法尺寸、超额会话和无效 sessionID；启动中项目删除或 Runner 替换会使 lease 失效，已启动 PTY 必须关闭且不得登记会话。
- 终端创建超时、PTY/SSH/bridge 启动中途失败时，所有子进程、session、管道和会话计数均被回收。
- 终端输入输出保持字节序列；二进制帧的 little-endian `seq`、64 KiB 输入上限、1 MiB 队列边界和 UTF-8 分段解码均有覆盖。包含 ANSI、UTF-8 中文、分段 UTF-8、超过单行长度的输出均不被按行截断或转码。
- WebSocket 正确拒绝没有桌面会话子协议的请求，且不会将 token 写入错误信息。
- 输出重放按 `seq` 有序；过期序列返回截断状态；慢客户端不会阻塞其他客户端或 PTY。
- 用户关闭、断线超时、项目删除、服务关闭与 SSH 断开均只关闭一次，且释放会话计数。
- Windows 自动化 POC 运行 `cmd`，验证 `echo`、中文、ANSI、`ping` 后 `Ctrl+C`、`resize`、子进程树清理。
- WSL POC 验证 `pwd` 为项目 Linux 路径、`echo`、`stty size` 与 UI 尺寸一致、`sleep` 后 `Ctrl+C`。
- SSH 集成测试使用可控测试 SSH 服务，验证 PTY 请求参数、工作目录、`WindowChange`、stdin、互斥合并的 stdout/stderr，以及连接被关闭后的会话回收和 reader 解除阻塞。
- WSL control-server 的 Windows 项目测试验证 bridge 缺失、bridge 启动超时、协议版本不兼容、协议帧损坏、little-endian 尺寸/退出码和 bridge 进程树清理；Windows 桌面打包测试验证 bridge 与 control-server 版本一致。

### 7.2 前端测试

- 路由、项目页签状态和键盘导航包含 `terminal`。
- mock WebSocket 验证 JSON 控制帧、二进制输入/输出帧、little-endian `seq`、`ready` 前输入禁用、resize 范围、replay、exit、错误和重连行为。
- `ResizeObserver` 驱动 FitAddon 后发送真实列/行；不可见容器不会发送 0 尺寸。
- 组件卸载时释放 xterm、FitAddon、observer、重连计时器和 WebSocket。
- 输出只写入 xterm，不使用 `dangerouslySetInnerHTML`，不在 React state 中累积无限日志。

### 7.3 人工端到端验收

在 Windows 桌面端、WSL 项目和 SSH 项目分别执行以下流程：

1. 打开项目的“终端”，确认提示符位于项目根目录。
2. 执行带中文、颜色和连续输出的命令，确认显示和滚动正常。
3. 执行持续命令，使用 `Ctrl+C` 中断，确认 Shell 仍可继续输入。
4. 改变窗口大小，验证 `stty size` 或等效命令与页面尺寸一致。
5. 启动一个有子进程的命令后关闭终端，确认进程树不残留。
6. 刷新/短暂断网并重连，确认 60 秒内可恢复会话和近期输出。
7. 对 SSH 项目断开连接，确认界面显示明确错误且会话释放；重新连接后可创建新终端。
8. 删除带活跃终端的项目、退出桌面应用，确认所有会话被回收且不阻塞退出。
9. 在同一会话重复打开页面，确认旧 WebSocket 被替换而不会出现两个输入源互相抢占。

## 9. 最终决策

一期终端不是运行日志的增强，而是一项新的跨 Runner 交互会话能力：

```text
Windows 项目 -> ConPTY（原生 control-server 或 terminal bridge） -> cmd.exe
WSL 项目     -> ConPTY -> wsl.exe -> Linux Shell
SSH 项目     -> SSH PTY -> Remote Shell
```

三条路径在前端表现为同一终端，在后端归一为 `TerminalSession`，由 `terminalManager` 统一承担安全认证、流控、断线重连和资源回收。只有三类环境均通过第 7 节验收，才视为一期完成。
