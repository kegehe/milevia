# 51-会话内提问交互（Ask User）调研与实施方案

> 日期：2026-10-28
> 状态：方案定稿，实现未开始。四个 spike 已在本机跑完，结论见 §3。
> 关联：[34-MCP连接与配置](./34-MCP连接与配置调研与实施方案.md)、[42-CLI工具管理页](./42-CLI工具管理页调研与实施方案.md)、[39-后台任务与回合边界](./39-后台任务与回合边界.md)

## 0. 一句话结论

平台只做**一条**通道：内置一个常驻注入的 HTTP MCP server，暴露 `ask_user` 工具；模型调用它，
服务端阻塞等用户作答，把答案作为工具结果返回。**不做** Claude 原生 `AskUserQuestion` 的适配。

## 1. 问题：CLI 会提问，平台没有回路

会话页现在只有一条人机回路——**工具审批**：hook 阻塞 → `approval.pending` → 用户点允许/拒绝
（`app.go:7763` `waitForApproval`、`ConversationPage.tsx:1709` `ApprovalBanner`）。它只回答
"这条命令能不能跑"，回答不了"你要选 A 还是 B"。

各 CLI 的提问能力当前处于三种"无人接手"的状态：

| CLI | 提问工具 | 现状 | 证据 |
| --- | --- | --- | --- |
| Claude Code | `AskUserQuestion` | 未接；能否出现在工具表取决于模型/供应商 | `sdk-tools.d.ts:1136 / 3799` 定义了输入与 `answers` 契约 |
| CodeBuddy | `AskUserQuestion`、`AskUserForStructuredInput` | 未接 | init 帧工具表里有，模型侧不一定拿到 |
| Qoder | `AskUserQuestion` | 未接 | `bundle/qodercli.js` 含该工具 |
| Codex | `request_user_input` | **exec 模式明确不支持** | 二进制内文案：`request_user_input is not supported in exec mode` |
| OpenCode | `question` | 被主动 deny，避免回合挂死 | `opencode_runner.go:402`、`:431` |
| Cursor | `askQuestionToolCall` | 只当普通工具卡显示一行"提问" | `cursor_runner.go:629` |

## 2. 方案选择：为什么砍掉原生通道

一度考虑的方案是"双通道"：原生 hook（`PreToolUse` + `updatedInput.answers`）为主，MCP 兜底。
实测后放弃，理由不是"原生不好"，而是它的**可用性不掌握在我们手里**：

- 同一台机器上，Claude 的 init 工具表 26 个工具里没有 `AskUserQuestion`；Qoder 也没有；
  CodeBuddy 有但模型不调用。工具表由**模型/供应商**决定，与 CLI 版本无关。
- 原生通道还有一条本机无法证明的契约（`updatedInput` 能否给提问工具注入答案）。
- 保留两条通道 = 两套 schema + 两个适配器 + 两处权限 + 两种失败模式，最后还要为"原生不可用"
  写回退。收益只有"模型更愿意用原生工具"这一条。

反过来，MCP 通道 claude / codebuddy / qoder 三个 CLI 全部实测调通（§3），且不依赖模型特性。
所以：**只做 MCP**。原生通道如果将来某个版本稳定暴露，再单独评估，不预留代码分支。

### 2.1 为什么是 HTTP 而不是 stdio helper

SSH 项目的审批回调本来就是 `curl` 直连控制服务（`ssh_runner.go:1360`），说明"CLI 所在环境能访问
控制服务"这个前提**已经被现有功能验证过**。HTTP 形态直接复用这个前提：

- 一处实现，**同一个端点**给三端用（实际接线见 §5.4：本期只接了 Windows）；
- 不需要为 Linux 交叉编译、不需要往远端传二进制；
- 代价只是要实现一个最小 JSON-RPC 端点，比 60 行 helper 重，但省掉三种环境的打包与分发。

## 3. 实测证据

脚本在 `scripts/spikes/ask-user/`（零依赖，可复跑，README 里有判定口径与完整记录）。

### 3.1 结论表（2026-10-28，Windows 11 / Node 22）

| 用例 | 结果 | 要点 |
| --- | --- | --- |
| hook `updatedInput`（Claude 系） | **PASS**（codebuddy / qoder） | hook 收到 `PreToolUse/tool_name=Bash`，命令被改写成 `echo SPIKE_INJECTED_OK` 并执行；payload 字段与 Claude 逐字段一致 |
| `AskUserQuestion` 注入 | INCONCLUSIVE | 三台 CLI 的模型侧都拿不到该工具（claude/qoder 没有，codebuddy 有但不调用） |
| HTTP MCP 连通 | **PASS**（claude / codebuddy / qoder） | `initialize → tools/list → tools/call` 全通 |
| 阻塞时长 | **90 秒 PASS** | claude 上 90s 的 `tools/call` 未被掐断；更长未验 |
| 权限 · codebuddy 生产档 | **PASS** | `--dangerously-skip-permissions`（`codebuddy_runner.go:172`）本来就放行 MCP |
| 权限 · qoder 生产档 | **PASS** | `accept_edits`（`qoder_runner.go:369`）放行 MCP |
| 权限 · 只读档 | FAIL（两个 CLI） | qoder 可用 `--allowed-tools` 精确放行；codebuddy 必须放开 `DeferExecuteTool`（面太宽） |
| codex | INCONCLUSIVE | 本机 codex 连普通回合都跑不完（卡在 `turn.started`），与 MCP 无关 |
| cursor / opencode | 未测 | 本机未安装 |

> 表里保留"hook `updatedInput` PASS"这一行，是因为它证明了 **Claude 系的 hook 通道本身是通的**
> （审批、审计都靠它），不等于本方案要走原生提问。原生通道的结论见 §2：不做。

### 3.2 由此确定的三件事

1. **主路径零改动**：codebuddy / qoder 在写入与完全控制两档上已经放行 MCP 调用，不需要额外权限配置。
2. **只读档不提供提问**：codebuddy 想放行只能把 `DeferExecuteTool` 一起放开，等于放开所有延迟工具；
   而只读会话本来就无法执行动作，问了也做不了。qoder 虽有精确解法，但两档行为不一致更难解释。
3. **必须按会话探测、但探测的不是原生工具**：探测的是"内置 MCP server 有没有注入成功"——
   会话 init 后 `tools/list` 是否出现 `ask_user`，决定了这个会话能不能提问。

## 4. 协议

### 4.1 事件族

与 `approval.*` 平行，不合并（审批是二元裁决 + 一段命令文本，提问是多题结构，混用会让重放、
手机通知、卡片渲染三处都长出条件分支）。

```
ask.pending    { askId, source:"mcp", toolUseId, questions:[...] }
ask.answered   { askId, answers:{ <questionId>: "<文本>" }, notes? }
ask.skipped    { askId }                        用户主动跳过
ask.expired    { askId, reason:"timeout" }      超过等待预算
ask.cancelled  { askId, reason:"stopped" }      run 被停止 / 控制服务关闭
```

事件经 `appendEvent`（`app.go:7955`）落库，因此断线重放、手机快照、通知推送三件事自动继承。
`remote_control.go:231` 的 `remoteNoticeTypesSQL` 增加 `type like 'ask.%'`。

### 4.2 问题结构（平台自有契约）

不复用 Claude 的 `answers` 以题目原文为 key（同题同文会撞）。平台用自己的 `id`：

```jsonc
{
  "questions": [
    {
      "id": "q1",                       // 必填，答案以它为 key
      "header": "数据库",                // 卡片上的短标签，≤12 字
      "question": "迁移到哪个数据库？",   // 正文
      "kind": "choice",                 // choice | text | number，默认 choice
      "options": [                      // choice 必填，2~8 项
        { "label": "PostgreSQL", "description": "需要新装服务" },
        { "label": "SQLite", "description": "零运维，单机上限" }
      ],
      "multiSelect": false,
      "placeholder": "",                // text 用
      "min": 0, "max": 100, "step": 1, "unit": "%"   // number 用
    }
  ]
}
```

一次调用 1~4 题（与原生习惯一致，也让卡片不会长到需要滚屏）。

### 4.3 工具结果

模型侧读到的是一段紧凑文本，不是 JSON：

```
用户已回答：
- 数据库：PostgreSQL
- 是否需要停机：否（用户补充：可以周末切换）

用户未回答的问题：无
```

超时/跳过时返回明确的空结果，**不伪造答案**，但允许模型带着显式假设继续：

```
用户未回答（已跳过）。不要猜测用户的选择；如果需要继续，请明确写出你采用的假设。
```

### 4.4 端点

| 端点 | 用途 |
| --- | --- |
| `POST /api/internal/mcp/interaction` | MCP JSON-RPC（initialize / tools/list / tools/call），token 鉴权 |
| `POST /api/asks/{askId}` | 桌面作答：`{ answers, notes? }`；跳过用 `{ action:"skip" }` |

内部端点复用审批那套凭据（`X-Auto-Approval-Token`），不新造一套鉴权。

**身份必须是会话维度，不是 run 维度。** 常驻会话跨多个 run，而 MCP 配置是**建会话时写一次**
（`app.go:6465` 的 `prepareMCPInjection`），那时还不知道后续会跑哪些 run。所以 header 只带
`X-Auto-Conversation-ID`，run 由服务端按 `session.activeRunID` 反查 —— 与 `waitForApproval` 的
会话分支（`app.go:7793`）完全一致。

**实现上有两个必改点**：

1. `token` 在 `app.go:6458` 生成、`prepareMCPInjection`（`app.go:6465`）在其后调用，所以 token 拿得到；
   但该函数**当前没有 token 参数**，且 SSH 形态走 `injection.remoteJSON()` 另写一份。两处都要把
   token 与 conversationID 透传进去，否则注入出来的配置里没有鉴权头，`tools/call` 会被 401 挡掉。
2. `requireSession`（`app.go:1641`）对内部端点做的是**精确路径白名单**：目前只有
   `/api/internal/approvals/wait` 带 `X-Auto-Approval-Token` 时豁免。新端点必须在这里再加一条，
   否则 CLI 的请求会在进 handler 之前就被 401 拦掉——现象是"本地 curl 能通，CLI 里全失败"。

MCP 客户端是否每个请求都带 header，实测过：spike 的假 server 日志里，claude / codebuddy / qoder
的 `initialize`、`tools/list`、`tools/call` 全部带上了 `Authorization`，所以不必为跨请求的
会话保持再加一层 `Mcp-Session-Id`。

### 4.5 超时与终态

| 参数 | 值 | 说明 |
| --- | --- | --- |
| 服务端等待预算 | 300s（`AUTO_ASK_TIMEOUT`） | 到点落 `ask.expired`，返回"未回答"结果 |
| 客户端工具超时 | 360s | claude 用 `MCP_TOOL_TIMEOUT`，codex 用 `mcp_servers.<n>.tool_timeout_sec` |
| 客户端必须比服务端长 | +60s | 否则被 CLI 掐断，模型看到的是"工具失败"而不是"用户没回答" |

**预算为什么是 300s 而不是 900s**：实测只验证到"90 秒的调用不会被掐断"，而 claude 二进制里
`MCP_TOOL_TIMEOUT` 的取值被 `Math.min(Math.max(值, 下限), 上限)` 夹过一次，上限是多少没测出来。
如果上限是 300s，写 900s 会被**静默截断**——表现是"用户还有 10 分钟可答，工具却先失败了"。
在 `§9` 那条约 600s 的实测做完之前，默认值必须压在已验证区间内；等验证通过再调大，不要反过来。

终态对齐：停止 run 时新增 `resolveRunAsks(runID, "cancelled")`，与 `resolveRunApprovals`（`app.go:7903`）
成对调用。**启动时对账**：把没有终态的 `ask.pending` 一律置为 `ask.cancelled`，否则重启后那张卡会
永远显示"等待你的回答"。

**迟到的答案**：`askId` 已进入终态后再 `POST /api/asks/{askId}` 返回 409，不静默吞掉——用户点了提交
却什么都没发生，比报错更让人困惑。

### 4.6 限流与上限

这一层的存在是为了让"提问"不会变成比"审批"更廉价的中断手段：

| 限制 | 值 | 超限后 |
| --- | --- | --- |
| 每个 run 的提问次数 | 5 次 | `tools/call` 直接返回"本轮提问次数已用完，请自行决策并说明依据"，不产生 `ask.pending` |
| 每题答案长度 | 4 KB | 截断并提示 |
| 每题选项数 | 8 | 超出在工具层拒绝，返回参数错误 |
| 同时挂起的 ask | 每会话 1 个 | 已有 pending 时新的调用直接报错（"当前会话已有一个未回答的问题"），不排队 |

"同时挂起 1 个"的取舍：一次 run 里模型是串行行动的，正常不会并发提问；但**子代理**的 tool 调用
也会走到同一个端点，所以还是要挡。让后来者直接拿到"前一个问题还没答"的明确回复，比让它挂两个 5 分钟的请求更可预测。

## 5. 注入与权限

### 5.1 注入

内置 server 名 `milevia`，工具 `ask_user`，**总是注入**（不依赖用户在 MCP 页勾选），与用户自己的
server 并列写入同一份 `--mcp-config` / `-c` 参数。注入点在 `prepareMCPInjection`（`mcp_config.go:124`），
在那里合并一个系统 server，而不是让用户目录多一条记录。

**"总是注入"要落在正确的分支上**，否则最常见的场景会直接失效：`prepareMCPInjection` 在
`len(servers) == 0` 时**早退并返回空注入**（`mcp_config.go:150`）——一个没配任何 MCP 的项目
（绝大多数项目）因此拿不到 `--mcp-config`，内置 server 也跟着消失。内置 server 必须在
`selectMCPServers` 之后、判空之前并入列表，不能写在函数末尾。

两条既有的早退要知道后果：

- **cursor** 在函数入口就早退（`MCPInjection=user-config`），所以它天然没有 `ask_user` —— 与 §5.3 一致。
- **远端 Claude 版本过低/探测失败**时同样返回空注入（`mcp_config.go:166` 一带），此时该会话无法提问。
  UI 不能只说"等待回答"，要能表达"这个环境不支持提问"，否则用户会一直等一个永远不会出现的卡片。

### 5.2 豁免

`mcpToolHookMatcher = "Bash|mcp__.*"`（`claude_runner.go:980`）会把 `ask_user` 也拦进审批，
变成"先审批再提问"。必须在 `waitForApproval` 里按工具名对 `mcp__milevia__ask_user` **提前返回 allow**，
且不写审计记录（它不是一次真实工具调用）。

### 5.3 各 CLI

| CLI | 是否注入 | 额外动作 | 状态 |
| --- | --- | --- | --- |
| claude-code | 是（`--mcp-config`） | 无 | 已验证 |
| codebuddy | 是（`--mcp-config`） | 无（生产档已放行） | 已验证 |
| qoder | 是（`--mcp-config`） | 无（`accept_edits` 已放行） | 已验证 |
| codex | 是（`-c mcp_servers.milevia.url=...`） | 配 `tool_timeout_sec` | 注入方式现成，本机未验 |
| opencode | 是（`OPENCODE_CONFIG_CONTENT`） | 配 MCP 段 | 未验证 |
| cursor | **否** | 无按轮注入通道（`MCPInjection=user-config`） | 一期不支持 |

只读档（`read_only` / plan）**不注入** `ask_user`，理由见 §3.2。

"不支持"要落到目录能力上，而不是只写在文档里：在 `agent_catalog.go` 增加
`SupportsUserQuestions bool`，由管理页与新建会话的 agent 选择器读它 —— 否则用户只会在提问那一步
发现没反应。


### 5.4 本期实际接线：只覆盖本地 Windows

实现时确认了一件在方案阶段没写透的事：**MCP 配置里的 URL 是 CLI 进程去访问的地址**，而三端能到的地址不一样。

| 目标环境 | CLI 进程看到的 127.0.0.1 | 结论 |
| --- | --- | --- |
| 本地 Windows | 就是控制服务本身 | 直接注入 |
| WSL | WSL 自己的回环（互操作 .exe 才走 Windows 网络） | **本期不注入** |
| SSH 远端 | 远端自己的回环；审批靠 `startApprovalTunnel` 的反向隧道，隧道地址在 runner 侧才确定 | **本期不注入** |

所以 `prepareMCPInjectionWith` 只在 `target == agentTargetEnvWindows` 时并入内置 server；
其余环境保持原样（没有提问能力，模型只能文字提问）。下一步两条路：

- WSL / SSH 把隧道地址**回填**进 MCP 配置（runner 建隧道 → 重写配置 → 再启动 CLI）；
- 或改回 stdio helper，代价是每个目标环境要有一份可执行文件。

两条都要单独验证，不要在没验证前把"不支持"写成"已支持"。

## 6. 界面形态

### 6.1 时间线卡片（原位、可回看）

- 顶部 `header` 小标签 chip + 问题正文；
- 选项行：label 加粗、description 灰色小字；多选带勾选框；
- 每题末尾固定一个"其他…"自由输入（不放进 options，避免和 CLI 的 Other 语义打架）；
- 一卡多题纵向排列，共用底部「提交」+「跳过这次提问」；
- 允许部分作答：只提交已填的题，未填的随结果告诉模型；
- 已答后折叠成一行 `✓ 已答 · PostgreSQL`；超时/跳过变灰；
- `kind:"number"` 渲染步进器 + 单位。

### 6.2 输入区横幅

与 `ApprovalBanner`（`ConversationPage.tsx:1709`）同一位置与样式族：
`❓ Claude 想确认一件事` + 第一题 header + 问题摘要 +「去回答」（滚动并聚焦卡片）+「跳过」。

等待期间输入框保持可用，但发送按钮文案变「作为回答发送」——**显式**，不做隐式改道，
否则用户以为在插话、实际在作答。

**只在待答问题里至少有一道 `kind:"text"` 时才改文案。** 全是选择题时保持原来的插话语义：
把一句自由文本当成"A 还是 B"的答案没有定义，硬映射只会得到模型看不懂的输入。

### 6.3 运行指示器

从"思考中"改为"等待你的回答"，停掉转圈。这是最容易被误判成"进程死了"的地方。

### 6.4 通知与手机

**先纠正一个容易踩空的假设**：桌面通知中心今天**没有任何服务端产出的 `approval.pending` 通知**。
`NotificationProvider.tsx:184` 那段去重逻辑是防御性代码，全仓搜不到对应的
`broadcastNotification(NotificationEvent{Type:"approval.pending"})` —— 所以"照抄审批"等于照抄一段
永远不会触发的分支。

要真的进通知中心，得在 ask waiter 里**新写**一次 `broadcastNotification`（`notification.go:277`），
类型 `ask.pending`，`conversation_id` 带上、`action_url` 指向该会话。这是 §7 里没有的工作量，
要么算进 P2，要么明确"一期只做会话内提示，不进通知中心"。

手机端同理：`MobileRemotePage.tsx` 的 `noticeFromEventFields` 只认 `approval.*`、`system`、
`stderr` 与诊断事件，`ask.*` 会走到最后的 `return null` 被丢掉。要出只读卡，必须在那里补一个分支，
文案与桌面共用同一份"已答/已跳过/已超时"词汇表 —— 否则两边措辞会漂移。

## 7. 分阶段实施

| 阶段 | 内容 | 验收 |
| --- | --- | --- |
| P0 | 服务端协议：waiter、`ask.*` 事件、`POST /api/asks/{id}`、超时、取消、启动对账 | 单测覆盖超时/停止/重启三条路径 |
| P1 | 内置 HTTP MCP 端点 + 注入 + 审批豁免 | claude 会话里能调通 `mcp__milevia__ask_user` |
| P2 | 前端卡片 + 横幅 + 指示器 + 通知；手机只读（含 `broadcastNotification` 与手机侧 `ask.*` 分支） | claude 端到端：提问→作答→模型继续 |
| P3 | codebuddy / qoder 接入 | 与 claude 同一条用例 |
| P4 | codex / opencode（视环境可用性） | — |

cursor 在 CLI 工具管理页（`agent_catalog.go` 的能力声明）里标"不支持提问"，不做假装。

## 8. 明确不做的事

1. **不把提问塞进 `approval.pending`**：裁决语义与问答语义不同，混用会让重放与手机端长出条件分支。
2. **不做原生 `AskUserQuestion` 适配**：可用性取决于模型，见 §2。
3. **不做 stdio helper**：三端打包与分发成本远高于 HTTP。
4. **不让两条通道并存**：同一会话里模型会在原生与 MCP 之间二选一，行为不可预期，测试也无法稳定。
5. **不解析模型自然语言提问去"猜"选项**：不稳定，且会把"模型在解释"误判成"模型在等你"。
6. **不在只读会话注入** `ask_user`：见 §3.2。
7. **不替用户预选默认答案**：题目里没有默认项，超时就是"没答"，不能挑第一个提交。
8. **不把 ask 事件交给 event_retention 的进程事件裁剪**：历史回放要能重看当时的问答（当前
   `replayableEventsPredicate` 是**排除式**`not in (...)`，新增类型默认可见，不需要改；但别把
   `ask.*` 加进 `eventsProcessEventTypes`）。

## 9. 未决项

- **codex 本机跑不完回合**（`turn.started` 之后无响应），MCP 通道结论待环境恢复后补测。
- **阻塞上限**只实测到 90 秒。`MCP_TOOL_TIMEOUT` 在 claude 二进制里被 `min(max(值, 下限), 上限)`
  夹过一次，上限未知；`tool_timeout_sec` 同理。**这是 P1 的门禁**：先跑一条 600s 的用例确认
  "客户端能等满 600s 且服务端先收尾"，通过之后才允许把 `AUTO_ASK_TIMEOUT` 调过 300s。
  没通过就维持 300s —— 强行写大值只会得到一个被静默截断的超时。
- **cursor** 是否有可用的按轮注入路径（例如工作区级 `.cursor/mcp.json` 是否可接受）未调研；
  默认按"一期不支持"处理。
- **模型是否愿意主动调用** `ask_user`：目前只验证了"被要求时能调"。工具描述的措辞需要在
  P2 做一轮真实任务观察，必要时补一段系统提示。
- **子代理提问**：Claude 的子代理共用同一个 MCP 连接，理论上也会走到同一个端点，但"子代理提问时
  `ask.pending` 该挂在子代理卡片上还是主时间线"没验证过。§4.6 的"每会话 1 个"能挡住并发，
  挡不住归属问题；P2 用一次真实子代理任务确认。
