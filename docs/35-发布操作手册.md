# 发布操作手册（供 AI 执行）

> 面向对象：任何 AI 工具 —— CLI（Claude Code、Codex…）或桌面端（Cursor、WorkBuddy…）。
> 当用户说「发布」「发版」「部署」「上线」「传个新版本」时，**照本文执行，不要凭记忆猜命令**。
> 本文只描述「怎么发」，涉及实现原理的历史记录见 `docs/33-远程控制实施进度.md`、
> 桌面端升级机制见 `docs/23-Windows打包与在线升级方案.md`、`docs/24-GitHub发布流程与Pages配置说明.md`。

## 0. 先判断要发什么

| 用户的说法 | 发布对象 | 去哪儿 |
|---|---|---|
| 远程控制服务 / 云端 / 中转服务 | `apps/cloud-control` | §1（通常**不需要你动手**） |
| 桌面端 / 电脑端 / Windows 版 / exe | `apps/desktop` | §2 |
| 手机端 / App / APK / Android | `apps/web/android` | §3 |
| 「都发」「全部发一版」 | 三个都发 | 按 §1 → §2 → §3 顺序 |

**不确定时先问用户要发哪个端。** 桌面端和手机端是两条独立的发版链路，版本号也各自递增。

## 1. 云端连接服务（`apps/cloud-control`）

**绝大多数情况不需要手动做**：推送到 `main` 且改动命中
`apps/cloud-control/**/*.go`、`go.mod`、`go.sum`、`scripts/deploy-cloud-control.sh`、
`.github/workflows/deploy-cloud-control.yml` 时，GitHub Actions 会自动部署。

- 工作流名：**部署云端连接服务**（`.github/workflows/deploy-cloud-control.yml`）
- 手动触发：GitHub → Actions → 「部署云端连接服务」→ Run workflow

**流水线做什么**：runner 上 `go vet` + `go test` → 打包源码（约 30KB，排除 `.tmp`）→ scp 到服务器
→ **服务器本地编译**（`GOPROXY=goproxy.cn`，Go 工具链按 `go.mod` 自动拉取）→ 替换容器内二进制
→ 重启 → 健康检查 → 固化镜像 → 清理临时产物。部署环节约 **5 秒**；失败自动回滚到上一版。

> **为什么传源码而不是二进制**：GitHub runner 在境外，往国内服务器传 10.2MB 二进制实测约
> **12.7 KB/s**，单这一项就要 14 分钟（整条流水线曾因此耗时 15 分钟）。传 30KB 源码只要 2 秒，
> 而服务器编译这个服务是**秒级**。**不要改回"上传二进制"。**

**日常改动要走这条路时**，你只需要确认改动落在上述路径内并提交推送（推送需用户授权，见 §5）。

### 新服务器（2026-10-29 起）

- 公网 `8.153.198.174`（内网 `172.16.125.18`），Ubuntu 26.04。旧机 `111.229.52.158` 到期后停用。

- PWA 静态站使用 0.1.13 发布包内的 web 资源；工作区未提交的 web 改动不要直接发布到 PWA，
  避免把 WIP 带上生产。
- CI Secrets 已指向新机；2026-10-29 手动运行「部署云端连接服务」成功（run 40817242920）。

### 阿里云接入备案通过后的收尾（新机）

1. 从公网确认拦截已解除：`curl https://keyanjia.info:8443/health` 返回 200 且 `remote_ip=8.153.198.174`；80 端口不再返回 “Non-compliance ICP Filing”。
2. 签发并切换证书：
   ```bash
   certbot certonly --webroot -w /var/www/certbot -d keyanjia.info \
     --key-type ecdsa --non-interactive --agree-tos --register-unsafely-without-email \
     --deploy-hook 'systemctl reload nginx'
   sed -i 's#/etc/nginx/ssl/keyanjia.info/fullchain.pem#/etc/letsencrypt/live/keyanjia.info/fullchain.pem#; s#/etc/nginx/ssl/keyanjia.info/privkey.pem#/etc/letsencrypt/live/keyanjia.info/privkey.pem#' \
     /etc/nginx/sites-available/milevia.conf
   nginx -t && systemctl reload nginx
   certbot renew --dry-run
   ```
3. 新证书验证通过后删除桥接私钥：`rm -rf /etc/nginx/ssl/keyanjia.info`。
4. 桌面端在远程页输入 `/etc/milevia/cloud-control.env` 里的注册令牌；手机重新扫码 + 校验码配对。
5. 若备案通过后 80 仍不可用：改用 DNS-01（阿里云 RAM DNS 子账号或手动 TXT），桥接证书可用到 2027-01-18 作为缓冲。

### 验证部署是否真的成功

```bash
curl -s -o /dev/null -w '%{http_code}\n' https://keyanjia.info:8443/health     # 期望 200
```

流水线「步骤成功」不等于线上生效，用户在意时按上面的命令实测一次。

### 本地如何跑云端的测试（不需要 Docker）

```bash
python scripts/run-cloud-control-tests.py
```

它会从部署文件读数据库 DSN、开 SSH 隧道连生产库，跑 `internal/cloud` 下的真实库测试
（LISTEN/NOTIFY 语义、事件流排空等）。它从 `/etc/milevia/cloud-control.env` 读 DSN；没配
`MILEVIA_TEST_DATABASE_URL` 时这些测试在 CI 里会**静默跳过**，所以 CI 通过不代表它们跑过。

### 手动部署（断网急救 / 排查用）

部署脚本在服务器上执行，支持两种输入：

```bash
# 方式 A（推荐）：只传源码，让服务器编译
SRC_ARCHIVE=/tmp/cloud-control-src.tar.gz bash /tmp/deploy-cloud-control.sh

# 方式 B：已有编译好的 Linux 二进制
NEW_BIN=/tmp/cloud-control-linux.new bash /tmp/deploy-cloud-control.sh
```

可用环境变量：`DRY_RUN=1`（只编译+校验，不碰容器）、`COMMIT=0`（不固化镜像）、
`PRUNE=0`（不清理悬空镜像）、`CONTAINER`、`TARGET`、`HEALTH_URL`。

**打源码包的正确姿势**（Windows 上要加 `--force-local`，否则 tar 会把 `C:/...` 当远程主机）：

```bash
tar --force-local -czf /tmp/cloud-control-src.tar.gz --exclude='./.tmp' -C apps/cloud-control .
```

## 2. 桌面端（Windows）

```bash
node scripts/release.mjs <新版本号> "更新说明"
```

发一版并推到线上更新源：

```bash
MILEVIA_DEPLOY_TARGET="root@8.153.198.174:/var/www/milevia/dist/updates/" \
  node scripts/release.mjs 0.1.7 "本次更新说明" --deploy
```

**前置**：`~/.tauri/milevia-updater.key` 与 `~/.tauri/milevia-updater-password.txt` 存在
（签名密钥，缺了脚本会失败）。

**可选参数**：

| 参数 | 作用 |
|---|---|
| `--bump-only <ver>` | 只同步三处版本号，不打包、不发版 |
| `--no-build` | 不重新构建，签现有安装包 |
| `--deploy` | 构建+签名后上传到自建源与 GitHub Release |

**脚本会做**：同步 `tauri.conf.json` / `Cargo.toml` / `desktop/package.json` 三处版本号 → 构建
→ 签名 → 写两份清单 → （`--deploy` 时）上传 → 清掉服务器上同形态的旧安装包。

### 升级安装为什么要先结束 sidecar

`milevia-control.exe`、`milevia-agent.exe`、`milevia-approval.exe`、
`milevia-terminal-bridge.exe` 是主程序运行时拉起的**独立进程**（见 `tauri.conf.json` 的
`bundle.resources`），不是主程序本身。tauri 内置的 `CheckIfAppIsRunning` 只结束主程序
`${MAINBINARYNAME}.exe`，而 NSIS 的 `File` 会把这些 exe 逐个覆写回 `$INSTDIR`：目标文件正被
自己的进程当映像占用时覆写失败，弹「无法打开要写入的文件: …\milevia-control.exe」
（Abort/Retry/Ignore）；点「忽略」还会留下新宿主 + 旧 sidecar 的混杂安装。三处必须同时成立才行：

| 位置 | 作用 |
|---|---|
| `apps/desktop/src-tauri/nsis-hooks.nsh` 的 `NSIS_HOOK_PREINSTALL` / `NSIS_HOOK_PREUNINSTALL` | **安装侧兜底**：复制文件前逐个结束这四个进程，结束失败再试一次，仍失败就明确报错中止。唯一不依赖时序的保障（用户双击安装包、上次崩溃留下的孤儿进程都覆盖）。判据用 `KillProcessCurrentUser` 的返回码（0=已结束、2=本来就不在），**不要**改成"再 Find 一次看还在不在"——被结束的进程在句柄全部关闭前仍会出现在进程列表里，会把正常情况误判成失败而中断安装 |
| `src-tauri/src/main.rs` 的 `install_update_inner` | **应用侧主动**：用 updater 的 `on_before_exit` 钩子在交给安装程序前 `stop_agent()` + `stop_sidecar()`（Windows 上 updater 启动安装包后直接 `std::process::exit(0)`，`RunEvent::ExitRequested` 不触发，原本那次清理从不执行） |
| `apps/control-server/internal/app/parent_watch_windows.go` | **sidecar 自己**：等父进程句柄（`WaitForSingleObject`），父进程一退出立刻收敛，去掉旧实现"最多 3 秒"的窗口 |

> 动其中一处就要回头核对另外两处——它们处理的是同一个竞态。

> **桌面端脚本不再碰 Android。** versionCode/versionName、APK 构建、清单里的
> `platforms.android` 段全部由 §3 的手机端脚本独占维护。别把 Android 职责挪回来。

## 3. 手机端（Android APK）

```bash
MILEVIA_DEPLOY_TARGET="root@8.153.198.174:/var/www/milevia/dist/updates/" \
  node scripts/release-mobile.mjs 0.1.7 "本次更新说明" --deploy
```

**脚本会做**：`versionCode` 自增、`versionName` 设为指定值 → 构建 Web → `cap sync android`
→ Gradle 出 APK → 算 sha256 → **只替换清单里的 `platforms.android` 段** → 上传 → 清理旧 APK。

**可选参数**：`--bump-only <ver>`、`--no-build`、`--deploy`。

**注意**：

- `versionCode` 必须**单调递增**（Android 只认它，`versionName` 只是给人看的）。
- 手机端与桌面端**版本号各自递增**，不必相同：清单顶层 `version` 属于桌面端，
  `platforms.android` 属于手机端。
- 构建需要 Android SDK；在 Windows 上跑 Gradle 需要放开沙箱（要写
  `apps/web/android/app/build/intermediates`）。

## 4. 发布后必须做的验证

**不要只看脚本退出码**。按下面回读线上状态：

```bash
# 1) 更新清单（两个平台各自的最新版本号与下载地址）
curl -s https://keyanjia.info:8443/updates/latest.json

# 2) 安装包确实可下载且支持断点续传（206 才对；404/200 都不正常）
curl -s -o /dev/null -r 0-1023 -w 'exe=%{http_code}\n' \
  https://keyanjia.info:8443/updates/Milevia_0.1.12_x64-setup.exe
curl -s -o /dev/null -r 0-1023 -w 'apk=%{http_code}\n' \
  https://keyanjia.info:8443/updates/Milevia_0.1.13_android.apk

# 3) 云端服务健康；同时确认实际连到的是新机
curl -s -o /dev/null -w 'health=%{http_code} ip=%{remote_ip}\n' \
  https://keyanjia.info:8443/health
```

`health=200` 但 `ip=111.229.52.158` 说明 DNS 还指向旧机 —— 旧机的 `/health` 也返回 200，
不能只看状态码。换机后还要回读 `https://keyanjia.info:8443/` 的 PWA 是否正常。

> 阿里云接入备案通过前，公网 `health` 会被 ICP 拦截（8443 TLS 重置 / 80 返回 ICP 页），
> 不是部署失败；见 §1「新服务器」。

**客户端能不能真的升级**，取决于三件事同时成立：

1. 清单里的 `version` / `versionCode` 比用户当前安装的高；
2. 清单里的 `url` **指向一个真能下到的地址**；
3. 桌面端还要能被 `signature` 验签通过（换了签名密钥就必须让用户手动装一次）。

## 5. 必须遵守的约束

### 5.1 Git

**除非用户在当前对话中明确要求，禁止 `git add` / `commit` / `push` / 建 PR。**
用户说「发布」**不等于**授权提交。默认把改动留在工作区，报告清楚即可。
（这条来自 `AGENTS.md`，不要自行放宽。）

### 5.2 服务器磁盘：每个平台只保留最新一份

服务器根分区 40G；新机虽然空间不紧，仍按“每个平台只保留最新一份”执行，避免日后堆叠：

- **安装包**：发版脚本上传后会清掉同形态的历史文件（`pruneRemoteDownloads`），
  **只删同形态、不跨平台**（桌面发版不会碰 APK）。不要手工往 `/updates/` 堆多个版本。
- **部署产物**：源码包、解包目录、临时二进制用完即删；回滚二进制固定一份覆盖；
  每次部署清悬空镜像。
- **代价**：想回退到上一版没有现成安装包，需从 GitHub Release 或本地 `release/` 取。

### 5.3 更新清单的两份分发

清单有两份，下载地址必须各指自己那侧（否则会出现「先弹提示、再下载失败」）：

| 清单 | 谁提供 | 地址指向 |
|---|---|---|
| `release/updates/latest.json` | 自建服务器 `/updates/` | 自建源（主用，国内快） |
| 仓库根 `latest.json` | GitHub Pages | GitHub Release 资产（备用） |

某平台在 GitHub 上没有已发布资产时，备用源那张**不写它的下载信息**（表现为「没有更新」）
—— 这是**刻意**的降级，不是 bug。

**改动这块逻辑要动 `scripts/lib/update-manifest.mjs`**，两个发版脚本共用它。

### 5.4 `platforms` 里每一段都必须有 `signature`（2026-09-11 踩的坑）

Tauri 更新器把清单读成 `platforms: HashMap<String, { url, signature }>`，**`signature` 不是可选项**
（`tauri-plugin-updater/src/updater.rs` 里 `ReleaseManifestPlatform.signature` 是 `String` 而非 `Option`）。

后果很反直觉：`platforms` 里**任何一段**缺 `signature`，**整份清单反序列化就会失败**，
客户端报 `missing field 'signature'`，而且这个失败发生在**版本比较之前** ——
**哪怕版本号相同、根本不该更新，用户点「检查更新」也会直接报错。**

手机端的 `android` 段不是 Tauri 的 target、这个字段永远读不到，但结构上仍然必须给一个
（`release-mobile.mjs` 放的是该 APK 的 sha256 作为占位，不是伪造的 minisign 签名）。

**防复发**：`writeManifest()` 已加入写入前硬校验 —— 任何平台段缺 `url` 或 `signature`、
或 `url` 不是 http(s)，都会**直接抛错中断发布**，而不是生成一份会让客户端更新失败的清单。
往 `platforms` 里加新段时，务必同时给 `url` 和 `signature`。

## 6. 常见故障

| 现象 | 原因 / 处理 |
|---|---|
| 用户端不提示更新 | 版本号没升，或清单没更新，或清单 `url` 下不到。按 §4 三项逐一核对 |
| 桌面端升级失败 | 安装包签名与 `signature` 不匹配（换过密钥）；需让用户手动装一次 |
| 升级时报「无法打开要写入的文件: …\milevia-control.exe」 | 安装程序覆写 sidecar 的 exe 时旧 sidecar 还在运行（NSIS 只结束主程序）。先确认 §2「升级安装为什么要先结束 sidecar」那三处机制还在；若仍复现，说明有残留进程：`tasklist /FI "IMAGENAME eq milevia*"` 查出来后结束，再重试 |
| 手机端装不上新包 | 签名不一致（debug keystore 换了机器）。只能卸载重装，手机上要重新配对 |
| APK 提示更新但下载 404 | 只更新了清单没传文件，或文件被清理规则误删。检查 `/updates/` 实际内容 |
| CI 部署耗时异常长 | 检查是否有人把「传源码」改回了「传 10MB 二进制」。见 §1 的说明 |
| 云控改完线上没生效 | 改动没命中 workflow 的 `paths`（比如只改了非 `.go` 文件），不会触发 |
| 公网 80 显示 “Non-compliance ICP Filing”、8443 的 TLS 被重置 | 域名未完成阿里云接入备案，阿里云在 SNI 层拦截；完成接入备案后重试，或改用 DNS-01 / Cloudflare 隧道。新机本机访问正常不代表公网可用 |
| 换机/换库后桌面显示「未注册」、手机回到配对页 | 新库为空：桌面端在远程页输入 `/etc/milevia/cloud-control.env` 里的注册令牌；手机重新扫码 + 校验码配对。先确认 DNS 已指向 `8.153.198.174`（`curl -w '%{remote_ip}'`）且备案拦截已解除 |
| 桌面端一直用旧凭据重试 | `%LOCALAPPDATA%\com.milevia.desktop\milevia-agent.env` 里若残留 `MILEVIA_INSTANCE_ID` / `MILEVIA_CLOUD_AGENT_TOKEN`，删掉它们并重启；必要时删除同目录 `agent-credentials.bin` 后重新注册 |
