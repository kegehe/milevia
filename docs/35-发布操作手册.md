# 发布操作手册（供 AI 执行）

> 面向对象：任何 AI 工具 —— CLI（Claude Code、Codex…）或桌面端（Cursor、WorkBuddy…）。
> 当用户说「发布」「发版」「部署」「上线」「传个新版本」时，**照本文执行，不要凭记忆猜命令**。
> 本文只描述「怎么发」，涉及实现原理的历史记录见 `docs/33-远程控制实施进度.md`、
> 桌面端升级机制见 `docs/23-Windows打包与在线升级方案.md`、`docs/24-GitHub发布流程与Pages配置说明.md`。

---

## 0. 先判断要发什么

| 用户的说法 | 发布对象 | 去哪儿 |
|---|---|---|
| 远程控制服务 / 云端 / 中转服务 | `apps/cloud-control` | §1（通常**不需要你动手**） |
| 桌面端 / 电脑端 / Windows 版 / exe | `apps/desktop` | §2 |
| 手机端 / App / APK / Android | `apps/web/android` | §3 |
| 「都发」「全部发一版」 | 三个都发 | 按 §1 → §2 → §3 顺序 |

**不确定时先问用户要发哪个端。** 桌面端和手机端是两条独立的发版链路，版本号也各自递增。

## 1. 云端连接服务（`apps/cloud-control`）

**绝大多数情况不需要手动做**：推送到 `main` 且改动命中
`apps/cloud-control/**/*.go`、`go.mod`、`go.sum`、`scripts/deploy-cloud-control.sh`、
`.github/workflows/deploy-cloud-control.yml` 时，GitHub Actions 会自动部署。

- 工作流名：**部署云端连接服务**（`.github/workflows/deploy-cloud-control.yml`）
- 手动触发：GitHub → Actions → 「部署云端连接服务」→ Run workflow

**流水线做什么**：runner 上 `go vet` + `go test` → 打包源码（约 30KB，排除 `.tmp`）→ scp 到服务器
→ **服务器本地编译**（`GOPROXY=goproxy.cn`，Go 工具链按 `go.mod` 自动拉取）→ 替换容器内二进制
→ 重启 → 健康检查 → 固化镜像 → 清理临时产物。部署环节约 **5 秒**；失败自动回滚到上一版。

> **为什么传源码而不是二进制**：GitHub runner 在境外，往国内服务器传 10.2MB 二进制实测约
> **12.7 KB/s**，单这一项就要 14 分钟（整条流水线曾因此耗时 15 分钟）。传 30KB 源码只要 2 秒，
> 而服务器编译这个服务是**秒级**。**不要改回"上传二进制"。**

**日常改动要走这条路时**，你只需要确认改动落在上述路径内并提交推送（推送需用户授权，见 §5）。

### 验证部署是否真的成功

```bash
curl -s -o /dev/null -w '%{http_code}\n' https://keyanjia.info:8443/health     # 期望 200
```

流水线「步骤成功」不等于线上生效，用户在意时按上面的命令实测一次。

### 本地如何跑云端的测试（不需要 Docker）

```bash
python scripts/run-cloud-control-tests.py
```

它会从部署文件读数据库 DSN、开 SSH 隧道连生产库，跑 `internal/cloud` 下的真实库测试
（LISTEN/NOTIFY 语义、事件流排空等）。没配 `MILEVIA_TEST_DATABASE_URL` 时这些测试在 CI 里
会**静默跳过**，所以 CI 通过不代表它们跑过。

### 手动部署（断网急救 / 排查用）

部署脚本在服务器上执行，支持两种输入：

```bash
# 方式 A（推荐）：只传源码，让服务器编译
SRC_ARCHIVE=/tmp/cloud-control-src.tar.gz bash /tmp/deploy-cloud-control.sh

# 方式 B：已有编译好的 Linux 二进制
NEW_BIN=/tmp/cloud-control-linux.new bash /tmp/deploy-cloud-control.sh
```

可用环境变量：`DRY_RUN=1`（只编译+校验，不碰容器）、`COMMIT=0`（不固化镜像）、
`PRUNE=0`（不清理悬空镜像）、`CONTAINER`、`TARGET`、`HEALTH_URL`。

**打源码包的正确姿势**（Windows 上要加 `--force-local`，否则 tar 会把 `C:/...` 当远程主机）：

```bash
tar --force-local -czf /tmp/cloud-control-src.tar.gz --exclude='./.tmp' -C apps/cloud-control .
```

## 2. 桌面端（Windows）

```bash
node scripts/release.mjs <新版本号> "更新说明"
```

发一版并推到线上更新源：

```bash
MILEVIA_DEPLOY_TARGET="root@111.229.52.158:/var/www/milevia/dist/updates/" \
  node scripts/release.mjs 0.1.7 "本次更新说明" --deploy
```

**前置**：`~/.tauri/milevia-updater.key` 与 `~/.tauri/milevia-updater-password.txt` 存在
（签名密钥，缺了脚本会失败）。

**可选参数**：

| 参数 | 作用 |
|---|---|
| `--bump-only <ver>` | 只同步三处版本号，不打包、不发版 |
| `--no-build` | 不重新构建，签现有安装包 |
| `--deploy` | 构建+签名后上传到自建源与 GitHub Release |

**脚本会做**：同步 `tauri.conf.json` / `Cargo.toml` / `desktop/package.json` 三处版本号 → 构建
→ 签名 → 写两份清单 → （`--deploy` 时）上传 → 清掉服务器上同形态的旧安装包。

> **桌面端脚本不再碰 Android。** versionCode/versionName、APK 构建、清单里的
> `platforms.android` 段全部由 §3 的手机端脚本独占维护。别把 Android 职责挪回来。

## 3. 手机端（Android APK）

```bash
MILEVIA_DEPLOY_TARGET="root@111.229.52.158:/var/www/milevia/dist/updates/" \
  node scripts/release-mobile.mjs 0.1.7 "本次更新说明" --deploy
```

**脚本会做**：`versionCode` 自增、`versionName` 设为指定值 → 构建 Web → `cap sync android`
→ Gradle 出 APK → 算 sha256 → **只替换清单里的 `platforms.android` 段** → 上传 → 清理旧 APK。

**可选参数**：`--bump-only <ver>`、`--no-build`、`--deploy`。

**注意**：

- `versionCode` 必须**单调递增**（Android 只认它，`versionName` 只是给人看的）。
- 手机端与桌面端**版本号各自递增**，不必相同：清单顶层 `version` 属于桌面端，
  `platforms.android` 属于手机端。
- 构建需要 Android SDK；在 Windows 上跑 Gradle 需要放开沙箱（要写
  `apps/web/android/app/build/intermediates`）。

## 4. 发布后必须做的验证

**不要只看脚本退出码**。按下面回读线上状态：

```bash
# 1) 更新清单（两个平台各自的最新版本号与下载地址）
curl -s https://keyanjia.info:8443/updates/latest.json

# 2) 安装包确实可下载且支持断点续传（206 才对；404/200 都不正常）
curl -s -o /dev/null -r 0-1023 -w 'exe=%{http_code}\n' \
  https://keyanjia.info:8443/updates/Milevia_0.1.5_x64-setup.exe
curl -s -o /dev/null -r 0-1023 -w 'apk=%{http_code}\n' \
  https://keyanjia.info:8443/updates/Milevia_0.1.6_android.apk

# 3) 云端服务健康
curl -s -o /dev/null -w 'health=%{http_code}\n' https://keyanjia.info:8443/health
```

**客户端能不能真的升级**，取决于三件事同时成立：

1. 清单里的 `version` / `versionCode` 比用户当前安装的高；
2. 清单里的 `url` **指向一个真能下到的地址**；
3. 桌面端还要能被 `signature` 验签通过（换了签名密钥就必须让用户手动装一次）。

## 5. 必须遵守的约束

### 5.1 Git

**除非用户在当前对话中明确要求，禁止 `git add` / `commit` / `push` / 建 PR。**
用户说「发布」**不等于**授权提交。默认把改动留在工作区，报告清楚即可。
（这条来自 `AGENTS.md`，不要自行放宽。）

### 5.2 服务器磁盘：每个平台只保留最新一份

服务器根分区只有 40G 且同机跑着其它生产容器。约定：

- **安装包**：发版脚本上传后会清掉同形态的历史文件（`pruneRemoteDownloads`），
  **只删同形态、不跨平台**（桌面发版不会碰 APK）。不要手工往 `/updates/` 堆多个版本。
- **部署产物**：源码包、解包目录、临时二进制用完即删；回滚二进制固定一份覆盖；
  每次部署清悬空镜像。
- **代价**：想回退到上一版没有现成安装包，需从 GitHub Release 或本地 `release/` 取。

### 5.3 更新清单的两份分发

清单有两份，下载地址必须各指自己那侧（否则会出现「先弹提示、再下载失败」）：

| 清单 | 谁提供 | 地址指向 |
|---|---|---|
| `release/updates/latest.json` | 自建服务器 `/updates/` | 自建源（主用，国内快） |
| 仓库根 `latest.json` | GitHub Pages | GitHub Release 资产（备用） |

某平台在 GitHub 上没有已发布资产时，备用源那张**不写它的下载信息**（表现为「没有更新」）
—— 这是**刻意**的降级，不是 bug。

**改动这块逻辑要动 `scripts/lib/update-manifest.mjs`**，两个发版脚本共用它。

## 6. 常见故障

| 现象 | 原因 / 处理 |
|---|---|
| 用户端不提示更新 | 版本号没升，或清单没更新，或清单 `url` 下不到。按 §4 三项逐一核对 |
| 桌面端升级失败 | 安装包签名与 `signature` 不匹配（换过密钥）；需让用户手动装一次 |
| 手机端装不上新包 | 签名不一致（debug keystore 换了机器）。只能卸载重装，手机上要重新配对 |
| APK 提示更新但下载 404 | 只更新了清单没传文件，或文件被清理规则误删。检查 `/updates/` 实际内容 |
| CI 部署耗时异常长 | 检查是否有人把「传源码」改回了「传 10MB 二进制」。见 §1 的说明 |
| 云控改完线上没生效 | 改动没命中 workflow 的 `paths`（比如只改了非 `.go` 文件），不会触发 |
