# 移动端通知修复与验证

日期：2026-10-27

## 本次修复

- `MobileRemoteProvider` 常驻于移动端路由之上，持有通知监听、权限状态及一条共享 SSE 连接。进入设置页只卸载页面订阅，不断开系统通知链路。
- 通知先写入本地待投递队列，插件接受后才记为成功。失败每轮最多尝试三次；重启、回前台、网络恢复或重新开启通知时可重新尝试。
- 同一服务器、同一电脑的接收断点持久保存，处理与通知入队完成后才推进断点。首次使用仅建立最新基线，避免弹出安装以前的历史通知。
- 冷启动从已有断点继续接收，前台恢复时只补结果通知，不补过时的运行中和审批状态。待投递通知保留最近 24 小时，最多 100 条；已处理事件的去重记录最多 1000 条。
- 检查应用总通知开关及“任务通知”渠道；渠道创建失败、被关闭或插件调用失败都会产生诊断信息。设置页提供“发送测试通知”和最近结果。
- 通知携带所属电脑标识，点击后切回对应设备与项目。失效或已解绑设备不会继续投递。
- 云端区分明确的 `Last-Event-ID: 0` 与无断点订阅，避免空实例的首批事件被跳过。该边界修复需要云端服务更新后生效。

## 复审补充

以下问题均有回归用例。后台状态、首次历史回扫、旧配对恢复及存储失败问题已观察到修复前失败、修复后通过。

- 原生 `getState()` 的旧前台状态晚返回时，可能覆盖较新的后台事件。现在只接受未被新事件取代的初始状态，路由切换也不再重装原生监听。
- 项目支持 Android 7，但该系统不支持通知渠道 API。仅在插件明确返回 `UNAVAILABLE` 时跳过渠道操作；其他渠道错误继续报错并重试。
- 满队列新增记录保存失败时，完整恢复原有待发送集合；前台去重记录保存失败也会回滚，避免上游错误推进断点。
- 生产 SSE 会回扫断点前的事件。现在固定保存首次通知基线，避免首次弹出历史结果；前台已处理的事件也持久去重，已有待发送项不会被回扫删除。内存与持久断点均保持单调，仍允许处理乱序到达的事件。
- 首次基线已保存、接收断点尚未保存便失败时，重试从原基线追赶，不重新跳到最新而漏掉新事件。
- 旧配对记录只有令牌、缺少电脑标识时，常驻服务自行恢复标识，并支持超时、重试和取消；从设置页启动也能建立通知连接。
- 再次复审通过实际设置页复现：关闭“任务完成与失败”后，后台完成事件仍调用原生通知插件。现在新通知遵守分类开关、免打扰时段及浏览器的后台通知开关；审批等高优先级通知仍服从系统通知总开关。待发送记录保存事件类型，重试前重新核对偏好，被静默处理的事件不写“已交给系统”的成功诊断。兼容此前没有事件类型的队列记录，保留其原投递语义。

## 自动验证

在 `apps/web` 运行：

```powershell
pnpm test
pnpm test:mobile-notifications
pnpm build
```

浏览器回归使用真实 React 路由与通知服务、原生插件桩、模拟 SSE 和快照接口。常驻连接的基础场景使用订阅探针；设置页和项目页另有实际页面验证。覆盖 StrictMode、一条连接跨路由、设置页切后台、失败重试、测试通知、冷启动补发、生产事件回扫、前台事件去重、重连断点、设备切换、晚到的初始前台状态、旧配对恢复及实际设置页的分类开关、免打扰和高优先级提醒。实际项目页覆盖从设置页点击跨电脑通知后等待快照定位、页面已挂载时再次跨电脑跳转，以及切换后的后台结果通知。本轮补充真实页面验证未复现新的业务代码缺陷，仅修改测试与验证记录。插件桩不能验证手机系统是否真正展示通知。

在 `apps/cloud-control` 运行：

```powershell
go test ./internal/cloud -count=1
```

真实 PostgreSQL 事件流测试仍需设置 `MILEVIA_TEST_DATABASE_URL`，未设置时这些测试会跳过。

## HarmonyOS 真机验收

1. 在设置的通知页开启“移动端系统通知”，点击“发送测试通知”，查看通知栏，并核对“最近结果”。部分系统不会弹出通知授权框。
2. 在项目页发起短任务，切换到其他 App，确认完成提醒。
3. 在设置页切后台，再完成一个任务，确认仍能收到。
4. 断网后恢复网络、关闭 App 后重新打开，确认遗漏的结果补发，已成功发送的不重复提醒。
5. 检查两台电脑切换、通知点击跳转，以及关闭系统总通知开关或“任务通知”渠道时的错误提示。
6. 单独验证长时间锁屏。当前仍使用本地通知，系统冻结或回收进程期间无法即时接收事件；本次恢复与补发机制不能替代华为等厂商的独立推送通道。
