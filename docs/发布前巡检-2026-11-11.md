## 1. P1：手机端优化建议无法启动分析或复核

位置：

- `apps/web/src/features/insights/InsightsPanel.tsx:153`、`:563`
- `apps/web/src/features/insights/mobile-insights-request.ts:67`、`:94`
- `apps/web/src/features/optimization/MobileOptimizationPanel.tsx:33`
- `apps/web/src/pages/MobileRemotePage.tsx:2403`

共用面板挂载后经 request 请求 `/api/runners/{runnerID}/status`，但手机注入的适配器只接受 `/api/projects/{id}/insights*`。请求在本地直接抛出“不是优化建议的请求”，并将 agentRunnerError 保持为非空；开始分析、全部验证和单条验证均被阻断。

用实际 InsightsPanel 与实际手机适配器做浏览器复现，并提供合法引擎目录：界面显示“不是优化建议的请求：/api/runners/windows/status”，“开始分析”和“验证全部建议”均 disabled，实际 RPC 只发出 insights.list。故障不依赖电脑 CLI 是否正常。

此外，面板的 useAgentCatalog 仍依赖同源 `/api/agents`，手机页面使用的是另一份移动工具目录。这是修复时必须一起接通的依赖，否则只消除 runner 请求错误仍可能没有可选引擎。

建议：为共用面板注入目标电脑的引擎目录、状态及探测状态，或增加受限中继读取；不要让手机访问桌面的同源 API。补充真实手机宿主与面板之间的集成回归。

## 2. P2：手机分析、复核的启动等待短于服务端就绪探测

位置：

- `apps/web/src/features/insights/mobile-insights-request.ts:77`
- `apps/control-server/internal/app/insights.go:250`、`:3230`
- `apps/control-server/internal/app/agent_readings.go:51`
- `apps/cloud-control/internal/cloud/rpc.go:52`

适配器调用 transport(op, params)，未提供第三个 timeoutMs；云端因此只等待 20 秒。扫描和复核在返回异步登记结果之前，会同步执行 requireInsightAgentReady，工具探测预算为 45 秒，冷探测可能合法超过 20 秒。桌面 api.ts 已单独放宽这两个端点，手机没有对应处理。

证据：实际调用适配器记录到扫描参数只有 `["insights.scan",{}]`，并沿真实调用链核对 20 秒与 45 秒预算。本项为调用链与协议核实，未在生产电脑上人为制造慢探测。

影响：修复问题 1 后，慢环境仍会出现启动超时；电脑端的调用并不会随云端等待结束自动撤回，用户可能遇到界面报失败而后台随后开始，或者重试冲突。

建议：按扫描、复核的同步探测阶段设置中继等待预算，并让手机自己的等待包含链路余量；同时修正 remote_insights.go 中“立刻返回、不会撞超时”的注释。

## 3. P2：通用 API 的超时保护未覆盖响应正文

位置：`apps/web/src/lib/api.ts:254`、`:260`。

fetch 收到响应头后即可返回 Response。当前代码在 fetch 结束的 finally 中清除超时并移除调用方的 abort 监听，之后才 await response.json()。如果正文传输停滞，后续读取没有超时和调用方取消保护，依赖 finally 恢复按钮的页面会一直显示处理中。

使用实际 apiWithTimeout，令 fetch 返回只传出部分 JSON、始终不结束的 ReadableStream：预算设为 40ms，200ms 后 Promise 仍未结束，内部 signal.aborted 仍为 false。数据流明确监听了 abort，因此不是模拟器忽略取消造成的。

建议：把读取、解析正文包含在超时和取消的生命周期内；204/205、错误正文及解析异常都应走统一清理。

## 4. P2：导出的任务文件可能无法被本项目重新导入

位置：`apps/control-server/internal/app/task_transfer.go:100`、`:232`、`:435`。

导出会读取所选范围全部任务，没有数量或文件大小门禁；导入只接受最多 2000 条、64 MiB。前端也有相同导入上限，但没有对应的分批导出入口。

通过临时 Go overlay 用实际数据库和 HTTP handler 复现：源项目 2001 条合法任务，导出 HTTP 200，文件包含 2001 条；原样导入另一个项目返回 HTTP 400：“任务导出文件包含的任务过多，请分批导出后再导入。”没有改动业务源码。

影响：积累较多历史任务后的整项目迁移无法完成。大量长描述也存在导出体积超过导入上限的同类不一致。

建议：确保导出文件满足导入契约，提供可用的分批导出或提高双方一致的限制；不能在成功生成文件后才要求用户自行拆 JSON。
