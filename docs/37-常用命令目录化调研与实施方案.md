# 常用命令目录化（命令选择器）调研与实施方案

> 日期：2026-09-15
> 状态：**Phase 0 与 Phase 1 已实施并通过真机验收**（Phase 2/3 未做，见 §4）
> 关联：docs/06（快捷任务与命令系统，本方案是它的 §10「后续能力」中「受控命令目录」的具体化）、docs/22（Skill 区域，命令的兄弟特性，文件扫描与三端发现可直接复用）、docs/36（会话页模型选择，接口形状/缓存/降级/静态兜底全部照抄）
> 结论摘要：**「常用命令」的自由输入必须拆成两条路**——CLI 斜杠命令（`/compact`）**只能从 CLI 自己的目录里选**；shell 命令请求（`pnpm test`）本质是提示词，**无法枚举、保留自定义**。目录的权威来源是 Claude CLI 的 `system/init` 事件字段 `slash_commands`，**实测可零 token、零凭据拿到**（探针 + 从真实运行中采样两条路）；它不是"最优来源"而是**唯一完整来源**——实测 47 条命令里有 17 条是编译进 CLI 的技能命令，磁盘扫描与现有技能面板都看不见。Codex 在 `codex exec` 路径下**没有斜杠命令**（已实测），因此命令选择器对 Codex 会话应只提供自定义 shell 请求；输入框里手敲 `/xxx` 是同根因的另一个入口，用同一份目录顺手补上。

## 1. 诉求与现状

### 1.1 诉求

「常用命令」的编辑器是一个自由文本输入框。用户可以填任何东西，但 CLI 不认得：

- 填 `/compact`、`/clear` 这类斜杠命令 → 由 CLI 本地执行（**只有这类才真正是"命令"**）；
- 填 `/review` 这类**当前 CLI 版本已隐藏但仍可用**的命令 → 能跑，但要花钱，且不在任何可见列表里；
- 填 `/zzz` 这类不存在的 → CLI 回一句 `Unknown command: /zzz`，白白多一条用户消息和一个 Run；
- 填 `pnpm test` 这类 shell 命令 → 应用会包装成提示词让模型执行，**不受斜杠命令识别问题影响**。

诉求：添加命令时不要让人凭空输入，给一个"当前 CLI 真正可用"的列表让人选。

### 1.2 现状链路

```
点击「新增常用命令」(ConversationPage.tsx:3248 / :3283)
  -> setShortcutEditor({ kind: "command_request" })
  -> ShortcutEditor（ConversationPage.tsx:932）: 名称 input + 命令内容 textarea（自由文本）
  -> POST /api/shortcuts（saveShortcut, app.go:4218）
  -> 点击标签 -> runShortcut（ConversationPage.tsx:2592）
       /clear 由前端本地拦成清空会话（:2609）
       其余走 POST /api/conversations/{id}/shortcuts/{id}/run（app.go:4454）
  -> renderShortcut（app.go:4361）:
       以 / 开头 -> 原样透传（交给 CLI 当斜杠命令）
       否则     -> 包装成「请在当前项目中执行以下命令：`xxx`」（交给模型执行）
  -> startMessage -> Claude 走长驻 stream-json 会话 / Codex 走 `codex exec <prompt>`
```

种子数据（`seedDefaultShortcuts`, app.go:4157）已经预置了三条命令：`/clear`、`/compact`、`/review`——**其中 `/review` 在当前 CLI（2.1.266）的目录里并不存在**（见 §2.4）。

### 1.3 三个既有缺陷（本方案顺带修）

| # | 缺陷 | 证据 |
| --- | --- | --- |
| 1 | **快捷命令与 agent 无关**。`shortcuts` 表没有 agent 维度，`promptShortcuts` / `commandShortcuts` 只按 kind 过滤（ConversationPage.tsx:3112-3113），所以 Claude 会话里的 `/compact` 在 Codex 会话里也能点——而 Codex 根本不认斜杠命令，`/compact` 会作为**普通提示词文本**发给模型。 | `conversation.AgentID == "codex"` 时强制 `streaming = false`（app.go:4784），走 `codex exec`；实测见 §2.6 |
| 2 | **种子数据含一条隐藏命令** `/review`：能跑、要花钱（实测 $0.15/次）、但不在 CLI 的可见目录里，用户无从判断它是否有效。 | §2.4 |
| 3 | **输入框里手敲 `/xxx` 走的是同一条"没人校验"的路**。`sendContent` 只硬编码拦了 `/resume`、`/clear` 两条（ConversationPage.tsx:2375 / :2385），其余 `/xxx` 原样上线。拼错的 `/compac`、过期的 `/review` 都会留下一条 `Unknown command` 消息——**这和"添加命令"是同一个根因，只是入口不同**。 | §2.3 |

## 2. 关键事实核查（全部为本机实测，2026-09-15）

本机环境：Claude Code `2.1.266`、codex-cli `0.153.4`、Windows 11；探针目录 `%TEMP%\cmdprobe`（含两个自定义命令）。

### 2.1 Claude CLI 有权威的机器可读命令目录：init 事件

用 `claude -p --verbose --input-format stream-json --output-format stream-json` 起一个会话，**第一行**就是 init 事件（下面是实测原文的节选，`slash_commands` 数组本身保持完整，其余字段用 `...` 省略）：

```json
{"type":"system","subtype":"init","cwd":"...","model":"claude-opus-5[1m]","permissionMode":"default",
 "slash_commands":["mycmd","nested:deep","deep-research","design","design-sync","dataviz","update-config",
   "verify","debug","code-review","simplify","batch","fewer-permission-prompts","doctor","loop","claude-api",
   "workflow-authoring","run","run-skill-generator","advisor","agents","auto-mode-setup","autocompact",
   "clear","color","compact","config","context","effort","fast","heapdump","init","mcp","model",
   "__remote-workflow","workflow-launch-exec","reload-plugins","reload-skills","rename","security-review",
   "usage","insights","recap","goal","design-consent","design-revoke","list-agents","team-onboarding"],
 "terminal_slash_commands":["doctor","color","reload-plugins"],
 "claude_code_version":"2.1.266","agents":[…],"skills":[…],"plugins":[…],"capabilities":[…]}
```

要点：

- `slash_commands` 就是 CLI 内部**命令注册表**里 `userInvocable !== false` 的那部分（从 2.1.266 二进制里可读到这段过滤逻辑），也就是用户按 `/` 时看到的那张表。它是**并集**：内置命令 + skills 暴露的命令（`deep-research`/`dataviz`…）+ 插件命令 + **项目/用户自定义命令**。
- 实测拆分（项目内含 1 条自定义命令时共 47 条）：**29 条内置命令 + 17 条技能命令 + 1 条项目自定义命令**。`skills` 数组 17 条**全部**是 `slash_commands` 的子集，但自定义命令只进 `slash_commands`、不进 `skills`。
- `terminal_slash_commands` 是"**UX 绑在本地终端**"的子集（本机为 `doctor`/`color`/`reload-plugins`）。二进制里的字段说明原文：*"Phone/remote UIs should hide these from command menus; desktop surfaces may keep them."*——**这是 CLI 官方给手机/远程 UI 的过滤建议**，正好对应本项目的 `MobileRemotePage`。
- 事件里还带 `claude_code_version`，可直接当缓存 key 的一部分。

### 2.2 项目级自定义命令确实进目录（且带命名空间）

在探针目录放 `.claude/commands/mycmd.md` 与 `.claude/commands/nested/deep.md` 后重跑：目录从 46 条变 48 条，多出的正是 `mycmd` 与 `nested:deep`（子目录用 `:` 连接）。目录**按 cwd 生效**——所以探针必须用项目路径作 cwd。

同一 cwd 下重复探测结果完全一致（46 vs 48 的差异只来自自定义命令），说明**目录是确定性的**，按 (cwd, CLI 版本, 用户配置) 缓存是安全的。

### 2.3 未知命令：CLI 本地兜底，零成本但会留一条垃圾消息

```
$ printf '{"type":"user",...,"text":"/zzz-not-a-command"}\n' | claude -p --verbose --input-format stream-json ...
{"type":"assistant","message":{"model":"<synthetic>","content":[{"type":"text","text":"Unknown command: /zzz-not-a-command"}]}}
{"type":"result","subtype":"success","num_turns":0,"total_cost_usd":0}
```

`model=<synthetic>`、`num_turns=0`、成本 0：CLI 没有把未知命令丢给模型，而是本地回一句。但在应用里它照样是一条用户消息 + 一个 Run + 一条助手回复（内容只有 "Unknown command"），**用户会以为是"命令执行失败"**。这正是诉求里说的"用户填的命令 CLI 不一定会识别"。

### 2.4 `/review`：隐藏但仍可用（种子数据里的坑）

`/review` **不在** `slash_commands` 里，但直接发送时确实会执行：

```
assistant model=<synthetic> -> "No findings — there is no diff to review. …"
result   subtype=success num_turns=0 cost=0.1523
```

即：**目录不是"能不能跑"的判定，而是"CLI 愿不愿意让用户看见"的判定**。所以目录适合做**推荐清单**，不适合做硬性白名单（硬拦会误伤 `/review` 这类隐藏可用命令）。

### 2.5 探针可以零 token、零凭据拿到目录

**零成本**：把 `/context` 作为第一条消息（CLI 本地命令）写入 stdin，返回 `model=<synthetic>`、`num_turns=0`、`total_cost_usd=0`，而 init 事件照常先发。

**零凭据**：用一个假 key + 不可达的 base URL 重跑，init 依旧完整（48 条），`/context` 依旧本地返回，成本仍为 0：

```
$ env ANTHROPIC_API_KEY=sk-bogus ANTHROPIC_BASE_URL=https://127.0.0.1:9 { printf '/context 消息'; sleep 10; } \
  | claude -p --verbose --input-format stream-json --output-format stream-json --session-id <uuid> --no-session-persistence
INIT ok, slash_commands=48  apiKeySource=ANTHROPIC_API_KEY
assistant model=<synthetic> -> "## Context Usage ..."   result cost=0
```

**耗时**：写 stdin 到拿到 init 首行约 **1 秒**（含进程启动）；加 `--no-session-persistence` 可在 2.1.266 的 stream-json 模式下正常使用，探针不会在用户历史里留下可 resume 的会话。

一个必须注意的坑：**不写任何 stdin 就不会有 init**（实测空 stdin 保持 18 秒后被杀，输出 0 字节）。所以探针必须写一条本地命令，不能"起进程等 init"。

### 2.6 Codex 在 `exec` 路径下不认斜杠命令（实测）

```
$ MSYS_NO_PATHCONV=1 codex exec --sandbox read-only --color never --skip-git-repo-check "/status"
--------
user
/status
codex
（随后模型开始按工作区探索，把 /status 当成普通诉求处理；消耗 5,385 tokens）
```

斜杠命令实现在 Codex 的 **TUI 层**（二进制里可见 `tui/src/app/event_dispatch.rs`、`fixed.slash_command` 等符号），`codex exec` 是非交互子命令，`codex exec --help` 里也没有任何命令目录。**结论：Milevia 的 Codex 会话下 `/xxx` 只会变成普通提示词文本。**

> 附带发现（本期不做，留给后续）：Codex 有非交互的 `codex review` / `codex exec review`（`--uncommitted` / `--base` / `--commit`），这才是 Codex 侧"代码审查"的正解，但它属于子命令而非斜杠命令，接入需要改 `codexExecArgs` 的参数形状。

### 2.7 目录里没有描述文本，且三分之一的命令文件扫描看不见

init 只给命令**名字**（数组），不给描述。可得的描述只有两处：

| 来源 | 覆盖 | 成本 |
| --- | --- | --- |
| `.claude/commands/**/*.md` 的 frontmatter（`description` / `argument-hint`） | 仅自定义命令 | 文件扫描，复用 skills.go |
| 插件目录 `~/.claude/plugins/**/commands/*.md` | 仅插件命令 | 同上 |
| **内置命令**（clear/compact/model/context…） | 无文件 | 只能人工维护静态中文表 |

`/help` 在 print 模式下不可用（实测返回 `/help isn't available in this environment.`），拿不到带描述的内置清单。

**更要紧的是：那 17 条技能命令在本机磁盘上根本不存在**（`deep-research` / `dataviz` / `verify` / `run` / `design-sync` / `simplify` 等，在 `~/.claude` 全树搜不到；`~/.claude/skills` 目录本身就不存在），它们是**编译进 claude.exe 的内置技能**（注册表里 `source:"bundled"`）。推论有两条：

1. **文件扫描无法替代 init 事件**——「静态表 + 扫描」的合成目录会稳定漏掉这 17 条（以及 MCP 提供的命令）。init（真实运行采样或探针）是唯一完整的来源，这一条从"最优解"升级为"必需项"。
2. **应用现有的「技能 (Skill)」面板也看不到这 17 条**（`skills.go` 只扫 `~/.claude/skills`、`~/.claude/plugins`、项目 `.claude/skills`）——这是同一个信息盲区的另一面，本方案不负责修，但值得记一笔（见 §6 未决 2）。

### 2.8 斜杠命令在两种投递方式下都生效（Claude）

`-p "/context"`（argv 提示词）与 stream-json stdin 两种方式实测都被识别（`num_turns=0`、成本 0）。所以本特性**不挑投递路径**，无需改动 runner。

## 3. 方案

### 3.1 产品形态：选择器为主，自定义 shell 为辅

「常用命令」编辑器改成两步式，**默认路径是选，不是输入**：

```
┌─ 新增常用命令 ─────────────────────────────────────┐
│ 搜索 [ compact            ]       会话：Claude Code │
│ 目录来源：最近一次运行（2026-09-15 14:20）  [刷新]  │
│                                                     │
│ CLI 命令（由 Claude Code 直接执行）                  │
│  ● compact      压缩当前上下文，保留结论             │
│  ○ clear        清空会话（由应用本地处理）           │
│  ○ context      查看上下文占用                       │
│  ○ mycmd        统计 TODO 注释  ← 项目自定义命令     │
│  ○ nested:deep  …                                   │
│                                                     │
│ ○ 自定义 shell 命令（让 AI 在本项目执行）            │
│    [ pnpm test                                    ] │
└─────────────────────────────────────────────────────┘
                    [取消]   [添加]
```

- 每一行显示**命令名 + 中文说明**；有 `argument-hint` 的命令显示 `命令名 <参数>`（一期只展示，二期可填参数）；
- 点一行即选中，名称默认取命令名，可改名；
- 目录里没有的（`/review` 这类）在**编辑已有快捷方式**时显示黄色徽标「⚠ 当前 CLI 未提供此命令」；
- 底部「自定义 shell 命令」是唯一保留自由输入的地方——**这一类本来就不是 CLI 命令，而是提示词**（`pnpm test` 无法穷举，docs/06 §4.1 已把它列为设计内容）。

**策展规则（不要原样倒出 47 行）**：实测目录里 17/47 是**技能命令**，其中一部分与应用已有的「技能 (Skill)」面板重叠；另有几条与应用原生能力重复（`clear` = 应用自己的清空会话、`model` = 底部模型栏、`context`/`usage` = 「使用状态」弹窗）。所以：

1. **分组**：`建议`（compact / context / init / recap / security-review / rename / agents…）→ `技能`（与技能面板同源的 17 条，折叠在二级）→ `项目自定义`→ `其它`；
2. **交叉引用**：与应用原生能力重复的条目，行内注明「应用已有等价入口」而不是删掉——目录要如实反映 CLI 有什么，但要让用户知道不必绕道；
3. **默认收起长尾**：搜索框是全量入口，不搜索时只展开「建议」与「项目自定义」两组。

> **需要用户拍板的取舍**：如果要更彻底（完全禁止自定义、只允许目录内的命令），代价是失去「让 AI 跑 `pnpm test`」这条真实在用的能力。本方案的建议是**保留但降级为第二入口**——默认视线落在目录上，就不会再有人凭空输入斜杠命令了。

### 3.2 目录从哪来：三层来源

| 层 | 来源 | 覆盖 | 成本 | 作用 |
| --- | --- | --- | --- | --- |
| A | **真实运行的 init 事件**（新增 hook 采样） | 全部（含 MCP/插件/项目/用户） | 0 | 常态来源：项目跑过一次就有 |
| B | **主动探针**（§3.4） | 全部 | 0 token，~1s | 冷启动 / 用户点「刷新」 |
| C | **文件扫描**（复用 skills.go 的三端发现） | 只有自定义/插件命令 | 0 | 给 A/B 补 description / argument-hint |
| D | **静态中文表** | 内置命令那二十来条 | 0 | 给内置命令补说明；CLI 目录读不到时兜底 |

A 是主路径（零成本、零噪音），B 是冷启动的补位。二者产出的都是同一份 `names[]`，合并后由 C/D 补描述。

**C/D 不能替代 A/B**：实测 47 条命令里有 17 条是编译进 CLI 的技能命令，磁盘上不存在对应文件（§2.7），文件扫描稳定漏掉它们；静态表只能覆盖内置的那 29 条，且需要随 CLI 版本人工维护。所以「只用静态表 + 扫描、不起探针」这个看起来更省事的方案**已被实测否决**。

### 3.3 后端：接口与缓存

形状完全照 `conversation_models.go`（`ConversationModelsView` + 单条 TTL 缓存 + 探测失败降级 + `Note` 如实说明来源）：

```
GET /api/projects/{projectID}/commands?agentId=claude-code[&refresh=1]
```

```jsonc
{
  "projectId": "...",
  "agentId": "claude-code",
  "env": "windows",                       // windows | wsl | remote-linux
  "claudeCodeVersion": "2.1.266",
  "source": "run|probe|scan|static",      // 这一份目录是怎么来的
  "refreshedAt": "2026-09-15T14:20:31Z",
  "terminalOnly": ["doctor", "color", "reload-plugins"],
  "commands": [
    { "name": "compact", "label": "压缩上下文", "description": "…",
      "source": "builtin|skill|plugin|project|user", "terminalOnly": false },
    { "name": "mycmd", "description": "统计 TODO 注释", "argumentHint": "[路径]",
      "source": "project" }
  ],
  "customAllowed": true,                  // 是否允许自定义 shell 命令
  "note": "目录来自项目内的 Claude CLI 探针；内置命令说明为本机维护的中文备注。"
}
```

- **缓存 key**：`runnerID | projectPath | agentId | claudeCodeVersion`；TTL 10 分钟（对齐 `modelCatalogTTL`）。CLI 版本号取自 init 事件，升级 Claude Code 后自动失效。
- **并发去重**：多个请求同时打进来只允许一个探针在跑（`singleflight` 语义；项目里已有"单条缓存 + 互斥"的写法可照抄）。
- **降级**：探针失败/超时 → 返回静态表（D）+ 文件扫描结果（C），`source` 与 `note` 如实说明，**不报错**（与 `codexFallbackModelCatalog` 同款）。
- **本期只读**：接口不提供"执行命令"，只提供"列出命令"。真正的执行仍然只走既有的 `POST /shortcuts` + `run`。

### 3.4 探针实现

```
cwd        = 项目路径（目录按 cwd 生效，必须）
argv       = -p --verbose --input-format stream-json --output-format stream-json
             --session-id <随机 uuid> --no-session-persistence
             [--permission-mode …] [--mcp-config …]      # 与真实运行同源，MCP 提供的命令才会出现
env        = 不带 profile 凭据（实测不需要，避免解密与泄漏面）
stdin      = 一条 {"type":"user",…,"text":"/context"}，读到含 slash_commands 的 init 行后立刻终止进程
超时       = 本机 5s / WSL 8s / SSH 10s（对齐 codexModelCatalog 的三端超时量级）
```

三端接法与 `codexModelCatalog` 完全同构（本机 `exec` / WSL `wslBridgeProbe` / SSH `execCommand`），各自实现 + 共用解析与缓存。

**为什么不用 `/help`**：print 模式下不可用（§2.7）。**为什么选 `/context`**：本地命令、零成本、输出稳定；若未来版本移除它，探针只需换一条本地命令（`/usage`、`/config` 均可），或直接退回只从真实运行采样（A 层）。

### 3.5 从真实运行中采样（A 层）

`agentRunSink.Event`（app.go:5426）是所有 runner（本机 Claude / WSL / SSH 长驻会话）的**唯一事件汇聚点**，`sshAgentSession.emit` 最终也是调它。在此处加一个廉价判断即可：

```go
// 先做零成本类型判断，再判断 payload 里有没有 slash_commands，最后才反序列化。
if eventType == "system" && bytes.Contains(payload, []byte(`"slash_commands"`)) {
    s.observeCommandCatalog(sink.projectID, sink.agentID, payload)
}
```

- sink 上补一个 `projectID` 字段（构造点两处：app.go:5168 / :5349，`conversation.ProjectID` 已在手）；
- 覆盖范围天然包含 WSL / SSH——它们的 init 也是同一条 init 事件；
- 写缓存不落库（内存即可），重启后由探针（B）补位。

| 场景 | 现在的行为 | 改后行为 |

### 3.7 数据模型：一期零迁移

斜杠命令的身份可以由 `template` 推断（首个 token 即命令名，其余是参数），**不需要新增列**：

- 目录外的判定 = `template` 以 `/` 开头 && 首 token 不在目录里；
- agent 判定 = 会话的 `agent_id`（已有）；
- 因此一期不动 `shortcuts` 表，`ShortcutEditorState` / `Shortcut` 类型也不用改。

二期若要做「命令改名后自动跟随」「按 agent 过滤常用命令」，再考虑加 `shortcuts.command_name` 一列（用 `ensureColumn`，app.go:1321）。

### 3.8 顺带补上输入框那条路（同一份目录，成本很低）

输入框和"添加命令"是同一个根因（§1.3-3），共用同一份目录即可，**不需要第二套数据**：

- **最小版（建议进 Phase 1）**：`sendContent` 在发出前判断 `draft` 以 `/` 开头且首 token 不在目录里 → 不发送，输入框下方给一行提示「`/compac` 不在当前 CLI 目录里，你是不是想用 `/compact`？」（附最近似项，用编辑距离挑一个）。这一条同时兜住了拼写错误与过期命令；

### 7.3 相对方案的偏差（均为实现中发现更优解）

1. **`scan` 来源并入 Phase 1**：原计划把自定义命令的文件扫描放 Phase 2，但"项目自定义"分组与命令描述都靠它，而它在本机是零成本的（复用 `skills.go` 的 frontmatter 解析思路）——放 Phase 2 会让新项目的选择器退化成"只有内置命令"。
2. **输入框的斜杠命令提示改为"只提示不阻断"**。方案里写的是"不发送 + 提示"，实现时发现目录有 10 分钟 TTL：用户刚建的 `.claude/commands/foo.md` 不在缓存里，若硬拦，用户会连自己刚写的命令都发不出去。于是只对**确定无解**的组合硬拦（Codex + 斜杠命令），"目录里没有"只提示并给一条最相近的建议。
3. **「未提供」徽标加了一道前提**：只在 `authoritative=true`（目录来自 CLI 本身）时显示。静态候选下"没找到"不代表失效——那会把 `/review` 这类隐藏但可用的命令误报成坏的。

5. **探针超时从 6s 提到 10s，收尾挪到后台**：真机实测稳态 1.0–3.2 秒，但在机器高负载时超过 6 秒（见 §7.4）。10 秒仍在前端 GET 的 15 秒超时之内，且进程收尾不再阻塞响应（否则最坏 14.6 秒）。

### 7.4 真机验收

用临时 data-dir 起真实控制服务，跑 `scripts/verify-command-catalog.mjs`（新建带项目级自定义命令的项目 → 读目录 → 探针 → 缓存 → Codex）：**全部通过**。关键读数：

```
来源=probe 版本=2.1.266 命令数=47 探针耗时=3321ms
前 8 条：probe-marker, deep-research, design, design-sync, dataviz, update-config, verify, debug
```

- 47 条 = 本机 2.1.266 的 46 条 + 本次新建的项目自定义命令 `probe-marker`——**这同时验证了"探针 cwd 用的是项目路径"**（自定义命令只在该目录下生效）；
- 自定义命令带 frontmatter 描述并归入 `project` 分组；`compact` 带中文名；`doctor` 被标为 `terminalOnly`；
- `probe=0` 不拉起进程、`refresh=1` 才探测、第二次读命中缓存、Codex 返回空目录 + 说明。

**真机运行暴露了三个真实问题**（都已在实施中修掉）：

1. **探针最坏耗时贴着前端超时**。一次刷新实测 **14.6 秒**：10s 探针超时 + 1.5s 等待进程退出 + `taskkill /T /F` 自身耗时（Windows 上可能数秒），全压在响应路径上，而前端 GET 的超时是 15 秒。修法是把进程收尾挪到后台 goroutine——修复后同样的超时路径实测 **10.1 秒**。
2. **刷新失败会丢掉手里那份真目录**。原本失败即退回"内置候选"，但一份几分钟前观测到的真目录比候选准确得多。改成：失败时若有过期目录就继续用它，并在说明里写明"展示的是 X 时观测到的目录"，不假装刷新成功。
3. **探针会留下孤儿进程（最严重的一个）**。连续 6 次刷新后机器上残留了 2 个 `claude.exe`，既不读 stdin 也不退出，会一直挂着。

第 3 条的根因值得记下来：Windows 上 `claude` 解析到 npm 的 `claude.cmd`，由它再拉起 `claude.exe`——**探针的直接子进程是 cmd.exe，真正的 CLI 是孙进程**。实测 `taskkill /PID <cmd.exe> /T /F` 在包装器还活着时确实能收掉整棵树，但包装器常常在我们动手前就已经退出（探针返回后再调用，taskkill 直接报 `exit status 1` 且无输出，即"进程已不存在"），于是 `/T` 无从遍历，孙进程变孤儿。**按父进程 PID 收尾在这个调用链上根本不可靠。**

修法是 Windows 的 **Job Object**（`probe_job_windows.go`）：创建带 `KILL_ON_JOB_CLOSE` 的作业对象，进程一启动就加入，收尾时关句柄——作业内所有进程（含后代）一起结束，不依赖任何进程还活着。`taskkill` 与 `Process.Kill()` 保留为兜底。修复后：连续 6 次刷新（含 6.6s / 7.6s 的慢探针）残留进程 **0**。

这条链要能被持续验证，靠的是一个不需要真机 CLI 的用例 `TestProbeKillsProcessTree`（用 `.cmd` 包装器 + 长睡的子进程复现同形调用链），以及一个默认跳过的真机用例 `TestLiveProbeLeavesNoProcess`（`MILEVIA_LIVE_PROBE=1` 时跑）。

**稳态耗时**（安静机器实测）：冷启动 3.2 秒，随后约 1.0 秒；目录条数稳定 47。机器满载（并行跑全量 Go 测试）时出现过超过 10 秒的超时——此时走上面的降级路径，返回上一份目录 + 说明，不报错。

**未做真机验证的部分**：WSL / SSH 项目的命令目录（Phase 2，当前走 `unsupported` 降级 + 真实运行采样）、桌面端的界面点击（前端由 `tsc -b`、`vite build` 与 376 条测试覆盖，未做人工点击验证）。
