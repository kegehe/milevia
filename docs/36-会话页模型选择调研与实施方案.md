# 会话页模型选择调研与实施方案

> 日期：2026-09-15
> 状态：**一期已实施**（二期/三期未做，见 §4）
> 关联：docs/05（对话上下文与使用状态）、docs/13（Codex CLI 集成）、docs/18（AI CLI 配置档案）、docs/20（按项目环境分发的 Agent Runner）、docs/21（项目级 AI 配置重塑）、docs/30（项目级 AI 凭据隔离）
> 结论摘要：**底部模型栏从"只显示"升级为"可选择"，落成会话级 `conversations.model_override`（持久化、非密钥、不动档案/revision）**。优先级（会话覆盖 > 档案模型 > CLI 默认）在控制服务里解析一次，作为 `AgentRunRequest.Model` 普通参数下传——不依赖 profile，因此本机 / WSL / SSH 三条路径统一生效。切换采用"改配置 → 退役长驻会话 → 下一条消息 `--resume` + 新 `--model`"的既有机制（与权限切换同一条路）。已实测可行的 `/model` 热切换列为三期快速通道。

## 1. 诉求与现状

### 1.1 诉求

会话页输入框下方（`composer-footer`）已经显示了当前使用的模型，但**只能看、不能选**。Claude Code 与 Codex CLI 本身都支持在会话中切换模型（Claude `/model`、Codex `/model`），用户希望在这里获得同等能力。

### 1.2 UI 现状

底部栏由 `ComposerRunnerInfo` 渲染（`apps/web/src/pages/ConversationPage.tsx:241`），模型是一个**纯文本 span**：

```
apps/web/src/pages/ConversationPage.tsx:367
<span className="composer-usage">
  <span className="composer-usage-model" title={displayedModel}>{displayedModel}</span>   ← 只读文本
  <span className="composer-usage-context ...">{contextLabel}</span>
  <span className="composer-usage-count">{taskCount} 次对话</span>
  <button className="usage-trigger">使用状态</button>
</span>
```

显示值来自用量接口（`:2964`）：

```ts
const displayedModel = usage?.context.model || currentUsage?.model || (isCodex ? "Codex" : "Claude Code");
```

即：**只有跑过一次之后**才拿得到真实模型名（Claude 从 `assistant.message.model`、Codex 从 `seedRunUsageModel` 预置，见 `apps/control-server/internal/app/usage.go:114`）。选择器要"选完立刻显示"，就必须让会话对象自己带出所选模型。

### 1.3 今天模型是怎么被"选"的

只有两处间接入口，都**不是会话级**：

| 入口 | 位置 | 粒度 |
| --- | --- | --- |
| 「AI 配置」弹窗的"模型"输入框 | `apps/web/src/features/run/ProjectAiConfigDialog.tsx:204` | 项目级（写入 agent profile revision，新会话套用） |
| 新会话对话框的"配置档案"下拉 | `ConversationPage.tsx:605` | 建会话时一次性选定 |

数据流（现状）：

```
projects.default_profile_id / 建会话时选定的 profileId
  → conversations.agent_profile_revision_id            (app.go:2988 / app.go:3053)
  → runtimeProfileTx(...) → AgentRuntimeProfile{Model} (agent_profiles.go:1298)
  → AgentRunRequest.Profile                            (app.go:4964)
  → CLI 参数 --model / -c model=                       (claude_runner.go:706,738 / codex_runner.go:308)
```

## 2. 关键事实核查

### 2.1 CLI 确实支持 --model（Claude）

```
$ claude --help | grep -A3 -- --model
  --model <model>   Model for the current session. Provide an alias for the latest model
                    (e.g. 'fable', 'opus', or 'sonnet') or a model's full name (e.g. 'claude-fable-5').
```

Codex 同样支持 `-m/--model`（`codex exec --help`），应用侧用的 `-c model="X"` 也已在使用中。

### 2.2 实测：切换模型后 `--resume` 能保住上下文（本机 Claude Code 2.1.266）

```
# 1) 新建会话，用 haiku
claude -p --model claude-haiku-4-5 --session-id <SID> --output-format json "只回复：HI"
   → modelUsage: {"claude-haiku-4-5": {...}}   session_id: <SID>

# 2) 同一会话换成 opus 继续
claude -p --model claude-opus-5 --resume <SID> --output-format json "只回复：OK2"
   → session_id: <SID>（同一会话）  modelUsage: {"claude-opus-5": {...}}
```

结论：**`--resume` + 新 `--model` 可在不丢上下文的前提下换模型**，这是本方案主路径能成立的前提（对应现有长驻会话的"退役 → 用 `--resume` 重启"机制）。

### 2.3 实测：`/model` 走 stream-json 也能热切换（二期快速通道）

把 `/model` 当普通用户消息写进长驻会话的 stdin：

```
{"type":"user","session_id":"","parent_tool_use_id":null,
 "message":{"role":"user","content":[{"type":"text","text":"/model claude-haiku-4-5"}]}}
```

实测事件流：

```
0 system    init
1 assistant model=<synthetic>  "Set model to `Haiku 4.5` for this session only"
2 result    success            num_turns=0, modelUsage=[]        ← 注意这一条
3 system    init                                                 ← CLI 重新 init
4 assistant model=deepseek-v4.1-flash   （thinking）
5 assistant model=deepseek-v4.1-flash   "OK"                     ← 下一条 prompt 已用新模型
6 result    success            num_turns=1, modelUsage=["claude-haiku-4-5"]
```

结论：**热切换可行且立刻生效**，但会额外产生一个 `assistant(<synthetic>)` + `result(num_turns=0)`。若走这条路，必须在服务端拦下这次"伪回合"（不落用户消息、不建 run、不计用量），否则会话历史里会多出一条 `/model X`，用量统计里也会多一次空任务。这跟 `/clear` 目前"只发 `conversation_reset` 事件、由应用本地拦成清空流程"是同一类处理。**因此列为二期，一期不做。**

### 2.4 长驻会话：换模型必然涉及进程重启

Claude 侧是长驻 `stream-json` 进程（`claude_runner.go:721 sessionArgs`），模型在**进程启动参数**里，进程内无法改。系统已有成熟的"配置变化即退役"机制：

```
conversation_session_manager.go:19-39   conversationSessionConfig{runnerID, agentID, projectPath, permissionMode, profileRevisionID}
conversation_session_manager.go:130-151 ensureConfiguration()   ← 结构体不等即退役
conversation_session_manager.go:180-201 retireForConfiguration() ← 仅空闲时退役，忙则返回 false
app.go:3870-3924                        setConversationPermissionMode  ← 权限切换就是这么做的，可直接照抄
```

**因此：只要把"当前模型"加进 `conversationSessionConfig`，切换模型就会自动复用这套机制**——空闲时退役、下一条消息带新 `--model --resume` 重启；忙时前端禁用入口，避免撞上 409。

### 2.5 今天模型真正生效的范围（比想象的窄）

`--model` / `-c model=` 只在**能拿到 profile** 的路径上注入：

| 目标环境 | 是否注入模型 | 原因 |
| --- | --- | --- |
| 服务端本机 runner（Windows 的 `windows-local`、Linux/WSL 的 `wsl-local`） | ✅ | 项目可设默认档案（`canManageProfileRunner` 为真，`agent_profiles.go:1135`） |
| Windows 服务端下的 `wsl-local` 项目 | ❌ **缺口** | runner 不是本机 runner → 不可管理档案 → 会话 revision 为空 → `request.Profile == nil`；但注意 WSL 侧代码本身是支持的（`wsl_agent_run.go:223` 复用 `r.claude.args`） |
| SSH 项目 | ❌ **缺口** | 同上；且 `ssh_runner.go:1152-1173 / 1235-1280` 自行拼 shell 命令，**压根没有 model 参数**（Claude 与 Codex 都没有） |
| WSL→Windows 跨端 | ❌ | 该 runner 仍是 POC，直接返回未就绪错误（`win_agent_runner.go:161-173`） |

> 注：`ssh_runner.go` 的 Claude 分支只拼了 permission / session / MCP 参数，两端都没有任何模型参数——**即"项目 AI 配置里填的模型"在 SSH 项目上今天就是静默失效的**，本方案顺带修掉。

**推论：如果只在 profile 上加模型，这个功能在一半的真实项目上会"看起来能选、实际不生效"。所以必须新增一条独立于 profile 的注入通道。**

### 2.6 模型目录从哪来

**Codex：有现成的机器可读目录。**

```
$ codex debug models
{"models":[{"slug":"gpt-6-astra","display_name":"GPT-6-Astra","description":"...",
  "default_reasoning_level":"low","supported_reasoning_levels":[...],
  "visibility":"list" | "hide", "supported_in_api":true, ...}, ...]}
```

本机（codex-cli 0.153.4）实测 11 条，其中 `visibility=list` 的 6 条：`gpt-6-astra`、`gpt-5.6-sol`、`gpt-5.6-terra`、`gpt-5.6-luna`、`gpt-5.5`、`gpt-5.2`。耗时 < 0.3s，**但属 `debug` 子命令，只能当 best-effort + 静态兜底**。

**Claude：没有 list 命令。** 可用来源三选一：

1. 静态目录（推荐兜底）：别名 `default/opus/sonnet/haiku/fable` + 具体版本 id。
2. 从本机安装的 CLI 二进制里提取（已验证可行）：
   ```
   $ strings .../@anthropic-ai/claude-code/bin/claude.exe | grep -o 'claude-\(opus\|sonnet\|haiku\|fable\)-[0-9.-]*'
   claude-sonnet-5 / claude-opus-5 / claude-haiku-4-5 / claude-fable-5 / claude-fable-5-1 / claude-haiku-4-5-20251001
   ```
   （属于"读实现细节"，脆弱，不建议作为运行时依赖，只用于人工维护静态表。）
3. 完全放开自定义输入——因为**第三方网关的模型名根本无法穷举**（本机 `~/.codex/config.toml` 用的就是 `gpt-5.6-sol`，Claude 走 `https://conflux-api.work/`）。

**结论：目录 = 静态别名表（Claude）/ `codex debug models`（Codex，失败则静态兜底）+ 永远允许自由输入。**

### 2.7 网关会改写模型名，显示要区分"所选"与"实际"

实测：请求 `--model claude-haiku-4-5`，事件流里 `assistant.message.model` 是 **`deepseek-v4.1-flash`**（网关映射），而 CLI 自己的 `modelUsage` 键仍是 `claude-haiku-4-5`。

所以底部栏需要两个信息：
- **所选模型**（会话 override 或项目配置）——选择器里显示；
- **实际使用模型**（来自 `usage.context.model` / `模型用量` 列表）——已经在"使用状态"弹窗里有明细（`ConversationPage.tsx:416`）。

两者不一致时不应判定为错误，只做如实展示。

## 3. 方案

### 3.1 数据模型（最小改动）

```sql
-- 幂等迁移，用既有 ensureColumn（app.go:1321）
alter table conversations add column model_override text not null default '';
alter table runs          add column model_override text not null default '';   -- 可选，便于事后审计
```

- **不新建 profile / revision**：revision 是不可变凭据快照，模型切换与凭据无关；动它还会连带触发 `retireForProfileRevision`、配额与路由链路。
- **不做全局默认模型列**：`projects.default_profile_id` 的单列限制（docs/21 §3.2）不要在这个功能里重开。
- 空串 = 跟随项目配置 / CLI 默认，语义与 `ProjectAiConfigDialog` 的"留空使用 CLI 默认"一致。

### 3.2 后端：把模型解析收敛到一处，再作为普通参数下传

**优先级解析（会话覆盖 > 档案模型 > CLI 默认）只在控制服务里算一次**，算完作为 `AgentRunRequest.Model` / `AgentSessionRequest.Model` 一个普通字符串下传；runner 只负责"有模型就拼参数"，不认识 override、不认识 profile 优先级：

```go
// app.go：请求构造处调用，全会话生命周期内唯一的优先级来源。
func runModel(conversation Conversation, profile *AgentRuntimeProfile) string {
    if m := strings.TrimSpace(conversation.ModelOverride); m != "" { return m }
    if profile != nil { return strings.TrimSpace(profile.Model) }
    return ""
}
```

全仓库构造 run 请求的地方只有 **5 处**（`grep -rn 'AgentRunRequest{\|AgentSessionRequest{'`）：

| 位置 | 是否受会话覆盖影响 | 做法 |
| --- | --- | --- |
| `app.go:5131` `submitStreamingRunWithProfile`（每次发言） | ✅ | `Model: runModel(conversation, profile)` |
| `app.go:5193` `streamingSession`（长驻进程启动） | ✅ | 同上 |
| `app.go:5299` `runAgent`（一次性 run） | ✅ | 同上 |
| `insights.go:632`（只读扫描） | ❌ | 保持 `profile.Model` |
| `orchestration.go:2648`（编排评审） | ❌ | 保持 `profile.Model` |

覆盖范围因此是完整的：用户消息、快捷指令、定时任务、任务面板下发**都走 `startMessage`**（`scheduled_tasks.go:1129`、`task.go:1340`），自动拿到同一个值。

runner 侧只做一件事——**删掉现有的 `request.Profile.Model` 读取，改读 `request.Model`**，让"模型"只有一个来源：

| 文件:行 | 位置 | 改动 |
| --- | --- | --- |
| `claude_runner.go:705-707` | `args()` | `Profile.Model` → `request.Model` |
| `claude_runner.go:737-739` | `sessionArgs()` | 同上 |
| `codex_runner.go:307-309` | `Run()` | 同上 |
| `wsl_agent_run.go:223` | `runClaudeOnce` | 复用 `r.claude.args`，自动生效 |
| `wsl_agent_run.go:326-327` | `runCodexOnce` | `Profile.Model` → `request.Model` |
| `ssh_runner.go:1152-1173` | SSH Claude 命令 | **新增** `--model` + `shellQuote(...)`（同时修掉历史缺口） |
| `ssh_runner.go:1235-1280` | SSH Codex 命令 | **新增** `-c model="..."` + `shellQuote(...)` |
| `app.go:4963` | `seedRunUsageModel` | 改为接收已解析的模型，避免"喂给 CLI 的"与"显示用的"分叉 |

**为什么不复用 `Profile.Model` 硬塞**：`managedCLIEnvironment`（`agent_profiles.go:117`）对非 nil profile 会**屏蔽**继承的 `ANTHROPIC_API_KEY` / `ANTHROPIC_BASE_URL` 等变量（`agent_profiles.go:105-108`）。为无档案的会话（SSH / Windows 侧 wsl-local，见 §2.5）凭空造一个 profile 会改变凭据注入语义。所以只把模型单独拎出来传，凭据链路一行不动。

**为什么不把 `effectiveModel(profile, override)` 放进 runner**：那样优先级要在 7 个注入点各算一遍，且每个 runner 都要理解"会话覆盖"这个上层概念；同时 `request.Profile` 与 `request.Model` 两个字段都能表达模型，迟早有人只改一个。收敛到构造处后，runner 侧是纯粹的"参数翻译"。

### 3.3 后端：会话配置与进程重启

```go
// conversation_session_manager.go:19-39
type conversationSessionConfig struct {
    ..., model string   // 与 request.Model 同源，由调用方传入
}
```

模型变化 ⇒ 结构体不等 ⇒ `ensureConfiguration` 退役旧进程 ⇒ 下一条消息 `--resume` + `--model` 重启。**这正是权限切换（`app.go:3903`）已经验证过的路径**，唯一的新增成本是一次进程冷启动。

### 3.4 后端：接口

复用 `setConversationPermissionMode`（`app.go:3870`）的形状：

```
POST   /api/conversations/{id}/model            body {model:"opus"} → 200 Conversation
GET    /api/conversations/{id}/models           → 模型目录 + 当前生效信息
```

`POST` 的校验与顺序（照抄权限切换）：

1. 编排会话只读（`isOrchestrationConversation`）；
2. `projectLifecycleMu` 串行化；
3. `model` 规范化：`TrimSpace`，长度 ≤ 128，拒绝控制字符与换行；
4. `conversation.Status != "idle"` → 409 "先停止当前任务"；
5. `retireForConfiguration(id)` 为 false → 409 "正在重启会话，请稍后重试"；
6. `update conversations set model_override=? where id=? and status='idle'`，`RowsAffected != 1` → 409；
7. 返回更新后的 `Conversation`。

`GET .../models` 返回：

```jsonc
{
  "agentId": "codex",
  "selected": "gpt-5.5",          // 会话覆盖，空 = 跟随
  "effective": "gpt-5.6-sol",     // 跟随时的实际来源（档案模型，或 CLI 默认探测值）
  "source": "override|profile|cli_default",
  "models": [{ "id": "gpt-5.5", "label": "GPT-5.5", "description": "..." }],
  "customAllowed": true,
  "catalogNote": "目录来自 codex debug models（本机）"
}
```

- Codex 目录：给各 Codex runner 加 `codexModelCatalog(ctx)`（本机 `codex debug models`、WSL 走 `wsl.exe`、SSH 走远端 exec），过滤 `visibility == "list"`，**带 TTL 缓存**（照 `wsl_agent_runner.go:42-43` 的 `codexModelAt/codexModelCache` 范式），失败即降级到静态兜底表。
- Claude 目录：服务端静态表（别名 + 版本 id），`customAllowed` 恒为 true。
- **不回显任何密钥/Base URL**，与 docs/18 §4 的只读视图约定一致。

`Conversation` 结构体（`app.go:422`）增加一个 JSON 字段 `modelOverride`（`json:"modelOverride,omitempty"`）。

**列清单同步是本方案最容易漏的一处**（漏一处就是启动即 `sql: expected N destination arguments`）。列全用这三条 grep，一次改完：

```bash
grep -rn "Scan(&conversation\.\|Scan(&previous\.\|Scan(&c\.\|Scan(&existing\.\|Scan(&fresh\." apps/control-server/internal/app/ | grep -v _test   # select 侧
grep -rn "insert into conversations" apps/control-server/internal/app/ | grep -v _test                                              # insert 侧
grep -rn "update conversations set" apps/control-server/internal/app/ | grep -v _test                                               # update 侧
```

当前 select 侧 9 处（`app.go:3039,3126,3169,3523,3830,3886,4332,4670` + `scheduled_tasks.go:1188`，另有 `remote_control.go:1012` 只取部分列，不需要改）；insert 侧**只有 `/clear` 的接续会话需要改**（`app.go:3203`，把旧会话的 `model_override` 带过去），其余 insert 可以不动——列不在列表里就吃默认值 `''`，这正好是"新会话跟随项目配置"的期望行为。

### 3.5 前端：底部模型栏 → 可点选

- `ComposerRunnerInfo` 的模型 span 改成 `<button className="composer-model-trigger">`，弹层直接复用 `.permission-menu / .permission-popover` 的样式与交互范式（`ConversationPage.tsx:3089-3092`）。
- 弹层内容：
  - 首项 **「跟随项目配置」**（= 置空 override，副标题显示 `effective`）；
  - 目录项：别名/版本（Claude）或 `display_name`（Codex），`description` 作 tooltip；
  - **自定义模型名**输入（网关场景必需）；
  - 底部一行说明："切换后下一条消息生效；本会话内持续有效。"
- 禁用条件与权限菜单完全一致：`readOnlyConversation || !!run || clearing || stopping`——**运行中不允许切换**，从根上避免 3.3 的 409 分支。
- `displayedModel` 改为 `conversation.modelOverride || usage?.context.model || ...`，选完立刻可见；实际使用模型仍在"使用状态"弹窗展示。
- `types.ts:22` 的 `Conversation` 类型同步加 `modelOverride?: string`。
- 可选增强：弹层里放一个「同时设为项目默认」，等价于直接调 `PATCH /api/agent-profiles/{id}`（复用 `ProjectAiConfigDialog` 的保存逻辑）。一期可不做。

### 3.6 校验与安全

- 模型名是**用户自填的普通 argv 值**，不是密钥：
  - 本机 / WSL 走 exec argv，无 shell 解析；
  - SSH 走拼串，必须与既有做法一致使用 `shellQuote`（`ssh_runner.go` 全部参数都是这么处理的）；
  - 长度与字符集白名单式收敛（`[A-Za-z0-9._:\-/]`，≤128），拒绝换行与 `$`、反引号等，双保险。
- 不写入 `agent_profile_revisions`，不参与凭据注入，不影响配额与路由；`retireForProfileRevision` 逻辑不变。
- 编排 / 定时任务 / 洞察扫描这些自动路径：编排与洞察各自传 `profile.Model`（不受会话覆盖影响），定时任务经 `startMessage` 下发、与普通发言行为一致。

### 3.7 明确不做

### 7.3 相对方案的偏差（均为实现中发现的更优解）

1. **注入字段用 `Model` 而不是 `ModelOverride`**，且优先级只在控制服务的 `runModel()` 里算一次——原方案要在 7 个 runner 注入点各调一次 `effectiveModel()`，会让每个 runner 都理解"会话覆盖"这一上层概念，并留下 `Profile.Model` 与 `ModelOverride` 两个来源分叉的隐患。实施时把探索出的真实约束（全仓库只有 5 处构造 run 请求）变成了更小的改动面。`runModel` 的签名最终定为 `runModel(override string, profile *AgentRuntimeProfile)`：调用处必须显式说明"有没有会话覆盖"，两个没有会话上下文的路径（洞察扫描、编排评审）直接传 `""`。
2. **SSH 的 `--model` 补在三个分支**而不是两个：除一次性 `Run` 外，长驻会话 `StartSession` 也自行拼命令（`ssh_runner.go`），漏掉它会导致 SSH 项目的长期会话仍用旧模型。
3. **Codex 目录探测在三端都实现**（本机 `exec` / WSL `wslBridgeProbe` / SSH `execCommand`），而不是只做本机：三者共用同一份解析与缓存，多出的代码量很小，但避免了"换个项目形态就没有目录"。

### 7.4 实施中发现的既有缺陷：Windows 上本机 Codex 根本起不来（已一并修复）

Codex 目录探测在真机上一直回退到静态表。查下去发现不是探测写法的问题，而是 `codexCommandContext`
（`codex_runner.go`）把 npm 的 `.cmd` shim 路径按 `"path"` 手工加引号：

```go
exec.CommandContext(ctx, "cmd.exe", "/d", "/c", `"`+path+`"`, args...)
```

Go 的参数转义面向 `CommandLineToArgvW`，会把引号转义成 `\"`；而 cmd.exe 解析的是 `/c` 之后的
**原始命令行**，于是它把 `\"C:\...\codex.cmd\"` 整串当成命令名去找，报
「不是内部或外部命令」。本机实测（均为退出码 1、stdout 为空）：

| 调用方式 | `--version` | `debug models` |
| --- | --- | --- |
| `codexCommandContext(path, …)`（加引号，修前） | 失败 | 失败 |
| `cmd.exe /d /c <path> …`（不加引号） | 成功 | 成功（517,840 字节目录） |

**这不只影响新功能**：`BinaryReady` 用的是 `exec.LookPath`（文件在就算就绪），而 `Version()` /
`Run()` 都要经 `codexCommandContext` 才能真正起进程——所以 windows-local 项目上的 Codex
一直是"显示就绪、版本号空白、一跑就失败"。修复后 `/api/runners` 里 windows-local 的 codex
版本从空串变成 `0.153.4`，即为该缺陷被修掉的可观测证据。

修法（只动 `.cmd/.bat` 分支）：路径不含空白时不加引号；**用户参数仍逐个作为独立 argv** 交给
Go 转义——绝不手工拼命令串，否则含引号/shell 元字符的 prompt 会被破坏。含空白的安装路径保留
旧的带引号形式（未验证可用，但不会更差）。回归测试：`TestCodexCommandContextQuotesOnlyWhenNeeded`。

> 该缺陷与"模型选择"本无关系，但它挡在 Codex 模型目录的探路上，且会让 Windows 用户以为 Codex
> 可用，故在同一批改动内修掉；若希望拆成独立提交，只需单独挑出 `codex_runner.go` 的
> `codexCommandContext` 那一段。

### 7.8 第二轮复查

再逐行过了一遍，新增 2 处修复，并把几处"看着可疑但确认没问题"的点也记下来备查。

修掉的：

| # | 问题 | 后果 | 修法 |
| --- | --- | --- | --- |
| 5 | 弹层开着时用户在输入框直接回车发起任务 | 弹层浮在输入框上方不会自动收起；此后的切换会被服务端拒绝，表现为"点了没反应" | 传入 `runActive`，任务一开始就关闭弹层（不影响切换请求进行中的 `busy` 状态，失败时弹层仍在） |
| 6 | 等待退役期间会话被删除/开始新任务 | 落库时 `RowsAffected != 1` 却报"请先停止当前任务"，与实际原因不符 | 文案改为"会话状态已变化（可能已开始新任务或被删除），请刷新后重试" |

确认没问题、无需改动的：

- **`projectApi` 与 `api` 是同一个函数**（`useProjectStore.tsx` 里就是 `api: apiFn`），所以模型目录用 `api`、切换用 `projectApi` 只是本文件的命名习惯，行为无差异。
- **行尾**：脚本批量改过的 Go 文件现在是纯 LF，前端仍是 CRLF，但两边都**没有混行尾**；`core.autocrlf=true` 会在 diff/提交时归一化，不会产生整文件 diff。
- **WSL 探测**：`wslBridgeProbe` 默认 5s 超时，但我传入的 8s 上下文有 deadline，会按 8s 走；`TrimSpace` 对 500KB JSON 无害。
- **SSH 探测**：`execCommand` 用的是 `CombinedOutput`，所以命令里的 `2>/dev/null` 不是多余的——没有它，远端 Codex 的任何 stderr 提示都会混进 JSON 里。
- **`modelOverride` 用 `omitempty`**：清空后在响应里字段直接消失，前端一律用 `conversation?.modelOverride || ""` 读取，已覆盖。

**第二轮的真机端到端验证**（这次不看接口返回，直接看 CLI 有没有收到）：

1. 给 Codex 会话设一个**不存在的模型名** `definitely-not-a-real-model-xyz`，发一条消息 → 运行 **failed**。若 `-c model=` 没传到 CLI，Codex 会用 `config.toml` 的默认模型正常完成——所以失败本身就是"参数确实到达 CLI 并被校验"的证据。
2. 清空覆盖后再发一条 → 运行 **completed**，模型回到 `gpt-5.6-sol`（与 `~/.codex/config.toml` 一致）。即选错模型不会把会话卡死，可随时退回跟随配置。
