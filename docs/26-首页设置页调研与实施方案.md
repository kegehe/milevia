# 首页设置页调研与实施方案

> 日期：2026-08-19  
> 状态：P0 与当前已规划的 P1 均已实施；主题、语言、自启动须在完成对应基础设施后另立方案  
> 关联：docs/15（跨项目通知）、docs/18（AI CLI 配置档案）、docs/21（项目级 AI 配置）、docs/23（Windows 打包与在线升级）、docs/25（项目主动优化建议）

## 1. 结论与定位

首页应新增一个设置入口和独立的 `/settings` 页面，但设置页的职责必须收敛为：**应用级偏好、设备级体验与新会话安全基线**。

它不是“把所有带有配置表单的功能收进来”的容器。模型、密钥、启动命令、环境变量、SSH 凭据、任务编排计划等都有明确的项目或资源归属；脱离上下文放入设置页，会弱化作用范围并增加误操作风险。

本期设置页的优先级如下：

1. **新会话与安全**：设置默认 Agent 和默认权限，避免每次新会话隐式落到高权限模式。
2. **通知**：让系统通知由用户主动授权，并可控制哪些事件打扰用户。
3. **本地偏好与数据**：统一管理代码字号、项目卡片排序和未发送草稿。
4. **关于与更新**：集中展示版本和更新状态，提供明确的手动检查入口。

## 2. 现状调研

| 能力 | 当前实现 | 设置页结论 |
| --- | --- | --- |
| 新会话 Agent / 权限 | 新会话默认 Claude Code + `full_control`；切到 Codex 时默认 `workspace_write` | 应纳入，属于影响每次会话安全边界的应用级默认值 |
| 项目 AI 配置 | 会话页“AI 配置”管理当前项目的模型、Base URL、认证与 API Key | 不搬迁，保持项目级入口 |
| AI 配置档案 | `/agent-profiles` 是停用、撤销 revision 的高级管理视图，且无常规导航入口 | 不作为首期设置项；保留深层链接即可 |
| SSH 连接 | 首页直接进入 SSH 管理器，连接可预检、编辑、连接和删除 | 不搬迁；可在设置页放“管理 SSH 连接”跳转 |
| 开发进程 | 每项目保存工作目录、命令、环境变量和执行目标 | 不搬迁，环境变量可能敏感且强依赖项目 |
| 通知 | 全局 WebSocket、Toast、通知中心、后台原生通知均已具备 | 应纳入，补上用户偏好与授权控制 |
| 代码字号 | 12–20px，默认 13px，已写入 `localStorage` | 应纳入 |
| 项目卡片排序 | 首页拖拽排序，已写入 `localStorage` | 应纳入“恢复默认顺序”动作 |
| 未发送草稿 | 本地保存，最多 50 条、保存 30 天 | 应纳入数据保留与清理动作 |
| 更新 | 桌面端启动时后台查询更新，横幅支持下载安装 | 应纳入版本与检查状态；不做自动下载安装 |
| 主题、语言、开机启动 | 当前没有完整深色主题、国际化或自启动基础设施 | 不应先做空开关 |
| 优化建议扫描 | 设计已明确为手动触发，避免后台消耗 token | 不应加入“自动扫描”设置 |
| 刷新间隔、重连重试 | 用于保证状态正确性的内部机制 | 不向普通用户暴露 |

## 3. 首页入口与页面结构

### 3.1 首页入口

在 `DashboardPage` 的右上角操作区增加一个齿轮图标按钮：

- 位于通知铃铛旁，SSH 连接按钮之前。
- 使用图标按钮而非带“设置”文字的大按钮；提供 `title` 和无障碍标签“设置”。
- 点击路由到 `/settings`。
- SSH 连接继续保持首页快捷入口，避免用户为了添加远端项目先进入设置页。

`App.tsx` 新增 `/settings` 路由，页面使用普通全页布局，不使用叠加在首页之上的模态框。设置是可反复进入、可浏览多个分组的工作区，而不是一次性表单。

### 3.2 信息架构

首期左侧或顶部使用固定分组导航，内容区按组展示设置行：

```text
设置
├── 通用
├── 通知
├── 新会话与安全
├── 数据
└── 关于
```

每个设置项应有简短名称、作用说明、当前值和对应控件；即时生效的偏好不应额外出现“保存全部”按钮。涉及权限升级、清空本地数据或更新安装的动作，必须有明确确认和结果反馈。

## 4. 首期应实现的设置

### 4.1 新会话与安全（P0）

这是首期优先级最高的分组。当前 `NewConversationDialog` 在初始状态选择 Claude Code 和 `full_control`；切换到 Codex 后则默认 `workspace_write`。权限的选择会决定 agent 是否可直接执行命令，因此不应由组件内的硬编码默认值长期决定。

设置项：

| 设置项 | 选项与行为 |
| --- | --- |
| 默认 Agent | Claude Code / Codex；若当前项目 Runner 不可用则新会话弹窗回退到可用 Agent，并显示原因 |
| Claude 默认权限 | `approval_required` 或 `full_control` |
| Codex 默认权限 | `read_only`、`workspace_write` 或 `full_control` |

具体规则：

1. 首次安装的安全默认值应为 Claude `approval_required`、Codex `workspace_write`、默认 Agent 为 Claude Code。不得再以 Claude `full_control` 作为隐式初始值。
2. “完全控制”可以被用户设为默认，但在保存该项时要单独确认并准确说明影响；不能在切换 Agent 时静默提升权限。
3. 这组设置仅决定“新建会话”弹窗的初始选择。每个会话仍保留当前的权限切换入口，已创建会话不被追溯修改。
4. 项目 AI 配置只负责本项目使用的模型、认证和档案；它不与默认 Agent / 默认权限混合，避免项目配置改变全局安全基线。
5. 新会话弹窗必须等待“应用偏好”和“当前项目 Runner 能力”都加载完成后再确定初始值。若首选 Agent 在该 Runner 上不可用，回退到可用 Agent 并在弹窗中解释原因；加载期间禁用创建按钮，不能短暂显示一个随后无法创建的 Codex 选项。

这里的“安全基线”是**默认体验**，不是访问控制策略。单用户应用中，用户仍可以在新会话或会话内选择该 Agent 支持的其他合法权限；服务端负责校验 Agent 与权限组合，而不应把偏好接口当成权限限制机制。服务端在创建会话请求省略 Agent 或权限时已经安全回退到 Claude Code + `approval_required`，本期需要消除的是前端弹窗显式预选 `full_control` 的不一致。

### 4.2 通知（P0）

现有通知基础已经完整：后端持久化未读通知，前端通过 `/ws/notifications` 接收事件，在应用内显示 Toast，并在页面不可见时发送浏览器/系统通知。

当前问题是：前端会在用户第一次点击或按键时调用 `Notification.requestPermission()`。系统通知权限应当由用户在设置页主动发起，而非由普通操作隐式触发。

设置项：

| 设置项 | 默认值 | 说明 |
| --- | --- | --- |
| 应用使用系统通知 | 关闭，用户主动开启 | 开启后点击“授权系统通知”才请求操作系统权限；关闭仅停止应用发送，不会撤销操作系统授权 |
| 系统通知授权状态 | 未授权 | 只读展示“未授权 / 已允许 / 已拒绝”，并在可授权时提供授权按钮 |
| 后台时显示系统通知 | 开启 | 仅当应用不可见时发出原生通知，符合现有行为 |
| 审批与人工介入 | 应用内必提醒；系统通知可选 | `approval.pending`、`needs_human` 等高优先级事件不能从通知中心丢失 |
| 任务完成与失败 | 默认系统通知开启 | 可以关闭系统通知，但通知中心仍保留记录 |
| 低优先级状态 | 默认关闭系统通知 | 避免常规状态变化造成噪音 |

“任务完成与失败”“低优先级状态”等分类开关只在“应用使用系统通知”开启时生效；主开关关闭时一律不发系统通知。首次安装将主开关设为关闭。对于升级前已经授予浏览器/WebView 通知权限的用户，迁移时只把“应用使用系统通知”初始化为开启以保持既有行为，**绝不重新请求权限**；用户仍可在设置页关闭该行为。

实现边界：通知偏好只控制前端 Toast 和系统通知的**呈现方式**，不应阻止后端生成或持久化通知事件。高优先级事件不可被偏好静默丢弃：用户已在所属会话时由会话内审批/状态界面承接，否则显示应用内持久提示；普通和低优先级事件才按用户偏好抑制 Toast 或系统通知。这样用户关闭提醒后，仍可在通知中心查看事件历史；审批等需要处理的事件也不会因偏好被吞掉。

浏览器/API 不允许应用主动撤销已经授予的系统通知权限。页面在“已拒绝”状态下应提示用户到操作系统或 WebView 设置中修改，而不是提供无效的关闭开关。

### 4.3 通用（P0）

通用分组只放已经存在且明确属于设备体验的偏好。

| 设置项 | 当前数据 | 交互 |
| --- | --- | --- |
| 代码字号 | `files:code-font-size`，范围 12–20，默认 13 | 使用步进器或滑块，显示当前 px；提供“恢复默认” |
| 项目卡片排序 | `milevia:project-order` | 仅提供“恢复默认排序”，清除用户拖拽顺序，后续按后端项目顺序显示 |

首期不要添加主题选择。现有页面、CodeMirror 渲染和大量 CSS 均为固定浅色主题；没有完整深色主题时，提供“深色/跟随系统”只会造成半成品体验。

### 4.4 数据（P0）

未发送草稿属于用户本地数据，应该可见、可控、可清理。当前草稿使用 `auto.conversation-draft.v2:` 前缀存储，每条有更新时间，最多保留 50 条，超过 30 天自动清理。

设置项：

| 设置项 | 默认值 | 行为 |
| --- | --- | --- |
| 自动保存未发送草稿 | 开启 | 关闭后停止后续写入，不删除已有草稿 |
| 草稿保留期限 | 30 天 | 可选 7 天、30 天、90 天；只影响本地草稿 |
| 清除全部未发送草稿 | 危险动作 | 显示受影响数量，二次确认后删除该前缀下的数据 |
| 恢复本地界面偏好 | 危险动作 | 仅清除字号、项目排序、通知呈现偏好等 UI 数据；绝不删除项目、会话、任务、SSH 连接或密钥 |

“恢复本地界面偏好”必须使用白名单清理具体的 `localStorage` key，不能调用 `localStorage.clear()`，避免误删其他页面或未来模块的数据。

自动保存开关与“清除全部未发送草稿”必须保持独立：关闭自动保存是可逆偏好，不能顺带执行不可逆删除。关闭时还要取消尚未落盘的 300ms 草稿写入计时器，避免用户刚关闭开关就被页面卸载流程重新写回草稿。保留期限缩短时，应立即按新期限清理过期草稿；延长时不恢复已经删除的数据。

### 4.5 关于与更新（P0 / P1）

关于页首期展示：

- Milevia 当前版本；
- 是否运行于桌面端；
- 最近一次启动检查到的更新版本和发布说明；
- 当前系统通知权限状态；
- 数据仅保存在当前设备的说明。

桌面端现有逻辑会在启动后后台查询一次更新，发现新版本后由横幅负责安装。首期设置页可复用该状态并提供“立即升级”入口。

“立即检查更新”需要新增一个只检查、不下载、不安装的 Tauri command，因此列为 P1；不能借用 `install_update` 来伪装检查，因为该命令会进入下载和安装流程。自动下载、自动安装和安装后自动重启均不纳入首期设置。

桌面端在“数据”分组提供“打开目录”动作，通过不接收前端路径参数的专用 command 打开 `app_local_data_dir()`；Web 环境不展示该控制项，也不回显绝对路径。

## 5. 设置页中的资源入口

以下项目可以作为“管理资源”的跳转链接出现，但不把其表单复制到设置页：

| 资源 | 设置页行为 | 原因 |
| --- | --- | --- |
| SSH 连接 | 跳转 `/ssh-manager` | SSH 连接是全局资源，但含预检、主机指纹和凭据流程，独立页面更安全 |
| 高级 AI 配置档案 | 首期不展示；仅保留深层链接 | docs/21 已明确普通用户应在项目会话页配置 AI，档案页仅用于停用/撤销 revision |
| 项目 AI 配置 | 不提供全局跳转 | 必须从目标项目的会话页进入，保证“配置作用于哪个项目”清晰 |

## 6. 明确不纳入设置页的内容

| 内容 | 应保留位置 / 原因 |
| --- | --- |
| 模型、Base URL、API Key | 项目会话页的“AI 配置”；受管 Key 不应进入通用偏好模型或被回显 |
| SSH 主机、密码、私钥路径、主机指纹 | SSH 管理器；属于连接资源和安全预检流程 |
| 启动命令、工作目录、环境变量、执行目标 | 项目运行页；强绑定项目且环境变量可能包含敏感值 |
| Git 配置和分支操作 | 项目 Git 工作台；必须围绕当前仓库执行 |
| 任务、编排计划、验证命令和修复轮次 | 任务/编排页面；作用域是单个项目或单个计划 |
| 优化建议的自动扫描 | 不做；docs/25 已规定扫描只能手动触发，避免后台消耗 token |
| HTTP 超时、轮询间隔、WebSocket 重连参数 | 内部可靠性策略；普通用户无法据此做出正确取舍 |
| 快捷键自定义 | 当前没有命令注册和冲突检测基础，不先提供不可维护的映射表 |
| 主题、语言、开机启动 | 相关基础能力尚未存在，先实现完整能力后再开放设置 |

## 7. 持久化与 API 设计

设置必须按数据性质分层，不能把所有值混在同一个 `localStorage` JSON 或服务端元数据表中。

### 7.1 服务端应用偏好

默认 Agent 和默认权限会影响 agent 的执行权限，应落入控制服务 SQLite，而不是只留在浏览器缓存。新增单用户表：

```sql
create table if not exists app_preferences (
  id integer primary key check (id = 1),
  default_agent_id text not null default 'claude-code',
  claude_permission_mode text not null default 'approval_required',
  codex_permission_mode text not null default 'workspace_write',
  updated_at datetime not null
);
```

迁移完成后必须立即建立单例行，不能假设 `default` 会在没有插入行时自动返回：

```sql
insert into app_preferences (
  id, default_agent_id, claude_permission_mode, codex_permission_mode, updated_at
) values (1, 'claude-code', 'approval_required', 'workspace_write', ?)
on conflict(id) do nothing;
```

`GET` 对旧数据库的缺失单例行仍应回退这组安全默认值；`PATCH` 使用单事务 `UPSERT` 更新，并同步刷新 `updated_at`。

路由：

```text
GET   /api/preferences
PATCH /api/preferences
```

约束：

- 后端校验 Agent 和权限模式的组合是否合法，不能相信前端枚举；Claude 仅接受 `approval_required` / `full_control`，Codex 仅接受 `read_only` / `workspace_write` / `full_control`。
- 仅保存偏好；创建会话请求仍需显式携带最终 `agentId` 和 `permissionMode`，便于审计和保持已有 API 语义。
- 应用默认值仅在前端打开“新会话”弹窗时读取并作为初始值；既有会话不被批量更新。
- 不复用 `app_metadata`。该表目前用于内部元数据，不具备类型、版本和偏好演进的边界。

### 7.2 设备和界面偏好

通知呈现方式和新增的草稿策略属于本设备/WebView 的体验偏好，适合保存在一个经过 schema 校验的 `milevia:settings:v1`。首期继续保留已有的 `files:code-font-size` 与 `milevia:project-order`，由一个白名单注册表统一读取、重置和测试；不要为了“收口”而在 P0 迁移所有既有 key。等相关模块都改为使用同一偏好访问层后，再单独实施存储迁移。

通知权限本身由浏览器/WebView 与操作系统保管，应用只保存“用户是否希望使用系统通知”的意图。即使本地偏好为开启，也必须再次检查 `Notification.permission === 'granted'` 才能发送。

前端新增轻量的 `UIPreferencesProvider`，在 `NotificationProvider` 外层挂载。设置页写入偏好时同时更新 Context 状态和 `localStorage`；`NotificationProvider` 通过 ref 读取最新偏好，避免把整份偏好放入 WebSocket effect 的依赖数组而在每次设置变化时断开、重连并重新处理通知。草稿 Provider 也从同一 Context 读取开关和保留期，使关闭自动保存后的内存草稿只在当前页面生命周期内可用、刷新后不再恢复。

### 7.3 机密与项目数据

- API Key：继续由 `profile_secrets` 加密存储，设置接口不得返回明文。
- SSH 密码：继续沿用 SSH 连接的安全存储和编辑流程。
- 项目、会话、任务、运行配置：继续使用各自已有表；“清除本地界面偏好”绝不触及这些数据。

## 8. 前端实施拆分

### P0：设置页可用闭环

1. 新增 `/settings`、首页齿轮入口、设置页样式和分组导航。
2. 新增 `app_preferences` 迁移、`GET/PATCH /api/preferences`、前端类型与请求封装。
3. 新增 `UIPreferencesProvider`，让通知与草稿功能在不重连 WebSocket 的前提下响应设置变更。
4. 让新会话弹窗在偏好和 Runner 能力加载后读取应用默认 Agent / 权限；保留每次会话创建前的显式选择。
5. 将系统通知改为设置页主动授权；实现主开关、分类过滤与老用户迁移，但保留通知中心记录。
6. 实现代码字号、项目排序重置、草稿开关、草稿清理和草稿保留策略；关闭草稿保存不删除已有草稿。
7. 增加关于页版本/更新状态展示，复用现有桌面端 updater 状态。

## 9. 验收与测试

### 9.1 服务端

- 首次读取偏好返回安全默认值。
- 缺失单例行时，`GET` 回退默认值；迁移或首次 `PATCH` 后只存在 `id=1` 的一行。
- 非法 Agent、非法权限模式、Agent 与权限不兼容的组合返回 `400`。
- `PATCH` 后重新读取值一致，重启控制服务后仍保留。
- 设置页和任意新会话请求都不会返回或写入 API Key、SSH 密码等机密。

### 9.2 前端

- 首页齿轮能进入和返回设置页；移动端不溢出。
- 新会话弹窗只在偏好和 Runner 能力加载完成后按已保存偏好预选；不可用 Agent 会有可见回退原因，且不静默提升权限。
- 首次普通点击/按键不再触发系统通知授权；只有点击“开启系统通知”才请求权限。
- 首次安装默认不发系统通知；已有授权用户升级后不重复弹授权窗，并保留原有系统通知行为直到用户关闭。
- 关闭通知呈现后，通知中心仍能看到对应未读事件。
- 免打扰时段仅抑制普通/低优先级的呈现，支持跨午夜；审批与人工介入保持应用内提醒和通知中心记录。
- “管理 SSH 连接”跳转既有专用管理页，不在设置页回显或编辑凭据。
- 字号跨文件查看器/编辑器保留；恢复默认与排序重置只影响对应本地 key。
- 清除草稿前显示数量，确认后不影响项目、会话和其他本地偏好。
- 关闭自动保存不删除已有草稿，也不会被待执行的草稿计时器重新写入。

### 9.3 桌面端

- 关于页能显示 `get_updater_status` 的当前版本和缓存更新状态。
- “检查更新”只调用检查命令并更新页面状态；仅“立即升级”会下载、安装并重启。
- 有更新时，从设置页触发升级与现有更新横幅行为一致；Web 环境不渲染桌面专属控制项。
- “打开目录”只打开 `app_local_data_dir()`，不接收前端路径，Web 环境不渲染该操作。
