## 1. 问题与目标

目前应用中的 AI 仅在**对话页**被用户主动提问时才动手——用户进入对话、描述问题，AI 才执行。本方案要解决的核心问题是：**让 AI 主动审视项目**，不等用户撞见问题，就自行通读项目并沉淀出「可优化点 / 可新增功能 / 已有 bug / 样式问题」，并以**一张张用户看得懂的逻辑卡片**（而非代码级描述）展示出来——例如「某卡片过大挤压了其它元素」「可在列表页加一个按名称筛选」。

由此，我们新增一个工作区 Tab：**优化建议**。它的两个核心价值是：

- **主动**：AI 自行通读项目、主动发现，而不是等用户在使用时暴露问题。
- **用户可读**：卡片内容是用户在界面上看得到、用得到、能理解的现象与建议，而非代码函数行号层面的诊断。

### 1.1 需求取舍（已确认）

分析用的 AI：**跟随项目当前默认**——复用项目 AI 配置（`docs/18`/`docs/21`）里已设定的 Claude / Codex 档案，用户在优化建议页无需再选。

卡片动作：**展示 + 轻交互**——卡片支持「添加到任务」「编辑」「删除」三个操作（见 §6），但不做「一键自动修改」「标记已处理/已忽略」等更重的工作流。建议必须转成任务后经任务下发执行，不能直接发送到对话。

扫描触发：**手动为主**——进入 Tab 后由用户点击「开始分析」才运行扫描，不在后台自动烧 token。

### 1.2 两条核心规则（新增）

用户为方案补充了两条规则，作为本功能的硬性要求：

1. **不重复**：再次扫描时，已经报告过、或项目里已经实现/具备的优化点、功能、bug，不得反复出现。
2. **必须核实**：每次扫描产出的问题/建议，都要反复确认确实存在，剔除伪需求与假 bug。

## 2. 范围与非目标

### 2.1 本阶段实现

- 新增「优化建议」工作区 Tab 与对应页面。
- 后端新增两张表（扫描 + 发现），并新增一个「只读 + 两趟式 AI 扫描」的后台任务与两组 REST 端点（触发扫描、查询结果）。
- 扫描结果以用户可读的逻辑卡片在前端展示，可用类型筛选。
- 落实「不重复」与「必须核实」两条规则。

### 2.2 本阶段不做

- 不做「一键自动修改」（建议必须转成任务后再下发执行）。
- 不做「标记已处理/已忽略」状态流转（删除为硬删，下次扫描可重新报告）。
- 不做自动定时扫描（仅手动触发）。
- 不做扫描历史的多版本并排对比与 diff 视图（数据已保留，UI 后续可补）。
- 不做样式/交互问题的真实浏览器渲染核验（agent 运行时不带浏览器），仅依据代码结构与组件树推断并提示核对。

## 3. 设计原则

复用后端已成熟的「只读 + 严格 JSON 输出」agent 运行套路：

- `orchestration.go` 的 `runIndependentReview`（约 L1226）示范了如何跑一次**只读**（Claude `plan` / Codex `read_only`）agent、给它一个「不要改文件、只输出 JSON」的 prompt、用 sink 收集助手文本并 `json.Unmarshal` 成结构化结果。
- `agent_target_env.go` 的 `resolveAgentTargetEnv` / `agentClaudeRunnerFor` / `codexRunnerFor` 负责按「项目所在环境（Windows / WSL / SSH）+ 默认 AI」选中正确的 runner。

本项目照此链路做「项目体检」，扫描结果落库、由前端轮询展示。全程只读、不改项目文件、不产生会话记录。

## 4. 两条规则如何实现

### 4.1 规则 1（不重复）——「提示清单 + DB 唯一指纹」双层防重

- **提示层**：后端将本项目「历史已报告过的建议清单」（`title` + `summary` 文本）以及当前 git `HEAD`（`repo_sha`）喂给发现 agent，要求它对已报告过、或经核对项目当前已具备/已实现的，一律不得再报。
- **兜底层**：落库时对每条发现计算规范化**指纹**（`fingerprint`，`title+summary` 做小写/去空白/去标点归一化），并用 `UNIQUE(project_id, fingerprint)` 唯一索引 + `INSERT ... ON CONFLICT DO NOTHING` 保证同一指纹绝不重复入库。
- 前端在扫描完成时提示「本次已忽略 N 条此前报告过的建议」。

当前假设：短语/措辞略异但实为同一项的，以 DB 唯一指纹为准判定重复；跨扫描认为「同指纹 = 重复」。若将来需要更语义化的去重，可扩展为 `文件SHA + 问题类型` 指纹（列为后续增强）。

> **转任务后的去重规则（2026-11-11 更新）**：转任务仍硬删建议，不把任务创建视为问题已解决。扫描发布时检查本项目同来源指纹的未完成任务，有则计入重复而不新增卡片；任务完成或取消后可重新发现仍存在的问题。历史语义匹配还会核对建议/任务是否仍存在且内容未变化，避免使用过期引用抑制新发现。见 §11。

### 4.2 规则 2（必须核实）——「两趟式扫描：发现 → 独立核实」

- **Pass A（发现）**：只读 agent 广撒网通读项目，产出候选发现清单（允许略为过度收集）。
- **Pass B（独立核实）**：把候选清单交给第二次只读 agent，对**每一条**逐项到项目里查证是否确实存在（读取相关文件/结构）。只有 `confirmed:true` 的进入落库；存疑/无法证实的标 `rejected`（附原因）并丢弃。

两趟式与既有 `runIndependentReview`「独立二审」的思路一致。代价是两次 agent 调用（更耗 token、更慢），因扫描为手动触发且用户知情，可接受；成本通过「候选数 ≤ 30 + 核实 Pass B 只查证候选而非全文重扫」收敛。

## 5. 后端设计

### 5.1 数据模型（`apps/control-server/internal/app/app.go` 迁移）

在 `migrate()` 大 heredoc（约 L1078-1095）追加**三张表**（**一份扫描行 + 每条发现一行 + 每条进度事件一行**，而非把 findings 塞进一个 JSON 字段——便于跨扫描去重、按 type/status 查询、以及后续 diff；进度事件独立成表以便按 seq 增量追加与持久化）：

```sql
create table if not exists project_insight_scans (
  id text primary key,
  project_id text not null references projects(id) on delete cascade,
  status text not null default 'running',      -- running|completed|failed|cancelled
  error text not null default '',
  agent text not null default 'claude-code',   -- 本次扫描用了 claude/codex
  repo_sha text not null default '',           -- 扫描时项目 HEAD（非 git 项目为空），规则 1/2 的上下文指纹
  findings_count integer not null default 0,   -- 本次实际入库的发现数（confirmed 且未重复）
  suppressed_count integer not null default 0, -- 本次因重复（规则 1）被忽略的条数，持久化供完成态展示
  created_at datetime not null,
  started_at datetime, completed_at datetime
);
create index if not exists project_insight_scans_project on project_insight_scans(project_id, created_at desc);

create table if not exists project_insights (
  id text primary key,
  project_id text not null references projects(id) on delete cascade,
  scan_id text not null references project_insight_scans(id) on delete cascade,
  type text not null,                          -- bug|style|optimization|feature|cleanup
  severity text not null default 'normal',     -- low|normal|high
  title text not null,                         -- 用户可读的一句话标题
  summary text not null,                       -- 用户可读的两三句说明
  file_hint text not null default '',          -- 尽力而为的单个文件路径，可为空，仅展示
  fingerprint text not null default '',        -- 规范化去重指纹（规则 1）
  status text not null default 'open',
  created_at datetime not null, updated_at datetime not null
);
create index if not exists project_insights_project on project_insights(project_id, status);
create index if not exists project_insights_scan on project_insights(scan_id);
create unique index if not exists project_insights_project_fingerprint on project_insights(project_id, fingerprint);
```

### 5.2 新文件 `apps/control-server/internal/app/insights.go`

**类型与常量**：`InsightScan` / `InsightFinding` / `insightsResponse{ Scan, Findings, HasScan, SuppressedCount, OpenCount }`；五类 type 常量 `bug | style | optimization | feature | cleanup`；严重度 `low | normal | high`。`OpenCount` 为当前仍有效的建议条数。

**新增 Server 字段**（并发/生命周期，仿 orchestration 的 `orchestrationMu/orchestrationActive/orchestrationWG`）：`insightMu sync.Mutex`、`insightActive map[string]bool`、`insightCancels map[string]context.CancelFunc`、`insightWG sync.WaitGroup`；初始化处（app.go ~L522 的 `&Server{...}`）补齐这些字段。两个 map 的键都是 `insightRunKey(projectID, kind)`——**互斥按「项目 × 种类」**而非只按项目（见 §5.5 的并发说明），`kind` 取 `insightRunScan` / `insightRunVerify`。登记/释放统一走 `beginInsightRun`。

**新增方法 `projectRuntimeProfile(ctx, project, agentID) (*AgentRuntimeProfile, error)`**：兑现「随项目默认」取舍——若 `project.DefaultProfileID` 非空则照 `startMessage`（app.go:3529-3535）用 `runtimeProfileTx`（agent_profiles.go:925）解析，否则返回 nil（退化 CLI 默认）。claude 与 codex 的 runner 都消费 `AgentRunRequest.Profile`（claude_runner.go:395 / codex_runner.go:259）。

**公共小助手 `runReadOnlyAgent(ctx, project, agentID, prompt) (string, error)`**：封装「选 runner → 解析项目默认档案 → sink → 超时 → `runner.Run` → 收集文本」，供 Pass A / Pass B 复用（仿 `runIndependentReview` L1257）：

```go
// 选 runner 与 startMessage（app.go:3556）同一语义：SSH 走 runnerRegistry、本机按
// 目标环境；agentClaudeRunnerFor/codexRunnerFor 对 remote 返回 nil，故兜底 s.runner。
var runner AgentRunner
policy := "plan"
isSSH := strings.HasPrefix(project.Runner, "ssh-")
target := s.resolveAgentTargetEnv(project.Runner, project.Path)
if isSSH {
  r, ok := s.runnerRegistry.get(project.Runner)
  if !ok { return "", fmt.Errorf("SSH 连接不可用") }
  runner = r
  if agentID == "codex" { policy = "read_only" }
} else {
  if agentID == "codex" { runner = s.codexRunnerFor(target); policy = "read_only" }
  else                  { runner = s.agentClaudeRunnerFor(target) }
  if runner == nil { runner = s.runner }
  if runner == nil { return "", fmt.Errorf("没有可用的分析运行器") }
}

profile, err := s.projectRuntimeProfile(ctx, project, agentID)
if err != nil { return "", fmt.Errorf("resolve project default profile: %w", err) }

sink := &orchestrationReviewSink{}
scanCtx, cancel := context.WithTimeout(ctx, 20*time.Minute)
defer cancel()
if err := runner.Run(scanCtx, AgentRunRequest{
  SessionID: uuid.NewString(), ProjectPath: project.Path,
  Prompt: prompt, PermissionMode: policy, RunID: uuid.NewString(),
  AgentID: agentID, Profile: profile,   // Profile 可为 nil，退化为 CLI 裸默认
  // 关键（只读执行，见上方说明）：claude 用 default + 只放行只读工具，prompt 走 stdin。
  // codex 走其自身 read_only sandbox，不设这两项。
  SkipSessionID:  agentID == "claude-code",
  ReadOnlyTools:  insightReadOnlyTools(agentID), // 仅 claude：["Read","Glob","Grep","List",...]
  PromptViaStdin: agentID == "claude-code",
}, sink); err != nil {
  return "", err
}
return strings.TrimSpace(sink.text.String()), nil
```

> **为何这里不直接用 `plan`**：`--permission-mode plan` 是 Claude Code 里唯一内置"只读"模式，但**实机验证**它只会产出"计划叙述"、从不执行并返回 JSON；而 `manual/dontAsk` 等可执行模式会 headless 挂起等审批。**正确姿势**（真机踩通）：走 `--permission-mode default` + `--allowedTools "Read Glob Grep List"`（仅放行只读工具）——agent 能真正执行（读、搜、结论）却**物理上无法修改任何文件**，且只读工具无需审批不会挂起；配合"你的整个回复只能是那个 JSON 数组"的强结构 prompt，能稳定返回单一 JSON 数组。本功能走的是**原始 `runner.Run`**（`Run` 的只读执行 + `PromptViaStdin` 把 prompt 写 stdin，见 claude_runner.go 的 `ReadOnlyTools`/`PromptViaStdin`），绕开了 HTTP 会话层的 `validAgentPolicy`。**不要**把 `plan` 传给 create-conversation/create-message 之类的 HTTP 端点——那里会被 `validAgentPolicy` 拒绝。

**扫描执行 `runProjectInsightScan(ctx, projectID)`**：

1. 取项目 `Project`；查当前会话 `select agent_id from conversations where project_id=? and is_current=true`（无则 `claude-code`）。据此决定两趟用 `claude`（`plan`）还是 `codex`（`read_only`）。
2. 读取本项目「历史已报告指纹集合」`alreadySeen`（供去重与 prompt 提示）；计算 `repo_sha`（`gitOutput(ctx, project.Path, "rev-parse", "HEAD")`，非 git / 出错取空串，需 error 兜底）。
3. **Pass A（发现）**：`textA, err := s.runReadOnlyAgent(ctx, project, agentID, buildInsightScanPrompt(repoSHA, alreadySurfaced))` → `json.Unmarshal(textA, &[]pendingInsight)`。模型常在通读项目后把最终 JSON 数组留到回合末尾、却在输出前 `end_turn`（实测：全程 0 个 `"type"` 键，只给散文/字符串数组残片）——此时用一条强约束的修正 prompt（`buildInsightRepairPrompt`，明确"整段回复必须且仅是 JSON 数组、别再重新通读、宁缺毋滥但必须给数组"）**重试一次**；仍失败才判 `failed`。
4. **Pass B（核实）**：`textB, err := s.runReadOnlyAgent(ctx, project, agentID, buildVerifyPrompt(candidates))` → 仅取 `confirmed:true` 的进入落库。与 Pass A 同因，解析失败也用修正 prompt（`buildVerifyRepairPrompt`）重试一次（`runInsightVerify` 封装）；agent 进程本身运行失败则不重试，直接判 `failed`。核实结果解码后用 `validateInsightVerdict` **强制完整性**：必须对全部候选逐一判定（漏判 / 越界 / 重复 index 都视为无效），否则重试仍无效时判 `failed`——不再把「未覆盖候选」当作已确认落库。
5. 归一化：type 钳四枚举、丢空 title、数量钳 ≤50。
6. 落库（规则 1 兜底）：逐条算 `fingerprint`，批量 `INSERT ... ON CONFLICT(project_id, fingerprint) DO NOTHING`；累加本次「被跳过（重复）的条数」`suppressed`。
7. 单事务更新 scan 行：`findings_count=实际入库数`、`suppressed_count=suppressed`、`status='completed'`、`completed_at`、`repo_sha`。任一 pass 的 runner 运行失败、或重试后仍解析失败 → scan 置 `failed` 并写友好错误（不 panic、不留半截数据）。

**扫描 prompt**（`buildInsightScanPrompt`，以 runIndependentReview L1239 为模板）：

- 你是项目主动分析顾问，**不要修改任何文件**，只读 + 只输出一段 JSON。
- 通读项目找五类发现：`bug` / `style`（用户可见样式问题，示例「某卡片过大挤压了其它元素」）/ `optimization` / `feature` / `cleanup`（无用文件、目录、构建产物、重复资源、不可达代码或死逻辑；必须要求人工确认后再清理）。
- 每条 `{"type","title","summary","severity","fileHint?"}`；**title/summary 必须用户可读，不得出现代码标识符、行号、堆栈**。
- **规则 1**：下方给出「前几批已报告过的建议清单」，凡已在清单里、或经核对项目当前已具备/已实现的，一律不得再报。
- **规则 2**：每条都必须先在项目里核实确有其事才能报；拿不准的不要报。
- 最多 30 条、宁缺毋滥；看不到运行时浏览器，样式问题依据结构与组件树推断并注明「建议核对实际渲染」。

### 5.3 路由与列表（`routes()`，`apps/control-server/internal/app/app.go` 任务块附近）

- `POST /api/projects/{projectID}/insights/scan` → `triggerInsightScan`：已有 `running` 扫描 → `409`；否则插入 `running` 扫描行并启动**单（项目 × 种类）互斥**的后台 goroutine（用 §5.2 新增的 `insightMu/insightActive/insightWG` 单飞，仿 `kickProjectOrchestrator`），返回 `202` + 扫描行。复核是另一种类，不在此互斥范围内。
- `GET /api/projects/{projectID}/insights` → `listInsights`：查本项目**最新**一条 scan（`order by created_at desc limit 1`）+ 本项目**当前仍有效的建议全集**（`project_id` 全量、severity 排序）。后者取全集而非只看最新一次扫描，是因为规则 1 让发现跨扫描**去重累积**——若只取最新一次扫描，仅命中重复的新扫描会让既有建议从视图消失。`suppressedCount` 取自最新 scan 行落库的 `suppressed_count`（完成态持久化，即使进程重启后仍能正确展示）。
- `DELETE /api/projects/{projectID}/insights/{findingID}` → `deleteInsightFinding`：硬删该发现行（含指纹），下次扫描可重新报告。无软删/已忽略状态。
- `PATCH /api/projects/{projectID}/insights/{findingID}` → `updateInsightFinding`：可编辑 `title` / `summary` / `severity`，编辑后重算指纹。
- `POST /api/projects/{projectID}/insights/delete` → `deleteInsightFindings`：**批量硬删**。body 二选一：`{"findingIds":[...]}` 删指定若干条（跨项目 / 已不存在的自动忽略，只计入 `skipped`），或 `{"scope":"open|invalidated|dismissed|all"}` 按范围删；**两者都不给一律 400** —— 批量硬删不可恢复，"缺省即全部"这种便利只留给「添加到任务」那类可追溯、能从任务板找回的动作。返回 `{deleted, skipped}`。`scope` 的三个谓词与 `listInsights` 的三条列表查询逐字对齐，所以「全部删除」删掉的就是汇总行「共 N 条有效建议」所指的那些；列表截断（> `insightFindingsListLimit`）时也能一次删干净，而不是只删看得见的部分。只动 `project_insights`，由建议转成的任务不受影响（"不想再看这条建议" ≠ "撤销已下发的任务"）。
  - **显式 ids 那一支的多个批次包在同一个事务里**（分批只为绕开 SQLite 变量数上限）。不包事务时第 2 批失败会留下"第 1 批已删 + 响应说失败"的半成品，而前端保留整份选择集让人重试 —— 重试后那半批只能记进 `skipped`，看起来像"这些建议本来就不在"。包事务后要么全删、要么全不删，`删除失败，请重试` 与前端"保留选择集可重试"才是配套的真话。
  - 端点本身不做「复核进行中」的拦截（那是前端的闸门，见 §6.7）：范围内既有 `pending` 的建议也会被删，复核 worker 之后的写回对已删行是 0 行的 no-op，复核记录照常跑完。

### 5.3.1 扫描方向（主题 + 类型）

`POST /insights/scan` 接受**可选 body** `{"theme":"security|performance|ux|architecture|stability|''","types":["bug","style",...]}`（省略等价于原全量扫描）。两值归一化后写入 scan 行（`theme`、`focus_types` 逗号串），并作用于 Pass A 的 prompt：

- **类型**：非空 → prompt 只让 agent 报这些类型；空/全选 → 仍覆盖全部五类。
- **主题**：非空 → prompt 追加「请从『安全』的视角审视项目」；空 → 不写。

方向只影响「本次扫描查什么」，**不影响规则 1 的去重**——去重指纹仍锚定 `project_id + fingerprint`，同一问题换主题/类型再扫仍会被忽略。主题/类型仅在 `project_insight_scans` 存两列只读展示，`project_insights` 与 `InsightFinding` 无 schema 变化。列用 `ensureColumn`（幂等 `pragma_table_info` + `alter table add column`）追加，`create table if not exists` 对已存在表不会补列。

### 5.5 建议再验证（re-verify，迭代补充）

Pass B 只保证「报告当下」候选真实存在；项目可能被**其它任务迭代**修改（bug 已修复、功能已实现），或原分析因上下文限制判断不准。迭代为既有建议卡片新增「再验证」：用户手动发起新一轮只读 AI 核验，确认每条建议在当前代码里是否仍然成立，再决定是否继续处理（添加到任务等）。

- **数据模型**：`project_insights` 追加三列（`ensureColumn` 幂等补列）：
  - `verification_result text not null default ''` —— `''`(未验证) | `pending`(验证中) | `valid`(仍存在) | `invalid`(已失效) | `failed`(验证失败，可重试)
  - `verification_note text not null default ''` —— AI 判断依据（或失败原因）
  - `verified_at datetime` —— 最近一次验证时间
  - 启动迁移把残留 `pending` 重置为 `''`（进程重启即中止，避免前端永久轮询"验证中"）。
- **端点**：`POST /api/projects/{id}/insights/verify`，body 可选 `{"findingIds":[...]}`（缺省 = 全部有效建议，`invalid` 不参与）。互斥按「项目 × 种类」：只有该项目**已有复核在跑**时才返回 409，扫描同时进行不受影响（同一项目上两条只读流水线互不干扰；两个复核才会争同一批建议的 pending 判定）。先把目标置 `pending` 并返回 202，后台 goroutine 跑一趟只读 agent 逐条判断。
- **并发下的凭据排队**：扫描与复核共用同一份凭据，而每趟 agent 调用都要过凭据额度组的并发准入（默认私有额度组 `max_concurrency=1`）。因此扫描 Pass A 正在跑时，复核的第一次调用会被拒——`reserveInsightQuotaWithWait` 在这种情况下**有界排队**（`insightQuotaWaitMax = 2min`，且被本次运行剩余预算夹住；重试间隔 `insightQuotaPollInterval = 1s`）而不是立即失败，排队期间通过 `progress` 明说在等（面板上显示「凭据额度暂时不可用，正在排队等待其他分析让出…」），超时则给出可读中文原因。`quotaWait=0`（冲突解法这类交互式调用）保持"要么马上给结果、要么明确失败"。
- **prompt**：`buildVerifyExistingPrompt` 把每条既有建议（含 id）交给 agent，输出契约与 Pass B 一致：`{"findings":[{"id":"...","exists":true,"reason":"..."}]}`；解析失败用强约束修正 prompt 重试一次（`buildVerifyExistingRepairPrompt`）。
- **结果写回**：`exists:true → valid`（保留在有效列表）、`exists:false → invalid`（从有效列表隐藏，进 `insightsResponse.Invalidated` 折叠展示含 AI 依据）、agent 遗漏条目或 runner 运行失败/输出非法 → `failed`（保留在有效列表，卡片提示可重试）。绝不把用户请求验证的建议静默留在 pending。
- **编辑联动**：`PATCH` 编辑建议会重置验证状态（内容已变，上一轮验证失效）。

### 6.7 卡片操作（添加到任务 / 编辑 / 删除）

后续迭代（commit `a3e161f`）为卡片新增了三个操作，打破最初的「纯展示」取舍：

- **添加到任务**（`POST /api/projects/{projectID}/insights/{findingID}/to-task`，handler `addInsightToTask`）：把该建议转成任务（标题=建议标题、说明=`buildInsightTaskDescription` 拼出的可执行提示词、优先级按严重度映射），并在同一事务内**硬删**该建议，使其从建议列表消失。优化建议必须转成任务后经任务下发执行，不能直接发送到对话。

  > 转任务仍硬删建议；未完成任务暂时抑制对应的新发现，任务完成或取消后可再次发现未解决的问题。不会写入永久抑制指纹，见 §11。
- **全部添加为任务**（`POST /api/projects/{projectID}/insights/to-task`，handler `addInsightToTasks`）：汇总行「全部添加为任务」按钮一键把当前全部有效建议转成任务。因批量转换会一次硬删全部建议、误触成本高，前端先弹确认框（展示当前有效条数），确认后逐条复用 `convertInsightToTask`（单条独立事务，一条失败不影响其余），返回 `{created, skipped, failed, tasks}`。语义：已失效（`invalid`）的建议不参与（单独折叠展示）；复核中（`pending`）的建议计入 `skipped` 跳过（由转换事务内的 `delete ... verification_result<>'pending' and <>'invalid'` 防护判定，避免为未定论/刚被复核判失效的问题建任务）；跨项目/不存在的显式 id 忽略。与逐条按钮一致，转成的任务会**硬删**对应建议。
- 手机 `insights.toTask` RPC 共用批量转换逻辑，但只返回 `{created, skipped, failed}`，避免完整任务正文超过中继帧容量；任务完整保存在目标电脑，桌面 REST 仍返回 `tasks`。
- **编辑**（`PATCH /api/projects/{projectID}/insights/{findingID}`，handler `updateInsightFinding`）：可编辑 `title` / `summary` / `type` / `severity` / `evidence` / `acceptanceCriteria`，编辑后重算指纹。
- **删除**（`DELETE /api/projects/{projectID}/insights/{findingID}`，handler `deleteInsightFinding`）：**硬删**该行（含指纹）。下次扫描时该问题因指纹不存在可被重新报告。不做软删/已忽略状态。
- **批量删除 / 全部删除**（`POST /api/projects/{projectID}/insights/delete`，handler `deleteInsightFindings`）：汇总行的「多选」开关进入选择模式，列表上方出现选择条（全选 / 范围说明 / 已选 N 条 / **删除选中** / **全部删除**）。
  - 选择集是一份**跨「有效 / 已失效 / 已忽略」三个列表共用**的 id 集合（折叠区里那堆「已忽略」也要能一次清掉）。卡片首行的复选框与类型徽标**同一行**——另起一行会让每张卡凭空长高一行（任务看板批量管理踩过同一个坑）；整卡可点，但**控件优先**（`isCardControl` 按"最近的可交互祖先"判定，点「编辑」「查看文件」不会顺带勾上这张卡）。复选框是原生 `input`，可 Tab 到、可用空格切换；整卡点击只是鼠标的顺路。
  - 「全选」只作用于**当前筛选下的可见列表**，并在提示里写明范围（`data-scope="filtered"` + 类型名与条数），避免"静默把选择范围改小"；已全选时按钮文案与可访问名一起改口为「取消全选 / 取消选择当前列表」。
  - 选择集在**每次刷新后按当前三个列表收敛**（`pruneInsightSelection`，2 秒轮询下没变化就返回原引用，不白重渲染）；切项目与退出多选都会清空它。
  - 两条删除路径各有确认框：「删除选中 (N)」发 `findingIds`，「全部删除」发 `scope: "open"`（**不是**把当前看到的 id 全发过去 —— 截断时那样删不干净）。确认框写明条数（真实总数，见 §10.9）、不可恢复、"其中 N 条来自折叠区"，截断与扫描进行中各补一句说明。两条都是硬删，语义与单条「删除」一致：指纹一起消失，下次扫描该问题可能重新出现（还没修好的话）。
  - **复核进行中不给「全部删除」**（与「全部添加为任务」在扫描进行中的待遇一致）：复核 worker 已按批次把建议送给 agent，删掉它们既停不下来也已经花掉，进度条还会继续数到 N（用户看到"复核 300/500"而列表是空的）。禁用原因写在 `title` 里并给出出路（先点复核进度块上的「停止」）。「删除选中」不受这条限制 —— 它与逐张点卡片「删除」等价，本来就是允许的。
  - 「删除选中」在确认框**开着**期间若选择集被轮询清空（选中的建议被别处删光），会收起确认框并提示"选中的建议已不在列表里，无需删除"，而不是留一个点确认什么也不发生的"删除 0 条"框。失败时保留选择集 + 留在屏上，理由写在该分支的注释里（后端整批一个事务）。
- `insights.css`：复用 `conversation.css` / `tasks.css` 的视觉 token（绿强调 `#2c7567`/`#e4f3ea`、中性边框、`priority-*` 式严重度 chip、`task-item` 卡片风格）。

### 6.9 建议再验证前端（re-verify）

- **汇总行**：新增「验证全部」主行动按钮（调 `POST /insights/verify` 空 `findingIds` = 全部有效建议）+「已失效 N 条」折叠开关。
- **卡片**：新增「验证 / 重新验证」动作按钮与验证状态徽章——未验证（不渲染）、验证中（旋转点 +「验证中…」）、已复核·仍存在（绿，附验证时间）、验证失败（红，可重试）；AI 判断依据（`verification_note`）以虚线框展示在卡片正文下。
- **异步轮询**：验证异步执行（后端先置 `pending` 再后台跑 agent）。前端 POST 后乐观显示「验证中…」，轮询条件扩展为「扫描 running **或** 任一建议 `pending`」，2s 一拉把 `valid/invalid/failed` 带回。
- **与扫描并行**：复核不再被进行中的扫描挡住（后端按「项目 × 种类」互斥）。面板相应放开三处：「验证全部」不再因 `scan.status==="running"` 禁用；「开始分析」不再因复核进行中禁用；**扫描进行中也照常渲染既有建议列表**（否则卡片上的「验证」入口在扫描期间根本够不着）。复核进度块也改为扫描进行中一并显示。扫描与复核各自的「停止」按钮只停自己那种（带 `kind` 调 `POST /insights/cancel`）。
- **已失效折叠区**：`invalidated` 建议以低调置灰卡片折叠展示，含「失效原因」与「重新验证 / 删除」动作；重新验证若判 `valid` 则回到有效列表。
- **状态机（勿改）**：已失效（`invalid`）是 AI 确认过的终局判定。对已失效建议再验证时，**只有 `valid` 判定才允许它复活进有效列表**；`invalid`/`uncertain`/agent 运行失败一律保持失效（写回 `invalid`），不得因复验失败落到 `failed` 而误入有效列表。`runInsightFindingsVerifyRun` 的 `failAll` 与最终写回均已实现该规则。
- **生命周期（勿改）**：运行中的扫描/复核按**（项目 × 种类）**记录可取消句柄（`Server.insightCancels`，键为 `insightRunKey(projectID, kind)`，受 `insightMu` 保护）。删除项目时 `deleteProjectLocked` 会 `cancelInsightRun(projectID)`（取消该项目下所有种类），让 goroutine 随 ctx 取消中止 agent 运行，避免删除后 agent 继续跑无用功；goroutine 自行清理 `insightActive`。`POST /insights/cancel` 支持可选 body `{"kind":"scan"|"verify"}` 只停一种（面板上扫描与复核各有自己的「停止」），空 body 等价于全停，保持旧客户端语义。

## 8. 关键风险与取舍

- **扫描耗时分钟级（且规则 2 多一趟）**：异步 + 轮询 + `context.WithTimeout(20m)`；runner 自带空闲超时会终止卡死 agent。前端提示时长写「几分钟」。
- **规则 2 的 token/耗时成本**：两次 agent 调用。靠手动触发（用户知情）+ 核实 Pass B 只查证候选收敛成本。
- **规则 1 的指纹语义局限**：文本归一化对「同问题换措辞」场景可能漏网（判为新指纹）。第一版接受；如需更稳可扩为 `fileSha+类型` 指纹（后续增强）。重复判定始终以 DB 唯一索引为准，不受 AI 措辞漂移影响。
- **WSL/SSH 环境差异**：选 runner 与 `startMessage` 同语义——**SSH 走 `runnerRegistry.get(project.Runner)`**，本机(WSL/Windows)按 `resolveAgentTargetEnv` + `agentClaudeRunnerFor / codexRunnerFor`（这两者**对 remote 返回 nil，故兜底 `s.runner`**）。`ProjectPath: project.Path` 交由对应 runner 处理（含远程路径）。远程 runner 缺失时扫描置 failed，不 panic。
- **服务关闭时仍有扫描在跑**：`triggerInsightScan` 在 `s.closing` 置位后拒绝新扫描；`insightWG` 的 `Done()` 在**扫描 goroutine 内**调用（非 HTTP handler 返回即 Done），`Close()` 先取 `insightMu` 再 `insightWG.Wait()`，与 Add(1) 建立次序，准确等待在卷扫描结束。`runtimeCtx` 取消会使 agent 中止、扫描快速收敛，不会长时间阻塞关闭。
- **扫描被打断后项目被锁**：若进程在扫描中途退出/崩溃，残留的 `running` 扫描行会让该项目的 start 永久 `409`。启动时 `migrate()` 会把所有残留 `running` 行置为 `failed`（"分析被中断，请重新发起"），保证重启后即可重新分析。
- **只读但 agent 想改文件**：`read_only` / `plan` 权限模式 + prompt 硬性「不得改文件」；Claude `plan` 模式按设计拒绝写入。
- **JSON 不健壮**：`extractInsightJSON` 剥 Markdown 围栏、取最后一个合法 JSON，再 `unmarshal`；容忍 `{findings:[...]}` 包裹。模型若在输出 array/object 前 `end_turn`（只给散文/字符串数组残片），Pass A / Pass B 会各自用强约束修正 prompt **重试一次**；重试后仍失败才置 scan `failed` 不崩溃。
- **刷屏 / 低价值**：prompt「最多 30 条、宁缺毋滥」+ 服务端数量钳 ≤50 + 空 title 丢弃；规则 1/2 进一步压低噪声。
- **烧 token**：手动触发（已拍板），用户点击「开始分析」即同意成本。

## 10. 修复轮（本文件之后的一次集中修复）

以下改动修正了初版实现里的若干问题。上文中与此冲突的表述以本节为准。

### 10.1 扫描不再长时间独占项目工作区

初版从 `triggerInsightScan` 到扫描结束**全程持有**项目工作区租约（key = 项目 id）。其后果是：点一次分析，此后十几分钟到一小时内，该项目的会话运行 / Git / 文件 / 终端操作全部 409（`isolated worktree` 的会话用另一个 key，不受影响）。对一个**只读**分析来说代价过高。

改为**准入检查 + 收口互斥**：

- 启动时做一次检查（拿得到就立刻释放）。若此刻项目正被别的任务改写，直接 409 让用户稍后再来——否则结论几乎必然在落库时被判作废，不如不让用户白等。
- 分析全程**不持有**租约，用户可以在分析期间正常使用项目。
- 真正的互斥只发生在"最终版本复核 + 写库"这一小段：`publishInsightResult` 内部取租约（`acquireWorkspaceWait`，上限 `insightPublishLeaseWait = 2min`，且被本趟运行的剩余预算夹住）→ 复核工作区自扫描开始未被修改 → 执行写库。这样对所有 Milevia 发起的写入仍是原子的，不存在"复核通过后有写入溜进来、结果仍被当成有效"的窗口。
- 代价（有意接受）：工作区一旦变化，本次结果作废并如实告知用户"项目代码在分析中发生变化，已丢弃本轮结果，请重新发起"。初版也是这么提示的，但那时它几乎只可能因外部（非 Milevia）修改而触发；现在用户自己在分析期间改动项目也会触发。这是"分析期间项目可用"换来的。

复核（re-verify）同样是准入检查 + 逐批收口。

### 10.2 扫描/复核增加总预算

> ⚠️ **2026-09-26 变更：扫描的限时已按用户要求关闭。** 实测生产 prompt 跑一个中等项目，
> 单趟 Pass A 就要 17.7 分钟（贴着本节的 20min 单趟上限，余量不足 12%），于是
> `insightScanPassTimeout` 与 `insightScanRunTimeout` **均改为 0 = 不限时**（0 走
> `beginInsightRun` 既有的 `if timeout > 0` 分支，不派生 deadline）。连带两处要注意：
> ① `insightPublishLeaseWait` / `insightQuotaWaitMax` 的"被总预算夹住"是
> `if deadline, ok := ctx.Deadline(); ok` —— 无 deadline 时跳过夹取、回落到各自的 2 分钟，
> 不会退化成 0；② **复核不受影响**，它仍受下面的 `insightVerifyRunTimeout` 约束。
> 不限时后挂死的兜底从定时器改为用户在界面取消（运行登记与 `insightCancels` 保留）。
> 本节下面的文字保留为当时的决策记录。

`insightScanPassTimeout`（20min）是**每趟**的上限。最坏情况 Pass A 重试 + Pass B 两批各重试 = 6 趟，没有总预算就会拖到 2 小时。新增：

- `insightScanRunTimeout = 45min`：整趟扫描的总预算（`triggerInsightScan` 的 `runCtx` 即带此 deadline）。取值口径是"必须宽于成功扫描的合理最坏情况"——预算落在合法慢扫描的耗时区间里，它自己就成了失败来源（跑满 30 分钟再把结果全丢掉是最差组合）。扫描期间不持有工作区租约，所以放宽它不会让任何项目的占用时间变长，代价只是更长时间窗口内工作区可能被改动、结果被判作废。
- `insightVerifyRunTimeout`：30min → **45min**。因为复核现在是**按批独立发布**（见 10.3），总预算触顶只影响尚未跑完的尾批，已发布的批次不受影响，所以可以放宽到与"最长单趟 × 常见批数"匹配。
- 超时文案区分"单趟跑满 20 分钟"与"整趟总预算用尽"（`runReadOnlyAgent` 里按父 ctx 是否也已结束判定）：前者建议换更快的模型档案，后者建议缩小分析范围。两者混为一谈会让用户按错误的方向重试。

### 10.3 复核改为按批独立发布（原来是全有或全无）

初版把所有批次的结果先收集、最后一次性发布，任何一批失败都会把**此前已成功的批次一起作废**——用户付了费却什么都拿不到。

现在每批跑完就立刻在租约内复核版本并落库：

- 某批自身失败（agent 报错 / 输出不合契约）→ 只标记该批为可重试的失败，**继续跑后续批次**。
- 整趟被取消/超时 → 中止剩余批次（它们各自都是独立的 agent 调用，继续跑没有意义），已发布的批次保留。
- 工作区在批次之间发生变化 → 中止剩余批次并保留已发布结论，提示用户重新验证。

版本一致性仍然成立：每批发布前都确认工作区自本轮复核开始起未被修改，因此所有已发布的结论都针对同一个版本。

终态：全部批次成功 → `completed`；有批次失败 → `failed`，message 写明"N/M 批成功，K 批失败"；中止 → `failed`/`cancelled` 附原因。

### 10.4 核实剔除的候选现在可见（规则 2 的可审计性）

Pass B 的输出契约一直要求每条给 `reason`，但解码结构体里没有这个字段——**模型给了理由、服务端直接丢掉**，用户只看到一个"确认 8 条有效"的数字，无从知道被剔除的是哪几条、为什么，也就无从发现模型误判。

现在：

- `insightVerifyVerdict` 增加 `Reason`，`runInsightVerify` 返回 `insightVerifyOutcome{Index, Confirmed, Reason}`。
- 被剔除的候选（title + reason，各截断）随 scan 落库到新增列 `project_insight_scans.rejected_json`，并写一条 `warn` 进度事件。
- 前端汇总行出现「核实剔除 N 条」开关，展开可看每条的 AI 依据。

### 10.5 「不再提示」——用户可显式压制一条建议

初版只有两种处置：转任务（硬删）或删除（硬删），两者都会让下次扫描**重新报告**同一问题。也就是说**用户无法让一条噪声/伪需求不再出现**。而 AI 复核出的 `invalid` 也不是静音开关：扫描会把它复活（`on conflict ... where verification_result='invalid'`），且历史清单查询刻意排除了 `invalid` 行。

新增用户侧的显式处置：

- `project_insights.status`：`open` | `dismissed`（`ensureColumn` 补列，默认 `open`）。
- `POST /api/projects/{id}/insights/{findingID}/dismiss` 标记、`DELETE` 恢复。
- 被标记的建议：移出有效列表，进「已忽略 N 条」折叠区（可恢复）；不参与复核与批量转任务；**落库时的复活会被拒绝**（`where ... and project_insights.status<>'dismissed'`），因此后续扫描不再上报它（计入 `suppressed_count`）。
- 与「转任务后硬删」的规则无关、也不冲突：那是"问题可能还没修好，要允许再被发现"，这是"用户已明确表示不需要处理"。

### 10.6 建议 ↔ 任务关联

初版没有记录"任务来自哪条建议"，于是同一条建议可以无限次被转成任务，任务板里也看不出它们同源。

- `tasks.source_insight_fingerprint`（`migrateTasks` 里 `ensureColumn` 补列 + 索引；建议行随即被硬删，只剩这个指纹）。
- `convertInsightToTask` 在事务内先查"同指纹是否已有**未完成任务**"，有则跳过（不建任务、不删建议）。任务进入终态（`done`/`cancelled`）后可再次转换。
- 扫描在发布时也核对本项目的未完成来源任务，跳过已覆盖的新发现；完成或取消后允许重新发现。删除、编辑和显式不再提示仍沿用各自语义。
- 列表接口按指纹关联任务的当前状态，卡片显示「已转为任务 · 进行中」（终态时附「可重新添加」）。

### 10.7 编辑建议后压制旧指纹

编辑会重算指纹，旧指纹随之消失 → 下次扫描可能把**编辑前的原文**当成一条新建议再报一次，与编辑后的卡片并存。

- 新增表 `project_insight_suppressions(project_id, fingerprint, reason, created_at)`。
- `PATCH` 时把旧指纹（`reason='superseded'`）记入；扫描组装去重集合时一并载入。
- 注意这张表只服务于"旧指纹"这类没有对应建议行的压制。用户显式「不再提示」不走它（那条建议本身还要在折叠区展示、还要可恢复）。

### 10.8 PATCH 支持改类型

`insightUpdateRequest` 增加 `type`（白名单归一，非法回退 `optimization`）。模型把 bug 报成 optimization 时用户可就地纠正，不必删掉重报（删掉重报会让同一问题以原类型再次出现）。

### 10.9 列表接口的防护与减负

- **进度事件只在扫描进行中返回**（前端也只在 running 时渲染日志）。此前无论如何都返回，每次进页面都要序列化整份日志（实测 205 条事件 ≈ 28KB）。轮询支持增量拉取，但游标**必须带扫描 id**（`?sinceScan=&sinceSeq=`）：只按 seq 过滤是不安全的——客户端手上的游标可能属于上一次扫描，而新扫描的 seq 从 1 重开，会把新扫描开头的事件永久漏掉。id 不匹配即当作首次拉取返回全量。`GetInsights` 类的 URL 参数无版本协商，改协议时前后端要一起改。
- **建议列表加上限** `insightFindingsListLimit = 500`（有效 / 已失效 / 已忽略各自独立计数），触顶时响应带 `truncated` + `findingsLimit`，前端如实提示"仅显示前 N 条"。排序改为严重度优先、同级取**较新**者，使触顶时丢掉的是"较旧的次要建议"而不是任意条目。
- **`openCount` 取真实总数，不跟着列表截断走**：它是汇总行「共 N 条有效建议」与三个"全部…"动作（验证 / 添加为任务 / 删除）确认框上的数字，而那三个动作在后端都是**全量**执行（`resolveVerifyTargets` / `resolveToTaskTargets` / `scope=open` 都没有 limit）。报截断上限（500）而实际处理 800，就是让用户在按下不可逆按钮之前读到一个假数字。列表仍然截到 `insightFindingsListLimit`，由 `truncated` + `findingsLimit` 单独提示；前端提示里**两个数字都写出来**（共 N 条 / 仅显示最近 M 条），并说明「全部…」作用于全部 N 条。
- **历史清单带上限** `insightHistoryPromptLimit = 100`（并按创建时间取最近的），避免 prompt 随项目历史无限膨胀；去重指纹集合仍来自全部历史行（含已忽略），最终仍由 DB 唯一索引兜底。
- 传给发现 agent 的历史条目从"只有 title"改为 `insightSurfacedLine`（title —— 摘要截断 80 字）：只给标题时模型很容易把同一件事换个措辞再报一次。

### 10.10 进度状态实时推送

项目总览卡片的「优化建议分析中」徽标与副标题进度、以及项目页的状态刷新，此前只靠 30s 兜底轮询——因为 `broadcastStateEvent` 从未在优化建议的生命周期里调用过（全库 12 处调用点无一在此）。现在：

- 扫描启动、每条进度事件（`appendInsightEvent`）、复核 run 的每次进度更新（`updateInsightVerificationRun{,Message}`）、复核启动，都广播 `stEvProjects`。进度事件本身已被 sink 节流（同一动作/同类 3s 最多一条），广播频率与进度更新频率一致。

### 10.11 worker 的 panic 兜底

扫描/复核跑在裸 `go func()` 里，`net/http` 的 handler recover 覆盖不到；整个模块此前 **0 处** `recover()`。长生命周期、跨 DB/runner/prompt 解析的代码里一次 panic 会带走整个控制服务（所有项目）。

现在 `runProjectInsightScan` / `runInsightFindingsVerifyRun` 各自 `defer/recover`：记录堆栈 + 把本次运行置为可重试的失败；两个 worker goroutine 外层再加一层兜底。

### 10.12 只读执行的边界加固

`insightReadOnlyDenyTools` 补齐到实机 `claude init` 事件的完整工具列表（新增 `LSP`、`ListAgents` 等），口径明确为"allow 之外一律不可用"，并写明核对方法。同一份 deny 清单也被 orchestration 的独立审查共用（其 allow 为 `Read/Glob/Grep/List/ReadMultiToolInfo`，新增项均不在其内，即同样只读、只是更难绕过）。

> **待办**：CLI 自 2.1 起提供真正的正向白名单 `--tools`（`--tools "Read,Glob,Grep"`），可从根上替代枚举式 deny。未启用的原因是远端（WSL/SSH）侧的 CLI 版本无法在本地核实，贸然加上会让旧版远端直接报错。远端升级后应切换过去。

### 10.13 前端配套

- 查找类型"最后一项不可取消"（`toggleInsightType`）：空数组在后端等价于"全查"，与用户意图相反。
- `fileHint` 变为可点击，跳到文件页并自动打开该文件（`FilesPanel` 新增 `initialPath`/`onInitialPathConsumed`，路径经 sessionStorage 传递，与既有"添加到对话"同一方式）。
- 卡片新增「不再提示」/「恢复」按钮、已转任务标注、已忽略折叠区、核实剔除折叠区、截断提示；编辑表单支持类型。

### 10.14 本轮的测试

- `insights_fix_test.go`（新增 9 例）：分析期间不持有工作区租约、落库时工作区被占用则如实失败、剔除原因落库并在响应中可见、复核某批失败保留已发布批次、不再提示会隐藏且抑制重扫（含恢复）、同指纹已有未完成任务时跳过、卡片带任务标注、编辑后旧指纹被压制、取消扫描不落库。
- `insights_test.go`：`TestListInsightsIncludesProgressEvents` 按新语义改写为 `TestListInsightsReturnsProgressEventsOnlyWhileRunning`（并覆盖 `sinceSeq` 增量）。
- `insights-model.test.ts`：新增 `toggleInsightType` / `maxInsightEventSeq` / `insightLinkedTaskLabel` / `isInsightDismissed` 四组。

### 10.15 复核与扫描可以并行（互斥从「项目」细化为「项目 × 种类」）

初版用一份 `insightActive[projectID]` 同时管扫描与复核，等于给两者上了一把共享锁：一次漫长的初扫进行期间，用户对既有建议发起的复核一律被 409 挡回（反之亦然），而复核恰恰是"扫描还在跑、旧建议想先核一遍"时最想做的事。

改动要点：

1. **占用键加一维**：`insightActive` / `insightCancels` 的键改为 `insightRunKey(projectID, kind)`，`kind` ∈ `insightRunScan` / `insightRunVerify`；登记与释放收敛到 `beginInsightRun`（返回运行上下文 + 一次性 `release`，早退路径与 goroutine 共用）。同类之间仍然互斥：两个扫描会争同一份历史指纹快照与同一条 running 扫描行，两个复核会把同一批建议并发置 `pending` 再互相覆盖判定。
2. **原子性没有放松**：唯一真正需要互斥的"复核版本 + 写库"那段（`publishInsightResult` 的工作区租约 + 版本对账）本就与占用键无关，扫描与复核的落库仍各自串行；单条建议的写入仍有 `updated_at`（内容版本）守卫，扫描落库改写了某条建议的内容时，在途复核对它的判定会被守卫拒绝，不会覆盖新内容。两个运行都不改工作区，各自的版本对账互不干扰。
3. **凭据额度排队**：两条流水线共用凭据，每趟 agent 调用都要过额度组的并发准入（默认私有额度组 `max_concurrency=1`）。扫描 Pass A 在跑时复核的第一次调用必然被拒——若不处理，用户刚发起的复核会立刻变成一堆"验证失败"（还附带一条英文内部错误）。因此新增 `reserveInsightQuotaWithWait`：额度暂时不可用时**有界排队**（`insightQuotaWaitMax = 2min`，被本次运行剩余预算夹住，按 `insightQuotaPollInterval = 1s` 重试），排队期间经 `progress` 明说在等，超时给出可读中文原因（哨兵 `errInsightQuotaWaitTimeout`）。复核按该哨兵**中止整趟**——额度在两分钟内没人让出，后续批次各再等一遍只会让用户多等几倍时间；扫描则直接以它的文案收尾。`quotaWait=0`（冲突解法这类交互式调用）保持立即失败。
4. **取消按种类**：`POST /insights/cancel` 接受可选 `{"kind":"scan"|"verify"}` 只停一种（面板上扫描与复核各有自己的「停止」，两种同时在跑时点一个不该杀掉另一个）；空 body 等价于全停，`cancelInsightRun(projectID)`（项目删除）也是全停。

测试：`TestVerifyInsightFindingsAllowedWhileScanRunning`（扫描占用中发起复核 → 202 且复核真的跑完写回判定）、`TestTriggerInsightScanAllowedWhileVerifying`（反方向 → 202）、`TestCancelInsightScanByKind`（按种类取消 / 未知 kind 400 / 空 body 全停）、`TestReserveInsightQuotaWithWait`（wait=0 立即失败、额度释放后排队成功并已告知在等、等满预算给出可读中文原因）。

### 10.16 复核输出的 id 归位（单字符笔误不再作废整批）

再验证要求模型把候选的 id（36 位随机 UUID）原样回传，服务端靠它把判定挂回建议。**让模型逐字符抄一串高熵随机字符串本身就是个易错动作**，而初版的精确匹配又是"全有或全无"：一处字符之差 → `AI 返回了未知建议` → 整批结论全废。更糟的是契约校验被放在修正重试**之外**——Pass B 的 `validateInsightVerdict` 在 `decode` 闭包内（契约违约会重试），复核却不会，两条路径对同一个契约问题的待遇不一致。

2026-09-28 生产事故即由此而来：18 条建议切成 3 批 × 6 条，第 1 批的输出里 5 条 id 逐字符正确、1 条把 `…-b0f8-…` 抄成 `…-b0b8-…`，该批 6 条建议全部被标"验证失败"；另两批同模型（`deepseek-v4-1-flash`，经中转）零错误——纯随机手滑，不是协议误解。按 6 条/批估，单条 id 抄错率即便只有 1%，也有约 6% 的批次会整批丢结论。

改动要点：

1. **id 归位容忍单字符笔误**（`matchReverifyTargetID`）：归一化（trim + 去包裹引号 + 小写）后逐级放宽——精确 → **唯一**前缀（≥ `reverifyIDMinPrefix = 8` 字符，模型抄了截断的 id）→ **唯一**编辑距离 1（抄错一个字符）。**只认唯一命中**：不唯一时宁可判"未知建议"交给重试，也不猜。猜错会把判定挂到别的建议上，那比整批失败更糟——整批失败用户看得见、可重试，静默错配直接污染建议的有效性结论。随机 UUID 下"一条错 id 同时距离 1 命中另一个目标"的概率约 6×36/16³²，可忽略。
2. **契约校验并进 `decode` 闭包**：与 Pass B 同侧，未知 id / 重复 id / 非法状态 / 缺条目一律触发一次强约束修正重试（`buildInsightReverifyPrompt(..., true)`），重试后仍不可用才判该批失败。agent 进程本身的失败（启动/退出/超时）不在其列——那是环境问题，重试无用。
3. **失败留证**：两种失败都打日志（非法 JSON 打原文片段，契约违约打"模型回传的 id 列表 vs 期望列表"）。此前复核路径一条 raw 都不打，界面只剩"AI 返回了未知建议"七个字，根因只能靠翻 CLI 的 session transcript 才挖得出来。
4. **状态归一化容忍大小写与空白**（`normalizeInsightReverifyStatus`）：schema 的 enum 经中转的上游并不保证被遵守，而 `Valid` / `valid ` 没有任何歧义，不值得为它花一次重试。
5. **prompt**：输出契约示例里的 id 占位符由 `candidate-id` 改为 `<candidate id>`（前者看着像可以直接照抄的字面量），并补一行"id 是 opaque UUID，逐字符复制，不得改写/缩写/补全"；修正重试的说明逐条点名全部违约类型，而非只说"不是合法 JSON"。
6. **错误文案**：`decodeInsightVerifyExisting` 的 `empty/non-json` 改为中文（它会经 `insightRunErrorMessage` 直接出现在卡片上）；重试仍失败时统一为"重试后仍未返回可用结果：…"，覆盖非法 JSON 与契约违约两类。

**不采用的方案**：把复核改成 Pass B 那种 "编号 + index" 协议能从根上消除抄写错误，但会把"响亮的失败"换成"静默错配"——模型把判定挂到错误的建议上时服务端无从察觉。这与本模块"宁可 `uncertain` 也不误判 `invalid`"的取向矛盾，故保留 id 并要求唯一命中。

**代价**：契约违约现在多花一趟 agent 调用。单趟 agent 本身没有时长上限（2026-09-26 起关闭），但整趟复核仍受 `insightVerifyRunTimeout = 45min` 约束（`runInsightFindingsVerifyRun` 的 `verifyCtx`）——重试会占用这份预算，预算用尽时未跑完的批次按"验证超时，未完成部分请重新验证"收尾，已发布的批次不受影响。重试只在该批原本会全废时才发生，对用户表现为该批慢一段，而非丢结论。

测试：`TestMatchReverifyTargetID`（精确/大写/引号/笔误/少抄/多抄/截断前缀/未知/空串）、`TestMatchReverifyTargetIDRejectsAmbiguousPrefix`（前缀命中不唯一必须放弃）、`TestMatchReverifyVerdictRejectsTypoDuplicate`（笔误不得绕过"重复返回同一条建议"）、`TestMatchReverifyVerdictRejectsInvalidStatus`、`TestNormalizeInsightReverifyStatusToleratesCaseAndSpace`、`TestReverifyAcceptsIdTypoWithoutExtraAgentRun`（端到端：笔误归位且不多花 agent 调用）、`TestReverifyRetriesUnknownID`、`TestReverifyUnknownIDAfterRetryMarksFailed`；`TestVerifyInsightFindingMissingResultMarksFailed` 按新语义改为断言"重试一次后仍失败"。


## 11. 持续迭代分析建议方案（2026-11-11）

### 11.1 目标与范围

项目已有大致方向、基础内容和框架后，用户可以反复使用分析建议，发现当前问题、值得投入的优化和符合方向的功能机会，再通过现有任务系统推进项目迭代。

本方案在现有功能上一次补齐分析质量、建议详情和历史防重，不拆分交付。保留五类建议、现有主题、手动触发和“发现 → 独立核实”两轮流程，复用现有任务执行与建议再验证能力。实现与验证结果见 §11.9，三项边界修正的具体规则见 §11.10。

方案不增加目标档案配置、自动调度、无限循环、检查覆盖矩阵存储或新的任务状态系统。项目方向从 README、AGENTS.md 和已有产品/设计文档获取；信息不足时说明假设，不擅自扩大定位。

“持续迭代”指每次基于当前代码重新分析，提供值得推进的新发现；不承诺每次都有新建议，也不以建议数量作为质量目标。没有可靠新发现时，正常返回零条建议。

### 11.2 使用流程

1. 首次使用直接开始分析；项目已有有效建议且代码已变化时，先用“验证全部”复核旧卡片，再开始新一轮分析，避免已解决的建议持续占据列表。两项操作均由用户手动触发，不自动串联。
2. 用户在“优化建议”中选择分析工具、主题和类型，手动开始分析；默认检查全部五类。
3. 发现轮读取项目资料、梳理模块与关键流程，结合历史建议和未完成任务收集候选。
4. 独立核实轮逐条检查候选是否有依据、是否符合方向、是否与已有建议或任务重复，剔除不成立的候选。
5. 用户查看建议摘要，展开依据与验收要点，按价值选择建议转为任务；任务沿用现有下发执行流程。
6. 任务执行后核对验收要点，再按上述流程复核保留的旧卡片、分析当前代码，确认剩余问题及新的优化机会。

转任务会硬删原建议，因此后续检查该问题通过重新扫描完成。创建任务不代表问题已解决；未完成任务覆盖的问题暂不重复报告，任务完成或取消后仍需核对当前代码。

“开始分析”只负责发现新候选，不自动再验证已有卡片，也不保证重新报告原建议。任务终态只是解除任务防重条件，不是“修复已验收”的证明；用户显式忽略和编辑旧文案抑制的影响另见 §11.6、§11.10。

### 11.3 检查范围与输出要求

下表是分析和核实的判断要求，沿用现有五类，不增加分类或持久化覆盖统计。只检查适用于当前项目且属于用户所选类型的内容。

| 检查内容 | 现有分类 | 必要依据与结果要求 |
|---|---|---|
| 功能错误、异常、边界处理、安全与数据一致性 | bug；无明确错误的改进归 optimization | 指出触发条件、预期与实际差异、受影响路径及代码依据 |
| 样式、布局、交互一致性 | style | 指出相关组件与具体影响；实际渲染尚未核对时写明验证方法 |
| 性能与维护成本 | optimization | 说明具体瓶颈或成本、预计收益的依据；未测量时不得给出虚构数据 |
| 无用代码、资源、重复内容、构建产物 | cleanup | 检查静态和动态引用、构建与配置用途，删除前保留人工确认 |
| 文档、测试、配置与工程质量 | optimization 或 bug | 关联实际使用或维护问题；不能仅因缺少某项最佳实践就提出建设要求 |
| 可拓展能力、后续功能与方向建议 | feature | 说明现有用户场景、与项目方向的关系、当前推进价值、已有替代能力与最小范围 |

方向建议需要落到可评估的具体功能或改进，不单独输出泛泛的路线口号。优先报告实际影响大、当前值得做、可以执行和验证的发现；同一根因合并说明，不为每种类型凑数量。

### 11.4 分析和核实规则

- 首轮与格式修正重试共用检查要求：先读取 README、项目规则和相关设计资料，结合技术栈梳理主要模块，检查适用的正确性、边界处理、样式、性能、安全、清理、文档、测试与配置问题。文档等沿用 bug / optimization 分类。
- 新功能需说明用户场景、与当前方向的关系、已有替代能力和最小范围；功能尚未实现不自动等于值得新增。允许没有可靠新发现，不要求每类有结果。
- 静态证据与运行结果严格区分。样式、性能等尚需实际验证的部分写明“待运行验证”及验证方法，不声称执行了测试、浏览器操作或性能测量。清理建议继续要求检查动态引用并在删除前人工确认。
- 初次核实、修正重试和既有建议再验证使用相同的分类判断标准。再验证的模型协议使用 valid / invalid / uncertain；uncertain 对原有效卡片按现有 failed 状态保留并说明“AI 无法确认”，原已失效卡片则保持失效，不新增数据库状态。
- 新扫描每轮最多收集 30 条候选，独立核实按最多 20 条分批。后批携带前批已确认候选，同批漏项修正也携带已保留的确认项；参考最多 30 条、每条不超过 1000 字节，复用原调用。语义判断仍依赖模型，具体规则见 §11.10。

### 11.5 依据和验收要点

- `project_insights` 增加 `evidence`、`acceptance_criteria` 两个默认空串字段，旧数据库自动补列，旧卡片无详情也可使用。
- API / 前端字段为 `evidence`、`acceptanceCriteria`；候选输出包含两者，初次核实的 reason 保存为最终 evidence（旧协议无 reason 时保留候选依据）。每项最多 2000 字。
- 新扫描在进入核实前检查有效类型、非空标题/摘要及保留候选的依据/验收要点；不完整输出与 JSON 错误共用原有的一次修正机会，仍不完整则明确失败。合法空数组和按用户所选类型过滤后的零结果允许完成；旧卡片兼容与用户主动清空不受影响。
- 卡片默认折叠展示“依据与验收要点”，可随建议一起编辑；转任务时将依据和验收要点加入任务说明，再验证保留这些内容。
- 列表按序列化字节数限制返回完整卡片，避免新增详情超过手机中继的 320 KiB 帧预算。有效建议保留数据库真实总数与截断提示，已失效/已忽略列表截断也明确提示；所有批量动作仍以数据库范围为准。进度事件返回有界前缀，后续通过既有 seq 游标继续拉取。

### 11.6 历史与任务防重

- 两轮分析均获得有界的历史建议与未完成任务（各最多 100 条、32 KiB）。历史建议按创建时间倒序；任务优先选建议转出的任务，再按创建时间倒序，手动任务也在候选范围内，但不保证全部传入。任务说明和建议摘要会截断，模型仅能按实际收到的内容判断重复。
- 同一根因和影响范围换措辞或分类仍应按重复核对，不能仅凭文件相同合并，也不能将同一功能方向下尚未覆盖的不同范围一并抑制。
- 核实输出增加 `duplicateOf`：无重复为空，有重复填写提供的 `finding:<id>` / `task:<id>`。服务端只接受参考清单内的引用，非法引用触发一次格式修正；修正仍非法则失败，不静默丢弃候选。
- 对通过核实且进入发布检查的候选，落库事务内再次核对其重复引用的归属、内容与有效状态。引用任务已结束、参考项被删除/编辑或判失效时，不再按该旧引用抑制；用户显式不再提示仍生效。
- 无论模型是否返回重复引用，落库前都查询同来源指纹的未完成任务，覆盖分析期间并发转任务的窗口；任务 done / cancelled 后允许重新发现并处理。
- 转任务仍硬删，不新增永久任务抑制记录；后端转换事务继续防止为同一来源的未完成任务重复建任务，卡片也禁用对应转换按钮。

语义去重依赖模型对已提供上下文的判断，服务端负责校验引用及当前状态；不能保证所有换措辞重复都被识别。受上下文预算限制，较早历史的语义匹配可能不完整，历史建议的精确指纹检查仍覆盖全部有效/显式忽略记录。

扫描使用启动时的历史快照。发现轮已因历史参考省略的内容、核实轮已判为 false 的候选，以及已按快照精确指纹跳过的候选，不会被发布时的引用检查追回。因此分析期间任务或建议发生变化，可能要在下一轮手动扫描才能反映；不自动重跑整轮。新结果也不会仅因旧卡片存在而自动替换其依据或验收内容。

“不再提示”与“删除”需要区分：前者保留记录并持续防重，恢复后可重新处置；后者硬删，允许后续重新发现。显式忽略的精确指纹不受模型上下文条数限制，换措辞匹配仍受语义判断限制。编辑产生的旧文案只在对应的当前建议或关联未完成任务仍需防重时抑制；连续编辑保持单层映射，删除/失效且无未完成任务后释放。显式忽略继续生效，具体规则见 §11.10。

### 11.8 验收标准

以下是方案验收目标；实际验证范围及模型、浏览器检查的边界见 §11.9。

| 场景 | 通过标准 |
|---|---|
| 项目已有框架和方向，开始全面分析 | 分析提示要求读取项目资料并按模块检查适用内容，结果符合所选类型和项目方向 |
| 发现真实问题或功能机会 | 卡片包含用户可读的标题、摘要，以及具体依据和可操作的验收要点；功能建议包含场景与最小范围 |
| 样式、性能尚未实际验证 | 明确标注“待运行验证”并说明方法，不把静态推断描述为浏览器观察或实测结论 |
| 编辑、再验证和转任务 | 详情可保存、查询，原详情在再验证后保留；转任务说明带入依据和验收要点 |
| 多次扫描同一问题 | 精确重复不新增；模型识别出的换措辞/换分类重复经有效引用校验后不新增 |
| 超过 20 条候选、同一问题分布在不同核实批次 | 后续批次也获得前批已确认问题的比对上下文；模型识别为同根因同范围时只保留一条，不能只测同批场景 |
| 已有未完成任务 | 同来源指纹不新增建议或重复任务；手动任务也进入语义防重参考 |
| 任务已完成或取消，但代码仍有问题 | 不因历史任务终态永久抑制，重新核实后可以再次报告 |
| 分析期间参考项变化，或模型编造引用 | 进入发布检查的候选不再被过期引用抑制；发现/核实轮已省略的内容允许下一轮扫描反映。非法引用重试一次，仍非法则明确失败 |
| 新候选缺失或仅有空白详情 | 在服务端识别不完整结果，复用一次格式修正重试；仍不完整时明确失败，不将其发布为详情完备的新卡片 |
| 编辑建议后转任务，任务终态但问题仍在 | 不因编辑前旧文案的永久指纹而静默漏报；显式“不再提示”的用户选择仍保留 |
| 旧数据或建议内容较多 | 旧卡片正常使用；响应保留完整卡片和真实总数，截断明确提示，手机中继响应不超预算 |
| 项目已变化但旧卡片仍在 | 单独扫描不会声称旧卡片均已复核；执行“验证全部”后，已解决项才移入已失效列表 |
| 没有可靠新发现 | 本轮正常完成且新增零条，不编造问题或扩展需求 |
| 模型调用失败、输出不完整、取消或结果版本过期 | 明确显示相应失败或取消状态，不以“新增零条”代替成功；没有新卡片不能作为项目无问题的证明 |

#### 11.10.3 编辑旧文案抑制的有效期

只在已有 `project_insight_suppressions` 表增加一个 `canonical_fingerprint text not null default ''` 字段，用于把旧文案指向当前文案；不增加新表、任务状态或任务完成回调。表中的 `fingerprint` 仍是旧文案指纹，主键不变。

幂等补列后，为 `(project_id, canonical_fingerprint)` 增加普通索引，供同组旧文案与任务查询使用；旧指纹直接查找继续复用原主键，不增加缓存或后台清理任务。

**写入规则**：编辑 A 为 B 时，在保存建议的同一事务中，先检查 B 的占用和旧映射，再将本项目现有 `reason=superseded` 且指向 A 的记录改为指向 B，最后将 A → B 写入或更新。连续编辑 A → B → C 后，A、B 都直接指向 C。仅编辑依据、验收要点或类型而指纹未变化时，不新建映射。事务失败时，内容和映射一起回滚。

目标指纹的处理明确如下，不能只依赖建议表的唯一索引：

- B 已是另一条建议的当前指纹，沿用冲突规则返回 409。
- B 是另一组仍生效的旧文案，例如已有 B → C 且 C 有有效/显式忽略建议或关联未完成任务，拒绝将 A 改为 B，返回 409；不得写出 A → B → C，也不得自动合并两组问题。
- B 属于本组旧文案时允许改回，例如 A → B 后把 B 改回 A。先清空目标 A 的 `superseded` 旧映射，再将其余本组旧文案直接指向 A；不保留自指映射或循环。
- B 的旧映射已经过期时，可先清空它的 `superseded` 对应字段再复用 B；其他组记录不随此次编辑迁移。其他 reason 不得被清空或覆盖，发生占用冲突时返回 409。

编辑事务内重新核对建议的 `updated_at` 与请求处理时读取的内容版本；已被其他请求修改则返回 409，要求刷新，不使用过期的 A 更新映射。映射更新仅操作 `reason=superseded`，不得用本次编辑覆盖其他原因的抑制记录。

**读取规则**：旧指纹的抑制仅在 `reason=superseded`、当前指纹非空，且下列任一条件成立时生效；查询始终限定同一项目。

| 当前指纹对应的状态 | 旧文案是否抑制 |
|---|---|
| 建议仍在有效列表，包括待复核或验证失败 | 是，避免已有卡片换旧文案再次出现 |
| 建议被用户显式设为“不再提示”，即使它此前被判失效 | 是，尊重用户选择 |
| 已无有效/显式忽略建议，但当前文案或关联旧文案已有未完成任务 | 是，沿用任务防重；todo、running、awaiting_review、action_required 均属于未完成 |
| 建议已删除或已失效，且没有对应未完成任务 | 否，允许重新核实并发现 |
| 只剩 done / cancelled 的历史任务 | 否，终态不代表问题已经解决 |
| 当前指纹为空，无法追溯归属的旧记录 | 否，不凭空推断归属 |

任务沿用现有 `source_insight_fingerprint`。统一查询时先把待检查的旧指纹单次归位到仍生效的当前指纹；没有生效映射时按原指纹处理。再匹配当前指纹及同项目内直接指向它的旧指纹，避免查询 A 时只检查“指向 A”的记录而漏掉 A → B 对应的 B 任务，也避免连续编辑后漏掉以较早文案创建的任务。所有映射均为直接指向，不做递归或构建语义关系图。

历史抑制、扫描发布、转任务和列表关联任务标注共用这一归位及任务查询口径。扫描发布事务实时重查旧文案的抑制资格，包括当前有效/显式忽略建议和未完成任务，避免历史快照之后新建的映射造成重复卡片；前端关联任务标签和转换按钮与服务端判定一致。

**重新建卡的映射处理**：上述写入约束也适用于扫描新增或复活建议，不能只在编辑入口维护。候选 A 通过版本和全部去重检查、确定要以 A 建卡时，在同一发布事务内清空以 A 为旧指纹且已经过期的 `superseded` 对应字段；映射仍生效则按重复跳过，不强制解绑。例如原有 A → B、B 已删除且无未完成任务，重新建 A 时必须清空 A → B，避免 B 日后出现时旧映射重新生效，把两张当前卡片误绑在一起。建卡失败或事务回滚时，映射清空也一起回滚；不改写其他 reason。

同组存在多条历史任务时，优先标注仍未完成的任务，只有全部终态才展示最新历史任务；不能因最新任务已结束而掩盖较早仍未完成的任务。

转任务事务还需核对所读卡片的 `updated_at`。若卡片已被编辑或删除，不使用旧摘要/旧验收要点创建任务，也不删除新版本：单条返回 409 并要求刷新，批量计入 skipped，任务创建和建议删除一起回滚。复核 pending/invalid、显式忽略的现有防护仍保留。

转任务硬删建议后无需移动映射，任务状态变化也无需额外同步。抑制资格每轮读取当前数据库时计算，不靠定时清理。快照之后状态变化仍遵守 §11.6 的边界，可能在下一轮体现。

**旧数据兼容**：`ensureColumn` 幂等补列后，旧 `superseded` 记录的新字段为空，按过期处理，不再永久拦截；保留原记录，不全量删除抑制表，不回填猜测关系。现存建议、未完成任务和 `project_insights.status='dismissed'` 的防重继续生效。未知 reason 不按本方案自动释放或重写，需保留原语义。
