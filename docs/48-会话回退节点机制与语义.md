# 48 - 会话回退节点（checkpoint）：机制、语义与入口

> 起因：2026-10-20 复查「回退到会话节点」。功能本身能用，但一路查下去发现四类问题：
> 一个硬 bug（恢复出来的文件在 Windows 上变成只读）、一个选错的存储机制（每轮整目录拷贝，
> 实测一个会话 7 轮 = 1.15 GB，其中 186 MB 是 frontend/node_modules）、一个说不清的语义
> （"恢复对话"并没有让模型失忆）、以及一个放错的入口（会话级功能挂在项目头部）。
> 本文记录**改成了什么**、**为什么这么定**，以及**哪些事不要做**。

## 1. 节点是什么

一轮 run **成功结束**后，服务端在 `conversation_checkpoints` 里留一行：

| 字段 | 含义 |
| --- | --- |
| `prompt` | 该轮的第一条用户消息（列表里显示的那句话） |
| `run_id` | 产生它的 run（界面按 `message.runId` 把它挂回时间线那条消息） |
| `native_turn_id` | 原生 agent 的 turn/会话标识（Codex 回退用） |
| `snapshot_path` | 代码快照所在目录（影子仓库或遗留拷贝目录） |
| `snapshot_ref` | 影子仓库里的提交对象 ID；空串 = 遗留拷贝型快照 |
| `workspace_path` | **这一轮实际跑在哪个目录**（会话切到隔离工作区时不是项目根，取自 `runs.workspace_path`） |
| `status` | `active`（还没被回退掉）/ `rewound`（被回退掉的历史） |

> `active` **不等于**"当前落点"：每个新节点插入时都是 `active`，没人回退过时整条会话都是
> `active`。**可见性边界不靠节点状态推导**，而是存在会话行上（见下）；保留策略里的
> "当前落点" = 最新的那个 `active`，且不能拿 `status='active'` 当豁免 —— 那样它一个都删不动。

**语义**：节点 N = "第 N 轮跑完之后"的那一刻。回退到节点 N = 保留 ≤ N 轮，丢掉 N 之后的内容。
所以时间线上那条用户消息下面的按钮写的是「回退到此处」，确认框会补一句"此后 M 轮不再显示"。

**失败的回合不留节点**：run 被停止或失败时不写节点（代码状态和对话状态都不确定）。
界面如实呈现：正在跑的那一轮显示"本轮结束后可回退"，失败的那一轮什么都不显示。

**"看得见什么"的判据**（`checkpointVisibilityClause`），两个边界都存在会话行上：

```
checkpoint_hidden_after = 最近一次回退的落点（目标节点的时间）
checkpoint_rewound_at   = 最近一次回退的时刻

visible = created_at <= checkpoint_hidden_after  OR  created_at > checkpoint_rewound_at
```

前半句藏掉被回退掉的历史；后半句保证回退**之后**新发生的回合（哪怕失败/被停止）照常显示
—— 只按落点过滤，会把用户回退后刚发的那条消息连同失败卡片一起藏掉，而那一刻正是他
最需要看见它的时候（失败不生成新节点）。

**落点必须存下来，不能由"最新 active 节点"推导**（早先的写法）：回退之后只要再成功跑一轮，
就会生成一个新节点，推导出来的边界立刻越过被丢掉的区间 —— **被回退掉的内容会重新出现**。
写入与节点状态翻转在同一个事务里，并随会话一起被级联删除。

这条判据同时用于会话详情、活动流、输入历史、手机快照、编排续跑的上下文、会话列表的预览与搜索。

**两端都要滤**：桌面端 reload 会合并本地消息、手机端的历史分页读过就留在本地缓存里 ——
服务端把 `messagesCutoff` / `messagesVisibleAfter` 一起发给客户端，客户端据此把本地那份里
被回退掉的条目也丢掉（`apps/web/src/lib/conversation-cutoff.ts`），否则"另一台设备回退"
在本机屏幕上根本看不出来。

**`只恢复代码`（mode=code）不动节点状态**：节点状态就是"对话看到哪一轮"的判据，跟着改会把
之后的对话也从界面上抹掉 —— 而那颗按钮写的是「对话历史不变」。

## 2. 存储机制：影子 git 仓库（替换掉整目录拷贝）

旧机制把整个项目目录逐文件拷进数据目录（只排除 `.git`）。真机实测：

```
conversation dirs: 1
files: 123112, total: 1155.3 MB      ← 一个会话 7 轮
\frontend\node_modules => 19966 files, 186.5 MB   ← 单份快照里被整份拷走的依赖目录
```

而且它**从不清理**：删会话只级联删 DB 行，磁盘目录永久残留。

现在每个会话有一个影子仓库 `<数据目录>/checkpoints/<conversationId>/shadow.git`（bare 仓库 +
显式 `--work-tree=<项目>`）：

| 动作 | 命令 | 为什么 |
| --- | --- | --- |
| 快照 | `git add -A -- :/` + `git commit --allow-empty` | `.gitignore` 命中不进快照（node_modules/target/dist 都不再进）；对象按内容去重，每轮只多存"这一轮改了什么" |
| 回退 | 先 `git add -A`（把现状记进索引）再 `git read-tree --reset -u <ref>` | 工作区对齐目标树：**快照之后新建的文件会被删掉**，而 `.gitignore` 命中的文件从不在索引里，永远不会被动到 |

要点：

- **快照拍的是"这一轮实际跑在哪个目录"**：会话可以切到隔离工作区（项目目录的兄弟目录），
  那时 `--work-tree` 必须是那个工作区，不是项目根。拿项目根去拍，快照里是另一份代码；
  恢复时更糟 —— 会把项目根上用户自己的改动当成"快照之后新建的文件"删掉。路径记在每个节点上
  （`workspace_path`），恢复认它，不认当时的项目根。
- **仓库不进用户仓库**：不写用户的 `.git`、不加忽略规则、不随项目推送。删会话时删的是
  **DB 行**（级联），磁盘目录由下次启动的清扫删掉；若别的会话（从节点分出去的分支会话）
  还引用着这里的仓库，清扫会**保留**它 —— 删了等于让分支会话的节点永远失去代码快照。
- **`core.autocrlf=false` 必须写死**：快照要逐字节保真，任何换行转换都会把"回退"变成"改文件"
  （本项目对行尾有前车之鉴，见 `.gitattributes` 那条规则）。
- **保留策略**：每会话保留最近 50 个节点 + 当前落点（最新的 `active` 节点，回退过的会话里
  它可能很老）。删的是行；影子仓库
  按内容去重，对象交给 git 的 gc；只有"一节点一目录"的遗留拷贝目录会随行删掉。
- **配置直接追加进仓库的 `config` 文件**，不走 `git config`：快照是在每轮 run 收尾时同步跑的，
  一次 `git` 调用就是一个进程（Windows 上 150–200ms、WSL 更贵）。同理，提交后的 ref 用文件读
  而不是再 spawn 一次 `git rev-parse`。稳态每轮只剩 2 个进程（`add` + `commit`）。
- **WSL 项目**由发行版内的 git 执行（与 Git 工作台同源，见 `gitRunnerForProject`）：工作区换成
  Linux 路径、影子仓库在数据目录上换成 `/mnt/<盘>` 形式。**远程（SSH）runner 项目仍不建快照** ——
  工作区在远端，快照放在哪一侧都是错的，所以如实标成"没有代码快照"。
- **失败不影响节点**：快照出错只写 `metadata.snapshotUnavailable`，节点本身照样留下，
  "恢复对话"仍然可用（`hasSnapshot=false` 会让界面把「恢复代码/恢复全部」收起来）。
- **命令前先清 `index.lock`**：被打断的 git 进程（超时、被杀）会留下它，而 Windows 上被 kill
  不走清理路径。这些仓库只有我们写、同一仓库上的操作在构造上就是串行的（快照在 run 收尾、
  恢复拿 `projectLifecycleMu`、转换在启动维护里），所以命令开始前还存在的锁一定是死的。
  不清掉的后果很恶劣：那个节点会**永远**转换失败，而失败是静默的 —— 真机上就撞到过
  （某份快照转了两次都失败，日志里只有一句 "Git --git-dir=… failed"）。
  同一条教训的另一半：快照类错误要把 git 自己的 stderr 带出来（`checkpointGitError`），
  否则日志里既没有子命令名也没有原因。
- **回退与"接纳新消息"互斥**：非 fork 的回退会改（甚至删）工作区文件，所以整段拿
  `projectLifecycleMu` —— 与 `sendMessage` 同一把锁。少了它，恢复大工作区的这几秒里
  新的一轮可以被接纳并开跑，两边同时动工作区。代价是恢复期间**所有项目**的发送都要等
  （通常不到 1 秒；大工作区可能几秒）。
- **破坏性部分不跟请求上下文走**：回退用服务运行时上下文（`checkpointRewindTimeout`）执行，
  客户端超时断开不会把 `read-tree` 杀在半路、留下改了一半的工作区。桌面端请求预算 180 秒，
  手机端 55 秒（受 agent 自身 60 秒 HTTP 上限约束）。
- **同一会话的快照类操作串行**（`checkpointLockSet`）：快照、恢复、遗留转换共用同一批仓库与
  同一个 index，而快照发生在 run 收尾（那一刻 run 已是 `completed`，回退的"有活跃 run"判据
  拦不住它）。并发下最糟的不是卡一下，而是两条 git 同时写 index，某个节点的提交树与工作区
  对不上。

### 遗留拷贝快照的迁移

升级前创建的节点还指着拷贝目录。启动后台维护（`sweepCheckpointSnapshots`）会把它们转成 git
提交（`imported-<nodeId>.git`，`-f` 全量收入，因为旧快照里本来就有被忽略的依赖目录），
然后删掉拷贝目录。顺序刻意如此：**git 提交先成功 → DB 指针后更新 → 目录最后删**，
任何一步中断都只是"下次启动再来"。转换过的节点标 `engine=git-legacy`，恢复用**覆盖式**
（`git checkout <ref> -- .`，不删工作区里多出来的文件）—— 旧机制跳过大文件与符号链接，
那些文件不在快照树里，按"该删"处理会删掉用户的东西。

**一次启动只转一个节点**（`checkpointImportPerStartup`），因为真机实测很贵：

| 实测项 | 数字 |
| --- | --- |
| 一份遗留快照（20 000 文件 / 186.7 MB）读完+哈希+压缩 | **5 分 57 秒**（Windows 小文件 I/O 是瓶颈，与 git 无关） |
| 转换后单份大小 | 186.7 MB → 48.5 MB（磁盘净减约 131 MB/节点） |
| 用户的 6 份遗留快照合计 | 1.12 GB → 约 290 MB（按节点独立仓库，未做跨节点去重） |

六份连做就是半小时的磁盘/CPU 占用，所以：每次启动最多一份，且转换前先等一个没有 run 在跑的
空档（`waitForIdleWindow`），不跟用户的 agent 抢磁盘；剩下的留给下次启动，每步幂等
（实测：第一次启动转 1 份后打印"budget for this startup is used up"停下，第二次启动接着转下一份）。
转换用的 git 预算单独放宽到 20 分钟（`checkpointImportGitTimeout`）—— 按常规的 30 秒会必然超时，
而超时是静默的（只是"下次再来"），没人会注意到快照一直没转过去。

同一份拷贝目录可能被**多条行**引用（从节点分出去的会话会复制 `snapshot_path`）：转换时
一次重指全部、共用同一个导入仓库，全部改完才删目录。只重指一条就删，另一条会静默失去快照。

## 3. 入口：主入口在时间线上，头部只留节点列表

节点是"某一轮"，那些轮次本来就摆在对话里。原先只有头部一个「回退」图标，点开是一张按回合
倒序的列表，用户得从 72 字截断的提示词里认出"我要回到哪一轮"。现在：

- **主入口**：每条用户消息下面的「回退到此处」（`.message-checkpoint`）。点它按节点能力选默认动作：
  有代码快照 → 恢复代码和对话；没有 → 只恢复对话。行内小字写明代价（"代码与对话都回到本轮结束时
  · 之后 3 轮不再显示"）。
- **头部入口**：退成「节点」列表，用于浏览全部节点、看哪个没有代码快照、以及「分支」这种
  非回退动作。两个入口共用同一份禁用判据（`rewindDisabled`）。
- **确认框必须说清代价**：回退不可撤销。旧文案"这会停止当前会话上下文"既没说会丢几轮，
  也没说快照之后新建的文件会被删除。

## 4. 上下文重建：`恢复对话` 让模型也回到那一刻

早先回退只 retire 掉长驻 CLI 进程，**不改会话身份**，所以下一轮仍然 `--resume <同一个 session>`：
界面上的消息被可见性边界藏起来了，但模型的原生上下文里那些回合还在。后果很实在 —— 用户回退到
第 N 轮，工作区已经按那一刻恢复，模型却还记得第 N+1 轮做过的事（"那个文件我已经创建了"，
而它并不存在）。

现在：**只要这次回退真的丢了回合**（回退到最新节点是空操作，那时什么都不动）：

1. 换一个新的原生会话（`agent_session_id` = 新 uuid、`initialized` 清零）→ 下一轮走
   `--session-id <新>` 而不是 `--resume <旧>`；
2. 置位 `conversations.pending_context_rebuild`，下一轮在**发出去的提示词**前面拼一段
   "【会话回退】…以下是保留的对话历史"（预算 48000 字，从最新往回吃，砍掉的是最前面那段）。
   标记在**这一轮真的跑完**（`finishRun` status=completed）之后才清：受理之后 CLI 仍可能拉不
   起来，那时历史没喂进去，下一轮重试必须重喂（多喂一次无害，少喂一次就是模型失忆）。

用户那条消息本身保持原样（界面里看到的仍然只是用户打的那句话），历史只出现在模型的视角里。

**Codex 走另一条路**：它有原生的 `thread/revert`，那条路成功时既保留会话、又真的回退到了那个
回合，保真度更高 —— 所以不再重置会话、也不再重建上下文。

为什么不是"截断 CLI 的 transcript JSONL 再 resume"：那依赖 CLI 的内部文件格式，比这脆得多。

## 5. 手机端：同一条服务端路径，多两个中继 op

手机端在自己的消息 ⋯ 菜单里给同一颗「回退到此处」：

- 中继上加了两条 op：`conversation.checkpoints`（读节点列表）与 `conversation.rewind`（按节点
  id 回退），两条都**复用桌面端的 handler**，不另写判据 —— 回退会改工作区文件，两端不能有
  两套"落到哪条会话"的规则（落点只认信封里的 conversationId，与 `conversation.stop` 同一条）。
- 手机端只发 mode，不发 `fork`（"从节点分支"是电脑端才有的动作）。
- 确认文案与"默认发哪个 mode"收口在 `apps/web/src/lib/conversation-rewind.ts`，两端共用一份：
  回退不可撤销，两端说岔了就是同一件事两种说法（本项目在"停止"的确认文案上栽过一次）。
- 快照与**客户端缓存**都要过滤：手机端的消息是"历史分页缓存 ∪ 快照"，历史页读过一次就留在
  本地。快照带上 `messagesCutoff` / `messagesVisibleAfter`，客户端据此把本地那份里被回退掉的
  条目也丢掉 —— 否则"电脑端（或另一台手机）回退了"在这台手机上根本看不出来。服务端的判据必须
  跑在快照那个事务的连接上（只有一条 SQLite 连接，事务里再去 s.db 查会死锁）。
- 手机端只有**一道**确认：那个弹层本身就是确认层，不再套 `window.confirm`（对不可撤销动作
  确认两次、且手机端别处从不使用原生 confirm）。

## 6. 不要做的事

- **不要只加"保留最近 N 份"**：每份还是 165 MB（含 node_modules），保留 5 份就是 800 MB。
  先解决"存什么"，再谈"存几份"。
- **不要在拷贝机制上补删除逻辑**：要先把整个快照读一遍才知道该删谁，而且认不出哪些是
  `.gitignore` 命中的、本来就不该管的文件。git 的 index 天然回答这个问题。
- **不要把影子仓库放进用户的 `.git`**：WSL 项目会逼出路径换算，而放在数据目录里两侧都能用；
  数据目录还能整目录删掉，孤儿清理不用去翻项目。
- **不要让"恢复代码"依赖 `entry.Type()` 当权限位**：普通文件的 `Type()` 是 0，`perm 0` 在
  Windows 上等于把每个恢复出来的文件打成只读（实测 `-r--r--r--` + 重写 `Access is denied`），
  之后 agent 再也改不动那些文件。遗留拷贝恢复走 `info.Mode()`，git 恢复不涉及权限位。
