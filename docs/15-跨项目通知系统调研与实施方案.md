# 跨项目通知系统调研与实施方案

> 日期：2026-07-26
>
> 决策：采用"**全局 WebSocket + Sonner Toast + BroadcastChannel 跨 Tab 同步**"方案，后端复用现有 gorilla/websocket 模式新增通知端点，前端用 Sonner 渲染持久通知，配合浏览器桌面通知和跨 Tab 同步。
>
> 非目标：不引入 SSE（与现有架构不一致），不引入 Service Worker Push API（实现复杂度过高），不使用轮询作为主通道（延迟不可接受）。

## 1. 问题背景

当多个项目同时运行时，用户可能正在查看项目 A 的页面，而项目 B 的任务完成了或需要审批。当前没有任何机制能将跨项目/跨会话的事件推送到用户当前所在的页面，用户完全不知道其他项目发生了什么。

### 1.1 现有实时通信机制

| 机制 | 端点 | 作用域 | 问题 |
| --- | --- | --- | --- |
| Conversation WS | `/ws/conversations/{id}` | 单个会话 | 只推送该会话的事件，其他项目完全收不到 |
| Run Log WS | `/ws/projects/{id}/run` | 单个项目运行日志 | 只推送日志，不推送任务状态变化 |
| HTTP 轮询 | 各页面 5-15s 间隔 | 各自页面 | 只刷新当前页面数据，无跨项目通知 |

### 1.2 通知场景

| 场景 | 事件源 | 优先级 | 需要用户操作 | 通知文案示例 |
| --- | --- | --- | --- | --- |
| 任务运行完成 | `task.status → done` | 中 | 否（可查看） | "项目 X 的任务「修复登录Bug」已完成" |
| 任务需要审批 | `task.status → action_required` / `approval.pending` | **高** | **是** | "项目 X 需要你审批工具调用" |
| 任务运行失败 | `task.status → action_required`（失败） | 中 | 可选 | "项目 X 的任务「重构API」执行失败" |
| 编排任务暂停 | `orchestration.status → needs_human` | **高** | **是** | "项目 X 的编排任务需要人工介入" |

## 2. 技术方案对比

### 2.1 方案 A：全局 WebSocket（推荐 ✅）

新增一个全局 WebSocket 端点，推送所有项目的事件给当前连接的浏览器。

```
浏览器 ←── WebSocket ──→ /ws/notifications
                              ↑
                    监听所有项目的事件变化
```

**优点**：
- 实时性最好，延迟 < 100ms
- 复用现有 gorilla/websocket 基础设施
- 与项目已有的 WebSocket 模式一致
- 前端只需一个全局连接
- Vite 代理已支持 `/ws` 路径，无需配置变更

**缺点**：
- 需要后端新增端点和广播逻辑
- 需要处理连接断开重连

### 2.2 方案 B：SSE（Server-Sent Events）

**优点**：单向推送足够、自动重连、HTTP 协议无需升级。

**缺点**：项目目前没有 SSE 基础设施需从零搭建、Go 的 SSE 实现不如 WebSocket 成熟、与项目现有模式不一致。

### 2.3 方案 C：轮询

**优点**：实现最简单。

**缺点**：延迟高（5-15s）、浪费带宽、用户体验差。

### 2.4 对比总结

| 维度 | 全局 WebSocket | SSE | 轮询 |
| --- | --- | --- | --- |
| 实时性 | ⭐⭐⭐ <100ms | ⭐⭐⭐ <100ms | ⭐ 5-15s |
| 实现复杂度 | ⭐⭐ 中 | ⭐⭐⭐ 高（新基础设施） | ⭐ 低 |
| 与现有架构一致性 | ⭐⭐⭐ 高 | ⭐ 低 | ⭐⭐ 中 |
| 服务器资源 | ⭐⭐⭐ 好（长连接） | ⭐⭐⭐ 好 | ⭐ 差（频繁请求） |
| 可靠性 | ⭐⭐ 需重连逻辑 | ⭐⭐⭐ 自动重连 | ⭐⭐⭐ 最可靠 |

## 4. 后端实现

### 4.1 新增数据结构

```go
// 通知事件
type NotificationEvent struct {
    ID             string          `json:"id"`
    Type           string          `json:"type"`       // "task.done", "task.action_required", "approval.pending", "run.completed", "orchestration.needs_human"
    ProjectID      string          `json:"projectId"`
    ProjectName    string          `json:"projectName"`
    ConversationID string          `json:"conversationId,omitempty"`
    TaskID         string          `json:"taskId,omitempty"`
    Title          string          `json:"title"`      // "项目 X 的任务已完成"
    Body           string          `json:"body"`       // "任务「修复登录Bug」已成功完成"
    Priority       string          `json:"priority"`   // "high" | "normal" | "low"
    ActionURL      string          `json:"actionUrl"`  // "/projects/xxx/conversations/yyy"
    CreatedAt      time.Time       `json:"createdAt"`
}

// 通知订阅者
type notificationSubscriber struct {
    conn      *websocket.Conn
    send      chan []byte
    closeOnce sync.Once
}
```

### 4.2 Server 结构体新增字段

```go
// 新增字段（使用独立互斥锁，不放入 s.mu）
notificationSubMu   sync.Mutex
notificationSubs    map[*websocket.Conn]*notificationSubscriber
```

**重要**：必须使用独立的 `notificationSubMu`，不能放入现有的 `s.mu`。`s.mu` 已经保护 12+ 个 map，在 14 个加锁点使用，再加通知订阅者会加剧锁竞争。应遵循 `runLogSubMu` 的模式。

### 4.3 新增常量

```go
notificationSubscriberQueueSize = 64   // 通知频率低，队列可小
notificationWriteTimeout        = 10 * time.Second
```

### 4.4 新增 WebSocket 端点

```go
// 路由注册（routes() 方法中）
r.Get("/ws/notifications", s.subscribeNotifications)

// 订阅处理器
func (s *Server) subscribeNotifications(w http.ResponseWriter, r *http.Request) {
    conn, err := s.upgrader.Upgrade(w, r, nil)
    if err != nil {
        return
    }
    sub := &notificationSubscriber{
        conn: conn,
        send: make(chan []byte, notificationSubscriberQueueSize),
    }

    // 连接后先发送未读通知
    unread, _ := s.getUnreadNotifications()
    for _, n := range unread {
        data, _ := json.Marshal(n)
        sub.send <- data
    }

    // 注册订阅者
    s.notificationSubMu.Lock()
    s.notificationSubs[conn] = sub
    s.notificationSubMu.Unlock()

    // writer goroutine + read loop（与现有 subscribe() 模式一致）
    // ...
}
```

**注意**：通知订阅者 map 是全局的（`map[*websocket.Conn]*notificationSubscriber`），不需要按 conversationID 或 projectID 分组，因为通知本身就是跨项目推送给所有连接的浏览器。

### 4.5 广播函数

```go
func (s *Server) broadcastNotification(event NotificationEvent) {
    // 1. 持久化到 notifications 表（$1 风格占位符，mattn/go-sqlite3 支持，与现有代码一致）
    if _, err := s.db.ExecContext(context.Background(),
        `INSERT INTO notifications (id, type, project_id, title, body, priority, action_url, dismissed, created_at)
         VALUES ($1,$2,$3,$4,$5,$6,$7,0,$8)`,
        event.ID, event.Type, event.ProjectID, event.Title, event.Body,
        event.Priority, event.ActionURL, event.CreatedAt); err != nil {
        log.Printf("persist notification %s: %v", event.ID, err)
        return // 持久化失败则不广播
    }

    // 2. 广播给所有通知订阅者
    data, _ := json.Marshal(event)
    toClose := make([]*notificationSubscriber, 0)
    s.notificationSubMu.Lock()
    for conn, sub := range s.notificationSubs {
        select {
        case sub.send <- data:
        default:
            delete(s.notificationSubs, conn)
            toClose = append(toClose, sub)
        }
    }
    s.notificationSubMu.Unlock()
    for _, sub := range toClose {
        sub.close()
    }
}
```

### 4.6 通知触发点

**关键原则**：通知广播必须在事务**提交后**触发，不能在事务内部。否则事务回滚会导致"虚假通知"。

#### 4.6.1 任务状态变更

任务状态变更散布在至少 7 个代码路径中，且部分路径完全没有记录事件。需要先补全遗漏的事件记录，再在事务提交后触发通知。

任务状态常量定义在 `task.go:18-23`：`todo`、`running`、`awaiting_review`、`action_required`、`done`、`cancelled`。注意是 `done` 而非 `completed`。

| 代码路径 | 文件 | 当前事件记录 | 需要补全 |
| --- | --- | --- | --- |
| `createTask` | task.go:272 | ✅ `task.created` | — |
| `updateTask` (todo↔action_required) | task.go:375 | ⚠️ 仅 `task.updated` | 补充状态专用事件 |
| `startMessage` (dispatch) | app.go:2370 | ✅ `task.dispatched` | — |
| `finishTaskRunTx` | task.go:1327 | ✅ `task.run_succeeded/failed` | — |
| `reviewTask` | task.go:1119 | ✅ `task.accepted/changes_requested` | — |
| **`retryOrchestrationJob`** | orchestration.go:1060 | ❌ 无事件 | **必须补全** |
| **`setOrchestrationJobPause`** | orchestration.go:422 | ❌ 无事件 | **必须补全** |
| **`failOrchestrationJob`** | orchestration.go:1095 | ❌ 无事件 | **必须补全**（设置 `needs_human`） |

**只对"需要用户关注"的状态发通知**，中间状态不发：

| 状态 | 是否发通知 | 原因 |
| --- | --- | --- |
| `action_required` | ✅ | 需要用户操作（包括失败、审批、编排介入） |
| `needs_human` | ✅ | 编排需要用户操作 |
| `done` | ✅ | 用户可能想查看结果 |
| `awaiting_review` | ✅ | 任务成功完成，等待审查 |
| `running` | ❌ | 中间状态 |
| `implementing` | ❌ | 中间状态 |
| `checking` | ❌ | 中间状态 |
| `preparing` | ❌ | 中间状态 |

说明：任务运行失败会进入 `action_required`（见 `finishTaskRunTx` 中 `run.failed/stopped/interrupted` 的映射），运行成功会进入 `awaiting_review`。两者都应通知。

#### 4.6.2 审批事件

审批事件（`approval.pending`）已通过 `appendEvent()` → `enqueueConversationEvent()` 推送到该会话的 WebSocket 订阅者。通知系统需要额外推送给**不在该会话页面**的用户。

前端需要去重：如果用户当前正在查看产生审批的会话页面，则不显示通知 toast（页面内已有审批提示）。

#### 4.6.3 编排事件

当前只有 `orchestration.queued` 和 `orchestration.preparing` 两个事件被记录。`needs_human`（最需要通知的状态）完全没有事件记录。需要补全以下事件：

| 状态 | 当前事件记录 | 需要补全 |
| --- | --- | --- |
| `needs_human` | ❌ | **必须补全**（最高优先级通知） |
| `paused` | ❌ | 可选 |
| `implementing` | ❌ | 不需要通知 |
| `checking` | ❌ | 不需要通知 |
| `integrated_to_dev` | ❌ | 可选 |
| `released_to_main` | ❌ | 可选 |

### 5.3 NotificationProvider 核心实现

```tsx
// components/NotificationProvider.tsx
import { useEffect, useRef, useCallback } from "react";
import { useNavigate, useLocation } from "react-router-dom";
import { Toaster, toast } from "sonner";
import { api } from "../lib/api";

interface NotificationEvent {
  id: string;
  type: string;
  projectId: string;
  projectName: string;
  conversationId?: string;
  taskId?: string;
  title: string;
  body: string;
  priority: "high" | "normal" | "low";
  actionUrl: string;
  createdAt: string;
}

export function NotificationProvider({ children }: { children: React.ReactNode }) {
  const navigate = useNavigate();
  const location = useLocation();
  const wsRef = useRef<WebSocket | null>(null);
  const dismissedRef = useRef(new Set<string>());

  // 判断用户是否正在查看产生通知的会话页面（用于审批去重）
  const isViewingConversation = useCallback((conversationId?: string) => {
    if (!conversationId) return false;
    return location.pathname.includes(`/conversations/${conversationId}`);
  }, [location.pathname]);

  // 处理收到的通知
  const handleNotification = useCallback((event: NotificationEvent) => {
    if (dismissedRef.current.has(event.id)) return;

    // 审批去重：如果用户正在查看该会话，不弹 toast
    if (event.type === "approval.pending" && isViewingConversation(event.conversationId)) {
      return;
    }

    const isHighPriority = event.priority === "high";
    const duration = isHighPriority ? Infinity : 8000;

    // 根据通知类型选择 toast 变体
    const variant = event.type.includes("failed") || event.type.includes("error")
      ? "error"
      : isHighPriority ? "warning" : "success";

    toast[variant](event.title, {
      id: `notif-${event.id}`,  // 去重：同一通知只显示一个
      description: event.body,
      duration,
      action: {
        label: "查看详情",
        onClick: () => {
          navigate(event.actionUrl);
          dismissNotification(event.id);
        },
      },
      onDismiss: () => dismissNotification(event.id),
    });

    // 页面不可见时，显示浏览器桌面通知
    if (document.visibilityState === "hidden" && Notification.permission === "granted") {
      new Notification(event.title, {
        body: event.body,
        tag: event.id,
      });
    }
  }, [navigate, isViewingConversation]);

  const dismissNotification = useCallback((id: string) => {
    dismissedRef.current.add(id);
    void api(`/api/notifications/${id}/dismiss`, { method: "POST" }).catch(() => {});
  }, []);

  // WebSocket 连接
  useEffect(() => {
    let reconnectAttempts = 0;
    let reconnectTimer: ReturnType<typeof setTimeout> | null = null;
    let cancelled = false;

    const connect = () => {
      if (cancelled) return;
      reconnectAttempts++;
      const protocol = location.protocol === "https:" ? "wss" : "ws";
      const ws = new WebSocket(`${protocol}://${location.host}/ws/notifications`);

      ws.onopen = () => { reconnectAttempts = 0; };
      ws.onmessage = (raw) => {
        try {
          const event: NotificationEvent = JSON.parse(raw.data);
          handleNotification(event);
        } catch { /* ignore parse errors */ }
      };
      ws.onclose = () => {
        if (cancelled) return;
        const delay = Math.min(500 * Math.pow(2, reconnectAttempts - 1), 15000);
        reconnectTimer = setTimeout(connect, delay);
      };
      ws.onerror = () => { ws.close(); };
      wsRef.current = ws;
    };

    connect();
    return () => {
      cancelled = true;
      if (reconnectTimer) clearTimeout(reconnectTimer);
      wsRef.current?.close();
      wsRef.current = null;
    };
  }, [handleNotification]);

  // BroadcastChannel 跨 Tab 同步
  useEffect(() => {
    const channel = new BroadcastChannel("app-notifications");
    channel.onmessage = (e) => {
      if (e.data?.type === "notification") {
        handleNotification(e.data.payload);
      }
    };
    return () => channel.close();
  }, [handleNotification]);

  return (
    <>
      <Toaster
        position="bottom-right"
        richColors
        closeButton
        style={{ zIndex: 35 }}  // Toaster 容器 z-index，高于模态框(z-index:30)
      />
      {children}
    </>
  );
}
```

### 5.7 浏览器桌面通知

页面不可见时（`document.visibilityState === "hidden"`），使用浏览器 Notification API 显示系统级通知。

**权限请求**：首次使用时由用户手势触发（不能页面加载时自动弹），建议在用户首次点击"查看详情"或通知铃铛时请求。

**限制**：
- `denied` 状态不可逆
- 需要 HTTPS（localhost 除外）
- iOS Safari 16.4+ 才支持，且需 PWA 模式
- 通知样式由操作系统控制

### 5.8 跨 Tab 同步

使用 BroadcastChannel API 在同一浏览器的多个 Tab 间同步通知：

```ts
// 发送端（WebSocket 收到通知时）
const channel = new BroadcastChannel("app-notifications");
channel.postMessage({ type: "notification", payload: event });

// 接收端（其他 Tab）
channel.onmessage = (e) => {
  if (e.data?.type === "notification") {
    handleNotification(e.data.payload);
  }
};
```

**去重策略**：多个 Tab 都会收到 WebSocket 通知，但只有**当前活跃 Tab** 显示 toast，其他 Tab 通过 BroadcastChannel 接收后仅更新通知铃铛的未读计数。

## 6. 通知持久化与"必须处理才消失"策略

用户要求通知只有等处理了才会消失，实现方式：

1. **后端持久化**：`notifications` 表存储所有未读通知
2. **前端状态**：`dismissedRef` 跟踪已处理的通知 ID
3. **Sonner 配置**：高优先级通知 `duration: Infinity`，不自动消失
4. **处理方式**：
   - 点击"查看详情" → 跳转 + 标记已读
   - 点击"忽略" → 标记已读 + 关闭 toast
   - 点击 toast 的 X 按钮 → 标记已读
5. **重连恢复**：WebSocket 重连后，从 `/api/notifications` 获取未读通知重新显示

## 7. 通知风暴防护

编排引擎的重试循环中，任务可能在极短时间内经历多个状态转换：

```
action_required → (50ms后) running → (几秒后) awaiting_review → checking → integrated_to_dev
```

防护措施：

1. **只通知需关注的状态**：`action_required`、`needs_human`、`done`、`awaiting_review`；中间状态（`running`、`implementing`、`checking`、`preparing`）不发通知
2. **Sonner id 去重**：同一任务的通知用 `notif-{notificationId}` 作为 id，新通知自动替换旧通知
3. **可选防抖**：同一任务在 2 秒内的多次状态变更只发最终状态的通知

## 9. 风险与注意事项

1. **通知触发点遗漏**：任务状态变更散布在 7+ 个代码路径，orchestration.go 部分路径完全没有事件记录。必须先补全事件记录，否则通知系统上线后会有"静默"的状态变更。
2. **事务内广播**：通知必须在事务提交后触发，否则事务回滚会导致虚假通知。
3. **锁竞争**：通知订阅者必须使用独立的 `notificationSubMu`，不能放入现有的 `s.mu`。
4. **审批重复通知**：用户正在查看该会话时，审批通知需要前端去重。
5. **通知权限**：浏览器 Notification API 需要用户授权，首次使用时需引导。
6. **移动端**：iOS Safari 对浏览器通知支持有限，应用内 toast 是主要方案。
7. **多 Tab**：同一浏览器多个 Tab 都会收到 WS 通知，需 BroadcastChannel 去重。
8. **服务器关闭**：新增 `closeAllNotificationSubscribers()` 在 `Close()` 中调用。
9. **通知风暴**：编排引擎重试循环可能导致快速状态转换，需只通知需关注的状态 + Sonner id 去重。
