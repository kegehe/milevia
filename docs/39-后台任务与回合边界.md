# 后台任务与 AI 回合边界

> 日期：2026-09-18
> 背景：Claude Code 在 `run_in_background` 下会**在后台任务仍在运行时先给出主回合的 `result`**。
> 控制服务此前把 `result` 直接当成回合终点，产生两处可见故障。本文记录根因与修复后的契约。

## 1. 现象（用户视角）

1. 时间线上明明有「后台任务启动 / 后台任务列表更新」卡片，**项目与会话状态却变成「没有执行中」**；
2. 过一会儿再对话几次，**中间的历史消息会一次性成批冒出来**（时间戳是旧的，位置在历史中间）。

## 2. 根因

四环相连，任何一环单独看都"像是正常的"：

1. **回合终点判据只看 `result`。** `claudeCLISession.readOutput` 收到 `result` 立即 `finishCurrent`，
   于是 `run.completed` 落库、`runs.status` 与 `conversations.status` 一起转出 `running`。
   而 Claude Code 在 `run_in_background`（交互式会话的 fork 模式默认开启）下，主回合的 `result`
   就是会先到 —— 官方文档的表述是「后台子代理的结果作为**完成通知在后续回合**到达」。
   → 这是"状态提前变空闲"的来源。
2. **回合结束后的事件被静默扣留。** `claudeCLISession.emit` 在 `turn == nil` 时只把事件
   append 进 `session.pending`，**既不落库也不广播**（落库与广播都发生在 sink 里）。
3. **待发队列只在下一次发言时回放**，而且回放用的是**新回合的 sink** —— 于是这批旧事件被挂到
   新 runId 下落库。
4. **前端按 `createdAt` 排序**（`mergeConversationItems`），旧时间戳的新事件自然插回时间线中间。
   → 这三点合起来就是"中间的历史消息一下子出来"。

还有一个比延迟更严重的后果：`claudeCLISession.finish()` 只收尾 turns、**不 flush `pending`**，
所以会话进程退出时那批事件是**永久丢失**，不是延迟。

## 3. 修复后的契约

### 3.1 回合终点要等后台任务收敛

`readOutput` 收到 `result` 时改走 `finishTurnOrWaitForBackground`：

- 本地跟踪的"在跑的后台任务"为空 → 照旧立刻收尾（正常路径不受影响）；
- 非空 → 把结果存进 `pendingResult`，**保持回合不结束**，等后台任务收敛后再收尾。

后台任务的跟踪来源（`noteBackgroundTaskEvent`）：

| 事件 | 处理 |
| --- | --- |
| `system/task_started` | **仅当 `is_backgrounded == true`** 才计入。前台子代理在同一回合内返回，计入会把正常回合挂住。 |
| `system/task_notification` | 按 `task_id` 移除（该事件一定是终态）。 |
| `system/background_tasks_changed` | 用 `tasks` 数组**整体替换**本地跟踪。这是权威快照，增量合并会让漏掉一次通知的任务变成永远清不掉的幽灵。 |

### 3.2 回合结束后的事件仍归原 run

会话新增 `lastTurnSink`（在 `startCurrentLocked` 绑定）。`emit` 与 `assistantText` 的归属规则改为：

```
当前回合存在 → 用当前回合的 sink
当前回合已收尾 → 用最近一个回合的 sink（后台任务本来就是它启动的）
两者都没有（进程刚起、还没发过言）→ 才进 pending
```

于是后台任务的完成通知与后台代理的最终汇报会**沿原 runId 落库并广播**，不再延迟、不再丢失，
也不会被错挂到下一个 run 上。

### 3.3 兜底：等不到就正常收尾

后台任务可能永远不回报（上游记录的完成记录丢失场景）。因此等待必须可放弃：

- `armBackgroundWaitTimer` 用 `AUTO_CLAUDE_TURN_IDLE_TIMEOUT`（默认 30 分钟）作上限；
- 到点后把 `pendingResult` 当回合终点**正常收尾**（不判失败），并清空后台任务跟踪
  （否则残留任务会顺延把下一个回合也挂住）；
- 定时器带**代际校验**（`backgroundGeneration`）：重新武装后，过期的那一个不得再收尾；
- 等待期间 `noteStreamEvent` **不再启动回合空闲计时器** —— 看门狗由兜底定时器统一负责，
  避免同一次等待有两个超时来源，也避免把"后台任务还在跑"报成"长时间无输出"。

`finish` / `Stop` / `failStalledTurn` / `abortFailedStart` 都统一调 `clearBackgroundWaitLocked()`。

### 3.4 判定一律保守

只有**明确读出**"有后台任务在跑"才推迟收尾；读不出来就按老行为立即收尾。
宁可短暂显示空闲，也不能让回合永远挂在运行中。

`background_tasks_changed` 的形状是**推断**的（前端 `timeline.ts` 只读过 `tasks[].description` /
`task_type`，没有读过 `task_id`）。因此多一层保护：`tasks` 非空、却一个 `task_id` 都读不出来时
**不做整体替换** —— 拿空表替换会被误判成"没有后台任务"而立刻收尾，保留原跟踪更保守。

### 3.5 复查修正（2026-09-18 二轮）

- `armBackgroundWaitTimer` 原先把 `time.AfterFunc` 的返回值直接赋给 `session.backgroundTimer`
  **（锁外）**，而这个字段会被 `clearBackgroundWaitLocked` 在锁内读写 ⇒ 数据竞争。
  已改为锁内赋值，并在挂上去之前复查 `stopped` 与代际（建计时器与挂上去之间会话可能已收尾），
  作废的那一个立即 `Stop`。
- `clearBackgroundWaitLocked` 一并清空 `backgroundTasks`（原先只有超时路径清），
  让"放弃等待"在所有停机路径上语义一致。
- `releaseTurnIfBackgroundTasksSettled` 与超时回调统一改走 `clearBackgroundWaitLocked`，去掉重复的三行清理。
- `RearmedBackgroundWaitIgnoresStaleTimer` 的时间参数放宽：原先断言点距两个定时器到点只有
  20/40ms，慢机器上会是随速度飘的假失败；现在均为 70ms 以上。

## 4. 范围

- 只适用于 **Claude 持久会话**（`StartSession`）。
- **Codex 走一次性 `Run`**（没有 `StartSession`），进程退出即回合结束，不存在这个问题。
- 前端不需要各自再判一遍：`activeRunId` 取自 `runs.status` / `conversations.status`，
  回合不结束它们就一直是 `running`，界面自然显示"执行中"。**单一真相留在后端**，
  既避免判据分裂，也避免前端因"完成通知丢失"而永远无法判定空闲。

## 6. 依据

- Claude Code 官方文档 · sub-agents：「后台子代理的结果作为完成通知在**后续回合**到达」。
- 上游 issue #94392：主回合结束即发 `result`（`subtype: success`、`is_error: false`），
  其后才是 `task_notification`；`run_in_background: false` 的对照组在同一回合内返回、不丢。
- 上游 issue #81681：后台代理可能丢失完成记录 —— 这正是前端
  `No completion record was found for background agent "…"` 模板的来源，也是本文 3.3 兜底的依据。
